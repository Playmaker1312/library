Selamat! Anda telah sampai di tahap transformasi terakhir: dari seorang yang "menulis kode yang jalan" menjadi seorang **Engineer** yang "menulis kode yang terbukti benar".

Dalam dunia profesional, kita tidak mengetes kode dengan cara menjalankan aplikasi lalu mengeklik tombol secara manual berulang-ulang. Kita menggunakan **Unit Test** dan metodologi disiplin yang disebut **TDD (Test Driven Development)**.

---

## 1. Apa itu Unit Test?

**Unit Test** adalah kode kecil yang ditulis untuk menguji satu "unit" terkecil dari logika aplikasi Anda (biasanya satu fungsi atau satu metode) secara terisolasi.

- **Tujuannya:** Memastikan bahwa jika Anda memasukkan _input_ A, fungsi tersebut **pasti** mengeluarkan _output_ B.
    
- **Keuntungannya:** Jika di masa depan Anda mengubah kode (Refactoring) dan tanpa sengaja merusaknya, Unit Test akan langsung berteriak "Gagal!" dalam hitungan detik.
    

---

## 2. TDD (Test Driven Development)

TDD adalah teknik pengembangan di mana Anda **menulis tesnya terlebih dahulu sebelum menulis kode fiturnya**. Ini terdengar aneh, tapi inilah cara terbaik untuk menghasilkan kode yang bersih dan minim _bug_.

Siklus TDD dikenal dengan sebutan **Red-Green-Refactor**:

1. **🔴 RED (Gagal):** Tulis tes untuk fitur yang belum ada. Jalankan tesnya, dan pastikan tes tersebut **gagal** (karena kodenya memang belum dibuat).
    
2. **🟢 GREEN (Berhasil):** Tulis kode seminimal mungkin—hanya agar tes tersebut lulus (menjadi hijau). Jangan pedulikan keindahan kode dulu, yang penting "jalan".
    
3. **🔵 REFACTOR (Rapikan):** Sekarang setelah tesnya hijau, rapikan kode Anda (terapkan DRY, SOLID, dll). Selama tesnya tetap hijau, berarti Anda tidak merusak logika apa pun.
    

---

## 3. Analogi: Membangun Jembatan

- **Tanpa TDD:** Anda membangun seluruh jembatan sampai selesai, lalu baru mencoba melewatkan truk di atasnya. Jika jembatannya roboh, Anda bingung baut mana yang longgar atau semen mana yang rapuh.
    
- **Dengan TDD:** Anda mengetes setiap baut sebelum dipasang, mengetes setiap batang besi sebelum disambung, dan mengetes kekuatan semen sebelum dicor. Saat jembatan jadi, Anda **yakin 100%** bahwa truk bisa lewat dengan aman.
    

---

## 4. Contoh Implementasi (JavaScript - Jest)

Bayangkan kita ingin membuat fungsi `tambah(a, b)`.

**Langkah 1: RED (Tulis Tes Dulu)**

JavaScript

```
// file: kalkulator.test.js
test('menambahkan 2 + 3 harus menghasilkan 5', () => {
    expect(tambah(2, 3)).toBe(5);
});
// Hasil: ERROR (Karena fungsi 'tambah' belum ada)
```

**Langkah 2: GREEN (Tulis Kode Minimal)**

JavaScript

```
// file: kalkulator.js
function tambah(a, b) {
    return a + b;
}
// Hasil: PASS (Tes jadi Hijau!)
```

**Langkah 3: REFACTOR (Opsional)** Misalnya kita ingin menambahkan validasi agar hanya menerima angka. Kita ubah kodenya, jalankan lagi tesnya. Jika tetap Hijau, kita aman!

---

## 5. Poin Penting: F.I.R.S.T Principles

Unit Test yang baik harus memenuhi prinsip **FIRST**:

- **Fast:** Harus sangat cepat (ribuan tes dalam beberapa detik).
    
- **Independent:** Satu tes tidak boleh bergantung pada hasil tes lainnya.
    
- **Repeatable:** Hasilnya harus sama di komputer mana pun, kapan pun.
    
- **Self-Validating:** Tes harus lapor sendiri "Lulus" atau "Gagal", tidak perlu dicek manual.
    
- **Thorough/Timely:** Mencakup berbagai kemungkinan (termasuk _input_ yang salah/error).
    

---

## 6. Koneksi dengan Web Development

Kenapa perusahaan besar seperti Google atau Netflix mewajibkan TDD?

1. **Dokumentasi Hidup:** Unit Test memberi tahu _programmer_ baru tentang bagaimana sebuah fungsi seharusnya bekerja tanpa perlu membaca dokumen PDF yang tebal.
    
2. **Berani Deploy Hari Jumat:** Dengan ribuan Unit Test yang menjaga kode Anda, Anda tidak akan takut melakukan _update_ aplikasi di sore hari sebelum libur, karena Anda tahu sistem sudah teruji secara otomatis.
    
3. **Membayar Technical Debt:** Anda tidak akan bisa melakukan _Refactoring_ dengan tenang jika tidak ada Unit Test yang menjamin keamanan logika lama Anda.
