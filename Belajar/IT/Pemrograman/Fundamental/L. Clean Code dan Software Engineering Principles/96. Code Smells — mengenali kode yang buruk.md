Selamat! Jika **Refactoring** adalah proses "bersih-bersih", maka **Code Smells** (Bau Kode) adalah indra penciuman Anda untuk mendeteksi di mana letak kotorannya.

_Code Smells_ bukanlah _error_ atau _bug_—kode tersebut mungkin berjalan dengan sempurna. Namun, ia "berbau" busuk karena mengindikasikan adanya kelemahan desain yang akan menyulitkan Anda di masa depan. Mengetahui cara mendeteksi bau ini adalah pembeda antara _Junior_ dan _Senior Developer_.

---

## 1. Kategori Utama Code Smells

Para ahli (seperti Martin Fowler) membagi bau kode ke dalam beberapa kelompok besar:

### A. The Bloaters (Si Raksasa)

Kode, metode, atau kelas yang ukurannya membengkak hingga sangat sulit dikelola. Biasanya terjadi secara perlahan seiring bertambahnya fitur.

- **Long Method:** Fungsi yang lebih dari 20-50 baris. Semakin panjang sebuah fungsi, semakin sulit dipahami dan dites.
    
- **Large Class:** Satu kelas yang mencoba melakukan segalanya (melanggar prinsip _Single Responsibility_).
    
- **Long Parameter List:** Fungsi yang meminta lebih dari 3-4 parameter. Ini membuat pemanggilan fungsi menjadi membingungkan.
    

### B. The Object-Orientation Abusers

Penerapan prinsip pemrograman berorientasi objek yang salah atau tidak lengkap.

- **Switch Statements:** Penggunaan `switch` atau `if-else` raksasa yang berulang di banyak tempat. Jika Anda menambah satu tipe baru, Anda harus mengubah semua `switch` tersebut. (Solusi: Gunakan _Strategy Pattern_).
    
- **Temporary Field:** Variabel di dalam kelas yang hanya mendapatkan nilai pada kondisi tertentu saja, sisanya kosong. Ini membingungkan karena seolah-olah variabel itu penting bagi seluruh kelas.
    

### C. The Change Preventers (Penghambat Perubahan)

Bau yang membuat Anda malas mengubah kode karena satu perubahan kecil akan merembet ke mana-mana.

- **Divergent Change:** Anda harus mengubah banyak metode di dalam satu kelas hanya untuk satu perubahan kecil di fitur.
    
- **Shotgun Surgery:** Satu perubahan kecil memaksa Anda mengubah puluhan file yang berbeda di seluruh proyek. Ini adalah tanda bahwa kode Anda terlalu saling ketergantungan (_tightly coupled_).
    

### D. The Dispensables (Si Mubazir)

Sesuatu yang tidak berguna dan seharusnya dihapus agar kode lebih bersih.

- **Comments:** Tunggu, komentar itu bagus, kan? Tidak selalu. Jika Anda harus menulis komentar panjang untuk menjelaskan apa yang dilakukan kode, itu tandanya kode Anda **tidak deskriptif**. Kode yang baik harus bisa "berbicara sendiri" (_self-explanatory_).
    
- **Duplicate Code:** Kode yang sama persis muncul di dua tempat atau lebih. (Gunakan prinsip _DRY_).
    
- **Dead Code:** Variabel, fungsi, atau kelas yang sudah tidak pernah dipanggil lagi tapi masih tersisa di proyek.

## 2. Cara "Mencium" Bau Kode (Contoh Nyata)

Mari kita lihat contoh kode yang "berbau":

JavaScript

```
// BAU: Comments & Long Parameter List
// Fungsi untuk memproses data user dan mengirim email jika sukses
function p(n, e, a, s, t, msg) { 
    // BAU: Unclear Name (apa itu n, e, a?)
    if (s == "active") {
        // ... 50 baris logika di sini ... (BAU: Long Method)
        console.log("Mengirim " + msg + " ke " + e);
    }
}
```

**Hasil Refactoring (Bau Hilang):**

JavaScript

```
function sendActiveUserMessage(user, message) {
    if (user.isActive()) {
        processUserData(user);
        emailService.send(user.email, message);
    }
}
```

## 3. Strategi Menghadapi Code Smells

1. **Jangan Panik:** Tidak semua bau harus dibersihkan detik itu juga. Prioritaskan bagian kode yang paling sering berubah atau sering mengalami _bug_.
    
2. **Gunakan Linter:** Gunakan alat seperti **ESLint** atau **SonarQube**. Alat ini bertindak sebagai "hidung elektronik" yang otomatis memperingatkan Anda jika ada fungsi yang terlalu panjang atau variabel yang tidak terpakai.
    
3. **Code Review:** Mata orang lain seringkali lebih tajam mencium bau di kode kita daripada hidung kita sendiri.
    

Mengenali _Code Smells_ adalah langkah awal menuju kode yang profesional. Setelah Anda bisa melihat "kebusukan" dalam kode, Anda akan merasa gatal untuk memperbaikinya menggunakan teknik **Refactoring** dan **Design Patterns**.
