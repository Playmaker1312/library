Selamat! Anda telah sampai pada salah satu konsep paling krusial dalam rekayasa perangkat lunak modern. Jika **Composition** mengajarkan kita untuk merakit objek dari berbagai komponen, maka **Dependency Injection (DI)** adalah teknik tentang **bagaimana** komponen-komponen tersebut diberikan kepada objek yang membutuhkannya.

DI adalah implementasi utama dari prinsip **Inversion of Control (IoC)**—membalikkan kendali pembuatan objek dari dalam kelas ke luar kelas.

---

## 1. Apa itu Dependency Injection?

**"Jangan membuat sendiri apa yang kamu butuhkan, biarkan orang lain memberikannya padamu."**

### Definisi Singkat

Dalam pemrograman tradisional, sebuah kelas biasanya membuat sendiri objek-objek lain yang ia butuhkan (_hard-coded dependencies_). Dengan **Dependency Injection**, kelas tersebut hanya menyatakan _"Saya butuh objek X"_, dan pihak luar (seperti _Inversion of Control Container_ atau _Main Program_) akan "menyuntikkan" (_inject_) objek X tersebut ke dalamnya.

---

## 2. Analogi: Restoran vs Tukang Masak di Rumah

### Tanpa DI (Tukang Masak Mandiri)

Bayangkan Anda adalah seorang tukang masak. Setiap kali ingin memasak nasi goreng, Anda harus pergi ke sawah untuk menanam padi, ke pasar untuk membeli bumbu, dan membuat wajan sendiri.

- **Masalah:** Jika pasar tutup atau bibit padi habis, Anda tidak bisa memasak. Anda terlalu sibuk mengurus "kebutuhan" daripada fokus pada "memasak".
    

### Dengan DI (Restoran Profesional)

Anda adalah tukang masak di restoran. Tugas Anda hanya memasak. Semua bahan (nasi, bumbu, wajan) **disediakan (disuntikkan)** oleh asisten dapur ke meja Anda.

- **Keuntungan:** Anda bisa fokus memasak. Jika wajan rusak, asisten tinggal memberikan wajan merek lain tanpa Anda harus tahu cara membuatnya. Anda menjadi sangat fleksibel.
    

---

## 3. Mengapa DI Sangat Penting?

1. **Loose Coupling (Kaitan Longgar):** Kelas tidak lagi terikat pada implementasi spesifik dari dependensinya.
    
2. **Kemudahan Testing (Mocking):** Anda bisa menyuntikkan "Database Palsu" (_Mock_) saat melakukan Unit Test agar tes berjalan cepat tanpa menyentuh database asli.
    
3. **Maintainability:** Mengubah cara kerja satu komponen tidak akan merusak komponen lain yang menggunakannya, selama "kontrak" (Interface) tetap sama.
    

---

## 4. Contoh Implementasi: Sebelum vs Sesudah

### A. Tanpa DI (Kaku)

Kelas `LayananPesanan` membuat sendiri objek `Database`.

JavaScript

```
class Database {
    simpan(data) { /* simpan ke MySQL */ }
}

class LayananPesanan {
    constructor() {
        // KAKU: LayananPesanan terkunci hanya pada MySQL
        this.db = new Database(); 
    }
}
```

### B. Dengan DI (Luwes)

`Database` dikirimkan melalui `constructor`.

JavaScript

```
class LayananPesanan {
    constructor(database) {
        // LUWES: Bisa disuntikkan MySQL, MongoDB, atau Database Palsu untuk Test
        this.db = database;
    }
}

// Proses "Penyuntikan" (Injection)
const mySql = new MySqlDatabase();
const service = new LayananPesanan(mySql);
```

---

## 5. Jenis-Jenis Injection

- **Constructor Injection:** Menyuplai dependensi melalui _constructor_ saat objek pertama kali dibuat. (Paling sering digunakan).
    
- **Setter Injection:** Menyuplai dependensi melalui metode _setter_ setelah objek dibuat.
    
- **Interface Injection:** Menggunakan _interface_ khusus yang mendefinisikan metode untuk menerima dependensi.
    

---

## 6. Kapan Menggunakan DI?

Hampir semua _framework_ modern (seperti **Angular**, **Spring Boot**, atau **NestJS**) menggunakan DI sebagai jantung arsitekturnya. Anda harus mulai memikirkan DI ketika:

- Aplikasi Anda mulai besar dan memiliki banyak kelas yang saling bergantung.
    
- Anda ingin menulis Unit Test yang benar-benar terisolasi.
    
- Anda ingin aplikasi Anda mudah dikonfigurasi (misal: ganti _Storage_ dari Lokal ke Cloud AWS hanya dengan mengubah satu baris kode di pusat konfigurasi).
    

## Kesimpulan

Dependency Injection adalah tentang **kerendahan hati sebuah objek**. Objek tidak lagi sombong dengan mencoba membuat segalanya sendiri; ia percaya pada sistem untuk memberikan apa yang ia butuhkan. Hasilnya? Kode yang jauh lebih rapi, fleksibel, dan profesional.
