Selamat! Anda telah tiba di gerbang dunia kerja profesional yang sesungguhnya. Memahami _commit_, _push_, dan _pull_ adalah satu hal, tetapi mengetahui cara berkolaborasi dalam tim yang terdiri dari belasan hingga ratusan _Software Engineer_ adalah keterampilan yang akan langsung membuat Anda siap dipekerjakan.

Di dunia industri, Anda **tidak diizinkan** melakukan `git push` langsung ke cabang `main` (Production). Anda harus melewati sebuah pos pemeriksaan ketat yang disebut **Pull Request** dan **Code Review**.

---

## 1. Definisi Singkat

- **Pull Request (PR):** Sebuah dokumen pengajuan formal di platform seperti GitHub atau GitLab. Anda pada dasarnya berkata kepada tim: _"Halo, saya sudah selesai mengerjakan cabang fitur saya. Tolong tarik (pull) kode saya ini dan gabungkan (merge) ke cabang utama."_
    
- **Code Review (Tinjauan Kode):** Proses di mana rekan kerja Anda (biasanya _Senior Developer_) membaca baris demi baris kode yang Anda ajukan di dalam PR tersebut. Mereka akan mencari _bug_, memastikan kode rapi, dan memberikan komentar persetujuan atau penolakan.
    

## 2. Analogi: Menerbitkan Sebuah Buku

Bayangkan cabang `main` adalah buku cetak final yang akan dijual ke toko buku, dan Anda adalah seorang penulis.

1. **Branching (Menulis Draf):** Anda menulis bab baru di draf naskah Anda sendiri (Cabang Fitur).
    
2. **Pull Request (Menyerahkan Draf):** Anda menyerahkan draf tersebut ke meja Editor Utama. Anda melampirkan catatan: _"Bos, ini draf Bab 5. Tolong direview."_
    
3. **Code Review (Pemeriksaan Editor):** Editor membaca draf Anda. Mereka mencoret kalimat yang salah ketik, memberi catatan di margin pinggir: _"Bagian ini alurnya membingungkan, tolong tulis ulang,"_ lalu mengembalikannya kepada Anda.
    
4. **Revisi:** Anda memperbaiki tulisan tersebut sesuai saran editor.
    
5. **Merge (Naik Cetak):** Setelah editor puas dan memberikan stempel **"Approved"**, barulah draf Anda digabungkan ke buku utama dan dicetak masal.
    

## 3. Poin-Poin Penting (Etika & Aturan Main)

- **Tinggalkan Ego Anda:** Saat kode Anda dikomentari atau dikritik banyak orang, jangan tersinggung. _Code review_ bukan serangan pribadi. Ini adalah jaring pengaman agar _bug_ yang Anda buat tidak merusak aplikasi yang dipakai jutaan pengguna.
    
- **Dua Pasang Mata Lebih Baik:** Sehebat apa pun seorang _programmer_, ia pasti akan melakukan kesalahan konyol (seperti lupa menghapus `console.log` atau salah ketik variabel). _Code review_ adalah cara termudah dan termurah untuk menangkap kesalahan ini sebelum mencapai _server_.
    
- **Beri Deskripsi yang Jelas:** Jangan membuat PR kosong tanpa penjelasan. Anda wajib menuliskan apa yang Anda ubah, _bug_ apa yang Anda perbaiki, dan cara mengetesnya. (Contoh: _"PR ini menambahkan tombol keranjang belanja di halaman detail produk"_).
    

## 4. Alur Kerja Nyata (Step-by-Step)

Bagaimana proses ini berjalan sehari-hari di perusahaan teknologi? Berikut adalah siklusnya:

1. **Buat Cabang Baru & Menulis Kode (Lokal):** Anda mengambil tugas dari papan kerja (seperti Trello/Jira), membuat cabang, dan mulai _coding_. `git checkout -b fitur-keranjang`
    
2. **Commit dan Push ke GitHub:** Setelah selesai, Anda mengunggah cabang tersebut ke internet. `git push origin fitur-keranjang`
    
3. **Buka Pull Request (Di Website GitHub):** Anda membuka _website_ GitHub. Akan muncul tombol hijau besar bertuliskan **"Compare & pull request"**. Anda mengkliknya, menulis deskripsi, dan menekan tombol **"Create pull request"**.
    
4. **Proses Review (Diskusi):** Rekan tim Anda akan membuka PR tersebut. GitHub akan menampilkan tampilan _Diff_ (perbedaan) yang menyorot baris kode yang dihapus (merah) dan ditambah (hijau). Jika ada yang aneh, rekan Anda akan meninggalkan komentar langsung di baris kode tersebut.
    
5. **Revisi (Jika Diperlukan):** Jika ada revisi, Anda cukup mengedit kodenya lagi di laptop, lalu melakukan `add`, `commit`, dan `push` ke cabang yang sama. PR di GitHub akan otomatis terbarui.
    
6. **Approve & Merge:** Setelah semua masalah selesai, rekan Anda akan memberikan status **"Approved ✅"**. Anda (atau _Tech Lead_ Anda) kini berhak menekan tombol sakral **"Merge pull request"**. Kode Anda resmi masuk ke cabang `main`!
    

## 5. Koneksi dengan Web Development

Ini adalah rutinitas yang akan membentuk karier Anda:

1. **Tempat Belajar Gratis Terbesar:** Sebagai _Junior Developer_, PR adalah tempat Anda belajar paling banyak. _Senior Developer_ akan meninggalkan komentar yang mengajarkan Anda teknik _coding_ yang lebih bersih dan efisien (_Best Practices_). Jangan takut membuat PR!
    
2. **CI/CD Pipeline (Bot Otomatis):** Di perusahaan modern, sesaat setelah Anda membuka PR, robot (seperti GitHub Actions) akan langsung mengambil alih. Robot ini akan menjalankan _Automated Testing_ (mengetes kode Anda secara otomatis). Jika robot mendeteksi _error_, tombol "Merge" akan dikunci (berwarna merah) dan tidak ada manusia yang bisa menyetujui PR tersebut sampai Anda memperbaikinya.
    
3. **Open Source Contribution:** Jika Anda melihat _bug_ di pustaka (_library_) populer seperti React atau Vue, Anda bisa melakukan perbaikan di laptop Anda dan mengirimkan Pull Request ke gudang kode asli milik Facebook/Meta. Jika mereka menyetujui PR Anda, nama Anda akan terukir abadi sebagai kontributor teknologi dunia!
