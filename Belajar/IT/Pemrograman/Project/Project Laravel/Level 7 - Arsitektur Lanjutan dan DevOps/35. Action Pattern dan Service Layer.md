# 35. Action Pattern dan Service Layer

Selamat datang di Level 7 — Arsitektur Lanjutan dan DevOps. Materi kali ini kita bahas **Action Pattern** (Single Action Class) dan **Service Layer**, dua pola arsitektur yang akan bikin controller kamu tetap tipis dan business logic mudah ditest. Ini lanjutan natural dari materi Service Container & Caching (Level 6), dan jadi fondasi sebelum masuk ke DevOps/Deployment (Level 7 berikutnya) karena kode yang terstruktur jauh lebih mudah di-deploy dan dirawat.

## 1. Penjelasan Singkat & Konsep Dasar

Action Pattern adalah pola di mana **satu kelas mewakili satu operasi bisnis spesifik**. Misalnya `PinjamBukuAction` hanya bertugas "meminjam buku", `KembalikanBukuAction` hanya bertugas "mengembalikan buku". Satu class, satu tanggung jawab, satu method utama bernama `execute()`.

Sedangkan Service Layer adalah lapisan yang menampung **kumpulan operasi terkait** dalam satu class. Contoh: `PeminjamanService` yang berisi method `pinjam()`, `kembalikan()`, `perpanjang()`, `cekDenda()`.

Hubungan keduanya dengan materi sebelumnya:
- **Level 6 (Service Container & Caching)**: Action dan Service otomatis disuntikkan via Service Container (constructor injection). Kalau kamu pakai `BukuRepositoryInterface`, Laravel langsung resolve bindings-nya.
- **Level 6 (Event)**: Action adalah tempat yang tepat untuk `dispatch()` event seperti `BukuDipinjam`.
- **Materi testing (Level 6)**: Action yang murni terima parameter dan mengembalikan value sangat mudah ditest dengan unit/feature test.

Materi berikutnya (DevOps/Deployment) akan terasa ringan karena arsitektur kamu sudah rapi — kode yang modular lebih mudah di-containerize dan di-scale.

## 2. Fungsi & Kegunaan Utama dalam Laravel

Kenapa Action Pattern dan Service Layer ada? Karena tanpa keduanya, business logic cenderung menumpuk di tempat yang salah:

1. **Controller jadi gemuk (Fat Controller)**: Semua validasi, perhitungan denda, transaction, dispatch event ditulis berjajar di dalam method `store()`. Controller seharusnya hanya jadi *pengantar* (glue) antara HTTP dan domain.
2. **Model jadi God Object**: Logika bisnis ditaruh sebagai method di model (`$buku->pinjam($anggota)`) sampai model jadi raksasa yang sulit dirawat.
3. **Logic duplikat**: Aturan "anggota maksimal 5 pinjaman aktif" ditulis ulang di controller, console command, dan API. Kalau berubah, harus diubah di tiga tempat.

Action Pattern menyelesaikan masalah ini dengan:
- **Isolasi**: Tiap aksi bisnis punya rumah sendiri, bisa diubah tanpa menyentuh yang lain.
- **Reusability**: Satu action bisa dipanggil dari web (controller), API (controller API), dan console (Artisan command). Sekali tulis, dipakai banyak entry point.
- **Testability**: Test langsung action tanpa harus mensimulasikan HTTP request.
- **Kejelasan alur**: Saat review kode, cukup baca `PinjamBukuAction::execute()` untuk paham seluruh aturan peminjaman.

## 3. Contoh Kode & Implementasi (Real-world Example)

Lokasi standar: `app/Actions/`. Contoh nyata di Perpustakaan Digital: action untuk meminjam buku.

```php
<?php

namespace App\Actions;

use App\Exceptions\BukuTidakTersediaException;
use App\Exceptions\BatasPinjamanTercapaiException;
use App\Models\Anggota;
use App\Models\Buku;
use App\Models\Peminjaman;
use App\Repositories\BukuRepositoryInterface;
use App\Events\BukuDipinjam;
use Illuminate\Support\Facades\DB;

class PinjamBukuAction
{
    public function __construct(
        private readonly BukuRepositoryInterface $bukuRepository
    ) {}

    /**
     * Eksekusi aksi peminjaman buku.
     * Mengembalikan model Peminjaman yang baru dibuat.
     *
     * @throws BukuTidakTersediaException|BatasPinjamanTercapaiException
     */
    public function execute(Anggota $anggota, Buku $buku): Peminjaman
    {
        $this->validasiBusinessRules($anggota, $buku);

        return DB::transaction(function () use ($anggota, $buku) {
            // 1. Kurangi stok buku
            $this->bukuRepository->decrementStok($buku);

            // 2. Buat record peminjaman
            $peminjaman = Peminjaman::create([
                'buku_id'       => $buku->id,
                'anggota_id'    => $anggota->id,
                'tanggal_pinjam' => now(),
                'batas_kembali' => now()->addDays(7),
                'denda'         => 0,
                'status'        => 'dipinjam',
            ]);

            // 3. Beri tahu sistem lain (mis. kirim notifikasi)
            event(new BukuDipinjam($peminjaman));

            return $peminjaman;
        });
    }

    private function validasiBusinessRules(Anggota $anggota, Buku $buku): void
    {
        // Buku harus tersedia (stok > 0 dan tidak rusak)
        if (! $buku->tersedia()) {
            throw new BukuTidakTersediaException("Buku '{$buku->judul}' sedang tidak tersedia.");
        }

        // Anggota maksimal punya 5 peminjaman aktif
        $peminjamanAktif = Peminjaman::where('anggota_id', $anggota->id)
            ->where('status', 'dipinjam')
            ->count();

        if ($peminjamanAktif >= 5) {
            throw new BatasPinjamanTercapaiException(
                "Anggota '{$anggota->nama}' sudah mencapai batas 5 peminjaman aktif."
            );
        }
    }
}
```

Controller yang tipis — hanya mencari data, mengeksekusi action, dan menangani hasil:

```php
<?php

namespace App\Http\Controllers;

use App\Actions\PinjamBukuAction;
use App\Models\Buku;
use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;

class PeminjamanController extends Controller
{
    public function store(Request $request, PinjamBukuAction $pinjamBuku): RedirectResponse
    {
        // Controller tetap tipis: cukup validasi input HTTP sederhana
        $validated = $request->validate([
            'buku_id' => ['required', 'exists:bukus,id'],
        ]);

        $buku = Buku::findOrFail($validated['buku_id']);
        $anggota = $request->user();

        try {
            $pinjamBuku->execute($anggota, $buku);
        } catch (\DomainException $e) {
            // Exception domain ditangkap di satu tempat -> flash message
            return back()->with('error', $e->getMessage());
        }

        return redirect()->route('peminjaman.index')
            ->with('success', 'Buku berhasil dipinjam.');
    }
}
```

Class exception domain (lokasi: `app/Exceptions/`):

```php
<?php

namespace App\Exceptions;

use DomainException;

class BukuTidakTersediaException extends DomainException {}
```

```php
<?php

namespace App\Exceptions;

use DomainException;

class BatasPinjamanTercapaiException extends DomainException {}
```

Catatan: karena kedua exception tersebut menurun dari `\DomainException`, controller cukup menangkap satu tipe di `catch` — praktis dan konsisten.

## 4. Analogi Sederhana

Bayangkan sebuah restoran yang punya banyak cabang. Action Pattern adalah **resep/SOP standar untuk tiap hidangan**.

Setiap hidangan punya resep tertulis yang lengkap dan terisolasi — bukan koki menulis semua resep dalam satu buku catatan besar yang tidak terstruktur. Resep untuk "Ayam Goreng", resep untuk "Soto Betawi", masing-masing berdiri sendiri di kartu resep terpisah. Di Laravel, kartu resep itu adalah `PinjamBukuAction`, `KembalikanBukuAction`, dan seterusnya — **satu class untuk satu aksi bisnis**.

Controller adalah pelayan atau koki dapur yang tinggal mengikuti resep: ambil bahan (`findOrFail`), ikuti langkahnya (`execute()`), lalu laporkan hasil ke pelanggan (`redirect` dengan flash message). Controller tidak perlu tahu detail racikan bumbu (transaction, event, aturan batas pinjaman) — itu semua sudah tertulis rapi di kartu resep.

Kalau suatu saat resep berubah (misal batas pinjaman naik dari 5 ke 10), cukup ubah di **satu tempat** saja, dan semua cabang (web, API, console) otomatis ikut konsisten karena semuanya memanggil action yang sama. Tidak ada lagi koki yang hafal resep berbeda-beda di tiap cabang.

Service Layer ibarat **buku kumpulan resep satu tema** (misal "Buku Resep Masakan Nusantara") — menampung banyak resep sejenis dalam satu buku, sedangkan action adalah satu kartu resep tunggal.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

**Gunakan Action Pattern ketika:**
- Business rule kompleks dan multi-step (validasi + perhitungan + transaction + event).
- Perlu `DB::transaction` karena melibatkan beberapa write (decrement stok + create peminjaman).
- Operasi akan dipakai dari lebih dari satu entry point: web controller, API controller, console command, bahkan test.
- Ingin exception domain yang spesifik per aturan (buku tidak tersedia, batas tercapai).
- Ingin unit-test business logic tanpa HTTP.

**Gunakan Service Layer ketika:**
- Ada banyak operasi yang saling terkait dalam satu domain (pinjam, kembali, perpanjang, hitung denda) — kumpulkan sebagai method dalam satu `PeminjamanService`.
- Action-action kecil mulai berbagi logika yang sama (misal `hitungDenda()`) — tarik logika itu ke service agar tidak duplikat.

**Kapan cukup pakai controller biasa:**
- Operasinya sederhana: satu `create`, satu `update`, tidak ada aturan tambahan.
- Tidak dipakai dari tempat lain selain satu controller.
- Tidak perlu transaction (single write).

Patokan praktis: mulai dengan controller yang ramping. Begitu ada aturan kedua yang ditambahkan, atau operasi mulai dipanggil dari dua tempat, itu sinyal untuk pindah ke action/service.

**Keuntungan dipakai dari banyak tempat:**

```php
// Dari web: controller
$pinjamBuku->execute($anggota, $buku);

// Dari API: API controller (mis. App\Http\Controllers\Api\PeminjamanController)
$peminjaman = $pinjamBuku->execute($anggota, $buku);
return response()->json($peminjaman, 201);

// Dari console: Artisan command
// php artisan peminjaman:buat {anggota} {buku}
public function handle(PinjamBukuAction $pinjamBuku): int
{
    $pinjamBuku->execute($this->anggota, $this->buku);
    return self::SUCCESS;
}
```

Satu logic, tiga entry point, nol duplikasi.

## 6. Poin-poin Penting & Best Practices

- **Satu class = satu aksi.** Nama pakai kata kerja di belakang: `PinjamBukuAction`, `KembalikanBukuAction`, `RegistrasiAnggotaAction`.
- **Method utama bernama `execute()`** — konsisten di seluruh action, mudah diingat dan dipanggil.
- **Validasi business rules di dalam action**, bukan di controller. Controller hanya validasi format input (misal `buku_id` wajib ada), action yang menilai layak-tidaknya operasi bisnis (stok, batas pinjaman, denda).
- **Gunakan `DB::transaction` untuk operasi multi-write.** Stok berkurang dan peminjaman dibuat harus atomik — kalau salah satu gagal, semuanya rollback.
- **Throw exception domain spesifik** (`BukuTidakTersediaException`, `BatasPinjamanTercapaiException`) yang menurun dari `\DomainException`, agar controller cukup satu `catch`.
- **Controller tetap tipis**: cari data (`findOrFail`), panggil `execute()`, `try/catch`, lalu `redirect` dengan flash message.
- **Action mudah ditest langsung** — murni terima parameter, kembalikan value/throw exception. Tidak perlu HTTP request.
- **Constructor injection via Service Container**: action di-resolve otomatis, interface repository langsung dibinding (materi 33).
- **Jangan taruh semua logika di action.** Kalau action membengkak atau banyak action berbagi logika (hitung denda, cek status), ekstrak ke repository atau service.
- **Konsisten naming & lokasi**: taruh semua di `app/Actions/`, ikuti pola `KataKerja + Objek + Action`.

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

1. **Action jadi terlalu besar.** Jika `execute()` sudah 50+ baris dengan banyak `if` bersarang, pecah: validasi ke method privat atau class validator tersendiri, hitung denda ke service.
2. **Logika duplikat antar action.** `hitungDenda()` ditulis ulang di `KembalikanBukuAction` dan `PerpanjangPeminjamanAction`. Ekstrak ke `DendaService` atau repository.
3. **Tidak memakai transaction.** Stok berkurang tapi pembuatan `Peminjaman` gagal — data tidak konsisten, buku "hilang" dari stok tanpa record. Selalu bungkus multi-write dengan `DB::transaction`.
4. **Exception tidak ditangani di controller.** Exception domain yang dilempar action tidak di-catch, muncul error 500 alih-alih flash message. Catat: selalu tangkap `\DomainException` (atau exception domain lain) di controller dan kembalikan `back()->with('error', ...)`.
5. **Action mengakses request langsung.** Jangan panggil `request()->input()` di dalam action — action harus menerima parameter murni (`$anggota`, `$buku`) agar bisa dipakai dari web, API, dan console tanpa bergantung pada HTTP.
6. **Controller tetap gemuk.** Ada yang pindah logika ke action tapi controller masih berisi perhitungan dan dispatch — tidak ada gunanya. Controller hanya mengatur alur.
7. **Over-engineering.** Semua hal dijadikan action padahal hanya `Anggota::create()` satu baris. Action untuk operasi sepele justru menambah kerumitan. Mulai sederhana, naikkan kompleksitas saat dibutuhkan.

**Troubleshooting cepat:**
- `BatasPinjamanTercapaiException` tidak tertangkap? Pastikan exception menurun dari `\DomainException` dan `catch (\DomainException $e)` sudah ada di controller.
- Transaction tidak jalan? Pastikan memakai `DB::transaction(...)` yang mengembalikan nilai dari closure (pakai `return` di dalamnya), dan model tidak me-nonaktifkan transaksi.
- Action tidak bisa di-resolve? Pastikan class ada di namespace `App\Actions` dan type-hint-nya benar; Service Container akan menangani sisanya.

## 8. Soal Latihan & Kunci Jawaban

### Tantangan

**Kasus 1: Buat `KembalikanBukuAction`.**
Buat action `app/Actions/KembalikanBukuAction.php` dengan method `execute(Peminjaman $peminjaman): Peminjaman` yang:
- Menolak jika buku dikembalikan terlambat (menghitung denda Rp 5.000 per hari keterlambatan).
- Memperbarui `tanggal_kembali`, `denda`, dan `status` menjadi `'kembali'`.
- Menambah stok buku kembali lewat `BukuRepositoryInterface->incrementStok()`.
- Semua dibungkus `DB::transaction`. Lempar `PengembalianTerlambatException`? Tidak — karena pengembalian terlambat tetap diproses, cukup hitung denda. Gunakan exception hanya untuk kasus aneh (misal peminjaman sudah dikembalikan dua kali).

**Kasus 2: Webhook/console reuse.**
Jelaskan bagaimana kamu memanggil `KembalikanBukuAction` dari sebuah Artisan command `pengembalian:proses {id}` dan apa untungnya dibanding menulis ulang logika di command tersebut.

### Jawaban & Pembahasan

**Jawaban Kasus 1:**

```php
<?php

namespace App\Actions;

use App\Exceptions\PeminjamanSudahSelesaiException;
use App\Models\Peminjaman;
use App\Repositories\BukuRepositoryInterface;
use Illuminate\Support\Facades\DB;

class KembalikanBukuAction
{
    // Denda per hari keterlambatan
    private const DENDA_PER_HARI = 5000;

    public function __construct(
        private readonly BukuRepositoryInterface $bukuRepository
    ) {}

    public function execute(Peminjaman $peminjaman): Peminjaman
    {
        // Kasus aneh: peminjaman sudah selesai, jangan diproses dua kali
        if ($peminjaman->status === 'kembali') {
            throw new PeminjamanSudahSelesaiException(
                "Peminjaman #{$peminjaman->id} sudah dikembalikan."
            );
        }

        return DB::transaction(function () use ($peminjaman) {
            $denda = $this->hitungDenda($peminjaman);

            // Update record peminjaman
            $peminjaman->update([
                'tanggal_kembali' => now(),
                'denda'           => $denda,
                'status'          => 'kembali',
            ]);

            // Kembalikan stok buku
            $this->bukuRepository->incrementStok($peminjaman->buku);

            return $peminjaman;
        });
    }

    private function hitungDenda(Peminjaman $peminjaman): int
    {
        $batasKembali = $peminjaman->batas_kembali;

        // Tidak terlambat -> tanpa denda
        if (now()->lte($batasKembali)) {
            return 0;
        }

        $hariTerlambat = now()->startOfDay()->diffInDays($batasKembali->startOfDay());

        return $hariTerlambat * self::DENDA_PER_HARI;
    }
}
```

**Alur pembahasan Kasus 1:**
1. Action pertama mengecek status: jika sudah `'kembali'`, lempar exception domain — ini mencegah proses dobel yang merusak data.
2. Perhitungan denda dipisah ke method privat `hitungDenda()` agar `execute()` tetap mudah dibaca.
3. Seluruh update (denda, status, tanggal) dan `incrementStok` dibungkus `DB::transaction` — kalau salah satu gagal, semuanya dibatalkan, stok tidak ganda bertambah.
4. Terlambat bukan exception, tapi dihitung denda — pengembalian tetap diterima, sanksi finansial yang menyesuaikan.

**Jawaban Kasus 2:**

```php
<?php

namespace App\Console\Commands;

use App\Actions\KembalikanBukuAction;
use App\Models\Peminjaman;
use Illuminate\Console\Command;

class ProsesPengembalianCommand extends Command
{
    protected $signature = 'pengembalian:proses {id}';
    protected $description = 'Proses pengembalian buku dari console';

    public function handle(KembalikanBukuAction $kembalikanBuku): int
    {
        $peminjaman = Peminjaman::findOrFail((int) $this->argument('id'));

        try {
            $kembalikanBuku->execute($peminjaman);
        } catch (\DomainException $e) {
            $this->error($e->getMessage());
            return self::FAILURE;
        }

        $this->info('Pengembalian berhasil diproses.');
        return self::SUCCESS;
    }
}
```

**Pembahasan Kasus 2:**
Keuntungan memakai action yang sama di console command:
- **Nol duplikasi** — aturan denda dan transaction ditulis sekali di action, dipakai controller dan command.
- **Konsisten** — tidak mungkin web dan console menghitung denda berbeda karena keduanya memanggil kode yang sama.
- **Testable** — kamu cukup mengetes `KembalikanBukuAction` sekali, dan semua entry point ikut teruji karena mereka memanggil kode yang sama.
- **Service Container** otomatis menyuntikkan `KembalikanBukuAction` ke `handle()` — tidak perlu manual instantiate.

Inilah inti dari Action Pattern: tulis sekali aturan bisnisnya, pakai dari mana saja (web, API, console), dan controller/command kamu tetap tipis seperti pelayan yang tinggal mengikuti resep.
