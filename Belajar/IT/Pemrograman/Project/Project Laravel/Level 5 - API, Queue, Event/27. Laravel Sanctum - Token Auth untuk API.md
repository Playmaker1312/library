# 27. Laravel Sanctum — Token Auth untuk API

Setelah API kita bisa mengeluarkan data lewat Resource (materi 26), pertanyaan berikutnya: bagaimana membatasi siapa yang boleh memanggil API? Jawabannya di materi ini: Laravel Sanctum. Sanctum memberi kita token auth yang ringan untuk SPA dan mobile app, lengkap dengan abilities (izin per scope) dan kadaluarsa. Kalau Level 4 kita pakai session + policy untuk web, sekarang kita pakai token untuk API.

## 1. Penjelasan Singkat & Konsep Dasar

Sanctum adalah paket autentikasi berbasis token yang ringan, bawaan Laravel. Untuk API, Sanctum menggunakan **token stateless**: setiap request membawa token di header `Authorization: Bearer <token>`, dan server memverifikasinya tanpa menyimpan sesi di sisi server. Ini beda dengan OAuth (yang berat dan butuh setup authorization server) — untuk kebutuhan perpustakaan kita yang hanya punya SPA/mobile app, Sanctum sudah lebih dari cukup.

Alur dasarnya:
1. Pengguna login -> server cek kredensial -> buat token -> kembalikan `plainTextToken`.
2. Aplikasi klien menyimpan token dan mengirimkannya di tiap request.
3. Server memverifikasi token lewat middleware `auth:sanctum`.
4. Logout -> token dihapus -> request berikutnya ditolak.

Kaitannya dengan materi lain: Resource (26) memakai `$request->user()?->tokenCan('admin')` untuk field kondisional — itu didukung oleh abilities Sanctum. Middleware `auth:sanctum` juga hasil belajar middleware di Level 4.

## 2. Fungsi & Kegunaan Utama dalam Laravel

Masalah yang diselesaikan Sanctum:

1. **Auth untuk API tanpa sesi** — mobile app dan sistem lain tidak punya cookie/sesi browser; mereka butuh token yang bisa dibawa-bawa.
2. **Multiple token** — satu user bisa punya banyak token (satu per device), masing-masing bisa dicabut terpisah.
3. **Abilities (scoped token)** — token bisa dibatasi izinnya: token "anggota" hanya boleh baca buku dan buat peminjaman, token "admin" boleh semua.
4. **Expiration** — token bisa diatur masa berlaku, mengurangi risiko kalau token bocor.
5. **Ringan dan tanpa OAuth** — tidak butuh tabel `oauth_clients` atau redirect flow yang kompleks; cukup `personal_access_tokens` table.
6. **SPA stateful (bonus)** — selain API stateless, Sanctum juga bisa handle login cookie untuk SPA Laravel + frontend Vue/React pada domain yang sama.

## 3. Contoh Kode & Implementasi (Real-world Example)

### 3.1 Instalasi

```bash
# 1. Install paket Sanctum
composer require laravel/sanctum

# 2. Publish migration & config (membuat tabel personal_access_tokens)
php artisan vendor:publish --provider="Laravel\Sanctum\SanctumServiceProvider"

# 3. Jalankan migration
php artisan migrate
```

### 3.2 Tambahkan trait di User model

```php
// app/Models/User.php
<?php

namespace App\Models;

use Laravel\Sanctum\HasApiTokens; // <-- tambahkan import
use Illuminate\Foundation\Auth\User as Authenticatable;
use Illuminate\Notifications\Notifiable;

class User extends Authenticatable
{
    use HasApiTokens; // <-- wajib
    use Notifiable;

    // ... fillable, hidden, casts seperti biasa
}
```

Setelah ini, tiap user punya relasi `tokens` (di tabel `personal_access_tokens`) dan method `createToken()`.

### 3.3 AuthController (login, logout, me)

Lokasi: `app/Http/Controllers/Api/V1/AuthController.php`

```php
<?php

namespace App\Http\Controllers\Api\V1;

use App\Http\Controllers\Controller;
use App\Models\User;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Hash;
use Illuminate\Validation\ValidationException;

class AuthController extends Controller
{
    /**
     * POST /api/v1/login
     * Validasi -> cek kredensial -> buat token dengan abilities sesuai role.
     */
    public function login(Request $request)
    {
        $data = $request->validate([
            'email' => ['required', 'email'],
            'password' => ['required', 'string'],
        ]);

        $user = User::where('email', $data['email'])->first();

        // Satu pesan error umum, jangan ungkap email terdaftar atau tidak
        if (! $user || ! Hash::check($data['password'], $user->password)) {
            throw ValidationException::withMessages([
                'email' => ['Kredensial yang diberikan tidak cocok.'],
            ]);
        }

        // Abilities berdasarkan role: admin dapat semua, anggota dibatasi
        $abilities = $user->role === 'admin'
            ? ['*']
            : ['buku:read', 'peminjaman:create'];

        // expiresAt (opsional): token mati otomatis setelah 1 hari
        $token = $user->createToken(
            $request->header('User-Agent') ?? 'api-token', // nama token (asumsi: device)
            $abilities,
            now()->addDay()
        );

        return response()->json([
            'message' => 'Login berhasil.',
            'user' => [
                'id' => $user->id,
                'name' => $user->name,
                'email' => $user->email,
                'role' => $user->role,
            ],
            'token' => $token->plainTextToken, // HANYA tampil sekali!
        ], 200);
    }

    /**
     * POST /api/v1/logout
     * Hapus token yang sedang dipakai.
     */
    public function logout(Request $request)
    {
        // Hapus token pada request ini saja (bukan semua token user)
        $request->user()->currentAccessToken()->delete();

        return response()->json(['message' => 'Logout berhasil.']);
    }

    /**
     * GET /api/v1/me
     * Data user yang sedang login. Dilindungi middleware auth:sanctum.
     */
    public function me(Request $request)
    {
        return response()->json($request->user());
    }
}
```

### 3.4 Register route dan proteksi

```php
// routes/api.php
<?php

use App\Http\Controllers\Api\V1\AuthController;
use App\Http\Controllers\Api\V1\BukuController;
use Illuminate\Support\Facades\Route;

Route::prefix('v1')->name('api.v1.')->group(function () {
    // Public: login tidak butuh token
    Route::post('login', [AuthController::class, 'login'])->name('login');

    // Protected: semua route di bawah butuh token valid
    Route::middleware('auth:sanctum')->group(function () {
        Route::get('me', [AuthController::class, 'me'])->name('me');
        Route::post('logout', [AuthController::class, 'logout'])->name('logout');

        // Buku hanya boleh diubah admin
        Route::middleware('can:buku:create')->post('buku', [BukuController::class, 'store'])->name('buku.store');

        Route::get('buku', [BukuController::class, 'index'])->name('buku.index');
        Route::get('buku/{buku}', [BukuController::class, 'show'])->name('buku.show');
    });
});
```

### 3.5 Contoh pemakaian dari klien

```bash
# Login -> simpan token yang dihasilkan
curl -X POST http://localhost:8000/api/v1/login \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"email":"anggota@mail.com","password":"rahasia123"}'

# Panggil API terproteksi dengan token
curl http://localhost:8000/api/v1/me \
  -H "Authorization: Bearer <isi_plainTextToken_di_sini>" \
  -H "Accept: application/json"
```

## 4. Analogi Sederhana

**Sanctum = Tiket akses untuk kurir delivery.** Saat aplikasi luar mau pesan, ia login dulu dan menerima tiket (token). Setiap request delivery harus menunjukkan tiket itu — petugas (middleware `auth:sanctum`) memeriksa tiket sebelum memproses. Tiket bisa kadaluarsa (`expiresAt`) dan bisa dicabut kapan saja (logout/`delete()`). Tiket admin (`'*'`) seperti akses ke seluruh area restoran, sedangkan tiket anggota hanya valid untuk area tertentu (`buku:read`, `peminjaman:create`). Tanpa tiket, kurir tidak masuk dapur — request ditolak dengan 401.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

1. **Mobile app perpustakaan** — pengguna login di aplikasi Android/iOS, app menyimpan token, lalu memanggil API dengan token tersebut.
2. **SPA Vue/React terpisah domain** — frontend di `app.perpustakaan.com`, backend API di `api.perpustakaan.com`, dikirim via header Bearer.
3. **Integrasi dengan sistem lain** — sistem kampus butuh akses baca data buku; beri token khusus dengan ability terbatas.
4. **Multi-device** — satu akun bisa login dari beberapa device, masing-masing punya token sendiri yang bisa dicabut terpisah (misal logout dari HP tapi tidak dari laptop).
5. **Token dengan masa berlaku** — misal token tamu kunjungan perpustakaan hanya berlaku 1 hari.

## 6. Poin-poin Penting & Best Practices

- **Install dengan benar urutannya**: `composer require laravel/sanctum` -> `vendor:publish` -> `migrate`. Jangan lupa migrate atau tabel `personal_access_tokens` tidak ada.
- **Tambah `HasApiTokens`** di User model, wajib agar `createToken` tersedia.
- **`createToken($name, $abilities, $expiresAt)`** — name untuk identifikasi device, abilities untuk scope, expiresAt untuk masa berlaku.
- **`plainTextToken` hanya muncul sekali** — simpan di sisi klien, jangan pernah simpan di database (hanya hash-nya yang disimpan).
- **Middleware `auth:sanctum`** untuk melindungi route. Bisa dikombinasi dengan `can:` untuk otorisasi policy (Level 4).
- **Abilities**: admin pakai `['*']`, anggota pakai scope spesifik. Cek ability di Resource/controller dengan `$user->tokenCan('buku:read')`.
- **Logout = hapus token**: `$request->user()->currentAccessToken()->delete()`.
- **Stateless**: jangan buat sesi, jangan simpan status login di server; biarkan token yang membuktikan diri.
- **Login API selalu kirim `Accept: application/json`** di header request klien (ini terkait error handling di materi 28).

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

1. **Lupa migrate** — tabel `personal_access_tokens` tidak ada, `createToken()` error. Selalu jalankan `php artisan migrate` setelah publish.
2. **Token tidak diterima** — biasanya karena: salah guard (pakai `auth:web` di route API), lupa header `Authorization: Bearer <token>`, atau token dihapus saat logout. Cek header dan guard `auth:sanctum`.
3. **`plainTextToken` disimpan di response/DB** — token plain hanya untuk klien. Jangan pernah log atau simpan.
4. **Expose data sensitif di login** — jangan kirim `password` atau hash token di response. Filter seperti di contoh `login` di atas.
5. **Token tidak expire** — kalau tidak memberi `expiresAt`, token hidup selamanya. Pertimbangkan `expiresAt` untuk keamanan.
6. **Ability `'*'` dipakai semua orang** — setiap token admin punya akses penuh. Untuk user biasa, gunakan scope spesifik.
7. **Logout tidak menghapus token** — kalau hanya "forget" di klien tapi token tetap ada di server, token bisa dipakai lagi. Hapus di server.
8. **Error HTML bukan JSON saat token invalid** — ini diatasi di materi 28 (error handling), karena Laravel akan mengembalikan halaman error kalau klien tidak mengirim `Accept: application/json`.

**Troubleshooting cepat:**
- `401 Unauthenticated` terus? Cek format header `Bearer` dan pastikan token belum expired/dihapus.
- `createToken` method not found? Pastikan `HasApiTokens` sudah di use di User model.
- Ability tidak berfungsi (`tokenCan` false)? Pastikan abilities dikirim saat `createToken`, bukan diubah setelahnya.

## 8. Soal Latihan & Kunci Jawaban

### Tantangan

**Tantangan 1: Login + proteksi route dengan Sanctum.**
Buat endpoint `POST /api/v1/login` yang menerima `email` dan `password`, memvalidasi, mengecek kredensial, lalu membuat token dengan ability `buku:read` untuk role anggota. Proteksi route `GET /api/v1/me` dengan `auth:sanctum` dan pastikan `GET /api/v1/logout` menghapus token yang dipakai.

**Tantangan 2: Logout hanya untuk token yang aktif.**
Pengguna punya 2 token (HP dan laptop). Saat logout dari HP, hanya token HP yang harus dihapus, bukan keduanya. Tulis logikanya.

### Jawaban & Pembahasan

**Jawaban Tantangan 1:**

```php
// app/Http/Controllers/Api/V1/AuthController.php
public function login(Request $request)
{
    $data = $request->validate([
        'email' => ['required', 'email'],
        'password' => ['required', 'string'],
    ]);

    $user = User::where('email', $data['email'])->first();

    if (! $user || ! Hash::check($data['password'], $user->password)) {
        throw ValidationException::withMessages([
            'email' => ['Kredensial tidak cocok.'],
        ]);
    }

    $abilities = $user->role === 'admin' ? ['*'] : ['buku:read'];

    $token = $user->createToken('device', $abilities, now()->addDay());

    return response()->json([
        'user' => $user->only('id', 'name', 'email', 'role'),
        'token' => $token->plainTextToken,
    ]);
}
```

```php
// routes/api.php
Route::prefix('v1')->name('api.v1.')->group(function () {
    Route::post('login', [AuthController::class, 'login'])->name('login');

    Route::middleware('auth:sanctum')->group(function () {
        Route::get('me', [AuthController::class, 'me'])->name('me');
        Route::post('logout', [AuthController::class, 'logout'])->name('logout');
    });
});
```

Alur: request `login` -> validasi -> cari user -> `Hash::check` memverifikasi password (jangan pernah bandingkan password plain) -> tentukan abilities berdasarkan role -> `createToken` menghasilkan token baru -> `plainTextToken` dikirim ke klien sekali saja. Request `me` dan `logout` melewati middleware `auth:sanctum`, jadi hanya berhasil kalau header `Authorization: Bearer <token>` valid.

**Jawaban Tantangan 2:**

```php
public function logout(Request $request)
{
    // currentAccessToken() = token yang dipakai pada request ini saja
    $request->user()->currentAccessToken()->delete();

    return response()->json(['message' => 'Logout berhasil.']);
}
```

Alur: Sanctum menyimpan semua token user di tabel `personal_access_tokens`. Saat logout, kita mengambil token dari request yang sedang berjalan (`currentAccessToken()`), bukan `$user->tokens()->delete()` (yang menghapus semua). Karena hanya satu baris token yang dihapus, token di device lain tetap valid — sesuai kasus: logout dari HP tidak mematikan token di laptop. Kalau ingin logout semua device sekaligus, barulah pakai `$user->tokens()->delete()`.
