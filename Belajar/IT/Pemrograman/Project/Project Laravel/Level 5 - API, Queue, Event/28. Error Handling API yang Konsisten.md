# 28. Error Handling API yang Konsisten

Sekarang API kita sudah bisa dikonsumsi (Resource, materi 26) dan dilindungi token (Sanctum, materi 27). Tapi ada satu masalah: secara default, Laravel mengembalikan **halaman HTML** saat terjadi error — bentuknya tidak konsisten dan tidak bisa dibaca aplikasi lain. Materi ini menyelesaikan itu: kita buat semua error API dikembalikan sebagai JSON dengan format yang seragam, lengkap dengan status code yang benar.

## 1. Penjelasan Singkat & Konsep Dasar

Laravel punya sistem exception handling yang bagus, tapi default-nya dirancang untuk browser. Kalau klien API (mobile app, sistem lain) mengalami error, mereka tidak mau menerima halaman HTML — mereka butuh JSON terstruktur agar bisa menangkap error dan menampilkan pesan yang tepat ke user.

Di Laravel 11, penanganan exception dikonfigurasi di file `bootstrap/app.php` (sebelumnya di `App\Exceptions\Handler`). Kita bisa menambahkan method `render()` custom: ketika request mengharapkan JSON (lewat header `Accept: application/json` atau URL berawalan `api/`), kita mengembalikan response JSON dengan format konsisten; kalau request dari browser biasa, biarkan Laravel mengembalikan halaman default.

Format error yang konsisten membantu: **status code** (401, 403, 404, 422, 429, 500) memberi tahu kategori masalah, dan **body JSON** memberi detail tambahan (seperti `errors` untuk validasi).

Kaitannya: ValidationException (dilempar Form Request dari Level 4), AuthenticationException (token Sanctum invalid), dan response Resource (materi 26) semuanya bertemu di satu titik: format JSON yang konsisten.

## 2. Fungsi & Kegunaan Utama dalam Laravel

Masalah yang diselesaikan:

1. **Konsistensi format error** — semua error API punya struktur `{message: ..., errors: ...}` yang sama, mudah diparsing klien.
2. **Status code benar** — klien tahu membedakan 401 (belum login), 403 (tidak punya akses), 404 (tidak ada), 422 (input salah), 429 (terlalu banyak request), 500 (error server).
3. **Tidak bocor detail internal** — di production, kita sembunyikan stack trace; di local/dev, detail tetap terlihat untuk debugging.
4. **Membedakan konteks** — request browser dapat halaman error bagus, request API dapat JSON.
5. **Titik tengah semua exception** — sekali konfigurasi, semua error (validasi, auth, not found, rate limit, exception tak terduga) mengikuti format yang sama.

## 3. Contoh Kode & Implementasi (Real-world Example)

### 3.1 Konfigurasi di bootstrap/app.php

Lokasi: `bootstrap/app.php`

```php
<?php

use App\Http\Resources\Api\ErrorResource;
use Illuminate\Auth\AuthenticationException;
use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Exceptions;
use Illuminate\Foundation\Configuration\Middleware;
use Illuminate\Http\Request;
use Illuminate\Validation\ValidationException;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\HttpKernel\Exception\TooManyRequestsHttpException;
use Illuminate\Database\Eloquent\ModelNotFoundException;

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        api: __DIR__.'/../routes/api.php',
        commands: __DIR__.'/../routes/console.php',
        health: '/up',
    )
    ->withMiddleware(function (Middleware $middleware) {
        // ...
    })
    ->withExceptions(function (Exceptions $exceptions) {
        // Custom render: hanya untuk request yang mengharapkan JSON
        $exceptions->render(function (\Throwable $e, Request $request) {
            // API? Atau klien yang eksplisit minta JSON?
            if ($request->expectsJson() || $request->is('api/*')) {
                return $this->formatApiError($e);
            }

            // Bukan API -> biarkan Laravel menangani (halaman HTML default)
            return null;
        });
    })->create();

// Bisa juga dipisah ke helper agar lebih bersih:
function formatApiError(\Throwable $e): \Illuminate\Http\JsonResponse
{
    // match(true) = "cocokkan yang pertama kali benar", diuji dari atas ke bawah
    return match (true) {
        // 422: validasi gagal (dilempar Form Request / ValidationException)
        $e instanceof ValidationException => response()->json([
            'message' => 'Validasi gagal.',
            'errors' => $e->errors(), // daftar pesan per field
        ], 422),

        // 401: tidak login / token invalid (dilempar middleware auth)
        $e instanceof AuthenticationException => response()->json([
            'message' => 'Anda harus login terlebih dahulu.',
        ], 401),

        // 403: tidak punya akses (dilempar Policy / AuthorizationException)
        $e instanceof AccessDeniedHttpException => response()->json([
            'message' => 'Anda tidak memiliki akses.',
        ], 403),

        // 404: resource tidak ditemukan
        $e instanceof ModelNotFoundException => response()->json([
            'message' => 'Data tidak ditemukan.',
        ], 404),

        // 429: rate limit terlampaui
        $e instanceof TooManyRequestsHttpException => response()->json([
            'message' => 'Terlalu banyak request, silakan coba lagi nanti.',
        ], 429),

        // Production: jangan bocorkan detail. 500 generic.
        app()->environment('production') => response()->json([
            'message' => 'Terjadi kesalahan pada server.',
        ], 500),

        // Development: tampilkan detail error untuk debugging
        default => response()->json([
            'message' => $e->getMessage(),
            'exception' => get_class($e),
            'file' => $e->getFile(),
            'line' => $e->getLine(),
        ], method_exists($e, 'getStatusCode') ? $e->getStatusCode() : 500),
    };
}
```

Catatan penting:
- Urutan `match(true)` diperiksa dari atas; pastikan tipe paling spesifik diletakkan sebelum yang generic.
- `app()->environment('production')` memastikan pesan error internal tidak bocor ke klien di production.
- `$request->expectsJson()` bernilai true jika header `Accept: application/json` dikirim, atau `X-Requested-With: XMLHttpRequest`. Gabungkan dengan `$request->is('api/*')` agar semua route API selalu mengembalikan JSON walaupun klien lupa header.
- Karena kita definisikan di closure di dalam `withExceptions`, kita perlu membuat fungsi pembantu di luar (di atas `return Application::configure`) agar bisa dipanggil — atau salin langsung di dalam closure.

### 3.2 Contoh response JSON yang dihasilkan

**422 — validasi gagal:**

```json
{
  "message": "Validasi gagal.",
  "errors": {
    "judul": ["Judul wajib diisi."],
    "isbn": ["ISBN sudah terdaftar."]
  }
}
```

**401 — belum login / token invalid:**

```json
{
  "message": "Anda harus login terlebih dahulu."
}
```

**403 — tidak punya akses:**

```json
{
  "message": "Anda tidak memiliki akses."
}
```

**404 — resource tidak ditemukan:**

```json
{
  "message": "Data tidak ditemukan."
}
```

**429 — rate limit:**

```json
{
  "message": "Terlalu banyak request, silakan coba lagi nanti."
}
```

**500 — production, generic:**

```json
{
  "message": "Terjadi kesalahan pada server."
}
```

### 3.3 Menguji dari klien

```bash
# Tanpa header Accept -> kalau URL api/* tetap dapat JSON karena $request->is('api/*')
curl http://localhost:8000/api/v1/buku/999

# Dengan header Accept: application/json (praktik terbaik dari klien)
curl http://localhost:8000/api/v1/buku/999 \
  -H "Accept: application/json"
```

Keduanya menghasilkan `{"message":"Data tidak ditemukan."}` dengan status 404.

## 4. Analogi Sederhana

**Error Handling = Prosedur standar restoran saat ada masalah.** Kalau menu yang dipesan tidak ada, kasir menjawab dengan status yang jelas: 404 (menu tidak ada). Kalau tamu tidak punya izin masuk area VIP, 403 (ditolak). Kalau tamu belum tanda tangan reservasi, 401 (belum terverifikasi). Kalau pesanan formatnya salah (misal jumlah minus), 422 (input salah). Kalau dapur kebakaran, 500 (server bermasalah) — dan di production, tamu hanya diberi tahu "maaf, ada kendala," bukan diajak melihat kekacauan di dapur (stack trace). Yang terpenting: semua jawaban diberikan dalam format yang sama — nota standar — supaya pelanggan aplikasi tahu persis apa yang terjadi dan bisa memperbaiki. **API Resource = pramusaji khusus** yang menyajikan pesanan sukses dalam format standar, dan **error handling = prosedur yang sama** saat pesanan gagal, agar seluruh pengalaman tetap konsisten.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

1. **API publik perpustakaan** — konsumen (mobile app, integrasi kampus) harus bisa membedakan "buku tidak ada" (404) vs "validasi gagal" (422) vs "token invalid" (401).
2. **Token Sanctum invalid/expired** — saat `auth:sanctum` gagal, `AuthenticationException` dilempar; dengan render custom, klien dapat JSON 401 dan bisa arahkan user ke halaman login.
3. **Validasi Form Request** — input salah di `store`/`update` melempar `ValidationException`; klien menerima `errors` per field untuk ditampilkan di form.
4. **Rate limiting** — terlalu banyak request -> 429; klien bisa menampilkan "terlalu cepat, coba lagi".
5. **Any exception tak terduga** — di production semua jadi 500 generic, tidak membocorkan struktur internal aplikasi.

## 6. Poin-poin Penting & Best Practices

- **API selalu mengembalikan JSON**; konfigurasi render di `bootstrap/app.php` (Laravel 11) adalah tempat tunggal untuk ini.
- **Gunakan `match(true)`** untuk memetakan tipe exception ke status code; urutkan yang spesifik lebih dulu.
- **`$request->expectsJson() || $request->is('api/*')`** — klien yang benar mengirim `Accept: application/json`, tapi route `api/*` tetap kita paksa JSON untuk berjaga-jaga.
- **Status code yang tepat**: ValidationException 422, AuthenticationException 401, AuthorizationException 403, ModelNotFoundException 404, TooManyRequestsHttpException 429, default 500.
- **Format body konsisten**: minimal `{message: ...}`; untuk validasi tambahkan `errors`.
- **Jangan bocorkan stack trace di production** — cek `app()->environment('production')`; hanya dev/local yang boleh melihat detail (`$e->getMessage()`, `$e->getFile()`, `$e->getLine()`).
- **Perhatikan `APP_DEBUG`** — di production set `APP_DEBUG=false` supaya Laravel juga tidak menampilkan debug page.
- **Gabungkan dengan Resource** — bentuk error JSON yang rapi sejajar dengan bentuk sukses dari `BukuResource`.
- **Jangan tangkap semua exception di controller** — biarkan exception naik ke `render()`; controller tetap bersih.

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

1. **Error HTML bukan JSON** — klien API menerima halaman HTML 404; penyebabnya klien tidak kirim `Accept: application/json` dan route tidak dianggap API. Solusi: selalu cek `$request->is('api/*')` dan ajarkan klien kirim header `Accept`.
2. **Message error bocor di production** — `$e->getMessage()` ditampilkan tanpa cek environment; di production bisa menampilkan path file dan detail DB. Selalu fallback ke 500 generic saat `environment('production')`.
3. **APP_DEBUG=true di production** — Laravel menampilkan halaman debug penuh; matikan di `.env` production.
4. **Status code salah** — misal validasi dikembalikan 200 atau 500; pastikan setiap exception dipetakan ke status yang benar.
5. **Menangkap exception dengan try/catch di controller** lalu mengembalikan pesan mentah — duplikasi logika dan format tidak konsisten; biarkan exception naik ke render.
6. **Order `match(true)` salah** — exception yang lebih spesifik ditempatkan setelah yang generic sehingga tidak pernah tercapai. Letakkan spesifik (Validation, Auth) di atas.
7. **Menampilkan password/input mentah di pesan error** — jangan pernah ikutkan data sensitif dalam body error.
8. **Rate limit tanpa pesan ramah** — 429 default terkadang tidak informatif; timpa dengan pesan konsisten.

**Troubleshooting cepat:**
- API dapat HTML? Periksa header `Accept` klien dan pastikan `$request->is('api/*')` di kondisi.
- Error 500 tanpa pesan di dev? Cek `APP_DEBUG` di `.env` (harus true di dev, false di prod).
- Validasi mengembalikan 500? Pastikan `ValidationException` diimpor dan terpetakan sebelum branch default.
- 401 muncul saat token valid? Cek guard `auth:sanctum` di route, bukan `auth:web`.

## 8. Soal Latihan & Kunci Jawaban

### Tantangan

**Tantangan 1: Konfigurasi error JSON lengkap.**
Tulis konfigurasi `render` di `bootstrap/app.php` yang mengembalikan JSON untuk: validasi (422 dengan `errors`), belum login (401), tidak punya akses (403), data tidak ditemukan (404), rate limit (429), dan error tak terduga (500 generic di production, detail di development). Pastikan hanya route API/`expectsJson` yang terpengaruh.

**Tantangan 2: Mencegah kebocoran detail.**
Di dev, error tak terduga menampilkan `$e->getMessage()`, file, dan line. Di production, semua harus menjadi 500 generic. Tulis logika kondisinya, lalu jelaskan peran `APP_DEBUG`.

### Jawaban & Pembahasan

**Jawaban Tantangan 1:**

```php
// bootstrap/app.php
->withExceptions(function (Exceptions $exceptions) {
    $exceptions->render(function (\Throwable $e, Request $request) {
        if ($request->expectsJson() || $request->is('api/*')) {
            return match (true) {
                $e instanceof ValidationException => response()->json([
                    'message' => 'Validasi gagal.',
                    'errors' => $e->errors(),
                ], 422),
                $e instanceof AuthenticationException => response()->json([
                    'message' => 'Anda harus login terlebih dahulu.',
                ], 401),
                $e instanceof AccessDeniedHttpException => response()->json([
                    'message' => 'Anda tidak memiliki akses.',
                ], 403),
                $e instanceof ModelNotFoundException => response()->json([
                    'message' => 'Data tidak ditemukan.',
                ], 404),
                $e instanceof TooManyRequestsHttpException => response()->json([
                    'message' => 'Terlalu banyak request, silakan coba lagi nanti.',
                ], 429),
                app()->environment('production') => response()->json([
                    'message' => 'Terjadi kesalahan pada server.',
                ], 500),
                default => response()->json([
                    'message' => $e->getMessage(),
                    'exception' => get_class($e),
                    'file' => $e->getFile(),
                    'line' => $e->getLine(),
                ], method_exists($e, 'getStatusCode') ? $e->getStatusCode() : 500),
            };
        }

        return null; // bukan API -> biarkan Laravel menangani
    });
})
```

Alur: setiap exception dari seluruh aplikasi (termasuk yang dilempar middleware Sanctum, Form Request, policy, dan route model binding) melewati `render` ini. Kondisi pertama memastikan kita hanya menyentuh request API/JSON. `match(true)` mengecek tipe exception dari yang paling spesifik ke generic, mengembalikan JSON dengan status code yang sesuai. Branch `default` mengembalikan detail lengkap di development dan 500 generic di production.

**Jawaban Tantangan 2:**

```php
// Di dalam match(true), urutan terakhir:
app()->environment('production') => response()->json([
    'message' => 'Terjadi kesalahan pada server.',
], 500),

default => response()->json([
    'message' => $e->getMessage(),
    'exception' => get_class($e),
    'file' => $e->getFile(),
    'line' => $e->getLine(),
], 500),
```

Alur: branch `default` hanya tercapai untuk exception yang tidak kita kenali secara spesifik. Pertama kita cek environment: kalau production, langsung kirim pesan generic — klien tidak pernah melihat detail internal seperti path file, nama exception, atau pesan yang bisa berisi data sensitif. Di development, kita tampilkan detail lengkap agar mudah debugging. Peran `APP_DEBUG`: Laravel sendiri juga menyembunyikan halaman debug jika `APP_DEBUG=false`. Jadi kombinasi keduanya — `APP_DEBUG=false` di production PLUS branch 500 generic — membuat dua lapis perlindungan: Laravel tidak menampilkan debug page, dan render custom kita tidak bocorkan detail ke klien API.
