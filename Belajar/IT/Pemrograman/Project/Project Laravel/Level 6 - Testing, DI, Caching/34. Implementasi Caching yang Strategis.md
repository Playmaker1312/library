# 34. Implementasi Caching yang Strategis

Caching itu senjata, bukan dekorasi. Kalau di-cache semua tanpa arah, kamu hanya menambah kerumitan; kalau di-cache di titik yang tepat, beban database bisa turun drastis. Materi ini membahas *strategi* caching — apa yang boleh di-cache, bagaimana membuat cache key yang aman, bagaimana membuangnya saat data berubah, dan bagaimana memproteksi operasi kritis (stok buku) dengan lock. Berhubungan erat dengan Service Container (33) untuk binding driver, queue (29) untuk invalidasi besar, dan deployment (36) untuk `cache:clear` serta pilihan driver production.

## 1. Penjelasan Singkat & Konsep Dasar

**Caching** adalah menyimpan hasil komputasi yang mahal (query DB, perhitungan, response eksternal) di tempat penyimpanan cepat, lalu melayaninya ulang tanpa menghitung dari awal. Konsep kunci yang harus dipahami: cache itu **sesaat dan tidak wajib benar** — selalu ada trade-off antara kecepatan dan kesegaran data.

Strategi, bukan sekadar "pakai cache":
- **Apa yang di-cache?** Data yang sering dibaca, jarang berubah (katalog buku), dan relatif seragam untuk semua user.
- **Apa yang tidak di-cache?** Data real-time, data pribadi per user tanpa key yang benar, dan hal yang berubah terus-menerus.
- **Bagaimana meng-invalidate?** Saat data berubah, cache harus di-flush. Kalau tidak, user melihat data basi.

Kaitannya:
- **Service Container (33)** — driver cache di-resolve dari container; ganti `CACHE_STORE` di `.env`, container yang menyediakan instance-nya.
- **Queue (29)** — invalidasi cache besar (flush seluruh tag) bisa dijalankan lewat job di background agar tidak memperlambat request.
- **Deployment (36)** — `php artisan cache:clear` dan `config:cache` wajib masuk checklist deploy, karena cache config/route bisa membuat kode lama terus disajikan.

## 2. Fungsi & Kegunaan Utama dalam Laravel

Mengapa cache penting:

1. **Performa.** Halaman katalog yang disambar ratusan user bisa langsung dilayani dari memori (mikrodetik) alih-alih query DB berulang (milidetik). Kecepatan naik, pengalaman user membaik.

2. **Mengurangi beban DB.** Query yang sama dijalankan berulang-ulang membebani database (apalagi kalau join + eager load berat). Cache menyerap beban itu — DB bernapas lega, biaya infrastruktur bisa turun.

3. **Menstabilkan respons di bawah lonjakan trafik.** Saat promosi atau momen ramai, cache mencegah database "tumbang".

Laravel menyediakan abstraksi cache yang seragam: `Cache` facade dengan driver yang bisa diganti tanpa mengubah kode (file, redis, memcached, database, array, null). Ini lagi-lagi berkat Service Container: binding `cache.store` menentukan implementasi nyata.

## 3. Contoh Kode & Implementasi (Real-world Example)

Kasus nyata: katalog buku yang sering dilihat + proses peminjaman yang harus aman terhadap race condition.

### a) Cache katalog buku dengan `Cache::remember`

Lokasi: `app/Http/Controllers/BukuController.php`

```php
<?php

namespace App\Http\Controllers;

use App\Repositories\BukuRepositoryInterface;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Cache;
use Illuminate\View\View;

class BukuController extends Controller
{
    public function __construct(
        private BukuRepositoryInterface $bukuRepository,
    ) {
    }

    public function index(Request $request): View
    {
        // Query string ikut masuk ke cache key agar hasil berbeda per pencarian
        // tidak saling tertukar (md5 supaya key pendek & unik).
        $query = (string) $request->input('q');
        $cacheKey = 'buku.katalog.' . md5($query);

        $daftarBuku = Cache::remember($cacheKey, 300, function () use ($query) {
            return $this->bukuRepository->findAll(); // query DB hanya sekali per 5 menit
        });

        return view('buku.index', [
            'daftarBuku' => $daftarBuku,
            'query' => $query,
        ]);
    }
}
```

Penjelasan `Cache::remember($key, $ttl, $callback)`:
- Cache kosong → jalankan callback, simpan hasilnya, kembalikan.
- Cache ada & belum kedaluwarsa → langsung kembalikan nilai tersimpan.
- `$ttl` dalam detik (300 = 5 menit).

### b) Invalidation via model events + cache tags

Saat buku ditambah, diubah, atau dihapus, semua cache terkait harus di-flush.

Lokasi: `app/Models/Buku.php`

```php
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Model;
use Illuminate\Support\Facades\Cache;

class Buku extends Model
{
    protected $fillable = [
        'judul',
        'penulis_id',
        'jumlah_stok',
        'deskripsi',
    ];

    // Jalankan otomatis setiap model di-save / di-delete.
    protected static function booted(): void
    {
        static::saved(function () {
            // Tags butuh driver yang mendukung (redis/memcached).
            // Dengan tags, flush hanya membersihkan cache ber-tag 'buku',
            // cache lain tidak ikut terhapus.
            if (config('cache.default') === 'redis') {
                Cache::tags(['buku'])->flush();
            }
        });

        static::deleted(function () {
            if (config('cache.default') === 'redis') {
                Cache::tags(['buku'])->flush();
            }
        });
    }
}
```

Buat katalog masuk ke tag `buku`:

```php
Cache::tags(['buku'])->remember($cacheKey, 300, function () use ($query) {
    return $this->bukuRepository->findAll();
});
```

Jika driver tidak mendukung tags (mis. `file`), pakai `Cache::forget('buku.katalog.' . md5(''))` atau flush semua — dengan catatan flush global mempengaruhi semua cache aplikasi.

### c) Peminjaman buku dengan atomic lock (anti race condition)

Masalah: dua user meminjam buku stok 1 secara bersamaan — tanpa lock, keduanya bisa lolos dan stok jadi negatif.

Lokasi: `app/Services/PeminjamanService.php`

```php
<?php

namespace App\Services;

use App\Models\Anggota;
use App\Models\Buku;
use App\Models\Peminjaman;
use Illuminate\Support\Facades\Cache;
use Illuminate\Support\Facades\DB;
use RuntimeException;

class PeminjamanService
{
    public function pinjam(Anggota $anggota, Buku $buku): Peminjaman
    {
        // Lock atomik: hanya satu "koki" boleh mengambil bahan terakhir.
        // Parameter kedua = detik lock berlaku; auto-expire mencegah deadlock abadi.
        $lock = Cache::lock("pinjam.buku.{$buku->id}", 10);

        if (! $lock->get()) {
            throw new RuntimeException('Transaksi sedang diproses, coba lagi.');
        }

        // finally = lock pasti dilepas, apa pun yang terjadi.
        try {
            return DB::transaction(function () use ($anggota, $buku) {
                // Kunci baris DB agar dua transaksi tidak baca stok bersamaan.
                $bukuSegar = Buku::whereKey($buku->id)
                    ->lockForUpdate()
                    ->firstOrFail();

                if ($bukuSegar->jumlah_stok < 1) {
                    throw new RuntimeException('Stok buku habis.');
                }

                $bukuSegar->decrement('jumlah_stok');

                return Peminjaman::create([
                    'anggota_id' => $anggota->id,
                    'buku_id' => $buku->id,
                    'tanggal_pinjam' => now(),
                ]);
            });
        } finally {
            $lock->release(); // wajib! tanpa ini terjadi deadlock.
        }
    }
}
```

Alur keamanannya berlapis:
1. `Cache::lock` — mencegah dua proses "berebut" di level aplikasi (bisa juga berbasis Redis).
2. `lockForUpdate()` — kunci baris di level database selama transaksi.
3. `decrement('jumlah_stok')` — pengurangan atomik oleh DB, bukan baca-tulis manual.
4. `finally { $lock->release(); }` — menjamin lock dilepas meski terjadi exception.

### d) Konfigurasi driver di `.env`

```dotenv
# Development: cepat, tanpa infrastruktur tambahan
CACHE_STORE=file

# Production: multi-server & dukung cache tags
CACHE_STORE=redis
```

Driver yang tersedia: `file`, `redis`, `memcached`, `database`, `array` (per-request, untuk testing), `null` (mematikan cache — pas debug).

## 4. Analogi Sederhana

Bayangkan restoran kembali. Setiap order nasi goreng tidak perlu dimasak ulang dari nol kalau ada stok yang sudah jadi:

- **Cache = Menu/hidangan jadi** yang disimpan lalu disajikan ulang. Kalau katalog buku (nasi goreng favorit semua orang) sering dipesan, jangan memasak ulang (query DB) setiap kali — simpan hidangan siap saji di etalase (cache), sajikan langsung.
- **TTL = umur hidangan di etalase.** Setelah beberapa menit, hidangan dibuang dan dimasak ulang agar tidak basi (data tetap segar dalam batas toleransi).
- **Invalidation = buang hidangan begitu bahan/menu berubah.** Kalau resep baru masuk (buku ditambah), hidangan lama di etalase dibuang supaya pelanggan tidak dapat menu usang. Tag `buku` = "etalase khusus menu buku" — yang dibuang hanya etalase itu, kios lain tidak terganggu.
- **Lock = hanya satu koki boleh mengambil bahan terakhir** agar tidak terjadi rebutan. Saat dua koki (dua user) sama-sama mau stok terakhir (1 kg beras / 1 eksemplar buku), lock memastikan hanya satu yang berhasil; satunya menunggu atau gagal dengan pesan yang jelas.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

**Saatnya pakai cache:**
- Endpoint populer yang dibaca jauh lebih banyak daripada diubah (katalog buku, daftar penulis, konfigurasi umum).
- Hasil query mahal: join banyak tabel, eager load besar, perhitungan agregat.
- Data konfigurasi yang jarang berubah (Laravel juga meng-cache config, route, event sendiri).
- Fragment tampilan yang sama untuk semua user (mis. daftar buku terpopuler di sidebar).

**Saatnya jangan pakai cache:**
- Data real-time yang harus selalu baru (stok yang ditampilkan live, saldo, notifikasi waktu nyata).
- Data pribadi per user **tanpa key yang menyertakan identitas user** — berisiko data bocor antar user.
- Data yang berubah setiap detik dan tidak memberi keuntungan performa (hitung-hitungan ringan yang jarang dipanggil).
- Saat tidak punya strategi invalidasi — cache tanpa cara membuang = bom waktu data basi.

**Pilihan per operasi:**
| Operasi | Cara |
|---|---|
| Ambil atau simpan hasil callback | `Cache::remember($key, $ttl, $callback)` |
| Simpan nilai eksplisit | `Cache::put($key, $value, $ttl)` |
| Baca saja | `Cache::get($key)` |
| Buang satu key | `Cache::forget($key)` |
| Buang banyak key (redis/memcached) | `Cache::tags(['buku'])->flush()` |
| Operasi atomik antar proses | `Cache::lock($key, $detik)` |
| Hapus semua cache | `php artisan cache:clear` |

## 6. Poin-poin Penting & Best Practices

- **`Cache::remember($key, $ttl, $callback)`** — pola utama: simpan hasil callback, ambil kembali saat perlu.
- **`Cache::put` / `get` / `forget`** — untuk operasi manual yang lebih eksplisit.
- **`Cache::tags(['buku'])->flush()`** — invalidasi selektif, butuh driver **Redis/Memcached**. Ini cara paling bersih untuk membuang semua cache terkait satu domain data.
- **`Cache::lock` untuk operasi atomik** — contoh peminjaman buku: `Cache::lock` + `lockForUpdate()` + `decrement()` stok, lalu **release di `finally`**.
- **Pilih driver sesuai lingkungan**: `file` untuk dev, **`redis`/`memcached` untuk production** (terutama multi-server), `database` sebagai alternatif sederhana, `array`/`null` untuk testing.
- **`CACHE_STORE` di `.env`** — ganti driver tanpa mengubah kode. Laravel membaca konfigurasi `cache.php` dari variabel ini.
- **Cache key harus unik** dan mempertimbangkan query string (`md5($query)`). Key yang sama untuk data berbeda = data tertukar antar user/pencarian.
- **Invalidation saat data berubah** — pasang di model events `booted()` (`saved`/`deleted`), atau flush manual setelah operasi tulis.
- **Jangan cache data pribadi per user tanpa key yang benar** — selalu sertakan `user_id` di key bila cache-nya spesifik per user, atau jangan di-cache sama sekali.
- **`php artisan cache:clear`** — wajib di checklist deployment setelah mengubah logika yang ter-cache.
- **`php artisan optimize`** — meng-cache config, route, view, event. Jangan lupa jalankan lagi (atau `cache:clear`) saat deploy versi baru.

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

1. **Cache key tidak unik** — mis. key `'buku.katalog'` tanpa `md5($query)`. Dua pencarian berbeda saling menimpa → user melihat hasil pencarian orang lain. Solusi: sertakan parameter pembeda di key.

2. **Cache tidak di-invalidate** — katalog di-cache 5 menit tapi tidak di-flush saat buku diubah. Setelah TTL, baru terlihat; jika TTL lama, data basi. Solusi: `Cache::tags(['buku'])->flush()` di model events.

3. **Memakai file cache di production** — `file` store per-server tidak konsisten di setup multi-server, dan lambat dibanding memori. Solusi: `CACHE_STORE=redis` (atau memcached) di production.

4. **Lupa release lock (deadlock)** — `$lock->get()` sukses tapi `release()` tidak dipanggil karena exception. Solusi: bungkus dengan `try { ... } finally { $lock->release(); }`.

5. **Mem-cache seluruh collection tanpa TTL yang masuk akal** — TTL 0/tidak ada membuat cache basi selamanya; TTL terlalu pendek membuat cache tidak berguna. Solusi: tetapkan TTL yang seimbang (mis. 5–15 menit untuk katalog).

6. **Race condition pada decrement stok tanpa lock** — dua request membaca stok 1, dua-duanya lolos, stok jadi -1. Solusi: `Cache::lock` + `lockForUpdate()` + `decrement()` di dalam transaksi DB.

7. **Troubleshooting cepat** — kalau data tampak lama/tidak berubah setelah deploy:
   - Cek apakah `CACHE_STORE` masih `file` di production.
   - Jalankan `php artisan cache:clear`.
   - Pastikan config ter-cache tidak basi: `php artisan config:clear` lalu `config:cache`.
   - Verifikasi invalidasi di model benar-benar terpanggil (log/event).

## 8. Soal Latihan & Kunci Jawaban

### Tantangan

1. Tulis method `katalogTerbaru` yang membaca katalog buku via `Cache::remember` dengan key `'buku.katalog'` dan TTL 300 detik, lalu jelaskan apa yang terjadi ketika ada dua pencarian berbeda (`q=laravel` dan `q=api`) pada implementasi pertama tanpa `md5(query)` vs yang sudah memakai `md5(query)`.
2. Lengkapi service `pinjam()` (seperti contoh di atas) dengan skenario stok habis: dua user meminjam serentak buku yang stoknya 1. Jelaskan peran `Cache::lock`, `lockForUpdate`, dan `finally release` dalam mencegah stok negatif dan deadlock.

### Jawaban & Pembahasan

**1. Katalog ter-cache dan masalah cache key**

```php
public function katalogTerbaru(Request $request): Collection
{
    $query = (string) $request->input('q');
    $cacheKey = 'buku.katalog.' . md5($query);

    return Cache::remember($cacheKey, 300, function () {
        return $this->bukuRepository->findAll();
    });
}
```

Pembahasan:
- Implementasi pertama (`'buku.katalog'` tanpa pembeda): pencarian `q=laravel` dan `q=api` memakai key yang sama. Pencarian pertama menyimpan hasil `laravel`, lalu pencarian `api` **menimpa** key itu. Pencarian `laravel` berikutnya mendapat hasil `api` — data tertukar. Ini bug data-leak antar pencarian.
- Implementasi kedua (`'buku.katalog.' . md5($query)`): tiap query punya key sendiri. Tidak ada penimpaan silang. `md5` dipakai agar key pendek dan deterministik, aman dimasukkan ke Redis/file.
- Catatan: `q` kosong juga menghasilkan key sendiri (`md5('')`) — pastikan pemanggil konsisten mengirim string kosong, bukan `null`.

**2. Peminjaman stok habis dengan lock**

```php
public function pinjam(Anggota $anggota, Buku $buku): Peminjaman
{
    $lock = Cache::lock("pinjam.buku.{$buku->id}", 10);

    if (! $lock->get()) {
        throw new RuntimeException('Transaksi sedang diproses, coba lagi.');
    }

    try {
        return DB::transaction(function () use ($anggota, $buku) {
            $bukuSegar = Buku::whereKey($buku->id)
                ->lockForUpdate()
                ->firstOrFail();

            if ($bukuSegar->jumlah_stok < 1) {
                throw new RuntimeException('Stok buku habis.');
            }

            $bukuSegar->decrement('jumlah_stok');

            return Peminjaman::create([
                'anggota_id' => $anggota->id,
                'buku_id' => $buku->id,
                'tanggal_pinjam' => now(),
            ]);
        });
    } finally {
        $lock->release();
    }
}
```

Pembahasan alur saat dua user meminjam serentak (stok = 1):
1. User A dapat `$lock->get()`, masuk. User B gagal mengambil lock → mendapat pesan "Transaksi sedang diproses, coba lagi." Tidak ada yang membaca stok bersamaan di level aplikasi.
2. Di dalam transaksi, `lockForUpdate()` mengunci baris buku di database. Kalaupun dua request sempat masuk, database memastikan transaksi berjalan serial.
3. User A cek stok (1 >= 1), `decrement` → stok 0, peminjaman dibuat, transaksi commit, `$lock->release()`.
4. Jika ada skenario di mana B lolos setelah A selesai, B membaca stok 0 → `throw new RuntimeException('Stok buku habis.')` → transaksi rollback → `finally` tetap melepas lock.
5. `finally` menjamin lock selalu dilepas, baik sukses maupun error — ini mencegah deadlock (lock yang tidak pernah dilepas akan menghambat semua transaksi berikutnya, dan `Cache::lock` dengan `10` detik juga auto-expire sebagai pengaman terakhir).

Hasil akhir: stok tidak pernah negatif, tidak ada dua peminjaman untuk satu eksemplar, dan tidak ada lock yang menggantung.
