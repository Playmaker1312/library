# 31. Feature Test — Simulasi HTTP Request

Feature test adalah cara Laravel menguji aplikasi seolah-olah ada pengguna nyata yang mengirim request lewat browser atau HTTP client. Kita sudah belajar API, Sanctum, Queue, dan Event di Level 5; sekarang saatnya memastikan semua itu benar-benar bekerja lewat pengujian otomatis. Materi ini jadi fondasi sebelum masuk ke Service Container & Caching (Level 6), karena testing juga butuh dependency injection yang rapi supaya mudah di-fake.

## 1. Penjelasan Singkat & Konsep Dasar

Feature test men-simulasikan satu siklus HTTP request penuh: request masuk ke route, diproses middleware, dieksekusi controller, dipanggil service/model, lalu dikembalikan sebagai response. Laravel tidak benar-benar membuka browser — ia memanggil aplikasi secara internal di dalam proses PHP yang sama, tapi semua lapisan (route, middleware, auth, session, database, queue) ikut jalan.

```bash
php artisan make:test BukuTest
```

Perintah di atas membuat file `tests/Feature/BukuTest.php`. Fitur ini ada sejak Laravel memakai PHPUnit sebagai basis, dan di Laravel 11.x dikelola lewat framework Pest atau PHPUnit yang sudah dikonfigurasi di `phpunit.xml`.

Konsep intinya: **jangan percaya kode jalan hanya karena sudah ditulis — buktikan lewat request palsu yang hasilnya bisa ditebak**. Ini melanjutkan pemahaman auth (23), policy (24), factory (17), dan API + Sanctum (26-28) dari materi sebelumnya. Nanti di materi 37 (CI/CD), feature test inilah yang otomatis dijalankan setiap kali kita push ke repository.

## 2. Fungsi & Kegunaan Utama dalam Laravel

Testing adalah *first-class citizen* di Laravel, bukan plugin tambahan. Alasan utamanya:

- **Confidence saat refactor**: ubah struktur controller, service, atau model tanpa takut merusak fungsi yang sudah ada — test yang hijau berarti tidak ada yang rusak.
- **Mencegah regresi**: bug yang sudah diperbaiki tidak muncul lagi di masa depan, karena ada test yang menjaga behavior lama.
- **Dokumentasi perilaku**: test yang ditulis rapi menjelaskan apa yang harus terjadi ketika aplikasi menerima request tertentu, lebih akurat daripada dokumentasi yang sering basi.
- **Pengujian tanpa setup manual**: tidak perlu login manual, isi form, atau klik-klik — semua otomatis dan bisa diulang ribuan kali.

Masalah yang diselesaikan: aplikasi yang makin besar membuat pengujian manual makin lambat dan rapuh. Feature test mengubah "semoga tidak error" menjadi "terbukti tidak error".

## 3. Contoh Kode & Implementasi (Real-world Example)

Semua kode di bawah berada di `tests/Feature/BukuTest.php` pada sistem Perpustakaan Digital.

**Setup dasar: pakai RefreshDatabase agar database di-reset sebelum setiap test.**

```php
<?php

namespace Tests\Feature;

use App\Models\Buku;
use App\Models\Kategori;
use App\Models\User;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Tests\TestCase;

class BukuTest extends TestCase
{
    use RefreshDatabase; // reset DB tiap test, mencegah data bocor antar test

    private function makeBuku(array $overrides = []): Buku
    {
        return Buku::factory()->create($overrides);
    }

    private function admin(): User
    {
        return User::factory()->create(['role' => 'admin']);
    }

    private function anggota(): User
    {
        return User::factory()->create(['role' => 'anggota']);
    }
}
```

**Test 1: halaman katalog bisa diakses publik.**

Route `buku.index` di katalog tidak butuh login. Kita pastikan status 200, view yang dipakai benar, dan data buku dikirim ke view.

```php
public function test_katalog_dapat_diakses_oleh_publik(): void
{
    $buku = $this->makeBuku(['judul' => 'Laravel untuk Pemula']);

    $response = $this->get(route('buku.index'));

    $response->assertStatus(200);
    $response->assertViewIs('buku.index');   // view yang dipakai benar
    $response->assertViewHas('bukus', function ($bukus) use ($buku) {
        return $bukus->contains($buku);      // buku hasil factory masuk daftar
    });
}
```

**Test 2: detail buku menampilkan info, dan 404 jika tidak ada.**

```php
public function test_detail_buku_menampilkan_informasi(): void
{
    $buku = $this->makeBuku(['judul' => 'Clean Architecture', 'pengarang' => 'Robert C. Martin']);

    $response = $this->get(route('buku.show', $buku));

    $response->assertStatus(200);
    $response->assertSee('Clean Architecture');    // judul tampil
    $response->assertSee('Robert C. Martin');      // pengarang tampil
}

public function test_detail_buku_menampilkan_404_jika_tidak_ada(): void
{
    $response = $this->get(route('buku.show', 9999)); // id yang tidak pernah ada

    $response->assertStatus(404);
}
```

**Test 3: form tambah di-redirect jika belum login.**

User anonim tidak boleh sampai ke form `buku.create` — ia harus dilempar ke halaman login.

```php
public function test_form_tambah_buku_dialihkan_ke_login_untuk_guest(): void
{
    $response = $this->get(route('buku.create'));

    $response->assertRedirect(route('login'));
}
```

**Test 4: admin bisa menambah buku.**

Alur lengkap: login sebagai admin (`actingAs`), kirim `POST` ke `buku.store`, lalu pastikan redirect sukses, pesan flash muncul, dan data benar-benar tersimpan di database.

```php
public function test_admin_dapat_menambah_buku(): void
{
    $admin = $this->admin();
    $kategori = Kategori::factory()->create(['nama' => 'Novel']);

    $response = $this->actingAs($admin)->post(route('buku.store'), [
        'judul'      => 'Sapiens',
        'pengarang'  => 'Yuval Noah Harari',
        'isbn'       => '9786020382063',
        'tahun'      => 2016,
        'harga'      => 125000,
        'stok'       => 10,
        'kategori_id' => $kategori->id,
    ]);

    $response->assertRedirect(route('buku.index'));
    $response->assertSessionHas('success');                     // flash message ada

    $this->assertDatabaseHas('bukus', [
        'judul'     => 'Sapiens',
        'isbn'      => '9786020382063',
        'stok'      => 10,
    ]);
}
```

**Test 5: anggota biasa dapat 403, dan data tidak tersimpan.**

Policy (materi 24) harus memblokir anggota untuk menambah buku.

```php
public function test_anggota_biasa_tidak_boleh_menambah_buku(): void
{
    $anggota = $this->anggota();
    $kategori = Kategori::factory()->create(['nama' => 'Novel']);

    $response = $this->actingAs($anggota)->post(route('buku.store'), [
        'judul'      => 'Buku Terlarang',
        'pengarang'  => 'Si Fulano',

        'harga'      => 50000,

}
```

**Test 6: validasi — judul wajib diisi.**

```php
public function test_validasi_judul_wajib_diisi(): void

        'harga'      => 10000,

    $this->assertDatabaseMissing('bukus', ['pengarang' => 'Tanpa Judul']);
}
```

**Test 7: soft delete bekerja.**

Jika model `Buku` memakai `SoftDeletes`, hapus lewat route `buku.destroy` lalu pastikan record masih ada di database tapi diberi `deleted_at`.

```php
public function test_buku_dapat_dihapus_secara_soft_delete(): void
{
    $admin = $this->admin();
    $buku = $this->makeBuku();

    $response = $this->actingAs($admin)->delete(route('buku.destroy', $buku));

    $response->assertRedirect(route('buku.index'));
    $this->assertSoftDeleted('bukus', ['id' => $buku->id]);
}
```

**Test API: kombinasi getJson, postJson, withToken, dan Queue::fake.**

Sesuai API `/api/v1/buku` dan `/api/v1/auth/login` dari materi 26-28. Kita fake queue agar email atau notifikasi tidak benar-benar terkirim saat test.

```php
public function test_api_login_mengembalikan_token(): void
{
    $user = User::factory()->create([
        'email'    => 'budi@perpustakaan.test',
        'password' => bcrypt('password123'),
    ]);

    $response = $this->postJson('/api/v1/auth/login', [
        'email'    => 'budi@perpustakaan.test',
        'password' => 'password123',
    ]);

    $response->assertStatus(200);
    $response->assertJsonStructure(['token']);   // pastikan struktur ada key token
    $response->assertJsonPath('token_type', 'Bearer'); // nilai spesifik pada path tertentu
}

public function test_api_daftar_buku_diproteksi_sanctum(): void
{
    $response = $this->getJson('/api/v1/buku'); // tanpa token

    $response->assertStatus(401); // Sanctum menolak
}

public function test_api_menambah_buku_dengan_token_dan_queue_fake(): void
{
    Queue::fake(); // job tidak benar-benar dijalankan
    $admin = $this->admin();
    $kategori = Kategori::factory()->create(['nama' => 'Novel']);

    $response = $this->withToken($admin->createToken('api')->plainTextToken)
        ->postJson('/api/v1/buku', [
            'judul'       => 'Atomic Habits',
            'pengarang'   => 'James Clear',
            'isbn'        => '9786020642990',
            'tahun'       => 2019,
            'harga'       => 108000,
            'stok'        => 7,
            'kategori_id' => $kategori->id,
        ]);

    $response->assertStatus(201);
    $response->assertJsonStructure([
        'data' => ['id', 'judul', 'harga', 'harga_format'],
    ]);
    $response->assertJsonPath('data.judul', 'Atomic Habits');

    Queue::assertPushed(TerbitkanNotifikasiBuku::class); // job ter-queue
}
```

## 4. Analogi Sederhana

Bayangkan sistem perpustakaan ini sebagai sebuah restoran, dan testing adalah **quality control menu sebelum dirilis**.

- **Feature test = QC end-to-end**: pelanggan pesan lewat pelayan, sampai hidangan keluar dari dapur. Kita tidak peduli detail per bahan; yang penting seluruh alur (login, form, database, response) menghasilkan hidangan yang benar. Saat test "admin bisa menambah buku" hijau, artinya dari memesan sampai meja penuh sudah berfungsi.
- **Unit test = QC resep per hidangan**: satu resep, bahan sekian + teknik sekian harus menghasilkan rasa sekian. Di sini kita uji satu method kecil seperti `Buku::tersedia()` — apakah stok 5 menghasilkan `true`.
- **Mocking/Faking = uji dengan bahan tiruan**: chef tidak bergantung pada supplier atau gudang asli. `Queue::fake()` dan `Mail::fake()` adalah bahan tiruan itu — email dan queue kita "bekukan" supaya test tidak bergantung pada server mail atau worker asli, dan tetap bisa kita periksa "apakah resep meminta bahan ini?" lewat `assertPushed`/`assertSent`.

Inti analoginya: jangan pernah mengandalkan feeling chef ("sepertinya enak"), tapi buktikan dengan uji rasa yang bisa diulang kapan saja.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

Gunakan feature test ketika kamu ingin memverifikasi **perilaku aplikasi dari sudut pandang pengguna/HTTP**:

- **Skenario lengkap CRUD**: pastikan halaman tampil, form tersimpan, redirect benar, dan data ada di database. Sangat cocok untuk route `buku.index`, `buku.show`, `buku.create`, `buku.store`, `buku.destroy`.
- **Kontrol akses**: test bahwa guest di-redirect ke login, admin bisa akses, anggota biasa dapat 403 (tergantung policy). Ini critical flow — jangan pernah dilewatkan.
- **Autentikasi & otorisasi**: login API (`/api/v1/auth/login`), token Sanctum, proteksi endpoint `/api/v1/buku`.
- **Validasi form**: pastikan error muncul (`assertSessionHasErrors`) dan data tidak tersimpan.
- **Soft delete / relasi**: pastikan `assertSoftDeleted`, atau relasi kategori-buku tetap konsisten.
- **Integrasi queue/event/mail**: dengan `Queue::fake()` dsb, pastikan job/event/email "dikirim" tanpa benar-benar terkirim.
- **CI/CD (materi 37)**: feature test dijalankan otomatis di pipeline setiap push, supaya kode rusak langsung terdeteksi sebelum deploy.

Gunakan unit test (materi 32) ketika kamu ingin menguji **logika murni** satu method tanpa melibatkan HTTP, seperti `Buku::tersedia()` atau `harga_format`. Aturannya: feature test untuk "alur", unit test untuk "kalkulasi".

**TDD**: tulis test dulu (merah), implementasikan (hijau), lalu refactor. Untuk critical flow seperti peminjaman, mulailah dengan feature test yang menggambarkan hasil akhir yang diharapkan, baru tulis kodenya.

## 6. Poin-poin Penting & Best Practices

- **Selalu pakai `RefreshDatabase`** di feature test (atau `DatabaseTransactions` jika butuh kecepatan dan tidak mau migrate ulang) agar setiap test mulai dari database bersih.
- **Naming method yang deskriptif**: gunakan `test_nama_apa_yang_dilakukan` atau `testSesuatuDalamBahasaInggrisDeskriptif`. Nama yang bagus menjadi dokumentasi; nama seperti `test_buku` tidak menjelaskan apa pun.
- **Assertion penting yang sering dipakai**:
  - `assertStatus(200 | 404 | 403 | 401 | 201 | 302)`
  - `assertSee('teks')`, `assertViewIs('buku.index')`, `assertViewHas('bukus')`
  - `assertDatabaseHas('bukus', [...])`, `assertDatabaseMissing(...)`, `assertSoftDeleted(...)`
  - `assertSessionHas('success')`, `assertSessionHasErrors('judul')`
  - `assertRedirect(route('...'))`, `assertRedirectToRoute('buku.index')`
  - API: `assertJsonStructure([...])`, `assertJsonPath('data.judul', '...')`
- **`actingAs($user)`** untuk mensimulasikan login user tertentu (misal role admin vs anggota).
- **Gunakan factory state**: di `BukuFactory`, buat state seperti `->state(['stok' => 0])` atau method `tersedia()/habis()` supaya test terbaca ("buku stok habis" lebih jelas daripada "stok 0").
- **Gunakan fakes bawaan Laravel** daripada Mockery untuk sebagian besar kasus: `Queue::fake()`, `Mail::fake()`, `Event::fake()`, `Storage::fake()`, `Http::fake()`. Fakes memungkinkan assertion seperti `Mail::assertSent(...)`, `Event::assertDispatched(...)`, `Storage::assertExists(...)`.
- **Isolasi test**: jangan biarkan test bergantung pada urutan eksekusi atau data nyata di database dev. Setiap test harus berdiri sendiri.
- **Jangan mock model Eloquent tanpa alasan kuat** — gunakan factory + database asli (in-memory) supaya query dan relasi ikut teruji.
- **Pisahkan environment test**: database test di `.env.testing` / `phpunit.xml`, jangan pernah menunjuk ke database produksi.
- **Buat data via factory** dengan nilai eksplisit yang relevan, bukan mengandalkan data default yang tidak jelas.

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

- **Lupa `RefreshDatabase`**: data dari test pertama bocor ke test kedua, sehingga test hijau di lokal tapi gagal di CI (atau sebaliknya). Solusi: selalu `use RefreshDatabase;` di feature test.
- **Test bergantung urutan**: test A membuat data, test B mengandalkan data itu. Jika dijalankan sendiri (`--filter=BukuTest` tanpa A), B gagal. Solusi: tiap test membuat data sendiri.
- **`assertSee` gagal karena HTML escaped**: misal harga "Rp 125.000" tampil sebagai "Rp 125.000" di HTML (spasi jadi `&nbsp;`), maka `assertSee('Rp 125.000')` bisa gagal. Gunakan `assertSee(...)`, periksa escaped output, atau cek bagian yang tidak ter-escape.
- **Test menjalankan koneksi ke database produksi**: environment test tidak dikonfigurasi sehingga query berjalan ke DB asli. Solusi: set `DB_CONNECTION` yang benar di `phpunit.xml` (misal `sqlite` in-memory atau DB test terpisah) dan jangan pernah commit `.env` berisi kredensial produksi ke test.
- **Mock/Fake terlalu banyak**: menge-fake semuanya membuat test "berbohong" — menguji kode yang disalin ke fake, bukan perilaku asli. Fokus ke dependency eksternal (mail, queue, http, storage); biarkan database dan Eloquent berjalan sungguhan.
- **Lupa `Queue::fake()`**: job asli benar-benar terkirim saat test berjalan, bisa mengirim email sungguhan atau memproses job produksi. Selalu fake queue/event/mail di test yang memicunya.
- **Menguji implementasi, bukan behavior**: mengecek query SQL tertentu atau nama variabel internal membuat test brittle — test akan pecah saat refactor tanpa perubahan perilaku. Uji hasil akhir (response, isi database, redirect), bukan cara internal.
- **Troubleshooting cepat**: jika test gagal padahal aplikasi jalan, cek urutan — jalankan `php artisan test --filter=TestYangGagal` sendiri. Jika hijau sendiri tapi merah saat digabung, itu indikasi kebocoran data atau ketergantungan urutan.

## 8. Soal Latihan & Kunci Jawaban

### Tantangan

1. Buat sebuah feature test di `tests/Feature/BukuTest.php` bernama `test_anggota_dapat_melihat_halaman_detail_buku`: anggota login, request ke `route('buku.show', $buku)`, dan pastikan response 200 serta menampilkan judul buku. Gunakan factory dan `RefreshDatabase`.
2. Buat test API bernama `test_api_mencoba_login_dengan_password_salah` di `tests/Feature/Api/BukuApiTest.php`: `POST /api/v1/auth/login` dengan password salah, pastikan status 422 (atau 401 sesuai implementasi) dan struktur error JSON berisi key `message`.

### Jawaban & Pembahasan

**Jawaban tantangan 1:**

```php
public function test_anggota_dapat_melihat_halaman_detail_buku(): void
{
    $anggota = User::factory()->create(['role' => 'anggota']);
    $buku = Buku::factory()->create(['judul' => 'The Pragmatic Programmer']);

    $response = $this->actingAs($anggota)
        ->get(route('buku.show', $buku));

    $response->assertStatus(200);
    $response->assertSee('The Pragmatic Programmer');
}
```

Alur: `actingAs` mensimulasikan login anggota; `Buku::factory()` membuat data di database test; request GET ke `buku.show` dijalankan melalui seluruh middleware; assertion memastikan policy/view mengizinkan anggota melihat detail dan judul tampil. Karena `RefreshDatabase`, data factory hanya ada selama test ini — tidak mengganggu test lain.

**Jawaban tantangan 2:**

```php
public function test_api_mencoba_login_dengan_password_salah(): void
{
    User::factory()->create([
        'email'    => 'siti@perpustakaan.test',
        'password' => bcrypt('password123'),
    ]);

    $response = $this->postJson('/api/v1/auth/login', [
        'email'    => 'siti@perpustakaan.test',
        'password' => 'password-salah',
    ]);

    $response->assertStatus(422); // validasi gagal di controller
    $response->assertJsonStructure(['message']);
}
```

Alur: data user dibuat dengan password yang benar; request login mengirim password salah; controller mengembalikan error (validasi/credential); assertion memastikan status error dan struktur JSON berisi `message`. Test ini menjamin alur login tidak pernah memberikan token untuk kredensial salah — critical flow untuk keamanan.
