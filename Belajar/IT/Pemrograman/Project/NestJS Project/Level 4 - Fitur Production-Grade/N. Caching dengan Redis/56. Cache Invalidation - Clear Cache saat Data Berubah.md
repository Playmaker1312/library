# 56. Cache Invalidation — Clear Cache saat Data Berubah

## Penjelasan

Masalah terbesar dari caching bukanlah menyimpan data, melainkan **menjaga data tetap akurat**. Ketika data di database berubah (buku baru ditambahkan, stok diupdate, judul diedit), cache harus segera dihapus atau diperbarui. Jika tidak, pengguna akan melihat data basi (stale data). Proses menghapus cache saat data berubah ini disebut **cache invalidation**.

Ada beberapa strategi invalidation: (1) **Write-through**: update database dan cache dalam satu operasi, (2) **Write-behind**: update database dulu, cache dihapus secara async, (3) **Cache-aside dengan eviction**: hapus cache yang relevan setiap kali ada operasi write. Strategi yang paling umum dan mudah diimplementasikan adalah **eviction** — cukup hapus key cache yang terkait saat data di-create, di-update, atau di-delete. Request berikutnya akan cache miss dan mengisi ulang dari database.

## Fungsi

Cache invalidation berfungsi untuk menjaga konsistensi data antara cache dan database. Dengan menghapus cache yang relevan setiap kali terjadi perubahan data, kita memastikan pengguna selalu mendapatkan informasi terbaru tanpa harus menunggu TTL habis.

## Cara Implementasi / Code

### 1. Helper Method untuk Clear Cache

```typescript
// src/books/services/books.service.ts (tambahan)
private async clearBooksCache(bookId?: string) {
  // Hapus cache detail buku tertentu
  if (bookId) {
    await this.cacheManager.del(`books:${bookId}`);
  }

  // Hapus semua cache yang berkaitan dengan daftar buku
  // Karena key menggunakan JSON.stringify(query), kita tidak bisa hapus satu per satu.
  // Solusi: gunakan pattern atau hapus dengan key prefix.
  // Di production, gunakan Redis SCAN atau simpan daftar key.
  await this.cacheManager.del('books:popular');
}

// Alternatif: clear semua cache dengan prefix 'books:'
private async clearAllBooksCache() {
  const keys = await this.cacheManager.store.keys('books:*');
  const promises = keys.map((key: string) => this.cacheManager.del(key));
  await Promise.all(promises);
}
```

### 2. Panggil di Setiap Method Mutation

```typescript
async create(createBookDto: CreateBookDto) {
  const book = await this.prisma.book.create({
    data: createBookDto,
    include: { category: true },
  });

  await this.clearAllBooksCache(); // Hapus semua cache buku

  return book;
}

async update(id: string, updateBookDto: UpdateBookDto) {
  const book = await this.prisma.book.update({
    where: { id },
    data: updateBookDto,
    include: { category: true },
  });

  await this.clearBooksCache(id); // Hapus cache buku ini + daftar

  return book;
}

async delete(id: string) {
  await this.prisma.book.delete({ where: { id } });

  await this.clearAllBooksCache();
}

async updateStock(id: string, stock: number) {
  const book = await this.prisma.book.update({
    where: { id },
    data: { stock },
  });

  await this.clearBooksCache(id);

  return book;
}
```

### 3. Cache Invalidation untuk Relasi Category

```typescript
// src/categories/categories.service.ts
@Injectable()
export class CategoriesService {
  constructor(
    private readonly prisma: PrismaService,
    @Inject(CACHE_MANAGER) private cacheManager: Cache,
  ) {}

  private async clearCategoryCache(categoryId?: string) {
    await this.cacheManager.del('categories:all');
    if (categoryId) {
      await this.cacheManager.del(`categories:${categoryId}`);
    }
  }

  async create(dto: CreateCategoryDto) {
    const category = await this.prisma.category.create({ data: dto });
    await this.clearCategoryCache();
    return category;
  }

  async update(id: string, dto: UpdateCategoryDto) {
    const category = await this.prisma.category.update({
      where: { id },
      data: dto,
    });
    await this.clearCategoryCache(id);
    return category;
  }
}
```

## Analogi

Kembali ke analogi notes tempelan petugas perpustakaan. Ketika sebuah buku baru masuk, atau ada buku yang dipindahkan raknya, petugas harus **membersihkan notes lamanya** dan menulis ulang jika ada yang bertanya. Jika ada anggota yang mengembalikan buku, stok di rak berubah — notes tentang stok harus dihapus. Tidak peduli seberapa sering notes dihapus, yang penting informasinya selalu akurat saat anggota bertanya. Lebih baik lambat sedikit (cache miss → ambil dari DB) daripada memberikan informasi yang salah.

## Penggunaan

Cache invalidation diterapkan di semua operasi **CREATE, UPDATE, DELETE** dan operasi lain yang mengubah data (seperti update stok, return buku,变更 status). Ini memastikan bahwa:
- Saat admin menambah buku baru, daftar buku langsung muncul
- Saat stok berubah, informasi ketersediaan akurat
- Saat kategori direname, buku-buku di dalamnya tetap terfilter dengan benar
- Saat buku dihapus, tidak muncul lagi di pencarian

## Kesalahan Umum yang Sering Terjadi

1. **Cache invalidation tidak dipanggil di semua mutation** — misalnya lupa clear cache di method `updateStock()` sehingga stok di cache tetap lama.
2. **Clear cache terlalu agresif** — menghapus semua cache (termasuk cache user lain) saat satu data berubah. Gunakan selective key deletion.
3. **Race condition** — dua request bersamaan: request A membaca cache (miss), request B mengupdate data. Request A kemudian menyimpan data lama ke cache. Solusi: gunakan distributed lock atau kurangi TTL.
4. **Lupa handle error saat cache clear gagal** — `cacheManager.del()` bisa throw error. Jangan sampai operasi utama gagal hanya karena cache clear error.
5. **Tidak mendelete cache dengan pattern** — di production dengan ribuan key, hapus satu-satu tidak efisien. Gunakan Redis `SCAN` atau simpan mapping key.

## Hubungan dengan Materi Sebelumnya

Di materi **#55 (Cache-Aside Pattern)**, kita hanya menyimpan data ke cache. Sekarang kita melengkapi siklus hidup cache dengan **penghapusan** saat data berubah. Kedua materi ini adalah dua sisi mata uang yang sama — caching tanpa invalidation akan menghasilkan data basi, dan invalidation tanpa caching adalah buang-buang resource. Bersama-sama mereka membentuk **strategi caching yang lengkap**.

## Soal Latihan

**Soal:**
Buat interceptor `CacheInvalidationInterceptor` yang secara otomatis menghapus cache berdasarkan dekorator `@InvalidatesCache(keys)` setelah method selesai. Terapkan di controller Book.

**Jawaban:**

```typescript
// src/common/interceptors/cache-invalidation.interceptor.ts
import { Injectable, NestInterceptor, ExecutionContext, CallHandler } from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { Observable, tap } from 'rxjs';
import { CACHE_MANAGER } from '@nestjs/cache-manager';
import { Cache } from 'cache-manager';

export const INVALIDATES_CACHE_KEY = 'invalidates_cache';

export const InvalidatesCache = (...keys: string[]) =>
  SetMetadata(INVALIDATES_CACHE_KEY, keys);

@Injectable()
export class CacheInvalidationInterceptor implements NestInterceptor {
  constructor(
    private reflector: Reflector,
    @Inject(CACHE_MANAGER) private cacheManager: Cache,
  ) {}

  async intercept(context: ExecutionContext, next: CallHandler): Promise<Observable<any>> {
    return next.handle().pipe(
      tap(async () => {
        const keys = this.reflector.get<string[]>(
          INVALIDATES_CACHE_KEY,
          context.getHandler(),
        );
        if (keys) {
          await Promise.all(keys.map((key) => this.cacheManager.del(key)));
        }
      }),
    );
  }
}

// Penggunaan di controller:
@Post()
@InvalidatesCache('books:all', 'books:popular')
@UseInterceptors(CacheInvalidationInterceptor)
async create(@Body() dto: CreateBookDto) {
  return this.booksService.create(dto);
}
```
