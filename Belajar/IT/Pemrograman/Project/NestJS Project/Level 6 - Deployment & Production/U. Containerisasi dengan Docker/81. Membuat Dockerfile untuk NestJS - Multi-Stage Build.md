# 81. Membuat Dockerfile untuk NestJS - Multi-Stage Build

## Penjelasan
Dockerfile adalah blueprint untuk membangun Docker image aplikasi NestJS kamu. Multi-stage build adalah teknik di mana kita menggunakan dua tahap (stage) dalam satu Dockerfile: **builder stage** untuk kompilasi aplikasi dan **runner stage** untuk menjalankan hasil kompilasi. Pendekatan ini sangat penting karena image akhir menjadi sangat kecil — hanya berisi file yang benar-benar diperlukan untuk runtime, bukan tools kompilasi seperti TypeScript compiler atau node_modules yang tidak dipakai.

Pada stage pertama (builder), kita menyalin seluruh source code, menginstall semua dependencies (termasuk devDependencies), lalu menjalankan `npm run build` yang menghasilkan folder `dist/`. Pada stage kedua (runner), kita mulai dari image baru (biasanya `node:20-alpine` yang sangat ringan), menyalin folder `dist/` dan `node_modules/` (hanya production) dari builder stage, lalu menjalankan aplikasi dengan user non-root untuk keamanan. Alpine Linux dipilih karena ukurannya kecil (sekitar 5MB) dan aman.

## Fungsi
- Membangun Docker image NestJS yang ringan, aman, dan efisien
- Memisahkan environment build dengan runtime sehingga image final tidak mengandung kode sumber atau tools yang tidak diperlukan
- Menggunakan non-root user untuk menjalankan aplikasi (best practice keamanan)

## Cara Implementasi / Code

**Dockerfile (2 stage):**

```dockerfile
# ===== STAGE 1: Builder =====
FROM node:20-alpine AS builder

WORKDIR /app

# Copy package files first untuk cache layer
COPY package*.json ./
COPY prisma ./prisma/

# Install semua dependencies (termasuk devDependencies untuk build)
RUN npm ci

# Copy seluruh source code
COPY . .

# Generate Prisma client dan build NestJS
RUN npx prisma generate
RUN npm run build

# ===== STAGE 2: Runner =====
FROM node:20-alpine AS runner

WORKDIR /app

# Buat user non-root untuk keamanan
RUN addgroup --system --gid 1001 nestjs && \
    adduser --system --uid 1001 nestjs

# Copy node_modules production saja dan hasil build dari builder stage
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/package.json ./
COPY --from=builder /app/prisma ./prisma

# Set environment
ENV NODE_ENV=production

# Gunakan user non-root
USER nestjs

# Expose port aplikasi
EXPOSE 3000

# Health check
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/api/health || exit 1

# Jalankan aplikasi
CMD ["node", "dist/main"]
```

**.dockerignore:**

```
node_modules
dist
.git
.gitignore
.env
.env.local
.env*.local
*.md
coverage
test
docker-compose*.yml
.vscode
.idea
```

**.dockerignore** sangat penting karena mencegah file-file yang tidak perlu (seperti `node_modules` lokal, `.env`, file dokumentasi) ikut masuk ke dalam konteks build Docker. Ini mempercepat proses build dan mencegah kebocoran rahasia.

## Analogi
Bayangkan perpustakaan ingin membuat **buku saku ringkas** dari sebuah **manuskrip tebal**. Stage Builder adalah proses penyuntingan di ruang kerja penuh dengan kamus, alat tulis, dan kertas coretan — semua alat produksi ada di sini. Setelah buku siap (dist/), manuskrip asli dan alat-alat produksi disimpan. Stage Runner adalah **buku saku final** yang hanya berisi teks bersih (dist + production modules) tanpa peralatan produksi. Pengunjung perpustakaan (user) hanya perlu membaca buku saku, bukan melihat alat produksinya.

## Penggunaan
Dipakai untuk membangun Docker image yang akan dideploy ke production environment — baik ke VPS, cloud platform (AWS ECS, Google Cloud Run), maupun Kubernetes cluster. Setiap kali ada perubahan kode, pipeline CI/CD akan menjalankan `docker build` menggunakan Dockerfile ini.

## Kesalahan Umum yang Sering Terjadi
1. **Tidak menggunakan .dockerignore** — mengakibatkan file `.env` atau `node_modules` lokal ikut terbawa, menyebabkan image besar dan potensi bocornya secrets.
2. **Meletakkan `COPY . .` sebelum `npm ci`** — setiap perubahan kode akan memecah cache Docker layer, membuat proses build selalu install ulang dependencies dari awal. Urutan yang benar: copy `package.json` dulu, install, baru copy kode.
3. **Lupa menyalin folder `prisma/`** — Prisma client gagal di-generate atau migration tidak bisa jalan karena schema tidak ada di runner stage.
4. **Menjalankan sebagai root user** — security risk; attacker yang berhasil masuk ke container punya akses root ke sistem.
5. **Menggunakan `CMD ["npm", "run", "start:prod"]`** — npm sebagai entry process (PID 1) tidak menangani sinyal SIGTERM dengan benar. Lebih baik langsung `node`.

## Hubungan dengan Materi Sebelumnya
Di Level 1–5, kita menjalankan aplikasi NestJS langsung dengan `npm run start:dev` di local machine. Sekarang kita bungkus aplikasi ke dalam container Docker agar bisa dijalankan di environment manapun secara konsisten — tanpa perlu install Node.js, PostgreSQL, atau Redis secara manual di server.

## Soal Latihan

**Soal:** Kamu memiliki proyek NestJS dengan folder `prisma/` yang berisi schema. Lengkapi Dockerfile berikut agar (1) menggunakan multi-stage build dengan Alpine, (2) meng-generate Prisma client di builder stage, (3) menjalankan sebagai non-root user, dan (4) menambahkan health check:

```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
# (lanjutkan...)
```

**Jawaban:**

```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
COPY prisma ./prisma/
RUN npm ci
COPY . .
RUN npx prisma generate
RUN npm run build

FROM node:20-alpine AS runner
WORKDIR /app
RUN addgroup --system --gid 1001 nestjs && \
    adduser --system --uid 1001 nestjs
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/package.json ./
COPY --from=builder /app/prisma ./prisma
ENV NODE_ENV=production
USER nestjs
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/api/health || exit 1
CMD ["node", "dist/main"]
```
