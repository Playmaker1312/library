# 16. Session — Sistem Login yang Aman

> **Level 3 · Form, Session, dan File** — HTTP itu *tanpa status*; session membuat aplikasi "mengingat" siapa kamu.

---

## 1. Penjelasan Singkat & Konsep Dasar

**HTTP tidak menyimpan status.** Setiap request adalah "orang asing" bagi server — server lupa siapa kamu begitu respons terkirim. Jika tidak ada mekanisme penyimpanan, login tidak ada artinya: halaman berikutnya tidak akan tahu kamu sudah login.

**Session** memecahkan ini:
1. Saat `session_start()`, PHP memberikan **session ID** unik (dikirim via **cookie**) dan membuat **penyimpanan di server** (file `/tmp` atau DB) yang dikunci oleh session ID itu.
2. Setiap request berikutnya, browser mengirim cookie session ID → PHP memuat data yang tersimpan → aplikasi "mengenal" kamu.

```php
session_start();                    // mulai/resume session
$_SESSION['user'] = ['id' => 1];   // simpan data di server
$id = $_SESSION['user']['id'];     // baca di request berikutnya
```

**Alur login aman:**

```
POST /login.php
   ├─ 1. Validasi CSRF + rate limit (materi 23)
   ├─ 2. Cek kredensial (prepared statement + password_verify)
   ├─ 3. login(): $ session_regenerate_id(true)  ← KUNCI anti session fixation
   │           $ $_SESSION['user'] = [...]       ← hanya data non-sensitif
   │           $ $_SESSION['login_time'] = time()
   ├─ 4. Redirect ke dashboard (PRG, materi 15)
```

**Benang Merah:** form (13-15) memberi cara input; session adalah cara aplikasi *mengidentifikasi & mengingat* user antar request. Di Level 5 (23-24), session diperkuat dengan rate limiting, metadata, dan keamanan tambahan.

---

## 2. Fungsi & Kegunaan Utama

- **Keadaan login antar request** — inti utama: siapa yang sedang login.
- **Flash messages** (materi 15) — data sementara lintas request (sukses/gagal).
- **Otorisasi** — `$_SESSION['user']['role']` dipakai `requireLogin` / `requireRole`.
- **Token CSRF** — disimpan di session (materi 14) — bukti bahwa "request ini berasal dari form saya".
- **Menyelesaikan masalah "HTTP stateless"** tanpa menyimpan data sensitif di cookie. Cookie hanya berisi session ID; data asli ada di server.

## 3. Contoh Kode & Implementasi Real-World

`config/session.php` — konfigurasi session yang lebih aman (panggil sebelum `session_start`):

```php
<?php
// File: config/session.php
function setupSession(): void {
    // Keamanan session
    ini_set('session.use_strict_mode', '1');      // tolak session ID yang tidak dikenal
    ini_set('session.cookie_httponly', '1');       // cookie tidak bisa dibaca JavaScript (anti-XSS steal)
    ini_set('session.cookie_samesite', 'Strict');  // cegah CSRF lewat cookie
    ini_set('session.gc_maxlifetime', '3600');     // session kedaluwarsa 1 jam

    // Aktifkan di production/HTTPS saja:
    // ini_set('session.cookie_secure', '1');

    if (session_status() === PHP_SESSION_NONE) {
        session_start();
    }
}
```

`functions/auth.php` — fungsi autentikasi inti:

```php
<?php
// File: functions/auth.php
declare(strict_types=1);

function login(array $user): void {
    // REGENERASI session ID — anti session fixation
    // (session fixation = penyerang memaksa user memakai session ID milik penyerang)
    session_regenerate_id(true);

    $_SESSION['user'] = [
        'id'    => $user['id'],
        'nama'  => $user['nama'],
        'email' => $user['email'],
        'role'  => $user['role'],
    ];
    $_SESSION['login_time']  = time();
    $_SESSION['last_active'] = time();
}

function logout(): void {
    // Hapus semua data session
    $_SESSION = [];

    // Hapus cookie session
    if (ini_get('session.use_cookies')) {
        $p = session_get_cookie_params();
        setcookie(session_name(), '', time() - 42000,
                  $p['path'], $p['domain'], $p['secure'], $p['httponly']);
    }
    session_destroy();
}

function sudahLogin(): bool {
    return isset($_SESSION['user']) && !empty($_SESSION['user']['id']);
}

function userSaatIni(): ?array {
    return $_SESSION['user'] ?? null;
}

function requireLogin(string $redirectTo = '/perpustakaan/login.php'): void {
    if (!sudahLogin()) {
        $_SESSION['redirect_after_login'] = $_SERVER['REQUEST_URI'];
        header('Location: ' . $redirectTo);
        exit;
    }
}

function requireRole(string $role): void {
    requireLogin();
    if (($_SESSION['user']['role'] ?? '') !== $role) {
        http_response_code(403);
        exit('Akses ditolak.');
    }
}
```

`login.php` — implementasi login dengan password hashing (materi lanjut: rate limit di 23):

```php
<?php
// File: login.php
session_start();
require_once 'config/session.php';
setupSession();
require_once 'functions/csrf.php';
require_once 'functions/auth.php';

$errors = [];

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    if (!verifyCsrfToken($_POST['csrf_token'] ?? '')) { http_response_code(403); die('Forbidden'); }

    $email    = strtolower(trim($_POST['email'] ?? ''));
    $password = $_POST['password'] ?? '';

    if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
        $errors['email'] = 'Email tidak valid.';
    }
    if ($password === '') {
        $errors['password'] = 'Password wajib diisi.';
    }

    if (empty($errors)) {
        // Level 3: user dari array; Level 4+: dari DB dengan prepared statement
        $admin = [
            'id' => 1, 'nama' => 'Admin Perpustakaan',
            'email' => 'admin@perpustakaan.id',
            // JANGAN simpan plain text — gunakan password_hash saat seed
            'password_hash' => password_hash('admin123', PASSWORD_BCRYPT),
            'role' => 'admin',
        ];

        if ($email === $admin['email'] && password_verify($password, $admin['password_hash'])) {
            login($admin);
            $redirect = $_SESSION['redirect_after_login'] ?? '/perpustakaan/dashboard.php';
            unset($_SESSION['redirect_after_login']);
            header('Location: ' . $redirect);
            exit;
        }
        // Pesan ambigu — jangan beri tahu mana yang salah
        $errors['general'] = 'Email atau password salah.';
    }
}
?>
<form method="POST">
    <input type="hidden" name="csrf_token" value="<?= esc(generateCsrfToken()) ?>">
    <input type="email" name="email" required>
    <input type="password" name="password" required>
    <button type="submit">Login</button>
</form>
```

## 4. Analogi Sederhana

Dalam **Sistem Administrasi Kantor**:

- **HTTP tanpa status** = setiap kali kamu datang ke kantor, resepsionis sama sekali tidak ingat kamu pernah datang. Tidak ada yang disimpan.
- **Session** = **kartu identitas/akses (ID badge)**. Saat pertama kali masuk, kamu diberi badge dengan nomor unik. Setiap kali kamu kembali, kamu serahkan badge → petugas membuka **lemari berkas pribadi** bergambar nomor badge-mu → "oh, si Budi, data kamu di sini".
- **Cookie session ID** = badge yang kamu pakai. **Data di `$_SESSION`** = isi lemari berkas di kantor (di server, bukan di badge). Badge hanya berisi nomor.
- **`session_regenerate_id()`** = setelah login resmi, petugas **memberi badge bernomor baru dan membuang yang lama** — sehingga nomor lama (yang mungkin sudah dicuri/disebar penyerang) tidak berguna lagi (anti session fixation).
- **`logout()`** = badge dicabut, lemari berkas dikosongkan, stempel tinta dihapus — semua jejak hilang.

---

## 5. Kapan Harus Digunakan & Kasus Penggunaan

- **Keharusan** untuk halaman yang butuh login: dashboard, CRUD, pengaturan → `requireLogin()` di atas halaman.
- **Otorisasi berbasis role**: `requireRole('admin')` — memblokir akses ke fungsi sensitif.
- **Flash messages** pada semua alur form.
- **CSRF token storage** (materi 14).
- **Penting — bedakan**: session untuk data *di server per user*; cookie hanya untuk session ID (dan preferensi ringan yang boleh dibaca server). Jangan simpan data sensitif (password, data kartu) di cookie.
- **Kasus nyata:** `dashboard.php` dipanggil `requireLogin()`; role admin/pustakawan di-otorisasi per aksi (edit/hapus buku).

---

## 6. Aspek Keamanan & Best Practices (Critical)

- **`session_regenerate_id(true)` setelah login** — Wajib. Mencegah *session fixation*: penyerang yang membagikan session ID-nya kepada korban akan kehilangan ID itu setelah login regenerasi.
- **Cookie flag**: `httponly` (JS tidak bisa baca → anti pencurian via XSS), `samesite` (`Strict` → browser tidak kirim cookie pada request lintas situs → memperkuat anti-CSRF), `secure` (hanya HTTPS) di production.
- **Jangan simpan password / hash di session** — `$_SESSION['user']` hanya id, nama, email, role. Security-sensitive data dibaca dari DB saat perlu.
- **Perbarui `last_active` & atur masa kadaluarsa** — session timeout untuk mengurangi risiko session yang ditinggalkan.
- **`logout()` yang benar** — hapus `$_SESSION`, hapus cookie, `session_destroy()`. Jangan hanya `unset($_SESSION['user'])` (cookie masih ada).
- **`session.use_strict_mode`** — menolak session ID yang tidak dikenal (mengurangi session hijacking).

---

## 7. Kesalahan Umum & Debugging

- **`session_start()` dipanggil dua kali** → *Warning: session already started*. Solusi: fungsi `setupSession()` yang cek `session_status()`, atau `if (session_status() === PHP_SESSION_NONE)`.
- **`headers already sent` saat `session_start()`/`header()`** — ada output (spasi, BOM) sebelum `session_start()`. Solusi: sesi di baris paling atas, hapus `?>` di akhir, cek encoding UTF-8 tanpa BOM.
- **Session "tidak tersimpan" antar halaman** — domain/path cookie tidak konsisten (`localhost` vs `127.0.0.1` = dua cookie berbeda!). URL harus konsisten.
- **Session hilang mendadak** — `gc_maxlifetime` habis, atau server meregenerate memori. Untuk produksi, gunakan session handler terpusat atau perbesar sementara saat debug.
- **Cookie tidak terkirim** — `SameSite=Strict` + redirect lintas-domain bisa memblokir cookie; pada tahap ini aman karena aplikasi satu domain.
- **`session_destroy()` tidak menghapus cookie** — jika cookie masih hidup, session ID lama bisa dipakai lagi. Pastikan `logout()` memakai cara di atas.
- **Debug**: `var_dump($_SESSION)` setelah `session_start()` adalah cara tercepat melihat isi sesi sebenarnya (dan pastikan `session_start()` memang dijalankan).

## 8. Soal Latihan & Kunci Jawaban

### Tantangan 1
Buat `dashboard.php` yang di lindungi `requireLogin()`, menampilkan nama user dari session (dengan `esc()`), tombol logout, dan role-aware section: hanya admin yang melihat link "Kelola Anggota". Lengkapi `logout.php`.

### Tantangan 2
Jelaskan langkah demi langkah apa yang terjadi pada `$_SESSION` dan cookie ketika: (a) user pertama kali buka `login.php`; (b) POST login berhasil (dipanggil `login($user)`); (c) browser dikirim cookie session setelah logout.

### Jawaban & Pembahasan

**Tantangan 1**

```php
<?php
// dashboard.php
require_once 'config/session.php';
setupSession();
require_once 'functions/auth.php';
requireLogin();

$user = userSaatIni();
?>
<!DOCTYPE html>
<html lang="id">
<body>
    <h1>Dashboard</h1>
    <p>Selamat datang, <?= esc(htmlspecialchars($user['nama'])) ?></p>

    <?php if (($user['role'] ?? '') === 'admin'): ?>
        <a href="kelola/anggota.php">Kelola Anggota</a>
    <?php endif; ?>

    <form method="POST" action="logout.php">
        <input type="hidden" name="csrf_token" value="<?= esc(generateCsrfToken()) ?>">
        <button type="submit">Logout</button>
    </form>
</body>
</html>
```

```php
<?php
// logout.php — harus POST + CSRF (jangan pernah logout via GET)
require_once 'config/session.php';
setupSession();
require_once 'functions/csrf.php';

if ($_SERVER['REQUEST_METHOD'] !== 'POST' || !verifyCsrfToken($_POST['csrf_token'] ?? '')) {
    http_response_code(403);
    die('Forbidden');
}
logout();
header('Location: login.php');
exit;
```

> **Pembahasan alur:** `requireLogin()` di baris atas memastikan tidak ada bagian HTML yang render jika belum login — jika belum login, redirect ke login (dengan `redirect_after_login`). Nama user diambil dari `$_SESSION['user']` dan di-escape. Link admin disaring lewat role di session (defense-in-depth: role juga diperiksa di handler aksi). `logout.php` diminta POST + CSRF — menghindari logout paksa via URL lain / CSRF logout.

**Tantangan 2**

- (a) Request GET pertama `login.php`: `setupSession()` → `session_start()` membuat session baru (ID acak) → cookie `PHPSESSID` dikirim ke browser untuk pertama kali. `$_SESSION` masih kosong; token CSRF di-generate dan disimpan.
- (b) POST login valid: `login($user)` memanggil `session_regenerate_id(true)` → session ID **baru** di-generate, cookie di-update, data lama dibuang — lalu `$_SESSION['user']` (id, nama, email, role), `login_time`, `last_active` diisi. Inilah kenapa session fixation gagal: ID penyerang sudah tidak valid.
- (c) `logout()`: `$_SESSION = []` (hapus konteks), cookie `PHPSESSID` dihapus (expired in the past) via `setcookie(..., time()-42000, ...)`, lalu `session_destroy()` menghapus penyimpanan sesi di server. Setelah ini, request berikutnya = session benar-benar baru.

> **Pembahasan:** Inti dari seluruh perbedaan ini adalah *session ID* (cookie) vs *data* (server). Regenerasi setelah login dan pembersihan penuh saat logout adalah dua momen paling penting untuk keamanan session.
