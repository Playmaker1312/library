# 28. Unit Testing dan Feature Testing

> **Level 7 · Testing, Optimasi, dan Deployment** — Jangan sampai "mengubah satu hal, merusak yang lain" tanpa sadar. Test membuat refactor aman.

---

## 1. Penjelasan Singkat & Konsep Dasar

**Testing otomatis** = menulis kode yang *memverifikasi* perilaku kode lain — dijalankan otomatis setiap kali kamu mau, tanpa klik manual. Dua level yang paling penting:

- **Unit test** — menguji *satu unit* (biasanya method/class) secara terisolasi. Cepat, deterministik, tanpa database/HTTP. Contoh: `Buku::tersedia()`, `Validator::required()`, `formatHarga()`.
- **Feature/integration test** — menguji *satu alur* lintas komponen (routing → controller → repository → DB). Lebih berat, membutuhkan state (biasanya DB test terpisah). Contoh: "POST /buku dengan data valid menyimpan buku".

**PHPUnit** — framework testing paling umum. Struktur:

```php
class BukuTest extends TestCase {
    #[Test]
    public function buku_tersedia_ketika_stok_lebih_dari_nol(): void {
        $buku = new Buku('Judul', 'Penulis', 2024, 10000, 5, 'Umum');
        $this->assertTrue($buku->tersedia());
    }
}
```

**Istilah penting:**

| Istilah | Arti |
|---|---|
| Assertion | pernyataan harapan (`assertTrue`, `assertEquals`, `assertSame`) |
| `setUp()` | kode yang dijalankan sebelum *setiap* test |
| `DataProvider` | sumber data untuk menjalankan test yang sama dengan banyak input |
| Mock/Stub | "pengganti" dependency agar unit diuji tanpa DB/HTTP |
| Coverage | persentase baris kode yang dijalankan test |

**Benang Merah:** OOP (18-19) membuat kode *dapat diuji* (encapsulation, injection). Arsitektur (25-27) memisahkan concerns sehingga kita bisa test tanpa menyentuh jaringan/DB. Testing adalah *jaring pengaman* untuk semua kode yang telah kamu bangun — sebelum deployment (30) dan optimasi (29) yang berisiko refactor.

---

## 2. Fungsi & Kegunaan Utama

- **Refactor dengan aman** — ubah internal class, test memastikan perilaku luar tidak berubah.
- **Deteksi regresi** — fitur baru yang merusak fitur lama terdeteksi *otomatis* saat `phpunit` dijalankan.
- **Dokumentasi hidup** — test membaca perilaku; siapa pun tahu apa yang dijamin class.
- **CI/CD** — test dijalankan di setiap push (GitHub Actions) — "jangan deploy jika ada yang merah" (materi 30).
- **Menemukan bug lebih awal** — bug edge case (stok negatif, harga 0) ditangkap sebelum masuk produksi.


**`tests/Unit/BukuTest.php`:**

```php
<?php
// File: tests/Unit/BukuTest.php
declare(strict_types=1);

namespace Tests\Unit;

use App\Models\Buku;
use PHPUnit\Framework\TestCase;
use PHPUnit\Framework\Attributes\Test;
use PHPUnit\Framework\Attributes\DataProvider;

class BukuTest extends TestCase {
    private Buku $buku;

    protected function setUp(): void {
        $this->buku = new Buku(
            judul: 'Clean Code',
            pengarang: 'Robert Martin',
            tahun: 2008,
            harga: 150000,
            stok: 5,
            kategori: 'Teknologi',
        );
    }

    #[Test]
    public function buku_tersedia_ketika_stok_positif(): void {
        $this->assertTrue($this->buku->tersedia());
    }

    #[Test]
    public function buku_tidak_tersedia_ketika_stok_nol(): void {
        $buku = new Buku('X', 'Y', 2024, 0, 0, 'Umum');
        $this->assertFalse($buku->tersedia());
    }

    #[Test]
    public function pinjam_mengurangi_stok(): void {
        $stokAwal = $this->buku->getStok();
        $this->buku->pinjam();
        $this->assertSame($stokAwal - 1, $this->buku->getStok());
    }

    #[Test]
    public function pinjam_gagal_ketika_stok_nol(): void {
        $buku = new Buku('X', 'Y', 2024, 0, 0, 'Umum');

        $this->expectException(\RuntimeException::class);
        $this->expectExceptionMessage('tidak tersedia');

        $buku->pinjam();   // harus throw
    }

    #[Test]
    #[DataProvider('providerFormatHarga')]
    public function format_harga_benar(float $harga, string $expected): void {
        $buku = new Buku('X', 'Y', 2024, $harga, 1, 'Umum');
        $this->assertSame($expected, $buku->formatHarga());
    }

    public static function providerFormatHarga(): array {
        return [
            'nol'      => [0,         'Rp 0'],
            'seribu'   => [1000,      'Rp 1.000'],
            'standar'  => [150000,    'Rp 150.000'],
            'juta'     => [1500000,   'Rp 1.500.000'],
        ];
    }
}
```

**`tests/Unit/ValidatorTest.php`:**

```php
<?php
// File: tests/Unit/ValidatorTest.php
declare(strict_types=1);

namespace Tests\Unit;

use App\Functions\Validator;
use PHPUnit\Framework\TestCase;
use PHPUnit\Framework\Attributes\Test;

class ValidatorTest extends TestCase {
    #[Test]
    public function required_gagal_untuk_kosong(): void {
        $v = (new Validator(['nama' => '']))->required('nama', 'Nama');
        $this->assertTrue($v->gagal());
        $this->assertArrayHasKey('nama', $v->getErrors());
    }

    #[Test]
    public function required_berhasil_untuk_tidak_kosong(): void {
        $v = (new Validator(['nama' => 'Budi']))->required('nama', 'Nama');
        $this->assertTrue($v->berhasil());
    }

    #[Test]
    public function email_gagal_untuk_format_salah(): void {
        foreach (['bukan-email', '@tanpadomain', 'tanpa@', ''] as $input) {
            $v = (new Validator(['email' => $input]))->email('email', 'Email');
            $this->assertTrue($v->gagal(), "Harus gagal untuk: $input");
        }
    }
}
```

## 4. Analogi Sederhana

Dalam **Sistem Administrasi Kantor**:

- **Test** = **cek prosedur berkala** yang ditulis di buku pedoman: "Setiap staf, saat menyelesaikan SOP hitung denda, harus diverifikasi — denda 7 hari × 1000 = 7000." 
- **Unit test** = staf **menguji satu SOP saja** di meja uji: cek hitungan, cek validasi, tanpa melibatkan kantor lain.
- **Feature test** = **uji alur utuh**: "tamu mengisi formulir → loket → arsip tersimpan → surat jawaban keluar" — dipastikan semuanya terangkai.
- **`setUp()`** = staf **menyiapkan meja & berkas kosong** sebelum setiap uji — agar tiap uji mulai bersih, tidak ketularan uji sebelumnya.
- **`DataProvider`** = staf menguji **satu SOP dengan banyak sampel**: harga 0, 1000, 150000 — semua harus memberi jawaban sesuai.
- **Coverage** = laporan "berapa persen SOP yang sudah diuji" — jangan biarkan banyak SOP tanpa uji.

## 5. Kapan Harus Digunakan & Kasus Penggunaan

- **Setiap logic bisnis** — Model (`Buku::pinjam()`, `hitungDenda`), Validator, format helper.
- **Sebelum refactor** — tulis/terapkan test dulu → ubah kode → test kembali.
- **Setelah menambahkan fitur** — test baru yang menutup fitur itu (regression guard).
- **Bug yang ditemukan** — tulis test yang mereproduksi bug dulu (test dulu, perbaiki) — ini *test-driven* mindset.
- **Repository/DB** — gunakan DB test (`perpustakaan_test`) + transaction per test (rollback) agar tidak mencemari data.
- **Kapan tidak perlu** — menguji eksternal library (PHPUnit sendiri), konfigurasi, atau tampilan murni.

---

## 6. Aspek Keamanan & Best Practices (Critical)

- **JANGAN commit secret di test** — `.env.testing` (bukan `.env` production) dengan DB terpisah. Test TIDAK boleh menyentuh DB produksi.
- **Jangan log password/data user nyata di test** — gunakan fixture fiktif.
- **Test harus deterministik** — tidak tergantung waktu acak, server nyata, atau state global yang bocor. Pakai `DateTimeImmutable`/clock injection jika perlu.
- **Best practices:**
  - Nama test = kalimat perilaku (`pinjam_mengurangi_stok`), bukan `test1`.
  - `assertSame` (strict) lebih baik daripada `assertEquals` untuk menghindari juggling (materi 6).
  - Satu test = satu perilaku; jangan "pungut banyak assert" yang tidak fokus.
  - Pisahkan DB test & jalankan per-suite (`Unit` cepat, `Feature` berat).
  - Coverage ≥ 70% untuk Models/Repositories (checkpoint Level 7).

## 7. Kesalahan Umum & Debugging

- **`Class not found` saat test** — autoload-dev belum di-dump (`composer dump-autoload`) atau namespace file salah (materi 25).
- **Test pass tapi "nyata" error** — mock salah mengisolasi, atau test tidak memvalidasi apa yang penting. Pastikan assertion benar-benar memeriksa perilaku (bukan `assertTrue(true)` asal).
- **Test saling pengaruh (state bocor)** — singleton `Connection` (materi 20) & variabel static tersisa antar-test. Solusi: `setUp()` membuat instance baru, dan method `reset()` pada singleton untuk test.
- **`expectException` tidak ter-trigger** — jika exception tidak dilempar, test **gagal** (itu benar!); periksa apakah kondisi benar mengarah ke throw.
- **DB test tercemar** — tanpa transaksi per-test, data menumpuk; pakai transaksi + rollback di `setUp`/`tearDown`.
- **`--filter` tidak match** — sintaks filter harus cocok dengan nama method (tanpa spasi). Cek `phpunit --list-tests`.
- **Debugging**: jalankan satu test dengan `--debug` / `--testdox` untuk melihat alur & pesan assertion yang jelas.

## 8. Soal Latihan & Kunci Jawaban

### Tantangan 1
Tulis unit test untuk `hitungDenda(int $hariTerlambat, int $dendaPerHari = 1000)` (materi 12): (a) denda normal; (b) default parameter; (c) denda 0 hari → 0; (d) `InvalidArgumentException` untuk hari negatif. Gunakan `DataProvider` untuk (a)-(c).

### Tantangan 2
Jelaskan perbedaan & kapan memilih: unit test vs feature test. Lalu, mengapa memakai DB test terpisah (`perpustakaan_test`) bukan DB development, dan mengapa test transaksi-dan-rollback di `tearDown`?

### Jawaban & Pembahasan

**Tantangan 1**

```php
<?php
// tests/Unit/DendaTest.php
declare(strict_types=1);

namespace Tests\Unit;

use PHPUnit\Framework\TestCase;
use PHPUnit\Framework\Attributes\Test;
use PHPUnit\Framework\Attributes\DataProvider;

require_once __DIR__ . '/../../functions/perhitungan.php';

class DendaTest extends TestCase {
    #[Test]
    #[DataProvider('providerDenda')]
    public function hitung_denda_benar(int $hari, int $perHari, int $expected): void {
        $this->assertSame($expected, hitungDenda($hari, $perHari));
    }

    public static function providerDenda(): array {
        return [
            'normal'     => [7,  1000, 7000],
            'nol hari'   => [0,  1000, 0],
            'default prm'=> [3,  1000, 3000],   // (test memakai nilai default-nya)
            'mahal'      => [5,  2000, 10000],
        ];
    }

    #[Test]
    public function hari_negatif_throw(): void {
        $this->expectException(\InvalidArgumentException::class);
        hitungDenda(-1, 1000);
    }
}
```

> **Pembahasan alur:** `DataProvider` menjalankan method yang sama untuk 4 kombinasi input; `assertSame` (strict) memastikan nilai int persis. Test exception memastikan `InvalidArgumentException` untuk `-1` — behavior negatif diharapkan. Jika suatu saat kode berubah (misal tidak throw), test akan **merah** — itulah fungsinya sebagai kontrak.

**Tantangan 2**

- **Unit test**: menguji satu unit (class/method) terisolasi — cepat, deterministik, tanpa dependency eksternal. Cocok untuk logika murni (Model, Validator, helper). Dijalankan ratusan kali dalam hitungan detik.
- **Feature test**: menguji alur lengkap lintas komponen (router → controller → repository → DB/HTTP) — lebih lambat, butuh state. Cocok untuk memastikan *integrasi* (misal API endpoint bekerja dengan DB).

- **DB test terpisah**: DB development berisi data nyata dan rawan korup oleh test. DB test (`perpustakaan_test`) terisolasi — test bebas membuat/menghapus tanpa merusak data asli, dan bisa di-reset penuh.

- **Transaksi + rollback di `tearDown`**: setiap test mulai dalam transaksi, setelah selesai di-rollback → perubahan DB tidak pernah *commit*, sehingga state database kembali bersih sebelum test berikutnya. Ini menjamin determinisme antar-test (test B tidak melihat data sisa test A) dan tetap memungkinkan test menulis apa pun.

> **Pembahasan:** Kedua jenis test saling melengkapi: unit untuk logika (cepat), feature untuk alur (komprehensif). Kebersihan state via DB terpisah + transaksi adalah praktik non-negotiable untuk keandalan suite.
