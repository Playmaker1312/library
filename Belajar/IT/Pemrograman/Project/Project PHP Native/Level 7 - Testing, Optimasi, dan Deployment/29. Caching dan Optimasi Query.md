# 29. Caching dan Optimasi Query

> **Level 7 · Testing, Optimasi, dan Deployment** — Performa yang terukur: tidak semua data harus diambil dari DB setiap saat.

---

## 1. Penjelasan Singkat & Konsep Dasar

Ketika aplikasi besar dan query berat muncul, kamisme kinerja menyusun dua pendekatan:

**1) Caching** — menyimpan *hasil komputasi/query* ke media cepat (file, memory) untuk reuse, menghindari kerja berulang:

```
Request pertama : DB (500ms) → simpan ke cache
Request kedua   : cache (1ms) → langsung pakai
```

Pattern inti: **cache-aside** (lazy):

```
$nilai = CACHE->get(key)
    if bukan null → kirim
    else → ambil dari DB
         → CACHE->set(key, ttl)
         → kirim
```

**`remember(key, ttl, callback)`** — mengabstraksi pola ini (callback hanya dijalankan jika cache kosong).

**2) Optimasi query** — mengurangi kerja DB itu sendiri:
- **Index** — `WHERE`, `ORDER BY`, `JOIN` memakai kolom yang di-index → jauh lebih cepat.
- **Hindari SELECT \*** — ambil kolom yang dibutuhkan.
- **Pagination** — jangan pernah `SELECT *` tanpa `LIMIT`.
- **Eager vs lazy loading** — muat relasi yang memang dibutuhkan, jangan query beruntun (N+1 problem).
- **Prepared statement reuse** — siapkan sekali, `execute` berulang.

**Benang Merah:** pola `Cache::remember` = `array_reduce` dari dunia "simpan hasil" — sekarang memakai media eksternal. Optimasi query memperbaiki `BukuRepository` (21) dan API (27) yang kini bisa jadi beban. Setelah ini baru deployment (30).

---

## 2. Fungsi & Kegunaan Utama

- **Cache** — akselerasi untuk data yang jarang berubah (daftar kategori, statistik, konfigurasi, halaman yang berat). TTL (time-to-live) menjaga kesegaran.
- **Query optimization** — DB adalah bottleneck utama; memperbaiki query = dampak paling besar.
- **Mengurangi beban DB & latensi** — halaman lebih cepat, server lebih hemat.
- **`remember` pattern** — satu baris memanggil untuk cache: ringkas & aman (bibliografi reusable).

## 3. Contoh Kode & Implementasi Real-World

Struktur:

```
src/Core/Cache.php
```

**`src/Core/Cache.php` — file-based cache sederhana (portable, tanpa dependency):**

```php
<?php
// File: src/Core/Cache.php
declare(strict_types=1);

namespace App\Core;

class Cache {
    private static string $dir;

    public static function init(string $dir): void {
        self::$dir = rtrim($dir, '/\\');
        if (!is_dir(self::$dir)) {
            mkdir(self::$dir, 0755, true);
        }
    }

    private static function file(string $key): string {
        return self::$dir . DIRECTORY_SEPARATOR . md5($key) . '.cache';
    }

    public static function get(string $key): mixed {
        if (!file_exists(self::file($key))) return null;
        $data = unserialize((string) file_get_contents(self::file($key)));

        if ($data['exp'] !== null && time() > $data['exp']) {
            unlink(self::file($key));
            return null;
        }
        return $data['val'];
    }

    public static function set(string $key, mixed $val, int $ttlDetik = 300): void {
        $data = ['val' => $val, 'exp' => $ttlDetik > 0 ? time() + $ttlDetik : null];
        file_put_contents(self::file($key), serialize($data), LOCK_EX);
    }

    /** Inti pola: ambil dari cache, kalau kosong jalankan callback & simpan. */
    public static function remember(string $key, int $ttl, callable $callback): mixed {
        $cached = self::get($key);
        if ($cached !== null) return $cached;

        $value = $callback();
        self::set($key, $value, $ttl);
        return $value;
    }

    public static function forget(string $key): void {
        if (file_exists(self::file($key))) unlink(self::file($key));
    }

    public static function flush(): void {
        foreach (glob(self::$dir . DIRECTORY_SEPARATOR . '*.cache') ?: [] as $f) {
            unlink($f);
        }
    }
}
```

**Integrasi ke repository (cache-aside untuk findAll):**

```php
<?php
// src/Repositories/BukuRepository.php (tambahan)
use App\Core\Cache;

public function findAll(int $halaman = 1, int $perHalaman = 10): array {
    $key = "buku:daftar:{$halaman}:{$perHalaman}";

    return Cache::remember($key, 300, function () use ($halaman, $perHalaman) {
        // — query sebenarnya hanya dijalankan jika cache kosong —
        return $this->queryFindAllSebenarnya($halaman, $perHalaman);
    });
}

public function create(array $data): int {
    $id = $this->queryCreate($data);
    Cache::flush();                 // data berubah → invalidate cache daftar
    return $id;
}
```

> **Penting — invalidation**: cache hanya berguna jika dibersihkan saat data berubah. `flush()` setelah INSERT/UPDATE/DELETE yang menyentuh daftar; atau `forget('buku:daftar:*')` lebih presisi.

**Optimasi query — contoh perbaikan `findAll`:**

```sql
-- Sebelum (mahal): SELECT * tanpa index
SELECT * FROM buku ORDER BY judul LIMIT 10 OFFSET 20;

-- Sesudah: ambil kolom yang dibutuhkan + pastikan index
SELECT id, judul, pengarang, harga, stok, kategori
FROM buku
WHERE deleted_at IS NULL AND kategori = 'Teknologi'
ORDER BY judul
LIMIT 10 OFFSET 20;
-- Index: INDEX idx_kategori (kategori), INDEX idx_judul (judul)
```

**Menghindari N+1 (lazy loading menyesatkan):**

```php
// ❌ N+1: query buku, lalu per buku query kategori (1 + N query)
$buku = $repo->findAll();
foreach ($buku as $row) {
    echo $row['judul'] . ' — ' . $this->kategoriRepo->findById($row['kategori_id'])['nama'];
}

// ✅ 1 query JOIN (atau eager load) — satu perjalanan DB
SELECT b.judul, k.nama AS kategori
FROM buku b
JOIN kategori k ON k.id = b.kategori_id
WHERE b.deleted_at IS NULL;
```

> Perhatikan: pada skema Level 4 (`kategori` adalah ENUM di tabel `buku`), kasus di atas adalah ilustrasi untuk tabel relasi yang nyata — prinsipnya: hindari query per-baris.

## 4. Analogi Sederhana

Dalam **Sistem Administrasi Kantor**:

- **Cache** = **papan rekap cepat di meja depan**. Data yang sering ditanya (daftar kategori, statistik hari ini) ditulis di papan; tidak perlu berlari ke gudang arsip (DB) setiap ditanya.
- **TTL** = jadwal penyegaran papan — "perbarui papan setiap 5 menit". Kalau ada perubahan besar, staf *menimpa papan* (invalidate) agar tidak ada info usang.
- **`remember`** = resepsionis cek papan: kosong? → pergi ambil ke gudang, tulis di papan; ada? → langsung jawab. 
- **Index** = **papan indeks di gudang** — menemukan berkas `judul = 'Clean Code'` tanpa membolak-balik seluruh lemari (index) vs harus memindai semua (full scan).
- **`SELECT *`** = memotret seluruh minyak berkas; padahal yang dibutuhkan hanya 5 kolom. Optimasi = minta hanya yang perlu.
- **N+1 problem** = staf bolak-balik 100 kali ke gudang untuk 100 buku; padahal bisa membawa kereta dalam **satu perjalanan** (JOIN).

## 5. Kapan Harus Digunakan & Kasus Penggunaan

- **Cache untuk**:
  - Data yang *jarang berubah* & sering dibaca: daftar kategori, statistik dashboard, halaman publik.
  - Hasil komputasi berat: laporan agregat.
  - Respons API yang mahal (`GET /api/buku` dengan pagination).
  - TTL pilih sesuai: statistik 5-10 menit; kategori 1 jam; config sangat lama.
- **Optimasi query untuk**: semua query yang sudah teridentifikasi lambat (profil dulu! jangan optimize-berlebihan), JOIN/relasi, pagination besar.
- **Kapan TIDAK cache**: data per-user yang sangat privat sering berubah (kursi keranjang, saldo) atau memerlukan konsistensi ketat — cache bisa menyimpan data kadaluarsa/satu-user ke user lain (hati-hati cache key harus mencakup user).

---

## 6. Aspek Keamanan & Best Practices (Critical)

- **Cache key harus mencakup konteks & identitas** — data per-user jangan cache dengan key global (`buku:daftar` tanpa user) jika berisi data privat → bisa bocor antar-user. Gunakan `buku:daftar:user:{$id}` atau hindari caching data per-user yang sensitif.
- **Jangan cache data sensitif** (password hash, token) — atau jika perlu, amankan lokasi (diluar web root, permission ketat).
- **Injection di cache**: `unserialize` dari file yang bisa ditulis attacker = RCE. Jangan pernah membiarkan cache dir ditulis dari upload/input; guard permission & validasi key.
- **Jangan cache halaman/endpoint yang membutuhkan auth tanpa versi/identitas** — lapiskan role ke key, atau cache hanya bagian publik.
- **Best practices:**
  - Profil dulu (jalankan query dengan EXPLAIN / time) — jangan optimasi tanpa data.
  - TTL realistis; invalidation eksplisit saat data berubah.
  - Hanya cache apa yang jelas menguntungkan; cache yang salah = bug "data lama terus".
  - Nama key konsisten & deskriptif (`buku:daftar:1:10`).
- **Prepared statement reuse** — jangan prepare ulang dalam loop; siapkan di luar.

## 7. Kesalahan Umum & Debugging

- **Cache "data lama" muncul padahal DB sudah berubah** — lupa invalidate (`flush`/`forget`) saat update/delete. Cache layanan: incoherence adalah biaya cache; kelola dengan disiplin.
- **Cache kosong setiap saat (tidak efektif)** — TTL terlalu pendek, atau key beda tiap request (misal key berisi timestamp). Pastikan key stabil (halaman, parameternya) — kecuali memang variabel.
- **Unserialize error / file korup** — cache file rusak karena konflik tulis. `file_put_contents` + `LOCK_EX`; atau gunakan format aman (serialized bawaan) dengan validasi.
- **Memory cache terlalu besar** — TTL panjang + banyak key → disk/memori penuh. Batasi jumlah key, set TTL, atau gunakan cache replacement.
- **Optimasi query "lambat tetap lambat"** — index tidak terpakai karena kolom difungsikan (`WHERE LOWER(judul) = ...` membuat index mati) atau `%..%` LIKE. Periksa `EXPLAIN` untuk melihat index yang dipakai.
- **N+1 terasa lambat** — cek query log; ganti dengan JOIN/eager load yang dibutuhkan.
- **Pagi ini lambat** — cache cold start: pertama request setelah TTL/fresh adalah lambat; terima sebagai normal (warm-up opsional).

## 8. Soal Latihan & Kunci Jawaban

### Tantangan 1
Implementasikan `Cache::remember` untuk method `hitungStatistik()` di sisi repo: simpan hasil 600 detik; jika `create()`/`update()` dipanggil, invalidate key. Jelaskan key yang dipakai.

### Tantangan 2
Punya query:

```sql
SELECT * FROM buku WHERE stok > 0 AND kategori = 'Teknologi' ORDER BY tahun DESC;
```

(a) Apa yang harus ditambahkan di sisi database agar cepat? (b) Apa optimasi sisi PHP/query untuk menghindari beban berlebih saat banyak halaman? (c) Apa satu risiko menggunakan cache di query ini?

### Jawaban & Pembahasan

**Tantangan 1**

```php
public function hitungStatistik(): array {
    return Cache::remember('buku:statistik', 600, function () {
        // query agregat (misal COUNT per status, SUM stok)
        $stmt = $this->db->query(
            "SELECT
                COUNT(*) AS total,
                SUM(CASE WHEN stok > 0 THEN 1 ELSE 0 END) AS tersedia
             FROM buku WHERE deleted_at IS NULL"
        );
        return $stmt->fetch();
    });
}

public function create(array $data): int {
    $id = $this->queryCreate($data);
    Cache::forget('buku:statistik');     // invalidasi khusus
    return $id;
}

public function update(int $id, array $data): bool {
    $ok = $this->queryUpdate($id, $data);
    Cache::forget('buku:statistik');
    return $ok;
}
```

> **Pembahasan:** Key `buku:statistik` stabil (tidak tergantung request) sehingga effective; TTL 600 detik wajar untuk statistik. Setiap mutasi memanggil `forget` dengan key yang sama — koheren cache terjaga. Ini kombinasi cache-aside + explicit invalidation.

**Tantangan 2**

- (a) **Index gabungan** di `buku` untuk `(kategori, stok)` dan `(tahun)` — memungkinkan DB melewatkan row yang tidak perlu (`WHERE`+`ORDER`) tanpa full scan. (b) **Kolom spesifik + pagination**: ganti `SELECT *` dengan `SELECT id, judul, pengarang, harga` dan tambahkan `LIMIT/OFFSET` (atau keyset pagination) agar tidak pernah mengambil semua. (c) **Risiko cache**: query ini bergantung pada `stok` yang *sering berubah* — jika cache `SELECT *` tanpa versi/parameter, hasil bisa kedaluarsa ("data lama" padahal stok sudah habis). Solusi: cache hanya data yang jarang berubah (kategori distin), TTL pendek, atau buat key mencakup parameter & invalidasi saat stok berubah.

> **Pembahasan:** Optimasi terbaik tergantung *pola akses* — indeks mempercepat `WHERE/ORDER`, pagination membatasi volume, dan cache hanya cocok bila frekuensi perubahan data < frekuensi baca. Ini alasan kenapa kamu harus *mengukur* (EXPLAIN, query log) sebelum memutuskan.
