# Membuat Interface Repository — Kontrak Data Access

## Penjelasan

Repository Pattern adalah pola arsitektural yang memisahkan logika akses data dari logika bisnis dengan cara memperkenalkan layer perantara yang disebut repository. Dalam konteks NestJS, kita mendefinisikan interface yang berisi kontrak method-method yang harus ada untuk mengakses data — seperti `findAll`, `findById`, `create`, `update`, dan `softDelete`. Interface ini menjadi perjanjian (contract) bahwa apapun implementasi konkritnya (apakah menggunakan Prisma, TypeORM, atau bahkan array in-memory), method-method tersebut harus tersedia dengan signature yang sama.

Keuntungan utama dari repository pattern adalah **abstraksi** dan **testability**. Dengan abstraksi, logika bisnis di service tidak peduli database apa yang digunakan di belakang layar. Jika suatu saat kita migrasi dari PostgreSQL ke MySQL, kita cukup membuat implementasi repository baru tanpa mengubah kode service sama sekali. Untuk testing, kita bisa dengan mudah membuat mock repository yang mengembalikan data palsu, tanpa perlu database sungguhan.

Setelah mendefinisikan interface, kita buat Injection Token menggunakan `@Inject()` decorator. Token ini (biasanya berupa string constant seperti `'BOOKS_REPOSITORY'`) digunakan untuk mendaftarkan repository sebagai custom provider di module. Dengan pendekatan ini, NestJS tahu implementasi mana yang harus di-inject saat service meminta `IBooksRepository`. Ini memungkinkan kita mengganti implementasi kapan saja tanpa mengubah kode yang menggunakan repository tersebut.

## Fungsi

Mendefinisikan kontrak antar muka untuk data access layer, memungkinkan loose coupling antara service dan database, serta memudahkan penggantian implementasi database dan pembuatan mock untuk testing.

## Cara Implementasi / Code

Buat folder `src/books/interfaces/` dan file `books-repository.interface.ts`:

```typescript
// src/books/interfaces/books-repository.interface.ts
import { Book, BookGenre } from '@prisma/client';

// DTO untuk create book
export interface CreateBookDto {
  title: string;
  author: string;
  isbn: string;
  publishedYear: number;
  genre: BookGenre;
  description?: string;
  stock?: number;
}

// DTO untuk update book
export interface UpdateBookDto {
  title?: string;
  author?: string;
  isbn?: string;
  publishedYear?: number;
  genre?: BookGenre;
  description?: string;
  stock?: number;
}

// Interface repository
export interface IBooksRepository {
  findAll(): Promise<Book[]>;
  findById(id: string): Promise<Book | null>;
  findByIsbn(isbn: string): Promise<Book | null>;
  create(dto: CreateBookDto): Promise<Book>;
  update(id: string, dto: UpdateBookDto): Promise<Book>;
  softDelete(id: string): Promise<Book>;
}
```

Buat file token constant:

```typescript
// src/books/constants/tokens.ts
export const BOOKS_REPOSITORY = 'BOOKS_REPOSITORY';
```

Atau bisa juga digabung di file yang sama. Penggunaan token memungkinkan kita menggunakan dependency injection yang fleksibel.

## Analogi

Interface repository adalah **formulir permintaan buku** standar di perpustakaan. Formulir ini memiliki kolom-kolom tetap: "Cari Buku", "Pinjam Buku", "Kembalikan Buku", "Cek Stok". Apapun petugas yang melayani — apakah petugas senior yang hafal letak semua buku (database), petugas magang yang masih lihat catatan (file JSON), atau robot pencari buku otomatis (API eksternal) — formulirnya tetap sama. Pengunjung (service) hanya perlu mengisi formulir dan menyerahkannya ke loket. Pengunjung tidak perlu tahu apakah buku diambil dari gudang utama, gudang cadangan, atau dipanggil dari perpustakaan cabang lain. Yang penting, buku yang diminta tersedia. Jika suatu hari petugas senior pensiun dan diganti robot, formulirnya tidak berubah, sehingga pengunjung tidak perlu belajar lagi cara meminjam buku.

## Penggunaan

Dipakai di semua aplikasi NestJS yang membutuhkan akses database dengan arsitektur yang rapi dan testable. Sangat berguna untuk proyek skala besar dengan tim banyak, di mana separation of concerns sangat penting. Juga digunakan untuk memudahkan unit testing karena repository bisa di-mock.

## Kesalahan Umum yang Sering Terjadi

1. **Interface terlalu spesifik ke database tertentu**: Misalnya menggunakan tipe data yang hanya ada di Prisma (`Prisma.BookCreateInput`). Interface harus agnostic terhadap implementasi.
2. **Tidak menggunakan Injection Token**: Langsung mendaftarkan class implementasi tanpa token, sehingga mengganti implementasi jadi sulit.
3. **Method terlalu banyak**: Interface memiliki puluhan method yang tidak semua implementasi butuh. Lebih baik pisah menjadi beberapa interface kecil (Interface Segregation Principle).
4. **Lupa export interface**: Module lain tidak bisa menggunakan interface untuk type checking.
5. **Tipe return tidak konsisten**: Antara satu method mengembalikan `Promise<Book | null>`, method lain `Promise<Book | undefined>`.

## Hubungan dengan Materi Sebelumnya

Sebelumnya di Level 1, kita mengakses data langsung dari array di service. Sekarang dengan repository pattern, service tidak lagi langsung memegang data — service hanya berbicara melalui interface repository. Ini adalah peningkatan arsitektural yang signifikan. Interface ini akan diimplementasikan oleh `PrismaBooksRepository` (materi 24) dan didaftarkan sebagai provider (materi 25).

**Soal 2:** Apa fungsi Injection Token (`BOOKS_REPOSITORY`) dalam repository pattern?

<details>
<summary>Jawaban</summary>

Injection Token berfungsi sebagai key identifier untuk mendaftarkan dan meng-inject repository ke dalam dependency injection container NestJS. Dengan token, kita bisa mengganti implementasi konkrit (misalnya dari PrismaBooksRepository ke MockBooksRepository) tanpa mengubah kode service yang meng-inject-nya. Cukup ganti provider di module.
