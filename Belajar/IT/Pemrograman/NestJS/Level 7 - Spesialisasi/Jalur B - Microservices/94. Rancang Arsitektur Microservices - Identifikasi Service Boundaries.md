# 94. Rancang Arsitektur Microservices - Identifikasi Service Boundaries

## Penjelasan
Microservices adalah gaya arsitektur di mana aplikasi dipecah menjadi beberapa service kecil yang independen, masing-masing memiliki domain bisnis sendiri, database sendiri, dan bisa di-deploy secara terpisah. Langkah paling krusial dalam microservices adalah **menentukan service boundaries** — batas antar service — berdasarkan **Domain-Driven Design (DDD)** dan konsep **Bounded Context**. Setiap context memiliki model data, aturan bisnis, dan bahasa sendiri yang tidak perlu diketahui context lain.

Dalam sistem perpustakaan, kita bisa mengidentifikasi beberapa service boundaries: **Books Service** (mengelola data buku, kategori, penulis), **Users Service** (manajemen anggota perpustakaan), **Loans Service** (proses peminjaman dan pengembalian), dan **Notification Service** (mengirim notifikasi email/push). Masing-masing punya database terpisah — misal Books pakai PostgreSQL, Users juga PostgreSQL tapi instance berbeda, Loans dengan PostgreSQL, Notification cukup database ringan untuk menyimpan log notifikasi. **API Gateway** adalah pintu masuk tunggal yang menerima request dari client dan me-routing ke service yang tepat. Gateway bisa juga menangani autentikasi, rate limiting, dan aggregasi response.

## Fungsi
- Memisahkan concern bisnis ke service yang independen agar tim bisa bekerja paralel
- Setiap service bisa di-deploy, di-scale, dan di-maintain secara terpisah (loose coupling)
- Menggunakan database yang paling sesuai untuk setiap service (polyglot persistence)
- API Gateway menyediakan single-entry point yang menyederhanakan komunikasi client

**2. ADR (Architecture Decision Record) — 001-service-boundaries.md:**
```markdown
# ADR-001: Identifikasi Service Boundaries

## Status
Accepted

## Context
Aplikasi perpustakaan monolitik perlu dipecah menjadi microservices
untuk mendukung tim terpisah dan scaling independen.

## Decision
Empat service boundaries berdasarkan Bounded Context:

1. **Books Service**
   - Domain: Manajemen katalog buku, kategori, penulis
   - Owns: Tabel Book, Category, Author
   - Database: PostgreSQL (instance sendiri)
   - Transport: TCP (sync) via API Gateway

2. **Users Service**
   - Domain: Manajemen anggota, staff, admin
   - Owns: Tabel User, Role
   - Database: PostgreSQL (instance sendiri)
   - Transport: TCP (sync) via API Gateway

3. **Loans Service**
   - Domain: Proses peminjaman, pengembalian, denda
   - Owns: Tabel Loan, Fine
   - Database: PostgreSQL (instance sendiri)
   - Transport: TCP (sync) + Emit event ke RabbitMQ

4. **Notification Service**
   - Domain: Kirim email notifikasi, reminder overdue
   - Owns: Tabel NotificationLog
   - Database: SQLite (ringan)
   - Transport: RabbitMQ (async, event-driven)

## Consequences
+ Isolation: setiap service bisa di-scale dan di-deploy independen
+ Separation of concerns: tim bisa fokus pada domain masing-masing
- Complexity: komunikasi antar-service via network (latency, failure)
- Data consistency: eventual consistency antar database
```

## Analogi
Bayangkan sebuah perpustakaan besar yang tadinya dikelola oleh **satu orang pustakawan** (monolith) yang melakukan semuanya: mendaftarkan anggota, mengkatalog buku, memproses peminjaman, dan mengirim surat tagihan. Sekarang perpustakaan berkembang dan dipecah menjadi **beberapa bagian**: (1) **Bagian Katalog** — urusan data buku saja (Books Service), (2) **Bagian Keanggotaan** — urusan member (Users Service), (3) **Bagian Sirkulasi** — urusan peminjaman (Loans Service), (4) **Bagian Notifikasi** — urusan kirim surat/email (Notification Service). Ada **meja informasi utama** (API Gateway) di pintu masuk: pengunjung datang, tanya "saya mau pinjam buku ini", meja informasi mengarahkan ke Bagian Sirkulasi. Setiap bagian punya **lemari arsip sendiri** (database terpisah) — Bagian Katalog tidak boleh mengakses lemari arsip Bagian Sirkulasi.

## Penggunaan
- Aplikasi perpustakaan (atau aplikasi bisnis apa pun) yang sudah terlalu besar untuk monolith
- Tim pengembang terpisah untuk setiap domain (tim buku, tim peminjaman, dll.)
- Ketika skala aplikasi memerlukan scaling independen (Books read-heavy, Loans write-heavy)
- Ketika perlu mengintegrasikan sistem eksternal (email service, payment gateway)

## Kesalahan Umum yang Sering Terjadi
1. **Service boundaries salah** — Memecah berdasarkan teknis (Controller Service Repository) bukan domain bisnis. Akibatnya perubahan bisnis sekecil apapun melibatkan banyak service.
2. **Shared database** — Dua service pakai database yang sama. Ini menghilangkan isolasi; perubahan schema di satu service bisa merusak service lain.
3. **Over-engineering** — Langsung microservices untuk aplikasi kecil (3 controller). Mulailah dari monolith, pisahkan hanya ketika benar-benar diperlukan.
4. **Tidak ada gateway** — Client berkomunikasi langsung ke setiap service, menyebabkan kompleksitas di client-side.
5. **Synchronous coupling berlebihan** — Service A memanggil Service B secara sync, yang memanggil Service C secara sync. Jika C lambat, A dan B ikut lambat. Ganti dengan event-driven untuk operasi yang tidak perlu real-time.

## Hubungan dengan Materi Sebelumnya
Selama Level 1–6 kita membangun monolith NestJS yang solid. Sekarang kita melihat batas-batas domain dalam monolith itu dan memisahkannya menjadi service-service independen. Pemahaman tentang module (Level 1), repository pattern (Level 2), dan event-driven dengan BullMQ (Level 4) menjadi fondasi untuk transisi ini. Materi 95–97 akan mengimplementasikan service-service ini secara konkret.

## Soal Latihan

**Soal:** Berdasarkan ADR di atas, kamu diminta menambahkan service kelima: **Inventory Service** yang bertanggung jawab melacak stok fisik buku di rak perpustakaan. Tentukan: (1) domain yang di-own, (2) tabel yang dimiliki, (3) database yang digunakan, (4) apakah komunikasi sync atau async, dan (5) bagaimana relasi dengan Books Service.

**Jawaban:**
```markdown
# Service: Inventory Service

Domain: Manajemen stok fisik buku — berapa eksemplar tersedia, rusak, hilang
Owns: Tabel BookStock (bookId, totalCopies, availableCopies, damagedCopies, location)
Database: PostgreSQL (instance sendiri)
Transport: 
  - TCP (sync) untuk query ketersediaan stok dari Loans Service
  - RabbitMQ (async) menerima event book.returned untuk update stok

Relasi dengan Books Service:
- Books Service adalah source of truth untuk metadata buku (judul, penulis, ISBN)
- Inventory Service hanya menyimpan bookId sebagai referensi (tanpa foreign key)
- Saat buku baru ditambahkan, Books Service emit event → Inventory Service membuat record stok
```
