# 37. Vite — Build Tool Modern untuk Vanilla JS

Materi ini membahas **Vite**: membangun project vanilla JS dengan `npm create vite`, memahami struktur (berkas `index.html`, folder `public/`, `src/`), perintah `npm run dev/build/preview`, konfigurasi `vite.config.js` (base, build outDir/minify, server proxy untuk menghindari CORS), membedah `package.json`, mengubah **env variables** (`VITE_`), dan alasan mengapa Vite menjadi pilihan build tool untuk produksi.

## 1. Penjelasan Singkat & Konsep Dasar

Sepanjang Level 1-6 kita bekerja dengan cara tradisional: `<script src="js/main.js">`, `css/style.css`, langsung dibuka lewat Live Server. Cara ini cocok untuk belajar, tetapi untuk produksi ia menyisakan masalah. ES Modules (materi 34) di browser modern sebenarnya sudah bisa dipakai tanpa build tool, tapi setiap `import` menjadi *request HTTP terpisah* — 20 modul = 20 request, lambat di jaringan nyata. Dan kita belum menyediakan *penanganan* resources non-JS (foto, CSS, asset) secara terpadu, belum ada pengecilan (minify), belum ada pemisahan vendor, dan belum ada lingkungan development yang nyaman dengan auto-refresh. Itulah yang dipecahkan **build tool**, dan **Vite** adalah pilihan modern yang paling ringan untuk vanilla JS.

Vite bekerja dalam dua mode. **Development**: Vite menjalankan *dev server* yang menyajikan kode kamu langsung sebagai ES Modules (native, tanpa membundel), dengan **HMR (Hot Module Replacement)** — saat file disimpan, browser memperbarui bagian yang berubah *tanpa me-refresh seluruh halaman*, sehingga state aplikasi (misal teks yang sedang kamu ketik) tidak hilang. Karena tidak ada bundling di dev, server ini (dan devitasi feedback-nya) hampir seketika. **Production**: `vite build` mengambil kode ES Modules, menganalisis grafik dependensi secara statis, dan **membundel** menjadi beberapa file kecil — JavaScript di-minify (dengan esbuild/terser), CSS digabung & diminify, asset diberi *fingerprint* (hash konten) agar cache browser bisa dipecah saat file berubah, dan **tree-shaking** membuang kode yang tidak dipakai.

Struktur project Vite vanilla singkat dan jelas. Ada `index.html` di *root* (bukan di dalam subfolder) — Vite memperlakukan HTML sebagai entry point asli, dan `<script type="module" src="/src/main.js">` di dalamnya adalah titik masuk kode. Folder **`public/`** berisi aset statis yang *tidak diproses* (berkas polos, favicon, robots.txt) dan disalin begitu saja ke output. Folder **`src/`** menyimpan semua kode yang diproses: `main.js`, `style.css`, dan `modules/` (arsitektur materi 34 pindah ke sini). Hasil build turun di folder **`dist/`**.

Konfigurasi hidup di **`vite.config.js`**: mengatur `base` (path asal asset — penting saat deploy ke subfolder/domain), pengaturan `build` (misal `outDir`, `minify`, manual chunks untuk memisahkan library besar), dan **server proxy** di development — mengarahkan request ke `/api` ke server backend (misal `http://localhost:8000`) sehingga *browser tidak terkena CORS* (CORS adalah kebijakan browser, bukan masalah server). Terakhir, **environment variables**: berkas `.env` berisi nilai rahasia/per-konfigurasi, dan hanya variabel berawalan **`VITE_`** yang diekspos ke kode klien (aman dibundel), sisanya tidak pernah bocor ke browser.

**Benang merah**: Vite menautkan seluruh materi sebelumnya. Ia butuh **ES Modules** (34) untuk bisa membundel dan tree-shake; menghasilkan **bundle kecil & minified** (35) yang menaikkan LCP; lalu menyerahkan output `dist/` yang siap untuk **deploy** (38). Vite juga memunculkan TypeScript (catatan 34) secara native. Dari sini aplikasi perpustakaan bukan lagi kumpulan file yang dibuka langsung, melainkan *produk* yang dibangun, diuji dengan `preview`, dan dikirim sebagai satu paket.

## 2. Fungsi & Kegunaan Utama dalam Web

Untuk **Perpustakaan Digital Kota**, Vite mengubah perawatan jadi lebih disiplin. Development menjadi cepat dan nyaman berkat HMR: saat memperbaiki `ui.js`, hanya katalog yang di-render ulang, bukan seluruh halaman reload — percobaan yang sia-sia mengetik ulang form (misal form favorit) benar-benar berkurang. Struktur `src/` persis seperti yang dibangun di materi 34 (`src/modules/api.js, storage.js, ui.js, state.js, events.js`, plus `main.js`) dan kini punya *alasan* — karena `index.html` merujuk ke `src/main.js`, dan seluruh modul diimpor dari sana.

Untuk produksi, `npm run build` menghasilkan `dist/` yang **siap dikirim**: JavaScript dari puluhan modul digabung dan diminify (bundle kecil — poin penting performa materi 35), CSS digabung, asset diberi hash sehingga browser bisa meng-cache lama, dan hanya kode yang benar-benar diimpor yang dibundel (tree-shaking). `npm run preview` melayani build produksi persis seperti deployment, jadi tim bisa memverifikasi sebelum benar-benar rilis ke Netlify/Vercel (materi 38).

Bagi backend/social: **proxy dev** memungkinkan aplikasi vanilla ini bekerja berdampingan dengan API nyata (`http://localhost:8000/api/...`) tanpa konflik CORS di development — browser mengira request itu same-origin karena Vite yang meneruskan. **Env variables** membantu tiga lingkungan: `VITE_API_BASE` bisa berbeda untuk development vs produksi, dan semua nilai naik dengan aman lewat `.env` tanpa hardcode di kode. Hasilnya: tim bisa menjalankan, menguji, dan menaikkan versi aplikasi dengan langkah yang sama di semua komputer (reproducible), hingga akhirnya memakai `netlify.toml`/workflow CI/CD di materi 38.

```javascript
// vite.config.js — konfigurasi utama
import { defineConfig } from "vite";

export default defineConfig({
    // Base URL path saat dipublikasikan. "/" untuk domain root.
    // Jika deploy ke subfolder (mis. github.io/nama/), ganti base: "/nama/".
    base: "/",

    // Optimasi build produksi
    build: {
        outDir: "dist",          // folder hasil build (default sudah begitu)
        minify: "terser",        // "esbuild" (default, cepat) atau "terser"
        rollupOptions: {
            output: {
                // Pisahkan library besar agar file utama tetap kecil &
                // bisa di-cache terpisah (tidak bust seluruh bundle saat update)
                manualChunks: {
                    vendor: ["lodash-es"],
                },
            },
        },
    },

    // Dev server
    server: {
        port: 3000,
        open: true,              // auto-buka browser saat npm run dev

        // Proxy: request /api/* → server backend di dev,
        // mengelabui browser agar percaya same-origin → BEBAS CORS.
        proxy: {
            "/api": {
                target: "http://localhost:8000",
                changeOrigin: true,
            },
        },
    },
});
```

## 4. Analogi Sederhana — Membangun Rumah

**HTML** adalah kerangka dan tata ruang, **CSS** adalah cat, **JS** adalah listrik, dan **TypeScript** adalah blueprint presisi. Vite adalah **pabrik prefabrikasi** yang menggabung semua material menjadi **paket efisien** sebelum rumah dikirim ke lokasi. Bayangkan para tukang menghasilkan 100 kotak material terpisah: kayu potongan kecil, kabel gulungan, cat galon — meletakkan semuanya begitu saja ke lokasi rumah membuat mobil kontainer penuh sesak dan butuh banyak trip. Pabrik Vite menerima semua bahan itu, *merakitnya menjadi modul modular panel* (bundle) yang sudah minified dan diberi label, lalu mengirimkan beberapa truk yang ringkas — rumah di perumahan (user browser) bisa dirakit jauh lebih cepat dari paket yang kecil.

**Mode development vs production** ibarat dua jadwal pabrik. Di *development*, pabrik bekerja "just-in-time": kamu (developer) masih sering mengganti potongan kayu (file kode), jadi pabrik menyalurkan bahan mentah seadanya secara instan — menyala tanpa menunggu (dev server + HMR) — **setiap kali kamu mengubah satu panel, hanya panel itu yang diganti pabrik, bukan seluruh rumah dibongkar** (itu HMR!). Di *production*, pabrik melakukan proses penuh: mengecek semua material, **membuang kayu yang tidak pernah dipakai** (tree-shaking), memotong semua menjadi ukuran standar yang padat (minify), dan memberi setiap panel nomor seri berisi tanggal perubahan (hash) supaya pembeli tidak mengangkut ulang panel yang sama.

**Proxy dev** seperti **tukang pajak** yang berdiri di pintu masuk ke lingkungan: dikirimnya request tidak langsung ke bank pusat (server backend yang punya billing lain), melainkan lewat dia, sehingga tidak ada cek yang ditolak (blokir CORS). **Env vars `VITE_`** adalah **kotak kunci yang nama-kotaknya dicap** di pabrik: hanya kotak bertanda `VITE_` yang diizinkan keluar dari pabrik menuju rumah publik — kunci lain (misal token backend) tinggal di pabrik dan tidak pernah menumpang di kontainer yang dikirim. Dan **hasil build (`dist/`)** adalah **paket jadi yang siap dikirim ke portal tugas** (Netlify/Vercel, materi 38) — tinggal serah terima, tanpa pekerjaan tambahan lagi.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

- **Project vanilla yang mau produksi** — kode sudah terstruktur modul (34): pindahkan `js/...` ke `src/...`, ganti path script di `index.html`, dan jalankan `npm run dev` — kamu langsung mendapat ES Modules + HMR tanpa mengubah satu baris logika.
- **Pengembangan yang butuh CORS ilegal dihapus** — app memanggil API pihak ketiga (materi 6) atau backend lokal: atur `server.proxy` untuk `/api` di `vite.config.js`; di production, backend dipanggil langsung dari domain produksi (atau tetap lewat proxy di gateway deploy).
- **Lingkungan dev/prod yang berbeda** — base URL API, flags fitur: definisikan `VITE_*` di `.env` dan `.env.production`; bacanya lewat `import.meta.env.VITE_*` di modul (mis. `api.js`).
- **Performa & bundle kecil** — memanfaatkan minify, tree-shaking, dan manual chunk vendor: ukur ukuran `dist/` sebelum materi 38 deploy; jika ada library besar, pisahkan ke `manualChunks`.
- **Uji build produksi sebelum rilis** — `npm run build` lalu `npm run preview`: cek route, asset, dan env produksi persis seperti deployment — menyelamatkan dari kejutan di production.
- **Basis menuju framework & TypeScript** — Vite adalah build tool untuk React/Vue/Svelte juga; pola `src/main.js` + modul + dev server ini transfer 1:1 bila tim berkembang ke React.

## 6. Poin-poin Penting & Best Practices

- **ES Modules + satu entry**: `index.html` memuat satu `<script type="module" src="/src/main.js">`; semua modul diimpor dari sana — dimungkinkan hanya karena arsitektur materi 34.
- **Kenapa Vite di produksi**: HMR di dev, bundling+minify+tree-shake+hash di build — kode yang dikirim kecil, cache bisa dipecah, dan build reproducible lewat `npm ci`.
- **Struktur**: `index.html` di root; kode di `src/` (diproses); aset statis polos di `public/` (disalin); hasil di `dist/`. Import CSS lewat JS (`import "./style.css"`) bukan `<link>` agar ikut dalam bundling.
- **Config minimum**: `base` penting hanya untuk subfolder; `build.outDir`, `minify`, `manualChunks` untuk memisahkan library besar; `server.proxy` menyelesaikan CORS dev dengan rapi.
- **`npm ci` vs `npm install`**: di CI (materi 38) pakai `npm ci` agar dependensi persis dari `package-lock.json` — reproducable dan cepat.
- **Env**: nama variabel **wajib** diawali `VITE_` untuk diekspos; nilainya dibaca `import.meta.env.VITE_X`; gunakan `.env.production` untuk nilai rilis; jangan pernah commit `.env` berisi secret.
- **Debug env**: `import.meta.env` berisi `MODE`, `DEV`, `PROD` — berguna untuk logika yang beda di dev/prod; document value dengan `.env.example` yang aman di-commit.
- **Jangan commit `dist/`** — hasil build adalah artifact; sumber sejatinya kode di `src/`, dan dist dibangun kembali oleh CI (materi 38).

## 7. Kesalahan Umum (Common Pitfalls & Bugs)

- **Path `base` salah di subfolder** — deploy ke `https://domain/nama/` tapi `base: "/"`: asset di-build dengan absolute `/` sehingga rusak (`/assets/...` tidak ketemu). Perbaikan: set `base: "/nama/"` sesuai path publik.
- **CORS kambuh karena tidak pakai proxy** — di dev, `fetch(`${API}`)` langsung ke backend lokal ditolak browser. Perbaikan: arahkan fetch ke `"/api"` dan pasang `server.proxy` (browser melihat domain sama).
- **Menulis env non-`VITE_` — tidak terbaca** — kode baca `import.meta.env.API_BASE` tapi bernilai `undefined` karena tidak diawali `VITE_`. Perbaikan: awali semua variabel publik dengan `VITE_`; sisanya (secret backend) tidak perlu masuk JS klien.
- **Menghapus `.gitignore` atau commit `node_modules`/`dist`** — repo membengkak dan build di CI menimbang file hasil. Perbaikan: pastikan `.gitignore` berisi `node_modules`, `dist`, `.env*` (kecuali `.env.example`).
- **Deploy path error (dist tidak ditemukan)** — menjalankan `npm run build` di folder yang salah atau direktori publish yang diset keliru di provider (materi 38) → Netlify/Vercel error. Perbaikan: verifikasi dengan `npm run build && npm run preview` lokal sebelum deploy, cocokkan `publish`/`buildCommand` dengan struktur nyata.

## 8. Mini Project / Soal Latihan & Kunci Jawaban

### Tantangan

1. Pindahkan project perpustakaan (dari materi 34-36: modul + lazy load + modal aksesibel) ke **Vite**: `npm create vite@latest`, salin `src/modules/*` ke project baru, pindahkan `index.html` dan CSS, buat berfungsi di `npm run dev`. Lalu jalankan `npm run build` dan `npm run preview` — pastikan aplikasi berjalan penuh di preview.
2. Latihan lanjutan: atur `vite.config.js` dengan `server.proxy` (misal `/api` → `http://localhost:8000`), tambahkan `.env` (`VITE_API_BASE`) yang dipakai `api.js`, dan ukur isi `dist/` (file apa saja, ukurannya) sebelum dan sesudah memisahkan satu library ke `manualChunks`.

**Pembahasan**: Tantangan 1 selesai ketika `npm run preview` menampilkan aplikasi yang berfungsi penuh — artinya build berhasil menggabung semua modul, CSS ikut ter-bundle (dari `import "./style.css"`), gambar/asset publik ikut disalin, dan tidak ada path yang patah. Jika ada JS lama yang memakai `window` global di modul, pastikan tidak ada yang mengandalkan `<script>` urutan manual; semua data lewat state (materi 34). Untuk latihan 2, `manualChunks` memisahkan "vendor" (library pihak ketiga) dari "kode sendiri" sehingga peramban bisa meng-cache library lama walaupun kode aplikasi di-update — buktinya terlihat dari dua file (main kecil + vendor besar) di dalam `dist/assets/`. Proxy `/api` di config membuat mode dev bebas CORS; saat `npm run build` dijalankan, `VITE_API_BASE` dari `.env.production` (jika dideklarasikan) dipakai oleh `api.js` via `import.meta.env`. Semua itu sekarang siap: buat `dist/` (bundle final) lalu lanjut ke materi 38 untuk meletakkannya di Netlify/Vercel.
