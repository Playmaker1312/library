# 75. Setup Database untuk Integration Test

## Penjelasan

Integration testing berbeda fundamental dari unit testing. Jika unit test mengisolasi komponen dengan mock, integration test justru menguji komponen dengan dependency nyata — terutama database. Tujuan utamanya adalah memverifikasi bahwa kode repository (seperti `PrismaBooksRepository`) benar-benar bisa berkomunikasi dengan database, menjalankan query SQL, mengembalikan data, dan menangani error koneksi. Untuk mencapai ini, kita membutuhkan database testing yang terpisah dari database development dan production.

Setup database untuk integration test memerlukan beberapa komponen: (1) file `.env.test` yang berisi konfigurasi database terpisah, (2) script migrasi yang menjalankan schema sebelum test dimulai, (3) konfigurasi Jest khusus e2e/integration (`jest-e2e.config.ts`), dan (4) utility untuk membuat dan menghapus data test (test fixtures). Best practice adalah menggunakan database PostgreSQL yang benar-benar berjalan (bisa local, bisa Docker) atau menggunakan pendekatan in-memory seperti `pg-mem` untuk test yang lebih cepat, meskipun kurang realistis.

Salah satu keputusan penting adalah apakah akan menggunakan transaksi rollback atau pembersihan manual antar test. Pendekatan transaksi — setiap test dibungkus dalam transaksi yang di-rollback di akhir — lebih cepat dan tidak meninggalkan data sampah. Namun, pendekatan ini tidak bisa mendeteksi masalah komit transaksi. Pendekatan alternatif adalah menjalankan migration sebelum semua test, lalu membersihkan tabel (TRUNCATE) di antara test suite. Pendekatan kedua lebih realistik karena mensimulasikan operasi database yang sesungguhnya. Untuk project NestJS dengan Prisma, kita bisa menggunakan `prisma migrate reset` sebelum test dan `prisma db push` untuk sinkronisasi schema.

## Fungsi

- Menyediakan environment database terisolasi khusus testing
- Menjalankan migrasi schema database sebelum test dieksekusi
- Membersihkan data test antar sesi pengujian
- Mengkonfigurasi PrismaClient atau TypeORM untuk koneksi test
- Memisahkan konfigurasi integration test dari unit test
- Menyediakan utility/fixtures untuk data test yang reusable

## Cara Implementasi / Code

### 1. `.env.test` — Environment Variable untuk Testing

```bash
# .env.test
# Database terpisah — jangan pernah memakai database production!
DATABASE_URL="postgresql://test_user:test_pass@localhost:5432/library_test"

# Redis terpisah (jika diperlukan)
REDIS_URL="redis://localhost:6379/1"

# JWT Secret untuk testing
JWT_ACCESS_SECRET="test-access-secret-do-not-use-in-prod"
JWT_REFRESH_SECRET="test-refresh-secret-do-not-use-in-prod"
JWT_ACCESS_EXPIRATION="15m"
JWT_REFRESH_EXPIRATION="7d"

# Environment
NODE_ENV="test"

# Nonaktifkan logging Prisma untuk mengurangi noise
DATABASE_LOGGING="false"
```

### 2. `jest-e2e.config.ts` — Config untuk Integration/E2E Test

```typescript
// test/jest-e2e.config.ts
import type { Config } from 'jest';

const config: Config = {
  moduleFileExtensions: ['js', 'json', 'ts'],
  rootDir: '../',
  testEnvironment: 'node',
  testRegex: '.*\\.(spec|e2e-spec)\\.ts$',
  testPathPattern: ['test/'],
  transform: {
    '^.+\\.(t|j)s$': 'ts-jest',
  },
  setupFilesAfterSetup: ['<rootDir>/test/setup-e2e.ts'],
  globalSetup: '<rootDir>/test/global-setup.ts',
  globalTeardown: '<rootDir>/test/global-teardown.ts',
  moduleNameMapper: {
    '^@/(.*)$': '<rootDir>/src/$1',
  },
  coverageDirectory: './coverage-e2e',
  coverageReporters: ['text', 'lcov'],
  collectCoverageFrom: [
    '**/(repository|controller|service|guard|filter|interceptor)/*.ts',
  ],
  verbose: true,
  maxWorkers: 2,
  testTimeout: 60000, // Integration test butuh waktu lebih lama
  forceExit: true,    // Pastikan proses keluar setelah test selesai
};

export default config;
```

### 3. `test/global-setup.ts` — Setup Sebelum Semua Test

```typescript
// test/global-setup.ts
import { config } from 'dotenv';
import { execSync } from 'child_process';
import * as path from 'path';

export default async function globalSetup() {
  // Load environment test variables
  config({ path: path.resolve(__dirname, '../.env.test') });
  process.env.NODE_ENV = 'test';

  console.log('\n🔧 Global Setup: Preparing test database...');

  try {
    // Jalankan migrasi database untuk testing
    execSync('npx prisma migrate deploy', {
      cwd: path.resolve(__dirname, '..'),
      env: { ...process.env, DATABASE_URL: process.env.DATABASE_URL },
      stdio: 'inherit',
    });

    console.log('✅ Migration complete');

    // Seed data dasar untuk test (jika diperlukan)
    execSync('npx prisma db seed', {
      cwd: path.resolve(__dirname, '..'),
      env: { ...process.env },
      stdio: 'inherit',
    });

    console.log('✅ Seed data complete');
  } catch (error) {
    console.error('❌ Global setup failed:', error.message);
    throw error;
  }
}
```

### 4. `test/global-teardown.ts` — Cleanup Setelah Semua Test

```typescript
// test/global-teardown.ts
import { execSync } from 'child_process';
import * as path from 'path';

export default async function globalTeardown() {
  console.log('\n🧹 Global Teardown: Cleaning test database...');

  try {
    // Drop semua data setelah test selesai
    execSync('npx prisma migrate reset --force', {
      cwd: path.resolve(__dirname, '..'),
      env: { ...process.env },
      stdio: 'inherit',
    });

    console.log('✅ Test database cleaned');
  } catch (error) {
    console.error('⚠️  Teardown warning:', error.message);
    // Jangan throw error di teardown agar laporan test tetap muncul
  }
}
```

### 5. `test/setup-e2e.ts` — Setup Per-Suite

```typescript
// test/setup-e2e.ts
import { PrismaClient } from '@prisma/client';

// PrismaClient singleton untuk semua test
const prisma = new PrismaClient();

beforeAll(async () => {
  // Verifikasi koneksi database sebelum test dimulai
  await prisma.$connect();
  console.log('📦 Database connected for integration tests');
});

afterAll(async () => {
  await prisma.$disconnect();
  console.log('📦 Database disconnected');
});

export { prisma };
```

### 6. Docker Compose untuk Database Test

```yaml
# docker-compose.test.yml
version: '3.8'

services:
  postgres-test:
    image: postgres:16-alpine
    container_name: library-db-test
    environment:
      POSTGRES_USER: test_user
      POSTGRES_PASSWORD: test_pass
      POSTGRES_DB: library_test
    ports:
      - '5433:5432'  # Port 5433 agar tidak conflict dengan database development
    tmpfs: /var/lib/postgresql/data  # Data hilang setelah container stop
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U test_user -d library_test']
      interval: 5s
      timeout: 5s
      retries: 5

  redis-test:
    image: redis:7-alpine
    container_name: library-redis-test
    ports:
      - '6380:6379'  # Port terpisah dari Redis development
    tmpfs: /data
```

### 7. Script di `package.json`

```json
{
  "scripts": {
    "test:integration": "docker compose -f docker-compose.test.yml up -d && pnpm test:e2e && docker compose -f docker-compose.test.yml down",
    "test:e2e": "jest --config ./test/jest-e2e.config.ts",
    "test:db:setup": "npx prisma migrate deploy",
    "test:db:reset": "npx prisma migrate reset --force",
    "pretest:e2e": "npx prisma migrate deploy"
  }
}
```

### 8. Menjalankan Integration Test


## Analogi

Bayangkan perpustakaan ingin menguji **sistem katalog digital barunya**. Daripada menguji dengan "buku kertas palsu" (mock), mereka memutuskan untuk menguji dengan **database buku sungguhan** tapi di ruangan yang terpisah — sebuah **perpustakaan mini (test database)** yang hanya digunakan untuk pengujian. Perpustakaan mini ini memiliki buku-buku sungguhan (data test) yang ditata rapi menggunakan sistem yang sama dengan perpustakaan utama (migrasi database). Setelah pengujian selesai, semua buku di perpustakaan mini dikembalikan dan rak-rak dibersihkan (teardown). Dengan cara ini, staf perpustakaan yakin bahwa sistem katalog digital benar-benar berfungsi dengan data nyata, tanpa risiko mengacaukan koleksi utama.

## Penggunaan

- Digunakan sebelum menulis integration test untuk memastikan database test tersedia
- Dipakai di pipeline CI dengan menggunakan service container GitHub Actions
- Memisahkan data test dari data development untuk menghindari kontaminasi
- Menyediakan lingkungan test yang konsisten di semua mesin developer
- Mengotomatiskan migrasi dan seeding database test

## Kesalahan Umum yang Sering Terjadi

1. **Menggunakan database development untuk testing**: Data development bisa terhapus, atau test menggunakan data development yang tidak terkontrol. Solusi: selalu gunakan database terpisah dengan URL berbeda di `.env.test`.

2. **Port conflict**: Database test menggunakan port yang sama dengan database development, menyebabkan service tidak bisa jalan bersamaan. Solusi: gunakan port berbeda (5433 untuk test, 5432 untuk development).

3. **Lupa menjalankan migrasi sebelum test**: Test gagal karena tabel belum ada. Solusi: gunakan `globalSetup` atau `pretest` script untuk otomatisasi migrasi.

4. **Data test tidak dibersihkan**: Data dari test sebelumnya masih ada dan mempengaruhi hasil test berikutnya. Solusi: gunakan `beforeEach` untuk truncate tabel atau gunakan transaksi rollback.

5. **Test timeout karena koneksi lambat**: Integration test butuh waktu lebih lama untuk koneksi database. Solusi: set `testTimeout: 60000` di Jest config.

6. **ForceExit tidak diset**: Proses Jest tidak keluar setelah test selesai karena koneksi Prisma masih terbuka. Solusi: set `forceExit: true` di Jest config dan pastikan `$disconnect()` dipanggil di `afterAll`.

## Hubungan dengan Materi Sebelumnya

Di file 70-74, kita melakukan unit testing dengan mock untuk menguji logika bisnis secara terisolasi. Sekarang di file 75, kita menyiapkan infrastruktur untuk integration test yang menggunakan database nyata. Ini adalah langkah maju dalam piramida testing: dari unit test (cepat, banyak, murah) menuju integration test (sedang, lebih realistis). Database test yang kita siapkan di sini akan langsung digunakan di file 76 untuk menguji `PrismaBooksRepository`. Ke depannya, database yang sama juga akan digunakan untuk e2e test di file 77-79. Pipeline CI di file 80 akan menggunakan Docker container atau service GitHub Actions untuk menyediakan database test secara otomatis.
