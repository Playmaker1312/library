# 11. Type Guards — Mempersempit Tipe Saat Runtime

> 🔵 **Level 2 — Bagian E** | 🧩 **Melanjutkan [[10. Optional Chaining dan Nullish Coalescing — Handle Nilai Null dengan Aman]]**

---

## 1. Penjelasan Singkat & Konsep Dasar

**Type guard** adalah mekanisme TypeScript untuk mengubah *tebakan tipe di compile-time* berdasarkan *fakta runtime*. Saat union `string | number | null`, TypeScript belum tahu nilai sebenarnya — sampai kita membuktikannya lewat kondisi. Proses "mempersempit" ini disebut **type narrowing** (sudah disinggung di materi 6).

Ada beberapa teknik type guard:

```text
typeof    →  typeof x === "string"
in        →  "lokasi" in buku            (cek keberadaan property)
instanceof→  error instanceof NotFoundError   (cek class)
discriminated union →  switch (buku.tipe)  (cek nilai literal 'tipe'/'kind')
is        →  user-defined type guard:     function x(y): y is Tipe
```

**Konsep penting**: 
- *Discriminated union* adalah pola antara dua (atau lebih) union member yang memiliki **field literal yang sama** (biasanya `type` / `kind` / `tipe`) — dan TypeScript mempersempit berdasarkan nilai field itu.
- *User-defined type guard* (`value is X`) memungkinkan kamu membuat fungsi validasi yang sekaligus "menyimpulkan" tipe untuk compiler.

**Benang merah**: materi 5-10 telah menangani null/undefined. Materi 11 adalah *puncak Level 2* — alat yang akan membawa kita ke model data yang kompleks (`BukuFisik`/`BukuDigital`) dan dipakai terus (validasi Zod memakai prinsip yang sama — "cegah sebelum masuk").

---

## 2. Fungsi & Kegunaan Utama

- **Mengautentikasi tipe union** sebelum mengakses properti khusus masing-masing anggota.
- **Discriminated union** menjadi fondasi untuk state machine yang aman (`loading | success | error`), event handling, dan form states.
- **`instanceof`** untuk membedakan error/exception class (impian untuk error handling di materi 21).
- **User-defined type guard** untuk validasi eksternal (data dari API, `unknown`) yang reusable dan type-aware.
- **Exhaustive checking** (default `never`) memaksa semua kasus dinegosiasikan — mencegah "lupa case" saat menambah anggota union.

## 3. Contoh Kode & Implementasi (Real-world Example)

```typescript
// src/utils/type-guards.ts

// ─── Model: Buku bisa fisik atau digital (discriminated union) ─────────
interface Buku {
    id: number;
    judul: string;
    harga: number;
    tipe: string;              // discriminator
}

interface BukuFisik {
    tipe: "fisik";
    lokasi: string;
    berat: number;
}

interface BukuDigital {
    tipe: "digital";
    formatFile: "PDF" | "EPUB";
    ukuranMB: number;
}

type ItemKoleksi = BukuFisik | BukuDigital;

// ─── 1. typeof guard — untuk primitif ────────────────────────────────
function prosesId(id: number | string): string {
    if (typeof id === "number") {
        return `#${id.toString().padStart(5, "0")}`;  // di sini: number
    }
    return id.trim().toUpperCase();                    // di sini: string
}

// ─── 2. in operator guard — cek keberadaan property ─────────────────
function tampilkanLokasi(buku: ItemKoleksi): string {
    if ("lokasi" in buku) {
        return `Fisik di rak ${buku.lokasi} (${buku.berat} gr)`;  // BukuFisik
    }
    return `Digital ${buku.formatFile} (${buku.ukuranMB} MB)`;    // BukuDigital
}

// ─── 3. discriminated union — PAKAI ini untuk union kompleks ─────────
function infoBuku(buku: ItemKoleksi): string {
    switch (buku.tipe) {
        case "fisik":
            return `Fisik: ${buku.lokasi}`;          // di sini: BukuFisik
        case "digital":
            return `Digital: ${buku.formatFile}`;    // di sini: BukuDigital
        default:
            return assertNever(buku);                // exhaustive check
    }
}

function assertNever(nilai: never): never {
    throw new Error(`Nilai tidak terduga: ${JSON.stringify(nilai)}`);
}

// ─── 4. instanceof guard — untuk class/errors ───────────────────────
class ValidationError extends Error {
    constructor(public field: string, message: string) {
        super(message);
    }
}

class DatabaseError extends Error {
    constructor(public query: string, message: string) {
        super(message);
    }
}

function tangani(error: unknown): string {
    if (error instanceof ValidationError) {
        return `Validasi gagal pada ${error.field}: ${error.message}`;
    }
    if (error instanceof DatabaseError) {
        return `DB error saat query ${error.query}: ${error.message}`;
    }
    if (error instanceof Error) {
        return `Error: ${error.message}`;
    }
    return "Kesalahan tidak diketahui";
}

// ─── 5. user-defined type guard (is) — validasi reusable ─────────────
function adalahBukuDigital(buku: ItemKoleksi): buku is BukuDigital {
    return buku.tipe === "digital";
}

function prosesKoleksi(koleksi: ItemKoleksi[]): string[] {
    return koleksi
        .filter(adalahBukuDigital)                    // TypeScript tahu sisanya BukuDigital
        .map(b => `Download ${b.formatFile}`);
}

console.log(prosesKoleksi([
    { tipe: "digital", formatFile: "PDF", ukuranMB: 8 },
    { tipe: "fisik", lokasi: "A-3", berat: 250 },
]));
// → ["Download PDF"]
```

## 4. Analogi Sederhana

**Sistem Perpustakaan.**

- **`typeof`** = **pustakawan mengecek jenis barang**: "ini angka atau teks?" — untuk identificasi primitif.
- **`in`** = **petugas melihat simplan fisik**: "apakah ada label 'lokasi' di kartu ini?" Jika ada → kartu buku fisik; jika tidak → digital.
- **Discriminated union + `switch`** = **form berlabel "Tipe" yang wajib diisi**: "Fisik" atau "Digital". Petugas langsung mengeluarkan langkah yang benar per tipe; jika suatu hari ada tipe baru yang belum diatur, *default* melempar error *("rani belum pernah melihat kartu jenis itu")* — sistem *memaksa* semua varian ditangani.
- **`instanceof`** = **petugas yang mengenali "keluarga error"** — sama seperti mengenali kartu mahasiswa vs kartu pegawai dari structurnya.
- **User-defined guard (`is`)** = **penyortir buku otomatis yang kamu latih**: berikan fungsi "apakah ini digital?" — dan setiap kertas yang lolos fungsi itu dianggap digital seterusnya oleh seluruh sistem (compiler ikut "percaya").

---

## 5. Kapan Harus Digunakan (Use Cases)

- **Discriminated union**: state machine (fetch, form, wizard), model status platform (`"draft" | "published"`), union-entity (BukuFisik/BukuDigital).
- **`typeof`**: primitif (string/number/boolean) — validasi input.
- **`in`**: union antar object yang *tidak* punya field literal pembeda (fallback bila discriminated tak bisa).
- **`instanceof`**: hierarki error class, manipulasi DOM element (`instanceof HTMLInputElement`), perbedaan tipe `Date`.
- **User-defined guard (`is`)**: validasi `unknown` dari API/parsing, fungsi yang mengecek bentuk object (prinsip Zod di Level 5), filter yang "menyimpan" tipe sempit.
- **Exhaustive `never` default**: setiap switch pada discriminated union.

---

## 6. Poin-poin Penting & Best Practices

1. **Discriminated union > `in`** untuk union yang sudah punya field literal — lebih tegas & kaya info.
2. **Selalu berikan default `assertNever`** pada switch union — menjamin *exhaustiveness* saat union bertambah.
3. **`is` guard harus berpredikat => implikasinya benar**: predikat dan tipe yang diklaim harus konsisten. `buku is BukuDigital` *hanya* dijalankan bila `buku.tipe === "digital"` — jangan kebenaran tidak sinkron.
4. **Gunakan `instanceof` untuk errors**, lalu rapikan hierarki di materi 21 (`AppError`).
5. **`in` lebih cocok & aman pada union object** daripada `typeof` (yang tidak valid untuk object).
6. **Keys for clean guards**: filter/map yang memakai guard `is` menghasilkan tipe yang lebih presisi tanpa `as`.

---

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

| Kesalahan | Contoh | Akibat | Perbaikan |
|---|---|---|---|
| `switch` tanpa `default` + never | lupa handle case baru | varian baru senyap | default dengan assertNever |
| Guard `is` yang salah | `return buku.tipe !== "digital"` di `buku is BukuDigital` | salah klasifikasi | samakan predikat dengan tipe klaim |
| `in` untuk primitif | `"length" in "abc"` (string dipakai objek) | hasil meleset | pakai `typeof` untuk primitif |
| `instanceof` pada interface | `x instanceof interface` | interface bukan class → tidak valid | beri class / use guard |
| Casting dulu baru guard | `(x as BukuFisik).lokasi` tanpa verifikasi | crash ketika salah tipe | guard dulu baru akses |
| Menumpuk guard dalam dan berbelit | if/else 5 level | sulit dibaca | ganti dengan switch / early return |

## 8. Soal Latihan & Kunci Jawaban

### Soal 1
Diberikan model berikut, buat fungsi `ringkas(koleksi: ItemKoleksi): string` yang memakai **discriminated union** dan default `assertNever` — sehingga saat kamu menambah tipe `"audio"` namun lupa menangani, TypeScript *melempar error compile-time*.

```typescript
type ItemKoleksi =
    | { tipe: "fisik"; lokasi: string }
    | { tipe: "digital"; format: string };
```

### Soal 2
Buat user-defined type guard `adalahBuku` yang menerima `unknown` dan mengembalikan `buku is Buku` (dengan `Buku` berisi `id: number`, `judul: string`). Gunakan di `prosesBukuUser(unknownData: unknown): string`.

---

### Jawaban & Pembahasan

```typescript
// Soal 1
type ItemKoleksi =
    | { tipe: "fisik"; lokasi: string }
    | { tipe: "digital"; format: string };

function assertNever(nilai: never): never {
    throw new Error(`Tipe tak terduga: ${JSON.stringify(nilai)}`);
}

function ringkas(koleksi: ItemKoleksi): string {
    switch (koleksi.tipe) {
        case "fisik":   return `Buku fisik di rak ${koleksi.lokasi}`;
        case "digital": return `Buku digital (${koleksi.format})`;
        default:        return assertNever(koleksi);
    }
}

// Jika nanti ditambah { tipe: "audio"; durasi: number },
// TS di `default` akan error: objek bertipe never → pengingat untuk menambah case.
```

**Pembahasan**: string literal `tipe` membuat TypeScript mampu mempersempit per case; default memanggil `assertNever` sehingga ketika union bertambah dan case belum ditulis, kompiler *menolak*.

```typescript
// Soal 2
interface Buku { id: number; judul: string; }

function adalahBuku(value: unknown): value is Buku {
    return (
        typeof value === "object" && value !== null &&
        "id" in value && typeof (value as { id: unknown }).id === "number" &&
        "judul" in value && typeof (value as { judul: unknown }).judul === "string"
    );
}

function prosesBukuUser(data: unknown): string {
    if (adalahBuku(data)) {
        return `Buku "${data.judul}" (id: ${data.id})`; // TS: data dianggap Buku
    }
    return "Data bukan buku";
}

console.log(prosesBukuUser({ id: 1, judul: "Clean Code" })); // "Buku \"Clean Code\" (id: 1)"
console.log(prosesBukuUser({ id: "satu", judul: "x" }));     // "Data bukan buku"
```

**Pembahasan**: fungsi `adalahBuku` mengecek bentuk object secara runtime, dan karena return type-nya `value is Buku`, TypeScript menyempitkan `data` menjadi `Buku` di dalam `if` — tanpa satu pun `as` di kode pemanggil. Inilah prinsip dasar yang nantinya dieksekusi lebih canggih oleh library Zod (Level 5).
