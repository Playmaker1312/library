# 6. Setup Git dan Konvensi Commit

## Penjelasan

Git adalah *version control system* yang melacak setiap perubahan kode. `create-vue` sudah otomatis menjalankan `git init` saat membuat project, jadi repository Git sudah aktif. Namun kita perlu setup remote, membuat commit pertama yang bersih, dan mengotomatisasi quality checks sebelum commit dengan **Husky** dan **lint-staged**.

**Konvensi commit** (Conventional Commits) adalah standar penulisan pesan commit yang membuat riwayat project mudah dibaca dan bisa di-automasi (changelog, semantic versioning).

## Fungsi

| Tool / Konsep | Fungsi |
|---------------|--------|
| Git | Melacak perubahan, kolaborasi tim, rollback jika error |
| Remote (GitHub/GitLab) | Backup kode, code review via Pull Request, CI/CD |
| Konvensi commit | Riwayat commit terstruktur: `feat:`, `fix:`, `chore:`, dll |
| Husky | Menjalankan script otomatis sebelum commit (`pre-commit hook`) |
| lint-staged | Menjalankan linter hanya pada file yang akan di-commit |

## Cara Implementasi

### 1. Cek Status Git

```bash
git status
git log --oneline
```

Jika project dibuat dengan `create-vue`, seharusnya sudah ada commit awal "init".

### 2. Setup Remote (GitHub)

```bash
# Buat repository baru di GitHub (via browser atau gh CLI)
gh repo create bookstore-ui --public --source=. --remote=origin

# Atau manual:
git remote add origin https://github.com/username/bookstore-ui.git
```

### 3. Commit Awal Project yang Sudah Dibersihkan

```bash
git add .
git commit -m "chore: initial project setup with Vue 3, TypeScript, Tailwind

- Scaffold project with create-vue
- Clean boilerplate and restructure folders
- Setup Tailwind CSS v4
- Configure ESLint, Prettier, and path alias
- Add common project folders (components, composables, types, utils)"
```

### 4. Push ke Remote

```bash
git push -u origin main
# atau jika branch bernama master:
git push -u origin master
```

### 5. Install Husky

```bash
npm install -D husky lint-staged

# Init Husky
npx husky init

# Setelah perintah di atas, folder .husky/ akan terbuat
# File .husky/pre-commit akan terisi otomatis
```

### 6. Setup lint-staged di `package.json`

Tambahkan konfigurasi lint-staged:

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vue-tsc && vite build",
    "lint": "eslint . --ext .vue,.ts --fix",
    "format": "prettier --write src/",
    "lint-staged": "lint-staged"
  },
  "lint-staged": {
    "*.{ts,vue}": [
      "eslint --fix",
      "prettier --write"
    ],
    "*.{css,json,md}": [
      "prettier --write"
    ]
  }
}
```

### 7. Update File `.husky/pre-commit`

```bash
npx lint-staged
```

(Husky akan otomatis menjalankan `npx lint-staged` setiap kali ada `git commit`)

### 8. Konvensi Commit

Gunakan format berikut:

```
<type>: <deskripsi singkat>

<opsional: deskripsi panjang>
```

| Type | Kapan Dipakai | Contoh |
|------|---------------|--------|
| `feat:` | Fitur baru | `feat: add book search component` |
| `fix:` | Perbaikan bug | `fix: fix price calculation on cart` |
| `style:` | Perubahan styling (CSS) | `style: update button hover color` |
| `refactor:` | Refactor kode (tanpa ubah behavior) | `refactor: extract fetch logic to composable` |
| `test:` | Menambah/mengubah test | `test: add unit test for BookCard` |
| `chore:` | Tugas maintenance | `chore: update dependencies` |
| `docs:` | Dokumentasi | `docs: update README with setup guide` |

## Analogi: Toko Buku

Git seperti **buku inventaris toko** — setiap kali ada perubahan (buku baru masuk, harga diubah, rak dipindah), semuanya dicatat: siapa yang mengubah, kapan, dan kenapa. Kalau ada masalah (misal, harga jadi kacau), kita bisa melihat catatan dan mengembalikan ke kondisi sebelumnya.

**Husky** adalah **satpam toko** yang memeriksa semua barang sebelum masuk gudang — memastikan tidak ada yang salah. **lint-staged** adalah petugas yang hanya memeriksa barang yang baru datang (file yang diubah), bukan seluruh gudang.

**Konvensi commit** adalah format standar pencatatan di buku inventaris — bukan "perubahan hari ini", tapi "`feat: tambah fitur pencarian buku`" atau "`fix: perbaiki bug harga diskon`". Jelas, terstruktur, dan mudah dicari.

## Dipakai Untuk Apa

- **Semua project software**: Git adalah standar industri. Tidak ada alasan tidak pakai Git.
- **CI/CD**: Github Actions atau GitLab CI membaca pesan commit untuk menentukan versi (major/minor/patch) otomatis.
- **Changelog generation**: Tools seperti `standard-version` generate CHANGELOG.md otomatis dari commit messages.
- **Team collaboration**: Pull Request, code review, issue tracking — semua terintegrasi dengan Git.
- **Disaster recovery**: Hapus kode penting? `git revert` atau `git checkout` bisa selamatkan.

## Kesalahan Umum

| Kesalahan | Dampak | Cara Hindari |
|-----------|--------|--------------|
| Pesan commit tidak deskriptif ("update", "fix", "perubahan") | Sulit追踪 perubahan | Ikuti konvensi: `feat:`, `fix:`, dll, dengan deskripsi jelas |
| Commit terlalu besar (100 file, 50 fitur) | Sulit di-review, sulit di-revert | Commit kecil dan fokus: 1 fitur = 1 commit |
| Lupa `git pull` sebelum `git push` | Conflict, reject | Selalu `git pull --rebase` sebelum push |
| Husky menghalangi commit padahal cuma format error | Frustrasi | Fix sesuai pesan error, atau `git commit --no-verify` untuk bypass (tapi jangan biasakan) |
| Commit langsung ke `main` | Branch main jadi kotor | Gunakan branch fitur: `git checkout -b feat/search-books` |
| Tidak ada `.gitignore` atau file besar ikut ter-commit | Repo membengkak | Cek `.gitignore` sudah dari create-vue. Tambahkan `node_modules/`, `.env`, `dist/` |

## Hubungan dengan Materi Sebelumnya

Ini adalah **poin terakhir** dari bagian A (Inisialisasi Project). Semua setup dari poin 1-5 sekarang diamankan dengan Git:

- **Poin 1**: Project dibuat → dicatat Git
- **Poin 2**: Struktur dipahami → dokumentasi mental
- **Poin 3**: Boilerplate dibersihkan → di-commit sebagai "chore: clean boilerplate"
- **Poin 4**: Tailwind di-setup → di-commit sebagai "feat: add Tailwind CSS"
- **Poin 5**: ESLint + Prettier + Path alias → di-commit

Dengan Git, setiap langkah bisa di-revert jika ada kesalahan. Dan dengan Husky, kualitas kode terjaga otomatis.

## Soal Latihan

**Soal 1:** Apa perbedaan antara `feat:`, `fix:`, dan `chore:` dalam konvensi commit? Berikan contoh masing-masing untuk project BookStore!

**Jawaban:**
- **`feat:`** — Fitur baru yang ditambahkan ke aplikasi.
  - Contoh: `feat: add book search by title and author`
  - Contoh: `feat: implement shopping cart checkout flow`
- **`fix:`** — Perbaikan bug.
  - Contoh: `fix: fix price calculation when discount applied`
  - Contoh: `fix: resolve 404 error on book detail page`
- **`chore:`** — Tugas maintenance yang tidak mengubah kode produksi.
  - Contoh: `chore: update vue-router to v4.3`
  - Contoh: `chore: configure husky and lint-staged`

**Soal 2:** Seorang teman melakukan `git commit -m "update"` dan langsung push ke branch `main`. Kemudian ternyata ada bug di production dan tim harus mencari perubahan apa yang menyebabkan bug. Mengapa commit "update" menyulitkan? Bagaimana seharusnya?

**Jawaban:**
Pesan "update" sangat ambigu — tidak jelas apa yang diubah: apakah fitur baru? perbaikan? refactor? Tim harus membuka diff satu per satu untuk mencari tahu. Jika ada 5 commit dengan pesan "update" dalam sehari, mencari penyebab bug seperti mencari jarum di tumpukan jerami.

Seharusnya:
```
git commit -m "fix: correct tax calculation on international orders

Previously, tax for international orders used domestic rate.
Now uses the country-specific tax rate from the shipping address."
```

Dengan pesan seperti ini, tim langsung tahu:
1. **Type**: `fix:` — ini perbaikan bug.
2. **Deskripsi**: "correct tax calculation on international orders" — area yang diubah.
3. **Body**: Penjelasan kenapa terjadi dan bagaimana memperbaikinya.

Jika commit ini yang menyebabkan bug, tim langsung fokus ke kode terkait pajak internasional, bukan mencari di seluruh codebase.
