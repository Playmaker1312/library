# 39. Repository dan Service Pattern — Arsitektur yang Maintainable

## Penjelasan

Untuk aplikasi yang kompleks, letakkan logika di controller langsung akan membuat "fat controller". Solusinya: pisahkan tanggung jawab ke pattern yang lebih terstruktur:

1. **Repository Pattern** — akses data (query database) dipisahkan dari business logic
2. **Service Layer** — business logic yang tidak bergantung pada framework
3. **Action Pattern** — satu class, satu tanggung jawab (Single Responsibility)

**Struktur Direktori yang Direkomendasikan:**
```
app/
├── Actions/
│   ├── PinjamBukuAction.php
│   ├── KembalikanBukuAction.php
│   └── DaftarkanAnggotaAction.php
├── Repositories/
│   ├── Contracts/
│   │   └── BukuRepositoryInterface.php
│   └── Eloquent/
│       └── EloquentBukuRepository.php
└── Services/
    └── PeminjamanService.php
```

## Fungsi

- **Repository**: memisahkan logika database dari business logic
- **Service**: business logic yang reusable dan testable
- **Action**: satu class melakukan satu hal spesifik
- **Tipis Controller**: controller hanya menerima request, panggil action/service, kirim response

## Cara Pengimplementasian

```php
<?php
// app/Actions/PinjamBukuAction.php

namespace App\Actions;

use App\Models\Peminjaman;
use App\Repositories\Contracts\BukuRepositoryInterface;
use App\Repositories\Contracts\AnggotaRepositoryInterface;
use App\Repositories\Contracts\PeminjamanRepositoryInterface;
use App\Events\BukuDipinjam;
use Illuminate\Support\Facades\DB;

class PinjamBukuAction
{
    public function __construct(
        private BukuRepositoryInterface       $bukuRepo,
        private AnggotaRepositoryInterface    $anggotaRepo,
        private PeminjamanRepositoryInterface $peminjamanRepo,
    ) {}

    public function execute(int $bukuId, int $anggotaId): Peminjaman
    {
        $buku    = $this->bukuRepo->findById($bukuId);
        $anggota = $this->anggotaRepo->findById($anggotaId);

        // Business logic validation
        if (!$buku->tersedia()) {
            throw new \DomainException('Buku tidak tersedia.');
        }

        if ($anggota->peminjamanAktif()->count() >= $anggota->getBatasPinjam()) {
            throw new \DomainException('Batas peminjaman tercapai.');
        }

        if ($anggota->memilikiDenda()) {
            throw new \DomainException('Ada denda yang belum dibayar.');
        }

        // Transaction
        return DB::transaction(function () use ($buku, $anggota) {
            $this->bukuRepo->kurangiStok($buku->id);

            $peminjaman = $this->peminjamanRepo->create([
                'buku_id'        => $buku->id,
                'anggota_id'     => $anggota->id,
                'tanggal_pinjam' => now()->toDateString(),
                'batas_kembali'  => now()->addDays(14)->toDateString(),
            ]);

            event(new BukuDipinjam($peminjaman));

            return $peminjaman;
        });
    }
}
```

        }
    }

## Analogi

Pattern ini seperti **organisasi perpustakaan yang terstruktur**:

- **Controller** = **Meja depan** — terima permintaan, arahkan ke bagian yang tepat. Tidak melakukan pekerjaan berat sendiri.

- **Action** = **Prosedur standar** — "Prosedur peminjaman: cek stok → cek anggota → catat peminjaman → kirim notifikasi". Satu prosedur, satu tanggung jawab.

- **Repository** = **Gudang penyimpanan** — tahu persis di mana buku disimpan, bagaimana mengambilnya (via database, API, file). Bagian lain tidak perlu tahu cara penyimpanan.

- **Service** = **Layanan perpustakaan** — "Layanan peminjaman: pinjam, kembalikan, hitung denda". Kumpulan prosedur yang terkait.

**Tanpa pattern (fat controller):**
```php
class PeminjamanController extends Controller
{
    public function store(Request $request) {
        // 50 baris: validasi, cek stok, cek anggota, buat peminjaman,
        // kurangi stok, kirim email, catat log, update statistik...
    }
}
```

**Dengan pattern (tipis controller):**
```php
class PeminjamanController extends Controller
{
    public function store(Request $request) {
        // 5 baris: terima request, panggil action, kirim response
    }
}
```

## Dipakai untuk Apa

- **Aplikasi menengah-besar** — >20 controller dengan logika yang kompleks
- **Tim development** — pembagian tugas yang jelas
- **Testing** — setiap class punya tanggung jawab yang terisolasi
- **API** — response yang konsisten dengan error handling yang terpusat

## Kesalahan Umum

1. **Over-engineering** — untuk aplikasi kecil (5 controller), pattern ini berlebihan
2. **Action terlalu kecil** — 1 method per file terasa berlebihan. Gunakan service untuk yang masih terkait
3. **Repository hanya "pass-through"** — jika hanya memanggil Eloquent tanpa logika tambahan, mungkin tidak perlu
4. **Controller masih fat** — jika controller masih >20 baris setelah pindah logika, ada yang salah
5. **Terlalu banyak layer** — Controller → Service → Repository → Model → Database — kadang 2-3 layer cukup

## Koneksi dengan Materi Sebelumnya

Poin 37 (Service Container) menyediakan DI untuk pattern ini. Poin 36 (Mocking) — interface repository memudahkan mocking. Semua materi sebelumnya (Eloquent, Validasi, Auth, Event) digunakan di dalam Action/Service.

**Benang merah ke depan:**
- Poin 40 (Deployment): Arsitektur yang bersih memudahkan deployment dan scaling
- Poin 42 (Monitoring): Setiap layer bisa di-monitor secara terpisah

2. **Praktik**: Pindahkan logika dari controller ke Action pattern. Controller hanya panggil action!

3. **Kriteria Action vs Service:**
   - **Action Pattern**: 1 method per class. Cocok untuk operasi bisnis yang kompleks dan spesifik (pinjam buku, kirim notifikasi, generate laporan). Setiap action punya 1 tanggung jawab.
   - **Service Layer**: beberapa method terkait dalam 1 class. Cocok untuk operasi yang berhubungan erat (PeminjamanService: pinjam, kembalikan, hitung denda, perpanjang).
   - **Rekomendasi**: mulai dengan Service, jika method mulai terlalu besar dan kompleks, pisahkan ke Action.
