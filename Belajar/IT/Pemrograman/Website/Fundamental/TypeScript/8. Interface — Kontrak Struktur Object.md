# 8. Interface — Kontrak Struktur Object

> 🔵 **Level 2 — Bagian D** | 🧩 **Melanjutkan [[7. Array dan Tuple — Koleksi Data yang Typed]]**

---

## 1. Penjelasan Singkat & Konsep Dasar

Di Level 1 kita punya primitif, union/literal, array, dan tuple — semuanya *satu nilai / satu kumpulan*. Sekarang waktunya hal yang membentuk 80% data aplikasi nyata: **object**.

**Interface** adalah cara TypeScript mendeskripsikan *bentuk (shape)* sebuah object:

```typescript
interface Buku {
    id: number;
    judul: string;
    stok: number;
}
```

Interface bertindak seperti **kontrak**: *objek mana pun yang bentuknya sesuai* — dibuat inline, di-`return`, diterima parameter — dianggap memenuhi `Buku`. Inilah *structural typing*: TypeScript membandingkan **struktur**, bukan nama kelas.

Konsep turunan yang perlu kamu kuasai:

- **`?` (optional property)** — field boleh ada/tiada: `deskripsi?: string`.
- **`readonly`** — field tidak bisa diubah setelah dibuat: `readonly createdAt: Date`.
- **`extends`** — interface mewarisi interface lain.
- **Index signature** — key tetap, nilai dinamis: `[kategori: string]: Buku[]`.
- **Declaration merging** — dua interface nama sama digabung.
- **Interface untuk function type & class contract**.

**Benang merah**: materi 7 menutup "koleksi nilai primitif"; materi 8 membuka "object berstruktur" — fondasi yang dipakai di *semua level berikutnya* (class di materi 12 mengimplementasikan interface, API response di Level 5, props React di materi 25).

---

## 2. Fungsi & Kegunaan Utama

- **Membuat "bentuk" object reusable dan self-documenting** — sekali definisikan, berulang pakai.
- **Menangkap typo saat menulis object** (`buku.judl` → error) — masalah dari materi 2.
- **Memodelkan data bisnis**: Buku, Anggota, Peminjaman — skenario perpustakaan.
- **Kontrak antar modul/tim & untuk API**: interface menentukan bentuk request/response.
- **Kontrak untuk class** (materi 12) dan **untuk function type** — fleksibel tanpa inheritance.
- **Declaration merging** untuk menambah tipe library dari luar (efektif dipakai di materi 19 saat extend `Express.Request`).

## 3. Contoh Kode & Implementasi (Real-world Example)

```typescript
// src/interfaces/buku.ts

// Interface dasar — desain data buku
interface Buku {
    id: number;
    judul: string;
    pengarang: string;
    isbn: string;
    tahun: number;
    harga: number;
    stok: number;
    kategori: string;
    deskripsi?: string;         // ?  = optional
    readonly createdAt: Date;   // readonly = tidak bisa diubah setelah dibuat
}

const buku1: Buku = {
    id: 1,
    judul: "Clean Code",
    pengarang: "Robert Martin",
    isbn: "9780132350884",
    tahun: 2008,
    harga: 150000,
    stok: 5,
    kategori: "Teknologi",
    // deskripsi tidak wajib
    createdAt: new Date(),
};

// buku1.createdAt = new Date(); // ❌ TS2540: readonly
buku1.stok = 4;                  // ✅ boleh diubah

// ─── Extending — mewarisi seluruh bentuk Buku + tambahan ────────────
interface BukuDenganRating extends Buku {
    rating: number;
    jumlahUlasan: number;
}

const bukuRated: BukuDenganRating = {
    ...buku1,              // spread semua property Buku
    rating: 4.8,
    jumlahUlasan: 234,
};

// ─── Interface untuk function type ──────────────────────────────────
interface CariBuku {
    (keyword: string): Buku[];
}

const cariBuku: CariBuku = (keyword) => {
    return keyword ? [buku1] : [];
};

// ─── Index signature — key dinamis dengan nilai bertipe tetap ───────
interface KatalogPerKategori {
    [kategori: string]: Buku[];
}

const katalog: KatalogPerKategori = {
    "Teknologi": [buku1],
    "Fiksi": [],
};

// ─── Declaration merging — TypeScript MENGGABUNGKAN interface sama nama ─
interface Anggota {
    id: number;
    nama: string;
}
interface Anggota {
    email: string;   // ditambahkan → Anggota kini punya 3 field
}

const anggota: Anggota = { id: 1, nama: "Budi", email: "budi@email.com" };
```

## 4. Analogi Sederhana

**Sistem Perpustakaan.**

Interface adalah **formulir pendaftaran** yang *sudah tercetak*:

- Setiap kolom di formulir punya label dan tipe — `judul` harus teks, `stok` harus angka.
- Kolom bertanda `?` = **opsional** (misal "deskripsi singkat boleh kosong").
- Kolom `readonly` = **tidak bisa diedit** setelah ditandatangani — seperti "ID anggota" tercetak pada kartu, tidak boleh dikoreksi dengan tipe-x.
- `extends` = **formulir versi lengkap** yang memuat semua kolom formulir dasar *plus* kolom tambahan (misal formulir "anggota premium" menyertakan kolom `rating`).
- Declaration merging = dua formulir tumpuk **menggabung** — formulir pertama menyediakan kolom `nama`, formulir kedua `email`; hasilnya satu kartu lengkap.
- Index signature = **lemari katalog** dengan laci berlabel kategori; label bebas apa saja, tapi *isi tiap laci* harus kumpulan kartu Buku.

Interface menjamin: **tidak ada formulir isian yang kolomnya salah lengkap atau salah tipe** — petugas menolak sebelum diproses.

## 5. Kapan Harus Digunakan (Use Cases)

- **Memodelkan objek domain**: `Buku`, `Anggota`, `Peminjaman`, `Pengembalian`.
- **Kontrak API**: interface untuk request body, response, hasil query — dipakai di Level 5–7.
- **Props & state komponen React** (`interface Props { buku: Buku }`) — materi 25.
- **Kontrak class** (dipakai `class X implements Interface`) — materi 12.
- **Menyatukan beberapa bentuk**: `extends` untuk varian (`BukuFisik extends Buku`).
- **Extend tipe pihak ketiga** via declaration merging — dipakai saat menambahkan `req.user` di Express (materi 19).
- **Function types** yang ingin diberi nama & dokumentasi.

## 6. Poin-poin Penting & Best Practices

1. **Gunakan `interface` untuk bentuk object** (kontrak & class) — dan **type alias untuk union, intersection, dan tipe kompleks** lain (detail di [[9. Type Alias — Nama untuk Tipe yang Kompleks]]).
2. **Optional `?` vs union dengan `undefined`**: `deskripsi?: string` berarti "boleh tidak ada"; `deskripsi: string | undefined` berarti "harus ada properti tapi boleh undefined". Pilih sesuai kebutuhan.
3. **`readonly` hanya compile-time** — di runtime tetap bermutasi. Ini *pengaman developer*, bukan penghalang fisik.
4. **Interface merging** adalah fitur untuk *library extension*, bukan penyebaran definisi dalam satu project — gunakan dengan disiplin.
5. **Berikan nama deskriptif**: `BukuPublik`, `BukuBaru`, `DataUpdateBuku` — jangan `Buku1`/`Buku2`.
6. **Jangan annotate object literal berlebihan** jika inference sudah jelas; annotate saat bentuknya harus "terkunci" ke kontrak (parameter, return, state awal).

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

| Kesalahan | Contoh | Akibat | Perbaikan |
|---|---|---|---|
| Property typo / kurang | `{ id, judl, stok }` saat kontrak `Buku` | TS2741 / TS2551 | deklarasikan semua field; autocomplete membantu |
| Tidak menyadari `readonly` | mengubah `createdAt` | TS2540 | jadikan bukan `readonly` bila akan berubah |
| Interface terlalu 'gemuk' (fat interface) | satu interface 20 field untuk semua konteks | sulit digunakan/readme | pecah dengan `extends` / kombinasi kecil |
| Memakai `extends` pada union | `interface X extends A \| B` | TS2312: tidak valid | gunakan intersection di type alias |
| Declaration merging berantakan | banyak file memperbesar `Anggota` tersebar | sulit dilacak | konsentrasikan definisi; merging hanya untuk extension/third-party |
| Index signature terlalu longgar | `[key: string]: any` | hilang type safety | beri tipe value yang konkret |

## 8. Soal Latihan & Kunci Jawaban

### Soal 1
Definisikan interface `Peminjaman` dengan:
- `id: number`, `bukuId: number`, `anggotaId: number`,
- `tanggalPinjam: Date`, `batasKembali: Date`,
- `tanggalKembali: Date | null` (boleh null, bukan optional),
- `readonly createdAt: Date`,
- `denda?: number` (opsional).

Lalu buat 2 objek valid dan 1 objek yang sengaja Anda buat salah (misal `id` string) untuk membuktikan error TS.

### Soal 2
Buat interface `AnggotaDasar` (id, nama) lalu `AnggotaPremium extends AnggotaDasar` (tambah `poin: number`, `tanggalKadaluarsa: Date`). Buat sebuah `AnggotaPremium`. Jelaskan kenapa `extends` lebih baik daripada menulis ulang field yang sama.

---

### Jawaban & Pembahasan

```typescript
// Soal 1
interface Peminjaman {
    id: number;
    bukuId: number;
    anggotaId: number;
    tanggalPinjam: Date;
    batasKembali: Date;
    tanggalKembali: Date | null;      // boleh punya nilai null (belum kembali)
    readonly createdAt: Date;
    denda?: number;                   // opsional
}

const peminjamanAktif: Peminjaman = {
    id: 1,
    bukuId: 10,
    anggotaId: 42,
    tanggalPinjam: new Date("2026-08-01"),
    batasKembali: new Date("2026-09-01"),
    tanggalKembali: null,             // belum dikembalikan
    createdAt: new Date(),
};

const peminjamanSelesai: Peminjaman = {
    ...peminjamanAktif,
    id: 2,
    tanggalKembali: new Date("2026-08-20"),
    denda: 15000,
};

// const salah: Peminjaman = { ...peminjamanAktif, id: "dua" }; // ❌ TS2322
```

**Pembahasan**: antarmuka menegakkan field wajib & tipe, `tanggalKembali: Date | null` mengekspresikan "belum kembali", dan `denda?` opsional bila tidak ada penalti.

```typescript
// Soal 2
interface AnggotaDasar {
    id: number;
    nama: string;
}

interface AnggotaPremium extends AnggotaDasar {
    poin: number;
    tanggalKadaluarsa: Date;
}

const premium: AnggotaPremium = {
    id: 3,
    nama: "Siti",
    poin: 250,
    tanggalKadaluarsa: new Date("2027-01-01"),
};
```

**Pembahasan**: `extends` memastikan `AnggotaPremium` *selalu* memuat field `AnggotaDasar`. Jika `AnggotaDasar` bertambah field (misal `email`), semua kode yang memakai `AnggotaPremium` otomatis ikut mewajibkannya — menulis ulang field secara manual rawan lupa dan inkonsisten.
