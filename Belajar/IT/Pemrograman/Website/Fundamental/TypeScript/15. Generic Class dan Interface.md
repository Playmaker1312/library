# 15. Generic Class dan Interface

> 🟡 **Level 3 — Bagian G** | 🧩 **Melanjutkan [[14. Generics Dasar — Fungsi yang Bekerja untuk Berbagai Tipe]]**

---

## 1. Penjelasan Singkat & Konsep Dasar

Generics (materi 14) tidak berhenti di fungsi — **class dan interface juga bisa generic**. Ini memungkinkan kita membuat *wadah/logika yang reusable* untuk berbagai tipe dengan tetap type-safe.

```typescript
interface Repository<T extends HasId> { ... }   // interface generic
class InMemoryRepository<T extends HasId> implements Repository<T> { ... }
```

**Konsep kunci materi ini**:
- **Generic interface** — mendeskripsikan kontrak "bentuk generik".
- **Generic class** — implementasi wadah yang bekerja untuk tipe apa pun (selama memenuhi constraint).
- **`Omit<T, "id">` / `Partial<T>`** — utility types (dibahas penuh di materi 16) sudah dipakai di sini untuk operasi CRUD.
- **`Result<T, E>`** — pola error handling yang *type-safe*: `{ success: true; data } | { success: false; error }` (dasar dari materi 21).

**Benang merah**: materi 14 memberi fungsi generic; materi 15 naik ke *struktur* generic (repository, result) — tepat di titik transisi ke Level 4 (utility types) yang akan memperkaya jenis transformasi ini.

---

## 2. Fungsi & Kegunaan Utama

- **Repository pattern** — satu implementasi CRUD untuk semua entitas (Buku, Anggota, Peminjaman).
- **Result/Maybe type** — mengekspresikan sukses/gagal tanpa exception, dengan data yang *tertentu* tipenya.
- **Kontrak API generic** — `ApiResponse<T>`, `Paginated<T>` (dipakai Level 5-7).
- **Container/wrapper** (cache, queue, event bus) yang bekerja untuk tipe apa pun.
- **Menjaga relationship antar method** (`create(): T`, `findById(): T | undefined`).

## 3. Contoh Kode & Implementasi (Real-world Example)

```typescript
// src/utils/repository.ts

interface HasId { id: number; }

// ─── Generic interface — kontrak CRUD ────────────────────────────────
interface Repository<T extends HasId> {
    findAll(): T[];
    findById(id: number): T | undefined;
    create(data: Omit<T, "id">): T;
    update(id: number, data: Partial<T>): T | undefined;
    delete(id: number): boolean;
}

// ─── Generic class — implementasi in-memory ──────────────────────────
class InMemoryRepository<T extends HasId> implements Repository<T> {
    protected items: T[] = [];
    private nextId = 1;

    findAll(): T[] {
        return [...this.items];   // return copy agar tak dimutasi dari luar
    }

    findById(id: number): T | undefined {
        return this.items.find(item => item.id === id);
    }

    create(data: Omit<T, "id">): T {
        const item = { ...data, id: this.nextId++ } as T;
        this.items.push(item);
        return item;
    }

    update(id: number, data: Partial<T>): T | undefined {
        const index = this.items.findIndex(i => i.id === id);
        if (index === -1) return undefined;
        this.items[index] = { ...this.items[index], ...data };
        return this.items[index];
    }

    delete(id: number): boolean {
        const index = this.items.findIndex(i => i.id === id);
        if (index === -1) return false;
        this.items.splice(index, 1);
        return true;
    }
}

// ─── Extend untuk kebutuhan spesifik Buku ─────────────────────────────
interface Buku extends HasId {
    judul: string;
    pengarang: string;
    harga: number;
    stok: number;
    kategori: string;
}

class BukuRepository extends InMemoryRepository<Buku> {
    cariTersedia(): Buku[] {
        return this.items.filter(b => b.stok > 0);
    }
    cariKeyword(kw: string): Buku[] {
        return this.items.filter(
            b => b.judul.toLowerCase().includes(kw.toLowerCase()),
        );
    }
}

// ─── Pemakaian ────────────────────────────────────────────────────────
const bukuRepo = new BukuRepository();
const anggotaRepo = new InMemoryRepository<Anggota>();

const b1 = bukuRepo.create({
    judul: "Clean Code", pengarang: "Robert Martin",
    harga: 150000, stok: 5, kategori: "Teknologi",
});
console.log(b1.id);            // 1 — T disimpulkan Buku

// ─── Generic Result type untuk error handling ─────────────────────────
type Result<T, E = Error> =
    | { success: true; data: T }
    | { success: false; error: E };

function cariAnggotaAman(id: number): Result<Anggota> {
    const anggota = anggotaRepo.findById(id);
    if (!anggota) {
        return { success: false, error: new Error(`Anggota ${id} tidak ada`) };
    }
    return { success: true, data: anggota };
}

const hasil = cariAnggotaAman(1);
if (hasil.success) {
    console.log(hasil.data.nama);        // ✅ TS tahu: Anggota
} else {
    console.error(hasil.error.message);  // ✅ TS tahu: Error
}
```

## 4. Analogi Sederhana

**Sistem Perpustakaan.**

- **Generic `Repository<T>`** = **SOP "pencatatan koleksi"** yang berlaku untuk *kartu buku*, *kartu anggota*, *kartu peminjaman*: semuanya punya prosedur sama (tambah, cari, ubah, hapus) dengan kolom `id` sebagai nomor kartu. Alih-alih menulis 3 SOP, kita tulis satu SOP generic — lalu untuk Buku, di-extend dengan aturan khusus (cari yang tersedia).
- **`Result<T, E>`** = **amplop laporan**: setiap permintaan "cari anggota" mengembalikan amplop yang *berlabel jelas* — `success` (berisi `data` tipe tertentu) atau `error` (berisi pesan). Penerima amplop langsung tahu membuka bagian mana; TypeScript juga "membuka" tipe yang sesuai di tiap cabang (`if (hasil.success)` → `hasil.data`).
- **`Partial<T>` / `Omit<T,"id">`** di sini seperti **form "ubah data" yang boleh diisi sebagian** dan **form "tambah" yang id-nya otomatis diberikan sistem**.

---

## 5. Kapan Harus Digunakan (Use Cases)

- **Repository layer** untuk semua entitas yang memiliki pola CRUD sama — dengan subclass untuk behavior spesifik.
- **Result/Maybe pattern** untuk fungsi yang bisa gagal, terutama di service & repository (dipakai Level 5).
- **Generic containers**: cache, queue, event bus (materi 24), pagination wrapper.
- **API layer**: `ApiResponse<T>`, `PagedResult<T>` (Level 5-7).
- **Pola "template method"** yang memakai abstract/generic class.

---

## 6. Poin-poin Penting & Best Practices

1. **Berikan constraint minimal** (`T extends HasId`) — repository benar-benar butuh `id`.
2. **Kembalikan salinan** (`[...this.items]`) saat memberikan koleksi ke luar — mencegah mutasi tak sengaja.
3. **Gunakan `Omit<T, "id">` untuk create & `Partial<T>` untuk update** — API-nya mencerminkan realita data.
4. **Prefer `Result<T, E>` untuk error yang bisa ditangani**, simpan exception untuk error tak terduga.
5. **Subclass memperluas bukan menggeser** — `BukuRepository extends InMemoryRepository<Buku>` menambah, tidak mengganti kontrak.
6. **Jangan menaruh logic "hanya untuk satu entitas" di generic** — dorong ke subclass/interface spesifik.

---

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

| Kesalahan | Contoh | Akibat | Perbaikan |
|---|---|---|---|
| Class generic tanpa constraint padahal butuh `id` | `class Repo<T> { findById(...) { return x.id } }` | TS2339 | `T extends HasId` |
| Casting paksa `as T` saat create | `{ ...data, id } as T` bila data salah bentuk | type safety semu | pastikan `data: Omit<T,"id">` benar |
| Mengembalikan array asli (`this.items`) | caller mem-push & mengubah state internal | bug tersembunyi | return `[...this.items]` |
| Over-generic pada subclass | semua method generic tak perlu | kompleks | konkretkan tipe pada subclass |
| `Result<T>` tanpa default `E` | callers harus menulis `Result<T, CustomErr>` selalu | ribet | default `E = Error` |
| Mengabaikan exhaustive check di Result | `if (hasil.success)` tanpa else | cabang error tak ditangani | selalu handle kedua cabang |

## 8. Soal Latihan & Kunci Jawaban

### Soal 1
Gunakan `InMemoryRepository` untuk `Anggota` (field `id`, `nama`, `email`). Lakukan: buat 2 anggota, update 1, delete 1, lalu cetak sisanya. Tunjukkan bagaimana `Partial<T>` membantu update.

### Soal 2
Definisikan generic interface `HasLabel` dengan `label: string`, lalu buat class `LabeledRepository<T extends HasLabel>` yang menambah method `cariByLabel(label: string): T[]`. Implementasikan dan buktikan satu pemakaian.

---

### Jawaban & Pembahasan

```typescript
// Soal 1
interface Anggota extends HasId { nama: string; email: string; }

const anggotaRepo = new InMemoryRepository<Anggota>();

const a1 = anggotaRepo.create({ nama: "Budi", email: "budi@x.com" });
const a2 = anggotaRepo.create({ nama: "Siti", email: "siti@x.com" });

anggotaRepo.update(a1.id, { email: "budi.baru@x.com" });   // partial → hanya email
anggotaRepo.delete(a2.id);

console.log(anggotaRepo.findAll());
// → [{ id: 1, nama: "Budi", email: "budi.baru@x.com" }]
```

**Pembahasan**: `update(id, data: Partial<Anggota>)` menerima objek parsial (hanya `email`) tanpa harus mengirim semua field — sesuai "form ubah sebagian". Create menolak tanpa `nama`/`email` karena `Omit<Anggota,"id">`.

```typescript
// Soal 2
interface HasLabel { label: string; }

interface RepoBase<T extends HasLabel> {
    findAll(): T[];
}

class LabeledRepository<T extends HasLabel> implements RepoBase<T> {
    items: T[] = [];

    findAll(): T[] { return [...this.items]; }

    cariByLabel(label: string): T[] {
        return this.items.filter(i => i.label === label);
    }
}

interface Rak extends HasLabel { id: number; }

const rakRepo = new LabeledRepository<Rak>();
rakRepo.items.push({ id: 1, label: "Sains" }, { id: 2, label: "Sains" });
console.log(rakRepo.cariByLabel("Sains").length);   // 2
```

**Pembahasan**: generic interface + class bekerja sama — `cariByLabel` tetap *return `T[]`* (tipe persis entitas yang dipakai), dan constraint `HasLabel` menjamin setiap entitas punya `label`. Ini menunjukkan komposisi generics lintas interface & class.
