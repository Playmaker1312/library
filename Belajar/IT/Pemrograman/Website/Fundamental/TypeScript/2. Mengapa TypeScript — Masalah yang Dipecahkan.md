# 2. Mengapa TypeScript? — Masalah yang Dipecahkan

> 🟢 **Level 1 — Bagian A** | 🧩 **Melanjutkan [[1. TypeScript adalah JavaScript dengan Tipe — Bukan Bahasa Baru]]**

---

## 1. Penjelasan Singkat & Konsep Dasar

Pada materi pertama kita paham bahwa TypeScript adalah JavaScript + tipe. Pertanyaan yang lebih dalam: **kenapa repot-repot menambah tipe?** Jawabannya sederhana tapi konsekuensinya besar — **JavaScript mengeksekusi semua kode tanpa memeriksa "apakah ini masuk akal?".** Error jenis *type mismatch* baru ketahuan ketika aplikasi *sudah berjalan* (runtime), paling parah di production.

Konsep inti materi ini adalah memahami "biaya" JavaScript tanpa tipe:

```text
Bug dengan JavaScript:
nulis kode → make → deploy → user pakai → BARU crash ❌

Bug dengan TypeScript:
nulis kode → type-check di editor → tidak bisa compile → perbaiki → deploy ✅
```

TypeScript menutup celah itu dengan **mengevaluasi tipe pada waktu *kompilasi* (compile-time)**, sebelum kode pernah dieksekusi satu kali pun.

**Jenis-jenis bug yang bisa ditangkap TS:**

| Kategori bug | Ditangkap TypeScript? |
|---|---|
| Typo nama property (`buku.judl`) | ❌ baru crash saat runtime → ✅ error TS2551 |
| Argument dengan tipe salah (`hitungDenda("7", 1000)`) | ❌ hasil string "7000" → ✅ error TS2345 |
| Null/undefined diakses tanpa cek | ❌ `TypeError` → ✅ dengan strictNullChecks |
| Memanggil method yang tidak ada | ❌ baru crash runtime → ✅ error saat compile |

**Hubungan dengan materi sebelumnya**: materi 1 menjelaskan *mekanisme* TS (superset + kompilasi). Materi ini menjelaskan *motivasi* di baliknya — masalah spesifik yang diatasi, sehingga kamu tidak bolak-balik bertanya "kenapa harus pelajari TS?". Materi berikutnya (materi 3–7) memakai motivasi ini untuk membangun project nyata.

---

## 2. Fungsi & Kegunaan Utama

- **Mengubah "waktu bug" dari runtime ke compile-time.** Bug muncul sebagai *pesan merah di editor*, bukan error 500 di server.
- **Autocomplete dari "tebak-tebakan" menjadi "kejelasan".** Mengetik `buku.` menampilkan hanya properti yang ada.
- **Refactoring dengan jaringan pengaman.** Menjadikan perubahan struktur besar (rename field, split fungsi) jadi operasi yang bisa diverifikasi sepenuhnya dengan `tsc`.
- **Self-documenting code.** Tipe menjawab pertanyaan "data ini bentuknya apa?" tanpa harus membaca 100 baris kode di bawahnya.
- **Kontrak antar tim / antar modul.** Ketika tim backend dan frontend berbagi tipe API, ketidakcocokan ketahuan sebelum deployment.

## 3. Contoh Kode & Implementasi (Real-world Example)

Scenario nyata: menghitung denda keterlambatan pengembalian buku.

```typescript
// src/mengapa-ts.ts

// ─── Skenario A: JavaScript murni ────────────────────────────────────
// Semua kode "lolos" tanpa error. Bug baru terlihat saat USER memakainya.
function hitungDenda(hariTerlambat, dendaPerHari) {
    return hariTerlambat * dendaPerHari;
}

const denda1 = hitungDenda("7", 1000);       // "7000"  ← string, BUKAN number
const denda2 = hitungDenda(undefined, 1000); // NaN     ← crash tersembunyi!
console.log(denda1 + 100);                    // "7000100" ← hasil aneh!

// ─── Skenario B: TypeScript yang sama, diberi tipe ───────────────────
function hitungDendaTS(hariTerlambat: number, dendaPerHari: number): number {
    return hariTerlambat * dendaPerHari;
}

// ketiga baris di bawah akan MEMBLOKIR kompilasi (error saat ini juga):
// hitungDendaTS("7", 1000);        // ❌ TS2345
// hitungDendaTS(undefined, 1000);  // ❌ TS2345
// hitungDendaTS("x", 1000);        // ❌ TS2345

const dendaAman = hitungDendaTS(7, 1000);    // ✅ 7000 (number!)
console.log(dendaAman + 100);                // ✅ 7100
```

> ✅ **Catatan pembeda**: `hitungDenda("7", 1000)` di JavaScript *tidak melempar error* — justru itu bahayanya. Itu menghasilkan string `"7000"` yang lolos tanpa terlihat, lalu merusak perhitungan di bawahnya. TypeScript mencegahnya **sebelum** baris itu pernah dipanggil.

## 4. Analogi Sederhana

Kembali ke **Sistem Perpustakaan**.

Bayangkan seorang **pustakawan** yang mencatat stok buku. Terjadi ini:

1. Pustakawan menulis di kartu stok: *"Harga: Rp lima belas ribu"* (salah format — harus angka).
2. Tidak ada yang memeriksa, kartu masuk rak.
3. Tiga minggu kemudian kasir menghitung *harga × jumlah*, hasilnya "Rp lima belas ribu15" — **jumlah yang tidak masuk akal**, tapi sudah terlanjur di kasir, sudah terlanjur di bukti transaksi.
4. Sekarang harus ditebus dengan kerja ekstra: telusuri dari mana bug-nya, minta maaf ke pembeli, perbaiki sistem.

JavaScript adalah perpustakaan **tanpa pustakawan pemeriksa kartu**. TypeScript adalah perpustakaan yang **memeriksa kartu katalog di pintu masuk**: kolom `harga` harus angka, kolom `judul` harus teks. Kartu yang salah *ditolak di depan pintu*, jauh sebelum kasir pernah melihatnya.

Jadi TypeScript bukan sekadar "melarang kode serampangan" — ia mengalihkan *deteksi kesalahan ke waktu paling murah*: saat mengetik, bukan saat layanan sudah berjalan.

## 5. Kapan Harus Digunakan (Use Cases)

- **Setiap kali bug "type mismatch" akan lebih mahal diperbaiki saat production** — hampir semua aplikasi bisnis (perpustakaan, e-commerce, perbankan, POS).
- **Saat mengerjakan basis kode besar / tim banyak anggota** — tipe mengkomunikasikan kontrak antar modul tanpa rapat panjang.
- **Sebelum ada kode yang berumur panjang** — biarkan TS tumbuh bersama project (persis pola roadmap ini).
- **Pada refactor besar (restrukturisasi, migrasi)** — pengaman refactor terbaik yang tersedia untuk JavaScript.
- **Library yang akan di-publish** — pengguna mendapat typing gratis via `.d.ts`, menjadikan library lebih "dipakai".

**Kapan TIDAK wajib**: prototype sekali-pakai (<1 minggu), script throwaway, proyek dempul yang tidak akan dirawat. Meski begitu, karena TS kompatibel dengan JS, mengaktifkannya pun punya biaya kecil.

---

## 6. Poin-poin Penting & Best Practices

1. **`strict: true` sejak awal.** Default TS "longgar"; tanpa strict Anda kehilangan perlindungan null/any yang justru inti masalah di atas.
2. **Hindari `any` bagai api.** `any` = "matikan type checker" untuk nilai itu — kembali ke mode JavaScript.
3. **Biarkan inference bekerja**, anotasi untuk kontrak: parameter fungsi, return type bila rumit, objek kosong, variabel dari input eksternal.
4. **Gunakan error TS sebagai alat belajar.** `TS2345` memiliki penjelasan; membacanya lebih cepat daripada Google.
5. **Jadikan kompilasi bagian dari alur kerja**: `npm run type-check` (=`tsc --noEmit`) sebelum commit.
6. **Tulis tipe dulu untuk data penting** (response API, database rows, form input) — ini "kontrak" yang melindungi seluruh lapisan di atasnya.

---

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

| Kesalahan | Contoh | Akibat | Perbaikan |
|---|---|---|---|
| `any` sebagai pelarian | `function f(x: any)` untuk "biar cepat" | Kehilangan semua perlindungan; bug type baru muncul runtime | Tipe konkret atau `unknown` + narrowing |
| Mengisi `strict: false` | tsconfig default | `null` lolos, kontrak lemah | `"strict": true` |
| Menulis anotasi berlebih | `let x: number = 5` | Verbose, redup; tidak merugikan tapi tidak membantu | Biarkan inference |
| Anggap type-check "menghambat" | mematikan eslint TS karena error banyak | Bug mengalir ke production | Fix tipe, bukan matikan pelindung |
| Tidak menguji null/undefined saat API/lib | `user.profile.birthdate` crash | `TypeError` runtime | optional chaining `?.` dan `??` (materi 10) |

## 8. Soal Latihan & Kunci Jawaban

### Soal 1
Ambil fungsi berikut (JavaScript). Sebutkan **tiga** skenario pemanggilan yang tidak menghasilkan error di JS tapi akan menghasilkan data salah atau crash — dan tulis ulang fungsinya dalam TypeScript sehingga ketiganya menjadi error kompilasi.

```javascript
function sapa(nama, waktu) {
    return "Selamat " + waktu + ", " + nama + "!";
}
```

### Soal 2
Bangun "verifikator stok buku" kecil:
- Definisikan tipe `Buku` yang hanya boleh dibaca `judul` (string) dan `stok` (number).
- Buat fungsi `kurangiStok(buku, jumlah)` yang mengembalikan `{ berhasil: boolean; pesan: string }`.
- Pastikan memanggil `kurangiStok` dengan argumen string menghasilkan error TS.

---

### Jawaban & Pembahasan

**Soal 1** — Mulai dari JS:

```javascript
sapa("Budi", "pagi");            // ✅ "Selamat pagi, Budi!"
sapa(123, "siang");              // JS: "Selamat siang, 123!" (string "123")
sapa(undefined, "pagi");         // JS: "Selamat pagi, undefined!"
sapa("Budi", null);              // JS: "Selamat null, Budi!"
```

TypeScript:

```typescript
function sapa(nama: string, waktu: string): string {
    return `Selamat ${waktu}, ${nama}!`;
}

sapa("Budi", "pagi");                 // ✅
// sapa(123, "siang");                // ❌ TS2345: number tidak assignable ke string
// sapa(undefined, "pagi");           // ❌ TS2345
// sapa("Budi", null);                // ❌ TS2345
```

**Pembahasan**: tiga pemanggilan bermasalah (argumen number, undefined, null) sebelumnya menghasilkan string aneh tanpa error di JS; di TS semuanya menjadi error **kompilasi** (TS2345), sehingga tidak pernah sampai ke runtime.

---

**Soal 2**

```typescript
interface Buku {
    judul: string;
    stok: number;
}

function kurangiStok(
    buku: Buku,
    jumlah: number,
): { berhasil: boolean; pesan: string } {
    if (jumlah < 0) {
        return { berhasil: false, pesan: "Jumlah tidak boleh negatif" };
    }
    if (buku.stok < jumlah) {
        return {
            berhasil: false,
            pesan: `Stok "${buku.judul}" tidak mencukupi (tersedia ${buku.stok})`,
        };
    }
    buku.stok -= jumlah;
    return { berhasil: true, pesan: `${jumlah} buku "${buku.judul}" dipinjam` };
}

const buku = { judul: "Clean Code", stok: 5 };
console.log(kurangiStok(buku, 2));  // { berhasil: true, pesan: "2 buku ... dipinjam" }
console.log(kurangiStok(buku, 99)); // { berhasil: false, ... keterangan }
// kurangiStok(buku, "2");          // ❌ TS2345: string tidak assignable ke number
```

**Poin penting**: selain mencegah `"2"` masuk, fungsi ini *menguji business logic* (stok negatif, stok tidak cukup) — contoh bagaimana TS mengamankan kontrak **sebelum** logika dijalankan.
