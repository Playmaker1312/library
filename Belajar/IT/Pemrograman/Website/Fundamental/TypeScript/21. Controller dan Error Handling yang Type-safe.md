# 21. Controller dan Error Handling yang Type-safe

> 🔴 **Level 5 — Bagian I** | 🧩 **Melanjutkan [[20. Typed Request Validation dengan Zod]]**

## 1. Penjelasan Singkat & Konsep Dasar

Di materi 19-20 kita punya app + validasi. Dua hal yang belum: **controller** (layer yang mengubah service output → response HTTP) dan **error handling yang konsisten & type-safe**.

Konsep inti:

```text
Controller: menerima req → memanggil service → merespons JSON
Error handling: semua error berjalan satu arah → middleware errorHandler
                    ├── AppError (kita buat) → status & pesan yang "aman"
                    ├── ZodError → 422 dengan field errors
                    └── error tidak dikenal → 500, tanpa bocorkan detail
```

**ApiResponse type**: format respons seragam supaya frontend punya kontrak tunggal:

```typescript
type ApiResult<T> =
    | { success: true; data: T; message?: string }
    | { success: false; message: string; errors?: Record<string, string[]> };
```

**Hierarki error yang kita bangun** (dasar untuk materi 23 testing & pengembangan skala besar):

```text
Error
└── AppError (statusCode, isOperational)
    ├── NotFoundError (404)
    ├── ValidationError (422)
    ├── UnauthorizedError (401)
    └── ForbiddenError (403)
```

**Benang merah**: interface (materi 8), discriminated union (materi 11), class/inheritance (materi 12-13), `Result<T>` (materi 15), dan `instanceof` guards (materi 11) — semua bertemu di sini untuk menghadirkan API yang merespons *dengan tenang* di semua situasi.

---

## 2. Fungsi & Kegunaan Utama

- **Pemisahan tanggung jawab**: controller berurusan dengan HTTP, service berurusan dengan bisnis — mudah diuji (materi 23).
- **Respons konsisten**: `{ success, data/message, errors }` di seluruh endpoint.
- **Hirarki error yang ekspresif**: `NotFoundError`, `ValidationError` — satu `errorHandler` untuk semua.
- **Operasi yang "diharapkan" (isOperational) vs bug**: disengaja → status tepat; tidak dikenal → 500 aman.
- **Jangan bocorkan detail internal** ke client (stack trace, pesan DB) kecuali di development.

## 3. Contoh Kode & Implementasi (Real-world Example)

### Respons types & helpers

```typescript
// src/types/api.ts
export interface ApiResponse<T> {
    success: true;
    data: T;
    message?: string;
}

export function sukses<T>(data: T, message?: string): ApiResponse<T> {
    return { success: true, data, message };
}
```

### Hierarki error

```typescript
// src/errors/AppError.ts
export class AppError extends Error {
    constructor(
        public message: string,
        public statusCode: number = 500,
        public isOperational: boolean = true,
    ) {
        super(message);
        Object.setPrototypeOf(this, AppError.prototype);
    }
}

export class NotFoundError extends AppError {
    constructor(resource: string, id: number | string) {
        super(`${resource} dengan ID ${id} tidak ditemukan`, 404);
    }
}

export class ValidationError extends AppError {
    constructor(message: string) {
        super(message, 422);
    }
}

export class UnauthorizedError extends AppError {
    constructor(message = "Tidak terautentikasi") {
        super(message, 401);
    }
}

export class ForbiddenError extends AppError {
    constructor(message = "Tidak memiliki izin") {
        super(message, 403);
    }
}
```

### Error handler middleware (harus 4 parameter)

```typescript
// src/middleware/errorHandler.ts
import type { Request, Response, NextFunction } from "express";
import type { ZodError } from "zod";
import { AppError } from "../errors/AppError";

export function errorHandler(
    error: unknown,
    _req: Request,
    res: Response,
    _next: NextFunction,   // wajib ada agar Express kenali sebagai error middleware
): void {
    if (error instanceof AppError) {
        res.status(error.statusCode).json({
            success: false,
            message: error.message,
        });
        return;
    }

    if (error instanceof ZodError) {
        res.status(422).json({
            success: false,
            message: "Data tidak valid",
            errors: error.flatten().fieldErrors,
        });
        return;
    }

    // Error tak dikenal — tidak ekspos detail
    console.error("Unhandled error:", error);
    res.status(500).json({
        success: false,
        message: "Terjadi kesalahan pada server",
        ...(process.env.NODE_ENV === "development" && {
            stack: error instanceof Error ? error.stack : String(error),
        }),
    });
}
```

### Controller (tipis, mengandalkan service)

```typescript
// src/controllers/buku.controller.ts
import type { Request, Response, NextFunction } from "express";
import { BukuService } from "../services/buku.service";
import type { CreateBukuDTO } from "../schemas/buku.schema";
import { sukses } from "../types/api";

export class BukuController {
    constructor(private bukuService: BukuService) {}

    index = async (req: Request, res: Response, next: NextFunction): Promise<void> => {
        try {
            const page  = parseInt(req.query.page as string) || 1;
            const hasil = await this.bukuService.getAll({ page });
            res.json(sukses(hasil));
        } catch (error) {
            next(error);               // serahkan ke errorHandler
        }
    };

    store = async (req: Request, res: Response, next: NextFunction): Promise<void> => {
        try {
            const data: CreateBukuDTO = req.body;   // sudah divalidasi Zod
            const buku = await this.bukuService.create(data);
            res.status(201).json(sukses(buku, "Buku berhasil ditambahkan"));
        } catch (error) {
            next(error);
        }
    };
}
```

## 4. Analogi Sederhana

**Sistem Perpustakaan.**

- **Controller** = **petugas loket**: menerima permintaan, menyampaikan ke *bagian layanan* (service), lalu menulis *nota respons* kepada tamu. Petugas tidak bertanya langsung ke gudang; ia menghubungi pelayannya, dan *tidak ikut mencampuri* alur bila ada masalah — cukup teriak di radio ("next(error)").
- **`ApiResponse<T>`** = **format nota resmi**: selalu ada kolom `success`, `data` atau `message`. Semua loket menulis dengan format sama, sehingga mesin/klien lain dapat membaca tanpa kejutan.
- **Hirarki `AppError`** = **klasiﬁkasi "penolakan" yang spesifik**:
  - `NotFoundError` → "Buku dengan ID 99 tidak ditemukan" (404),
  - `ValidationError` → "Kolom ISBN tidak valid" (422),
  - `UnauthorizedError` → "Belum login" (401),
  - `ForbiddenError` → "Tidak punya izin membersihkan rak ini" (403).
- **Error handler** = **ruang darurat satu pintu**: semua masalah masuk satu ruang, dipilah:
  - masalah *terkenali* (AppError/Zod) → diperlakukan dengan pesan ramah + status yang pas,
  - masalah *tidak dikenal* (bug tak terduga) → dicatat + diberi tanggapan umum "Terjadi kesalahan server" (500) tanpa membocorkan isi gudang (mesin DDB, stack trace) ke tamu.

## 5. Kapan Harus Digunakan (Use Cases)

- **Setiap proyek API**: controller+service separation; satu errorHandler untuk apa pun yang bisa salah.
- **Validasi/NotFound pada semua endpoint** — gunakan subclass AppError dari awal agar klien mendapat status HTTP yang benar.
- **Saat ingin menguji service & controller secara terpisah** (Level 6) — pemisahan layer mempermudah.
- **Frontend mengonsumsi API** (materi 25-27) — implikasi `{ success, data/message }` secara langsung dibaca tipe.
- **Mendevelop middleware `validateBody`** (materi 20) — gabung dengan Zod untuk seluruh pipeline.

---

## 6. Poin-poin Penting & Best Practices

1. **Controller SEPENUHNYA tipis** — tanpa logika bisnis; serahkan ke service.
2. **`next(error)` untuk meneruskan error** — jangan `throw` di handler async tanpa di-catch (lekas ter-delegasi errorHandler).
3. **Error handler harus 4 parameter** (`(err, req, res, next)`) — Express membedakannya dari middleware biasa via jumlah argumen.
4. **`AppError` subclass untuk tipe error bisnis** — `NotFoundError.resource(id)` menghasilkan pesan + status yang benar.
5. **Jangan ekspos stack/internal ke luar** di production — hanya log.
6. **`sukses(data, message)` helper** menghindari pengulangan struktur response di semua controller.
7. **Gunakan `Result<T, E>` (materi 15) di service** bila prefer ber-typed union di atas exceptions.

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

| Kesalahan | Contoh | Akibat | Perbaikan |
|---|---|---|---|
| Error handler diletakkan tidak di akhir | middleware diletakkan sebelum route | tidak pernah dijalankan | letakkan paling akhir |
| Error handler hanya 3 parameter | `(err, req, res)` | dianggap middleware biasa | tambahkan `_next` |
| Controller berisi bisnis langsung | controller menulis `repo.findById` | sulit diuji/variasi | ke service |
| `throw` di async tanpa catch | `async handler` melempar begitu saja | jadi unhandled rejection | wrap try/catch + next(error) |
| Bocor stack trace di prod | `.json({ stack })` tanpa conditional | ekspose struktur internal | hanya dev mode |
| Tidak pakai subclass error | satu `Error` dengan `status: 500` poso | status selalu salah | definisi per-kategori |
| Menekankan `send`/`json` bermacam-macam | tiap controller beda format | kontrak rusak | selalu `ApiResponse`/helper |

## 8. Soal Latihan & Kunci Jawaban

### Soal 1
Definisikan class `BukuNotFoundError extends AppError` (resource = "Buku") dan gunakan di service `getById` yang melempar bila buku kosong. Tambahkan case tersebut di `errorHandler`.

### Soal 2
Mengapa error handler HALUS memerlukan tepat 4 parameter? Jelaskan dengan satu kalimat dan tunjukkan potongan middleware yang *benar* square.

---

### Jawaban & Pembahasan

```typescript
// Soal 1
// src/errors/AppError.ts (tambahan)
export class BukuNotFoundError extends AppError {
    constructor(id: number) {
        super(`Buku dengan ID ${id} tidak ditemukan`, 404);
    }
}

// src/services/buku.service.ts (potongan)
export class BukuService {
    constructor(private repo: BukuRepository) {}

    async getBuku(id: number) {
        const buku = await this.repo.findById(id);
        if (!buku) {
            throw new BukuNotFoundError(id);
        }
        return buku;
    }
}

// errorHandler menangani otomatis via `instanceof AppError`
```

**Pembahasan**: subclass mewarisi statusCode (404) dan pesan — satu `if (error instanceof AppError)` sudah menangani semua turunannya. Service melempar saat entity absen; errorHandler menerima 404 + pesan yang jelas, dan tidak bocor detail.

```typescript
// Soal 2
// Error handler HARUS punya 4 parameter karena Express
// membedakan "error middleware" dari "handler biasa" berdasar arity.
export function errorHandler(
    error: unknown,
    _req: Request,
    res: Response,
    _next: NextFunction,
): void { /* ... */ }
```

**Pembahasan**: kalau kita menulis `(err, req, res)` = 3 param, Express menganggapnya *request handler* (untuk normal route) dan tidak melewatkan error ke sana — sehingga error tak pernah tertangani. Empat parameter (`err, req, res, next`) menandakan ini adalah *error-handling middleware*.
