# 5. Primitive Types — Tipe Paling Dasar

> 🟢 **Level 1 — Bagian C** | 🧩 **Melanjutkan [[4. tsconfig.json — Konfigurasi Compiler TypeScript]]**

---

## 1. Penjelasan Singkat & Konsep Dasar

Ini adalah materi *pertama yang menulis tipe*. Ada dua cara memberi tipe pada nilai:

- **Type annotation**: kamu yang menyatakan tipenya — `let judul: string = "Clean Code"`.
- **Type inference**: TypeScript menebak dari nilai awalnya — `let judul = "Clean Code"` otomatis dianggap `string`.

Primitive types yang tersedia di TypeScript = primitif JavaScript + penjaga keamanan:

```text
Primitive JavaScript            Penjaga tambahan TypeScript
─────────────────────           ─────────────────────────────
number, string, boolean
null, undefined                 →  expect eksplisit (strictNullChecks)
                              + any      (nonaktifkan penjagaan — HINDARI)
                              + unknown  (tipe "belum diketahui" yang aman)
                              + never    (tidak pernah menghasilkan nilai)
                              + void     (tidak mengembalikan nilai)
```

**Konsep yang paling penting di materi ini**: perbedaan **`any` vs `unknown`** dan perbedaan **`null` vs `undefined`** — karena keduanya yang paling sering membingungkan pemula dan menentukan kualitas type safety kamu.

**Benang merah**: materi 4 menyetel `strict` — di sinilah efeknya pertama kali terasa. `strictNullChecks` dari tsconfig menyebabkan `string | null` *tidak bisa* dipakai seperti `string` biasa, dan kamu harus menangani null-nya. Materi selanjutnya ([[6. Union Types dan Literal Types — Tipe yang Lebih Ekspresif]]) akan memperluas konsep tipe dasar ini.

## 2. Fungsi & Kegunaan Utama

- **Menetapkan "bahasa data" paling dasar** untuk seluruh aplikasi — stok buku (number), judul (string), tersedia/tidak (boolean).
- **`unknown`** memberi jalan aman ke tipe dinamis (misal data dari JSON `fetch`, input user) — kamu *boleh* mengaksesnya setelah melewati pengecekan tipe.
- **`never`** menandakan jalur kode yang *tidak pernah* selesai normal (error yang dilempar), berguna untuk exhaustive check pada union (materi 6 & 11).
- **`void`** menjelaskan bahwa fungsi melakukan *sesuatu* (biasanya efek samping) tanpa mengembalikan nilai.

## 3. Contoh Kode & Implementasi (Real-world Example)

```typescript
// src/types/dasar.ts

// ─── Annotation vs Inference ─────────────────────────────────────────
// Annotation (eksplisit)
let judul: string = "Clean Code";

// Inference (ditebak TS) — biasanya CUKUP, lebih ringkas
let hargaBuku = 150000;   // number
let stokBuku  = 5;        // number

// hargaBuku = "mahal";        // ❌ TS2322: 'string' tidak assignable ke 'number'

// ─── Primitive types ─────────────────────────────────────────────────
const namaPerpus: string = "Perpustakaan Kota";
const tahunBerdiri: number = 1985;
const aktif: boolean = true;

// null = sengaja tidak ada nilai; undefined = belum pernah diisi
const pengarang: string | null = null;       // kita TAHU belum diisi, dan sengaja
let sedangPinjam: undefined;                  // belum pernah di-set

// ─── unknown: aman, harus dicek dulu ────────────────────────────────
// Contoh nyata: data dari JSON.parse atau API belum dikenal strukturnya
let dataDariApi: unknown = JSON.parse('{"judul":"Laskar Pelangi"}');

// dataDariApi.judul;             // ❌ TS18046: objek ber-tipe unknown
if (typeof dataDariApi === "object" && dataDariApi !== null) {
    // setelah narrowing, kita bisa akses dengan casting yang hati-hati
    const judulTerisi = (dataDariApi as { judul: string }).judul;
    console.log(judulTerisi);     // ✅ "Laskar Pelangi"
}

// ─── never: fungsi yang selalu melempar error ───────────────────────
function buangError(pesan: string): never {
    throw new Error(pesan);      // tidak pernah mengembalikan nilai normal
}

// ─── void: fungsi efek samping ──────────────────────────────────────
function logStok(judul: string, stok: number): void {
    console.log(`📚 ${judul}: tersedia ${stok} kopi`);
}

logStok("Clean Code", 5);
```

## 4. Analogi Sederhana

**Sistem Perpustakaan.**

- **`string`** = label/nama buku: *"Clean Code"*. Selalu teks.
- **`number`** = angka pada rak & stok: *3, 150000*. Selalu angka.
- **`boolean`** = saklar "Tersedia/Tidak". Dua pilihan: ya/tidak.
- **`null`** = *sengaja* mengosongkan kolom — misal pustakawan menulis `pengarang: (kosong)` karena memang belum dicatat.
- **`undefined`** = kolom yang *belum pernah dibuka* di form — tidak ada nilai karena belum diisi apa pun.
- **`void`** = tindakan pustakawan yang *tidak menghasilkan buku baru*, misal menandai stok: dia melakukan sesuatu, tapi tidak "mengembalikan" apa pun.
- **`never`** = jalur permintaan yang *ditolak tanpa hasil buku* — misal pustakawan selalu melempar "Buku tidak ditemukan" dan tidak pernah menyerahkan apa pun.
- **`unknown`** = kotak paket yang datang *tanpa label*, belum tahu isinya — sebelum dibuka dan diperiksa (`typeof`/broadening), tidak boleh diambil barang di dalamnya.
- **`any`** = kotak "anggota VIP tanpa pemeriksaan" — pustakawan langsung percaya isinya *apa saja*, sehingga semua penjagaan dibebaskan. Berbahaya.

## 5. Kapan Harus Digunakan (Use Cases)

- **`unknown`** untuk:
  - hasil `JSON.parse`
  - body request yang belum divalidasi
  - data dari library tanpa typing (lalu sempitkan dengan type guard di materi 11)
- **`void`** untuk: handler event, fungsi logging, fungsi yang menulis ke DB tanpa return.
- **`never`** untuk: fungsi yang melempar error, exhaustive switch default (materi 11), guard di conditional type (materi 17).
- **`null`** untuk: kolom yang *eksplisit* kosong (misal `tanggalKembali` saat buku masih dipinjam).
- **`undefined`** untuk: parameter opsional / property optional (`?`) yang memang belum pernah di-set.
- **Hampir tidak pernah**: `any`. Gunakan hanya untuk migrasi JS ke TS secara bertahap atau data luar yang benar-benar tak berstruktur — lalu segera narrow.

---

## 6. Poin-poin Penting & Best Practices

1. **`any` = musuh terbesar.** `any` mematikan type checker untuk nilai itu — kembali ke semua bug materi 2. Prefer `unknown` bila tipe belum tahu.
2. **`unknown` bukan alternatif lemah `any`** — ia *lebih kuat*: memaksa kamu membuktikan tipenya sebelum memakai.
3. **`null` dan `undefined` berbeda makna**: null = "sengaja kosong", undefined = "belum pernah diisi". Dokumentasikan perbedaannya via tipe union (`string | null`).
4. **Jangan annotasi yang sudah jelas** — `const nama = "perpus"` tidak perlu `: string`. Annotation dipakai untuk parameter fungsi, tipe return, variable yang nilainya akan berubah, dan variabel tanpa initializer.
5. **`const` mempertahankan literal & immutable**, `let` membolehkan perubahan — pilih sesuai kelaziman.
6. **Manfaatkan pembeda**: `typeof x === "string"` dan pengecekan `null`/`undefined` adalah *narrowing* — keterampilan yang dipakai terus-menerus (materi 6, 10, 11).

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

| Kesalahan | Contoh | Akibat | Perbaikan |
|---|---|---|---|
| Membuat segalanya `any` | `function f(x: any)` | kehilangan semua perlindungan tipe | tipe konkret atau `unknown` |
| Menggabungkan `null` & `undefined` | `let x: string \| null` lalu akses tanpa cek | `strictNullChecks` menolak | guard `if (x !== null)` atau `??` |
| `JSON.parse` langsung akses property | `JSON.parse(s).nama` | TS18046 karena `unknown`/`any` | narrowing + type guard |
| `undefined` vs `null` tercampur | return `null` tapi dipanggil `== undefined` | logika tak konsisten | pilih salah satu representasi |
| Menggunakan `never` untuk "tidak ada" | `let x: never = 5` | error TS2322 — salah paham makna | never untuk control flow |
| Escape dengan `as any` | `(x as any).foo` | tipe rusak | perbaiki tipe yang benar |

## 8. Soal Latihan & Kunci Jawaban

### Soal 1
Untuk sistem perpustakaan, definisikan variabel berikut dengan tipe yang benar (pilih antara annotation/inference yang hemat):
1. `namaPerpustakaan` = "Perpustakaan Kota" (string)
2. `tahunBerdiri` = 1985 (number)
3. `bukaHariIni` = true (boolean)
4. `kepalaPustakawan` — bisa string, tapi mungkin belum diisi (gunakan `string | null`)
5. `versiSoftware` — belum tahu tipenya dari API (gunakan `unknown`)

Untuk poin 4, tulis ulang akses yang aman (guard) sehingga `--noEmit` lolos.

### Soal 2
Bedakan dengan singkat (1-2 kalimat):
```typescript
let a: any = "5";
let b: unknown = "5";
```
Mengapa `a.length` legal di TS tapi `b.length` bukan? Bagaimana cara aman memakai `b`?

---

### Jawaban & Pembahasan

```typescript
// Soal 1
const namaPerpustakaan = "Perpustakaan Kota";   // inference: string
const tahunBerdiri     = 1985;                   // inference: number
const bukaHariIni      = true;                   // inference: boolean

// Annotation PERLU: union tidak bisa di-infer dari null
let kepalaPustakawan: string | null = null;

// Akses yang aman (guard):
if (kepalaPustakawan !== null) {
    console.log(`Kepala: ${kepalaPustakawan.toUpperCase()}`);
}
// Atau: console.log(kepalaPustakawan?.toUpperCase() ?? "Belum ditentukan");

// unknown — dari API belum tahu strukturnya
const versiSoftware: unknown = await fetch("/api/version").then(r => r.json());
if (typeof versiSoftware === "object" && versiSoftware !== null &&
    "versi" in versiSoftware) {
    const versiStr = String((versiSoftware as { versi: string }).versi);
    console.log(versiStr);
}
```

**Pembahasan**: `string | null` dan `unknown` *tidak bisa* di-infer dari sebuah nilai — kamu **wajib** annotasi, karena maknanya lebih luas dari nilai awal.

```typescript
// Soal 2
let a: any = "5";
let b: unknown = "5";

console.log(a.length);   // ✅ any: penjagaan dimatikan, semua akses diizinkan
// console.log(b.length); // ❌ TS18046: objek bertipe unknown

// Cara aman memakai b:
if (typeof b === "string") {
    console.log(b.length);   // ✅ setelah narrowing, b dianggap string
}
```

**Pembahasan**: `any` menonaktifkan semua type-checking pada nilai itu (`a.length` lolos walau bisa saja `a = 5` nanti). `unknown` *memaksa* kamu membuktikan tipe (`typeof b === "string"`) sebelum mengakses properti — itulah alasan TS aman dan kenapa `unknown` lebih disukai daripada `any`.
