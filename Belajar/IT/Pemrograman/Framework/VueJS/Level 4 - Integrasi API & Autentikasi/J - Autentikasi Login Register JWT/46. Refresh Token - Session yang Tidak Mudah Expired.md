# 46. Refresh Token — Session yang Tidak Mudah Expired

## Penjelasan

Access token JWT biasanya berlaku singkat (15 menit) untuk keamanan. Refresh token berlaku lebih panjang (7 hari). **Refresh token flow** memperbarui access token secara otomatis tanpa user sadari menggunakan Axios interceptor.

Pattern penting: **Failed request queue** — jika beberapa request gagal 401 bersamaan, hanya SATU request yang melakukan refresh. Request lainnya menunggu dan menggunakan token baru.

```ts
// api/axios.ts
import axios from 'axios'
import { useAuthStore } from '@/stores/auth'
import router from '@/router'

let isRefreshing = false
let failedQueue: Array<{
  resolve: (token: string) => void
  reject: (err: any) => void
}> = []

function processQueue(error: any, token: string | null = null) {
  failedQueue.forEach(prom => {
    if (error) {
      prom.reject(error)
    } else {
      prom.resolve(token!)
    }
  })
  failedQueue = []
}

const api = axios.create({
  baseURL: import.meta.env.VITE_API_URL,
})

// Request interceptor — lampirkan access token
api.interceptors.request.use(config => {
  const auth = useAuthStore()
  if (auth.accessToken) {
    config.headers.Authorization = `Bearer ${auth.accessToken}`
  }
  return config
})

// Response interceptor — handle 401, refresh token
api.interceptors.response.use(
  response => response,
  async error => {
    const originalRequest = error.config

    if (error.response?.status === 401 && !originalRequest._retry) {
      if (isRefreshing) {
        // Queue — tunggu refresh selesai
        return new Promise((resolve, reject) => {
          failedQueue.push({ resolve, reject })
        }).then(token => {
          originalRequest.headers.Authorization = `Bearer ${token}`
          return api(originalRequest)
        })
      }

      originalRequest._retry = true
      isRefreshing = true

      const auth = useAuthStore()
      try {
        const res = await axios.post(
          `${import.meta.env.VITE_API_URL}/auth/refresh`,
          { refreshToken: auth.refreshToken }
        )
        const { accessToken } = res.data
        auth.accessToken = accessToken
        localStorage.setItem('accessToken', accessToken)

        processQueue(null, accessToken)
        originalRequest.headers.Authorization = `Bearer ${accessToken}`
        return api(originalRequest)
      } catch (refreshError) {
        processQueue(refreshError, null)
        auth.clearAuth()
        router.push('/login')
        return Promise.reject(refreshError)
      } finally {
        isRefreshing = false
      }
    }

    return Promise.reject(error)
  }
)

export default api
```

## Fungsi

Memberikan **seamless authentication** — user tidak perlu login ulang setiap 15 menit. Session tetap aktif selama refresh token masih berlaku.

## Cara Implementasi

1. Setup Axios instance dengan request interceptor (lampirkan Bearer token).
2. Setup response interceptor: jika 401, coba refresh token.
3. Implementasi **failed request queue** untuk handle concurrent requests.
4. Jika refresh sukses → update `accessToken` di store + localStorage, retry original request.
5. Jika refresh gagal (refresh token juga expired) → `clearAuth()` + redirect ke login.
6. Pastikan endpoint `/auth/refresh` ada di backend.

## Analogi — Toko Buku

Kartu anggota toko punya **masa berlaku 15 menit** (access token), tapi ada **"kartu perpanjangan"** (refresh token) yang berlaku 7 hari.

Setiap kali kartu utama mau habis, sistem otomatis perpanjang dengan kartu perpanjangan — tanpa pelanggan sadari. Kartu baru diberikan, masa berlaku di-reset.

**Bayangkan 3 pelanggan (3 request)** yang kartunya habis bersamaan di kasir:
- Tanpa queue: sistem perpanjang 3 kali → boros, bisa error duplicate request
- Dengan queue: sistem hanya perpanjang **SATU KALI**, lalu beri kartu baru ke semua pelanggan

Kalau kartu perpanjangan juga habis (`refreshToken` expired), pelanggan diminta ke meja registrasi lagi (`clearAuth` → redirect login).

## Dipakai untuk Apa

- Semua aplikasi dengan JWT authentication
- Mobile-friendly session (user tidak perlu login terus)
- Dashboard/admin panel yang digunakan jam kerja penuh

## Kesalahan Umum

| Kesalahan | Akibat | Solusi |
|-----------|--------|--------|
| Lupa handle concurrent request | Multiple refresh token call, race condition | Pakai failed request queue + boolean `isRefreshing` |
| Infinite retry loop | Axios terus-menerus retry 401 | Tandai request dengan `_retry: true` agar hanya sekali retry |
| Refresh token tidak dihapus saat logout | Token expired tidak berguna tapi masih disimpan | Panggil `clearAuth()` di catch refresh error |
| Tidak update token di store setelah refresh | Request berikutnya pakai token lama | Update `auth.accessToken` + localStorage |

## Hubungan dengan Materi Sebelumnya

**Poin 45:** Router guard cek token, tapi token punya masa berlaku. Refresh token memperpanjang session tanpa user sadari. Guard mencegat user yang belum login, interceptor mencegat request yang tokennya expired.

**Poin 43:** Interceptor membaca dan memperbarui `accessToken` di auth store. Store adalah sumber kebenaran token — interceptor membaca dari store, menulis hasil refresh ke store.

## Soal Latihan

### Soal 1

Jelaskan apa yang terjadi jika `isRefreshing = true` dan ada 5 request gagal 401 masuk bersamaan. Bagaimana failed queue mengatasinya?

<details>
<summary>Jawaban</summary>

Request pertama masuk → `isRefreshing = false` → memulai refresh token.  
4 request berikutnya masuk → `isRefreshing = true` → masuk ke `failedQueue` sebagai Promise.

Saat refresh selesai:
- **Sukses:** `processQueue(null, newToken)` — semua 4 Promise di-resolve dengan token baru. Masing-masing melanjutkan request dengan token baru.
- **Gagal:** `processQueue(error, null)` — semua 4 Promise di-reject. Semua request gagal.

Hasil: hanya 1 kali panggil refresh, bukan 5 kali. Efisien dan aman dari race condition.

</details>

### Soal 2

Apa risiko keamanan menyimpan refresh token di localStorage? Bagaimana mitigasinya?

<details>
<summary>Jawaban</summary>

**Risiko:** localStorage dapat diakses oleh JavaScript (XSS). Jika attacker berhasil injeksi script, mereka bisa mencuri refresh token dan membuat token baru sesuka hati.

**Mitigasi:**
1. Cegah XSS — sanitasi input, jangan pakai `v-html`, Content Security Policy headers.
2. Gunakan HttpOnly cookie untuk refresh token jika backend mendukung (tidak bisa diakses JS).
3. Set refresh token expiry pendek (7 hari atau kurang) — batasi window serangan.
4. Implementasikan refresh token rotation — setiap kali refresh, token lama invalid, token baru diberikan. Jika token curian dipakai, token asli akan invalid.
5. Gunakan `httpOnly` + `secure` + `sameSite: strict` cookies sebagai alternatif localStorage.
</details>
