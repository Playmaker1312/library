# 93. Database Indexing & Query Optimization

## Penjelasan
Seiring pertumbuhan data, query yang tadinya cepat bisa menjadi lambat secara drastis. Database tanpa index akan melakukan **sequential scan** — membaca setiap baris tabel satu per satu — yang untuk tabel dengan 1 juta baris bisa memakan waktu detik bahkan menit. **Index** adalah struktur data terpisah (seperti tabel hash atau B-tree) yang mempercepat pencarian dengan cara mengorganisir kolom tertentu agar pencariannya O(log n) bukan O(n).

Di Prisma, index didefinisikan langsung di schema dengan `@@index` atau `@@unique`. Namun index bukan solusi gratis — setiap index mempercepat `SELECT` tetapi memperlambat `INSERT`/`UPDATE`/`DELETE` karena index harus diperbarui. Jadi kita harus selektif: index hanya pada kolom yang sering difilter (`WHERE`), di-join (`JOIN ... ON`), atau di-sort (`ORDER BY`). **EXPLAIN ANALYZE** adalah perintah PostgreSQL untuk melihat execution plan query — apakah sequential scan atau index scan — sehingga kita bisa memutuskan index apa yang diperlukan. Masalah **N+1** terjadi ketika aplikasi melakukan 1 query untuk parent, lalu N query untuk setiap child (misal: ambil 100 buku, lalu untuk setiap buku ambil penulisnya — total 101 query). Fix-nya: gunakan `include` atau `join` agar jadi 1 query.

## Fungsi
- Mengurangi waktu eksekusi query dari detik ke milidetik dengan index yang tepat
- Mengidentifikasi query lambat melalui EXPLAIN ANALYZE dan logging
- Menghilangkan N+1 problem dengan eager loading (Prisma `include` / `join`)
- Menjaga performa database tetap stabil meskipun data tumbuh hingga jutaan baris

## Cara Implementasi / Code

**1. Prisma Schema dengan index — schema.prisma:**
```prisma
model Book {
  id         String   @id @default(cuid())
  title      String
  author     String
  isbn       String   @unique
  categoryId String
  category   Category @relation(fields: [categoryId], references: [id])
  published  DateTime
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt

  // Single-column index untuk pencarian by author
  @@index([author])

  // Composite index untuk filter category + published date
  @@index([categoryId, published])

  // Full-text search index (PostgreSQL)
  @@index([title], type: BTree)
}

model Loan {
  id         String   @id @default(cuid())
  bookId     String
  memberId   String
  borrowedAt DateTime @default(now())
  returnedAt DateTime?
  status     LoanStatus @default(ACTIVE)

  @@index([memberId, status])       // Index untuk cari peminjaman aktif member
  @@index([bookId, borrowedAt])     // Index untuk riwayat peminjaman buku
  @@index([status, borrowedAt])     // Index untuk laporan overdue
}

enum LoanStatus {
  ACTIVE
  RETURNED
  OVERDUE
}
```

**3. Query optimization — Fix N+1 problem:**
```typescript
// ❌ BURUK — N+1 problem
async getBooksWithCategory() {
  const books = await this.prisma.book.findMany(); // 1 query
  for (const book of books) {
    book.category = await this.prisma.category.findUnique({
      where: { id: book.categoryId }, // N query (100 buku = 100 query tambahan)
    });
  }
  return books;
}

// ✅ BAIK — Eager loading dengan include
async getBooksWithCategory() {
  return this.prisma.book.findMany({
    include: {
      category: true,  // 1 query dengan JOIN
    },
  });
}

// ✅ LEBIH BAIK — Select spesifik hanya field yang diperlukan
async getBooksWithCategory() {
  return this.prisma.book.findMany({
    include: {
      category: {
        select: { id: true, name: true },
      },
    },
  });
}
```

**4. EXPLAIN ANALYZE — Identifikasi query lambat:**
```sql
-- Jalankan langsung di database (pgAdmin, psql, dll)
EXPLAIN ANALYZE
SELECT * FROM "Book"
WHERE "author" = 'Tere Liye'
ORDER BY "published" DESC
LIMIT 20;

-- Output SEQUENTIAL SCAN (tanpa index):
-- Seq Scan on "Book"  (cost=0.00..22500.00 rows=5000 width=256)
--   Filter: (author = 'Tere Liye')
--   Planning Time: 0.123 ms
--   Execution Time: 1850.000 ms  ← 1.8 detik!

-- Output INDEX SCAN (setelah tambah @@index([author])):
-- Index Scan using "Book_author_idx" on "Book"  (cost=0.00..150.00 rows=5000 width=256)
--   Index Cond: (author = 'Tere Liye')
--   Planning Time: 0.098 ms
--   Execution Time: 12.500 ms  ← 12ms!
```

**5. Logging query lambat di Prisma:**
```typescript
// PrismaService dengan logging query
import { Injectable, Logger } from '@nestjs/common';
import { PrismaClient } from '@prisma/client';

@Injectable()
export class PrismaService extends PrismaClient {
  private readonly logger = new Logger(PrismaService.name);

  constructor() {
    super({
      log: [
        { emit: 'event', level: 'query' },  // Log semua query
        { emit: 'stdout', level: 'info' },
        { emit: 'stdout', level: 'warn' },
        { emit: 'stdout', level: 'error' },
      ],
    });
    this.$on('query' as any, (e: any) => {
      if (e.duration > 100) {
        // Query lebih dari 100ms — logging sebagai warning
        this.logger.warn(`Slow query (${e.duration}ms): ${e.query}`);
      }
    });
  }
}
```

## Analogi
Bayangkan perpustakaan dengan **10.000 buku** yang disusun RANDOM di rak. Seorang pengunjung ingin mencari buku "Laskar Pelangi". Pustakawan harus berjalan dari rak 1 ke rak 10.000 melihat satu per satu — itulah **sequential scan**. Setelah ditambahkan **katalog indeks** (index), pengunjung cukup melihat "A — Laskar Pelangi, Rak 7, Baris 3". Pustakawan langsung ke rak 7 dan mengambil buku dalam 10 detik — **index scan**. N+1 problem analog dengan: pengunjung bertanya "buku apa saja yang dipinjam Budi?", petugas cek 1x daftar pinjaman Budi (dapat 5 buku), lalu untuk setiap buku petugas lari ke rak, ambil buku, dan baca judulnya — 1 + 5 = 6 perjalanan. Dengan JOIN, petugas cukup baca 1 daftar yang sudah mencantumkan judul buku.

## Penggunaan
- Endpoint daftar buku dengan filter (author, kategori, tahun) — perlu composite index
- Dashboard laporan overdue loans — index di status + borrowedAt
- Search buku berdasarkan judul — index di title atau full-text search
- API yang meresponse data dengan relasi (book + category + loans) — eager loading

## Kesalahan Umum yang Sering Terjadi
1. **Index di kolom yang salah** — Membuat index di kolom boolean seperti `isActive` tidak berguna karena kardinalitasnya rendah (hanya true/false). Index efektif untuk kolom dengan kardinalitas tinggi (ribuan nilai unik).
2. **Terlalu banyak index** — Setiap index memperlambat write operation. Jangan buat index untuk kolom yang tidak pernah di-`WHERE` atau di-`ORDER BY`.
3. **Tidak memonitor slow query** — Tanpa logging query >100ms, kita tidak sadar ada bottleneck sampai pengguna complain.
4. **N+1 di service layer** — N+1 tidak selalu terlihat di kode; gunakan `prisma.$on('query')` untuk melihat jumlah query yang dieksekusi.
5. **Lupa menjalankan ANALYZE** — PostgreSQL menggunakan statistik untuk execution plan. Setelah buat index, jalankan `ANALYZE` agar query planner sadar ada index baru.

## Hubungan dengan Materi Sebelumnya
Di Level 2 kita membuat Prisma schema dan repository pattern. Sekarang kita optimasi schema tersebut untuk performa. Indexing adalah natural next step setelah aplikasi mulai memiliki data riil. Load testing (materi 91) akan mengungkap endpoint mana yang lambat; indexing adalah solusi pertama yang harus dicoba sebelum beralih ke solusi lebih mahal seperti caching atau hardware upgrade.

## Soal Latihan

**Soal:** Tabel `Loan` memiliki 500.000 baris. Query berikut lambat (>2 detik): mencari semua peminjaman aktif milik member tertentu, diurutkan dari yang terbaru. Tambahkan index yang sesuai di Prisma schema.

Query SQL:
```sql
SELECT * FROM "Loan"
WHERE "memberId" = 'cm123...' AND "status" = 'ACTIVE'
ORDER BY "borrowedAt" DESC
LIMIT 20;
```

**Jawaban:**
```prisma
model Loan {
  id         String   @id @default(cuid())
  bookId     String
  memberId   String
  borrowedAt DateTime @default(now())
  returnedAt DateTime?
  status     LoanStatus @default(ACTIVE)

  // Composite index mencakup filter + sort
  @@index([memberId, status, borrowedAt])
}
```

Index `[memberId, status, borrowedAt]` mencakup seluruh query: `WHERE` memfilter member dan status, lalu `ORDER BY` menggunakan borrowedAt yang sudah terindex. Ini disebut **covering index** untuk query tersebut.
