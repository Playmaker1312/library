# 33. Membuat User Schema di Prisma - Tambah Model User

## Penjelasan

Setelah sukses membuat BooksModule dan PrismaModule di level sebelumnya, sekarang kita masuk ke inti dari sistem autentikasi: **User Model**. Di NestJS dengan Prisma ORM, model User adalah representasi tabel users di database yang akan menyimpan data identitas pengguna. Model ini mencakup field seperti id, email, password (yang sudah di-hash), name, role, dan refreshToken. Role sendiri adalah enum yang membedakan tipe pengguna: USER (biasa), LIBRARIAN (petugas perpustakaan), dan ADMIN (administrator sistem).

Pendekatan Prisma sangat menguntungkan karena kita mendefinisikan schema sekali dalam format Prisma Schema Language, lalu Prisma akan meng-generate TypeScript types secara otomatis. Ini memberikan type safety penuh dari database hingga ke kode aplikasi. Setiap perubahan schema harus diikuti dengan migrasi database menggunakan `prisma migrate dev` agar perubahan tercermin di database sebenarnya.

## Fungsi

Model User berfungsi sebagai fondasi identitas digital pengguna dalam sistem perpustakaan digital ini. Setiap pengguna yang terdaftar akan memiliki record di tabel users. Role menentukan hak akses pengguna terhadap resource tertentu. Field refreshToken digunakan untuk mekanisme session persistence tanpa harus login ulang. Tanpa model ini, tidak mungkin ada sistem autentikasi dan otorisasi.

## Cara Implementasi / Code

**Tambahkan Enum Role dan Model User di `prisma/schema.prisma`:**

```prisma
enum Role {
  USER
  LIBRARIAN
  ADMIN
}

model User {
  id           Int      @id @default(autoincrement())
  email        String   @unique
  password     String
  name         String
  role         Role     @default(USER)
  refreshToken String?

  // Relasi ke model lain (jika ada, contoh: peminjaman)
  // borrowings  Borrowing[]

  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  @@map("users")
}
```

**Jalankan Migrasi:**

```bash
npx prisma migrate dev --name add-user-model
```

Perintah di atas akan:
1. Membuat file migrasi SQL di folder `prisma/migrations/`
2. Mengeksekusi migrasi ke database
3. Me-regenerate Prisma Client

**File migrasi yang dihasilkan (contoh):**

```sql
-- CreateEnum
CREATE TYPE "Role" AS ENUM ('USER', 'LIBRARIAN', 'ADMIN');

-- CreateTable
CREATE TABLE "users" (
    "id" SERIAL NOT NULL,
    "email" TEXT NOT NULL,
    "password" TEXT NOT NULL,
    "name" TEXT NOT NULL,
    "role" "Role" NOT NULL DEFAULT 'USER',
    "refreshToken" TEXT,
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    "updatedAt" TIMESTAMP(3) NOT NULL,

    CONSTRAINT "users_pkey" PRIMARY KEY ("id")
);

-- CreateIndex
CREATE UNIQUE INDEX "users_email_key" ON "users"("email");
```

**Generate Prisma Client kembali:**

```bash
npx prisma generate
```

**Type yang di-generate oleh Prisma (dapat digunakan di kode):**

```typescript
// Prisma akan meng-generate tipe ini secara otomatis
// Kita bisa menggunakannya di service/repository

import { User, Role } from '@prisma/client';

// User memiliki field: id, email, password, name, role, refreshToken, createdAt, updatedAt
// Role adalah enum: USER, LIBRARIAN, ADMIN
```

## Analogi

Di perpustakaan, setiap anggota memiliki **kartu anggota** yang berisi data pribadi (nama, email, foto). Model User ini persis seperti format kartu anggota tersebut. Kolom `role` ibarat **status keanggotaan**: pengunjung biasa (USER) hanya bisa membaca di tempat, pustakawan (LIBRARIAN) bisa mengelola buku di rak, dan kepala perpustakaan (ADMIN) bisa mengatur kebijakan seluruh perpustakaan. Kolom `refreshToken` seperti **stempel perpanjangan** di kartu — menandakan bahwa anggota masih aktif dan tidak perlu mendaftar ulang setiap kali datang.

## Penggunaan

Model User digunakan di hampir semua operasi yang melibatkan pengguna: registrasi, login, manajemen profil, dan tentu saja otorisasi akses ke endpoint-endpoint tertentu. Service seperti UsersService dan AuthService akan sangat bergantung pada model ini untuk menyimpan dan mengambil data pengguna.

## Kesalahan Umum yang Sering Terjadi

1. **Lupa migrate setelah mengubah schema**: Jika hanya mengubah schema.prisma tanpa migrasi, database tidak akan berubah dan Prisma Client akan error karena mismatch.
2. **Menyimpan password plain text**: Jangan pernah menyimpan password tanpa di-hash. Gunakan bcrypt sebelum disimpan ke kolom `password`.
3. **Lupa properti `@unique` pada email**: Tanpa constraint unique, bisa terjadi duplikasi email yang menyebabkan bug autentikasi.
4. **Tidak menjalankan `prisma generate`**: Setelah migrasi, Prisma Client perlu di-regenerate agar type definitions terbaru tersedia.

## Hubungan dengan Materi Sebelumnya

Di Level 2, kita membuat BooksModule dengan model Book. Sekarang kita menambahkan model User yang akan berinteraksi dengan Book melalui sistem autentikasi. Nantinya, hanya user dengan role tertentu yang bisa melakukan operasi CRUD pada Book. Ini adalah jembatan menuju sistem otorisasi penuh.

## Soal Latihan

**Soal 1:** Apa yang terjadi jika kita menambahkan field baru ke model User tanpa menjalankan `prisma migrate dev`?

**Jawaban:** Prisma Client akan tetap menggunakan tipe lama yang tidak memiliki field baru tersebut. Jika kita mencoba mengakses field baru di kode TypeScript, akan terjadi error type-checking. Database juga tidak akan memiliki kolom baru tersebut, sehingga query yang mencoba mengaksesnya akan gagal.

**Soal 2:** Buatlah migrasi tambahan yang menambahkan field `phoneNumber` (String, opsional) ke model User.

**Jawaban:**

```prisma
model User {
  id           Int      @id @default(autoincrement())
  email        String   @unique
  password     String
  name         String
  phoneNumber  String?  // Tambahan field baru
  role         Role     @default(USER)
  refreshToken String?
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  @@map("users")
}
```

Kemudian jalankan `npx prisma migrate dev --name add-phone-number`.

**Soal 3:** Mengapa field `refreshToken` dibuat opsional (menggunakan `?`) dan bukan wajib?

**Jawaban:** Karena saat user baru registrasi, mereka belum memiliki refresh token. Refresh token baru dibuat setelah user berhasil login. Jika field ini wajib (required), kita harus memberikan nilai dummy saat registrasi yang tidak diperlukan. Dengan opsional, kita bisa membiarkannya `null` sampai user login pertama kali.
