# 4. Error Reporting — Baca Error, Jangan Takut

> **Level 1 · Fondasi PHP** — Keterampilan paling menentukan yang membedakan programmer dan "orang yang menyalin kode".

---

## 1. Penjelasan Singkat & Konsep Dasar

Error bukan musuh — error adalah **komunikasi dari PHP** yang memberi tahu kamu *di mana* dan *mengapa* kode bermasalah. Masalahnya, secara default PHP bisa "diam saja" (menelan error) atau menampilkan pesan yang tidak lengkap. **Error reporting** adalah pengaturan untuk memastikan PHP menceritakan semuanya kepadamu selama development.

Dua hal yang diatur:

1. **`error_reporting(E_ALL)`** — "kategori error apa saja yang harus diberitahukan?" `E_ALL` = semuanya (termasuk Notice kecil yang sering disepelekan).
2. **`ini_set('display_errors', '1')`** — "bolehkah PHP mencetak error ke layar?" di development = **ya**, di production = **tidak** (ganti ke log).

Jenis-jenis error PHP (semakin parah ke bawah):

| Tipe | Contoh pesan | Akibat |
|---|---|---|
| **Notice** | `Undefined variable` | Script tetap jalan, tapi ada potensi bug |
| **Warning** | `include(): Failed opening` | Script lanjut, tapi ada bagian yang gagal |
| **Fatal Error** | `Call to undefined function` | Script berhenti di baris itu |
| **Parse Error** | `syntax error, unexpected ';'` | Script **tidak bisa dijalankan sama sekali** |

**Benang Merah:** materi 1-3 sudah membuat kamu bisa menulis dan menjalankan PHP. Tanpa skill membaca error, setiap bug akan terasa seperti menebak-nebak. Materi ini membekali kamu *bahasa* untuk mendiagnosis — keterampilan yang akan kamu pakai di semua 29 materi berikutnya.

## 2. Fungsi & Kegunaan Utama

- **Menemukan bug lebih cepat** — pesan error PHP sangat informatif: berisi *jenis error, pesan, file, dan nomor baris*. Belajar membacanya = debugging 10x lebih cepat.
- **Membedakan development vs production** — di development kamu *ingin* error tampil; di production kamu *harus* menyembunyikannya (detail error bisa membocorkan struktur kode, path, atau info database ke penyerang) dan mencatatnya ke file log.
- **Menangkap "silent failure"** — banyak bug nyata muncul sebagai *Notice/Warning* yang sepi; `E_ALL` memastikan tidak ada yang lolos diam-diam.

Cara membuat file config yang reusable:

```php
<?php
// File: config/development.php — include di awal setiap file saat development
error_reporting(E_ALL);
ini_set('display_errors', '1');
ini_set('display_startup_errors', '1');
ini_set('log_errors', '1');
ini_set('error_log', __DIR__ . '/../logs/php_errors.log');
```

```php
<?php
// File: config/production.php — JANGAN pernah dipakai di development
error_reporting(E_ALL);
ini_set('display_errors', '0');   // user tidak melihat error
ini_set('log_errors', '1');        // tapi developer bisa lihat di log
ini_set('error_log', '/var/log/php_errors.log');
```

> `ini_set()` mengubah konfigurasi saat *runtime* untuk script ini saja. Perubahan tidak permanen — ini bagus karena tiap file bisa menentukan kebijakannya.

## 3. Contoh Kode & Implementasi Real-World

`index.php` dengan error reporting aktif di bagian paling atas:

```php
<?php
// File: perpustakaan/index.php
error_reporting(E_ALL);
ini_set('display_errors', '1');
ini_set('display_startup_errors', '1');

$namaPerpustakaan = "Perpustakaan Kota";
echo "Halo, {$namaPerpustakaan}!<br>";

// Contoh error yang akan muncul berkat E_ALL:
echo $jumlahStok; // Notice: Undefined variable $jumlahStok ...
```

Output di browser (development):

```
Halo, Perpustakaan Kota!
Notice: Undefined variable: jumlahStok
in C:\laragon\www\perpustakaan\index.php on line 9
```

**Cara membaca pesan error:**

```
[Notice:] [Undefined variable: jumlahStok]
   ↑ tipe       ↑ isi masalah
[in C:\...\index.php] [on line 9]
   ↑ lokasi file      ↑ baris
```

Aturan praktis: cek **file** dan **baris** yang disebut, lalu baca variabel/fungsi yang bermasalah.

**Anti-pattern yang sering dilakukan pemula (hindari):**

```php
// ❌ Menutup error di development — kamu buta, bukan "rapi"
error_reporting(0);
@$koneksi = mysqli_connect(...); // @ juga menyembunyikan error!

// ✅ Benar: biarkan error muncul, tangani dengan benar
error_reporting(E_ALL);
```

> `@` (error suppression) menyembunyikan pesan dan memperlambat script. Jarang sekali alasan yang sah untuk memakainya. Jangan biasakan.

## 4. Analogi Sederhana

Dalam **Sistem Administrasi Kantor**:

- **Error** = memo/komplain dari staf bahwa ada masalah dalam instruksi kerja.
- **`error_reporting(E_ALL)`** = kebijakan kantor: "semua memo, sekecil apa pun, wajib dilaporkan".
- **`display_errors = 1`** = memo ditempel di papan pengumuman **kantor internal** (pengembang) — semua orang boleh lihat.
- **`display_errors = 0` + log** = di kantor cabang (production), memo ditulis di **buku besar rahasia** (log file), tidak ditempel ke dinding — pelanggan tidak perlu tahu masalah internal.
- **Parse error** = memo yang ditulis dalam bahasa yang tidak bisa dibaca staf → seluruh pekerjaan hari itu gagal dimulai.

## 5. Kapan Harus Digunakan & Kasus Penggunaan

- **Development (selalu):** aktifkan `E_ALL` + tampilkan error. Ini wajib sejak materi ini sampai seterusnya — roadmap menetapkan *"error reporting aktif di semua file"* sebagai checkpoint Level 1.
- **Saat memecahkan bug:** baca pesan error → cek file & baris → perbaiki → ulangi.
- **Production (wajib):** matikan tampilan error, aktifkan log. Jangan pernah menampilkan stack trace ke user (membocorkan struktur aplikasi).
- **Kasus nyata:** kamu membuat `katalog.php`, lupa satu variabel. Tanpa `E_ALL` halaman tampil "normal" tapi kosong — membingungkan. Dengan `E_ALL`, langsung terlihat *Notice: Undefined variable* dan lokasinya.

---

## 6. Aspek Keamanan & Best Practices (Critical)

- **Jangan pernah biarkan `display_errors` aktif di production** — pesan error sering memuat path absolut (`C:\...`), versi PHP, atau struktur query yang bisa membantu penyerang. Log ke file saja.
- **Jangan gunakan `@`** untuk menekan error — itu membuat bug tidak terlihat dan memperlambat eksekusi.
- **Best practices:**
  - `error_reporting(E_ALL)` di **setiap** file development, atau lebih baik: di file config yang di-`require` sekali.
  - Selalu baca *file* dan *line* yang ditunjukkan error sebelum mengubah kode.
  - Catat error ke log (`log_errors`, `error_log`) bahkan di development — berguna untuk kasus yang tidak muncul di browser.
  - Bedakan konfigurasi development/production — jangan disatukan dalam satu file yang diaktifkan selalu.

---

## 7. Kesalahan Umum & Debugging

- **"Halaman putih tanpa pesan apa pun"** → `display_errors` mati, atau error terjadi *sebelum* konfigurasi dijalankan. Perbaiki: letakkan `error_reporting(E_ALL); ini_set('display_errors','1');` di baris paling atas, atau cek log server (Apache error log).
- **Parse error (syntax error)** → satu `;` hilang, kutip tak seimbang, atau tag `<?php` ganda. PHP **tidak menjalankan file sama sekali** — ini yang paling "mematikan" tapi paling mudah diperbaiki.
- **"Error muncul tapi tiba-tiba hilang saat dipindah ke server"** → kamu pindah ke environment yang `display_errors=0`. Selalu ikutkan konfigurasi dev di file, atau cek log.
- **Membaca error yang salah** → sering kali *penyebab asli* ada di atas, dan error yang terlihat adalah *akibat* di bawahnya. Baca seluruh stack, mulai dari error pertama.
- **"Fatal error: Allowed memory size exhausted"** → script terlalu boros memori (misal loop tak berujung). Cek logika loop, naikkan `memory_limit` hanya sebagai tindakan terakhir.

## 8. Soal Latihan & Kunci Jawaban

### Tantangan 1
Aktifkan error reporting di sebuah file, lalu panggil variabel yang belum didefinisikan dan panggil fungsi yang tidak ada (`cetakHalo()`). Tuliskan *persis* pesan error yang muncul untuk masing-masing, dan sebutkan file serta barisnya. Apa perbedaan antara keduanya?

### Tantangan 2
Seorang teman melihat "halaman putih" saat membuka `profil.php` milikmu di production. Apa tiga kemungkinan penyebab yang paling mungkin, dan apa langkah pertama untuk memastikan penyebabnya?

### Jawaban & Pembahasan

**Tantangan 1**

```php
<?php
error_reporting(E_ALL);
ini_set('display_errors', '1');

echo $hargaBuku;      // 1) variabel belum didefinisikan
cetakHalo();          // 2) fungsi tidak ada
```

Output:
```
Notice: Undefined variable: hargaBuku in .../index.php on line 5
Fatal error: Uncaught Error: Call to undefined function cetakHalo()
in .../index.php on line 6
```

> **Pembahasan:** Kasus 1 adalah **Notice** — script tetap lanjut (dilanjutkan ke kasus 2). Kasus 2 adalah **Fatal Error** — script langsung berhenti, fungsi tidak pernah dieksekusi. Ini menunjukkan hierarki severity: Notice tidak menghentikan eksekusi, Fatal menghentikannya. Keduanya memberi tahu *file* dan *baris* — itulah kunci debugging.

**Tantangan 2** — Kemungkinan:
1. **Parse error** dalam `profil.php` (misal lupa `;`) → seluruh file gagal diproses, browser menerima kosong.
2. **`display_errors` off** sehingga fatal error tidak terlihat (konfigurasi production).
3. **Server error 500** (misal karena `include` file yang tidak ada) dan error handler default menampilkan blank.

> **Pembahasan alur:** Langkah pertama = **lihat log error** (file `error_log` atau log server Apache/Nginx). Log memberi tahu jenis error dan baris persisnya. Kedua, aktifkan sementara `display_errors` hanya di environment development untuk memverifikasi — jangan di production. Ketiga, periksa apakah file yang di-`include` memang ada dan path-nya benar. Urutan ini memastikan kamu memakai *data*, bukan menebak.
