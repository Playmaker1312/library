# 30. Event System — Arsitektur yang Loosely Coupled

Setelah memahami queue di materi 29, kita lanjut ke konsep yang melengkapi: Event System. Jika queue menangani *cara* menjalankan tugas berat, event menangani *cara memisahkan* satu kejadian dari banyak reaksi. Materi ini membuat arsitektur perpustakaan digital kita tidak "saling tempel" — controller tidak perlu tahu ke mana harus mengirim email, mencatat log, atau memperbarui statistik. Ini juga menjadi modal penting untuk Testing di Level 6, karena event bisa di-*fake*.

## 1. Penjelasan Singkat & Konsep Dasar

Event adalah cara Laravel memberi tahu sistem bahwa "sesuatu telah terjadi" tanpa perlu tahu siapa yang akan bereaksi. Saat sebuah buku dipinjam, yang terjadi adalah `BukuDipinjam` — bukan langsung "kirim email", "tulis log", "update statistik". Reaksi-reaksi itu ditangani oleh *listener* masing-masing yang bisa ditambah/hapus tanpa mengubah controller.

Ini melanjutkan semangat decoupling dari materi queue (29): di sana kita memisahkan *eksekusi* dari *request*, di sini kita memisahkan *pemicu* dari *aksi*. Nantinya listener yang berat juga bisa di-queue, menggabungkan kedua materi. Di Level 6, `Event::fake()` memudahkan kita menguji bahwa event benar-benar ter-dispatch.

## 2. Fungsi & Kegunaan Utama dalam Laravel

Masalah yang diselesaikan event adalah **coupling** (ketergantungan yang kaku). Bayangkan di `PeminjamanController::store` kita menulis langsung:

```php
Mail::to(...)->send(...);        // kirim email
Log::info('Buku dipinjam');      // tulis log
Statistik::increment('total');   // update statistik
```

Setiap kali ada reaksi baru (misal kirim WhatsApp, audit trail), kita harus *mengedit controller yang sama*. Controller jadi tambun, susah diuji, dan rawan salah.

Dengan event, controller cukup menyatakan fakta: `BukuDipinjam::dispatch($peminjaman)`. Semua reaksi terdaftar sebagai listener terpisah. Menambah reaksi baru = membuat listener baru + mendaftarkannya, tanpa menyentuh controller. Itu yang disebut *loosely coupled*.

## 3. Contoh Kode & Implementasi (Real-world Example)

**Kasus:** saat buku dipinjam, kita ingin (1) mengirim notifikasi email dan (2) memperbarui statistik perpustakaan — tanpa mengubah controller.

### Langkah 1 — Buat event

```bash
php artisan make:event BukuDipinjam
```

File: `app/Events/BukuDipinjam.php`

```php
<?php

namespace App\Events;

use App\Models\Peminjaman;
use Illuminate\Foundation\Events\Dispatchable;

class BukuDipinjam
{
    use Dispatchable;

    // public readonly supaya listener bisa akses tapi tidak bisa ubah
    public function __construct(
        public readonly Peminjaman $peminjaman,
    ) {}
}
```

### Langkah 2 — Buat listener

```bash
php artisan make:listener KirimNotifikasiPeminjaman --event=BukuDipinjam
php artisan make:listener UpdateStatistikPerpustakaan --event=BukuDipinjam
```

File: `app/Listeners/KirimNotifikasiPeminjaman.php`

```php
<?php

namespace App\Listeners;

use App\Events\BukuDipinjam;
use App\Mail\NotifikasiPeminjamanMail;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Support\Facades\Mail;

class KirimNotifikasiPeminjaman implements ShouldQueue
{
    // implements ShouldQueue membuat listener berjalan async lewat queue
    public function handle(BukuDipinjam $event): void
    {
        Mail::to($event->peminjaman->anggota->email)
            ->send(new NotifikasiPeminjamanMail($event->peminjaman));
    }
}
```

File: `app/Listeners/UpdateStatistikPerpustakaan.php`

```php
<?php

namespace App\Listeners;

use App\Events\BukuDipinjam;

class UpdateStatistikPerpustakaan
{
    public function handle(BukuDipinjam $event): void
    {
        $buku = $event->peminjaman->buku;
        $buku->increment('total_dipinjam');
    }
}
```

### Langkah 3 — Registrasi event-listener (Laravel 11)

Di Laravel 11, pendaftaran default dilakukan di `bootstrap/app.php`:

```php
<?php

use App\Events\BukuDipinjam;
use App\Listeners\KirimNotifikasiPeminjaman;
use App\Listeners\UpdateStatistikPerpustakaan;
use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Exceptions;
use Illuminate\Foundation\Configuration\Middleware;

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        api: __DIR__.'/../routes/api.php',
        commands: __DIR__.'/../routes/console.php',
        health: '/up',
    )
    ->withMiddleware(function (Middleware $middleware) {
        //
    })
    ->withEvents(function () {
        // Pasangkan event ke listener-nya
    })
    ->withExceptions(function (Exceptions $exceptions) {
        //
    })->create();
```

Catatan: jika kamu menggunakan `EventServiceProvider` (style Laravel lama), pendaftarannya sama saja:

```php
protected $listen = [
    BukuDipinjam::class => [
        KirimNotifikasiPeminjaman::class,
        UpdateStatistikPerpustakaan::class,
    ],
];
```

### Langkah 4 — Fire event dari controller

File: `app/Http/Controllers/PeminjamanController.php` (sebagian)

```php
<?php

namespace App\Http\Controllers;

use App\Events\BukuDipinjam;
use App\Models\Peminjaman;
use Illuminate\Http\Request;

class PeminjamanController extends Controller
{
    public function store(Request $request)
    {
        // ... validasi input

        $peminjaman = Peminjaman::create($request->validated());

        // Kurangi stok buku langsung (reaksi ini murni data, tetap di sini)
        $peminjaman->buku->decrement('stok');

        // Terjemahkan kejadian bisnis. Dua cara yang setara:
        BukuDipinjam::dispatch($peminjaman);
        // event(new BukuDipinjam($peminjaman));

        return response()->json($peminjaman, 201);
    }
}
```

Dengan pola ini, jika nanti ingin menambahkan reaksi "kirim notifikasi WhatsApp", cukup buat listener baru — controller tidak berubah sama sekali.

## 4. Analogi Sederhana

**Event/Listener = lonceng dapur (buzz) yang memicu banyak staf.** Saat pesanan siap, dapur membunyikan lonceng. Bagian yang relevan — pramusaji, kasir, pencuci piring — masing-masing bereaksi tanpa dapur harus tahu detailnya. Dapur cukup "memberitahu", sedangkan pelaku reaksi tersebar dan bisa datang/pergi sendiri. Itulah decoupling.

Pada sistem kita: `PeminjamanController` adalah dapur yang membunyikan lonceng `BukuDipinjam`. Staf-nya adalah `KirimNotifikasiPeminjaman` (mengantar email ke pelanggan) dan `UpdateStatistikPerpustakaan` (mencatat pesanan di buku besar). Dapur tidak peduli siapa yang mendengar lonceng — yang penting loncengnya berbunyi.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

**Gunakan event ketika "sesuatu telah terjadi" dan mungkin banyak pihak bereaksi:**

- `BukuDipinjam` -> kirim email, update statistik, tulis log aktivitas, sync ke sistem lain.
- `BukuDikembalikan` -> hitung denda, kirim bukti pengembalian, kosongkan slot.
- `AnggotaTerdaftar` -> kirim email selamat datang, buat profil default, kirim ke CRM.
- `BukuTersediaKembali` -> notifikasi anggota yang ada di antrean tunggu.

**Kapan pakai queue vs event:**

- **Queue (materi 29)** untuk *tugas antrian*: satu pekerjaan berat yang dikerjakan belakangan (email, PDF, gambar).
- **Event** untuk *kejadian dengan banyak reaksi*: satu kejadian, banyak listener independen.
- Keduanya bisa dikombinasikan: event di-fire, dan setiap listener yang berat `implements ShouldQueue` sehingga otomatis lewat queue.

**Sync vs queue driver:** di dev, `QUEUE_CONNECTION=sync` membuat listener dijalankan langsung (mudah debug). Di production, pakai `database`/`redis` supaya listener async tidak memblokir request — sama seperti job di materi 29.

## 6. Poin-poin Penting & Best Practices

- Buat event dengan `php artisan make:event` dan listener dengan `php artisan make:listener Nama --event=NamaEvent`.
- Event cukup membawa data (`public readonly Peminjaman $peminjaman`) dan menggunakan trait `Dispatchable`.
- Listener harus punya method `handle(EventNama $event)` — nama tipe parameter menentukan event mana yang diterima.
- **Pastikan listener terdaftar.** Tanpa registrasi (di `bootstrap/app.php` atau `EventServiceProvider`), event tidak memicu apa pun dan error tidak muncul.
- Listener yang berat (kirim email, API eksternal) `implements ShouldQueue` agar jalan async; listener ringan (update counter) cukup sinkron.
- Gunakan `BukuDipinjam::dispatch($peminjaman)` (trait `Dispatchable`) atau `event(new BukuDipinjam($peminjaman))`. Konsisten memilih salah satu di seluruh codebase.
- Nama event berupa kata benda kejadian (past tense): `BukuDipinjam`, `BukuDikembalikan`.
- Jangan taruh logika bisnis berat di dalam event; event itu "fakta", listener yang "bereaksi".
- Jangan duplikasi logika: jika reaksi bisa langsung sinkron maupun via event, pilih satu jalur agar tidak dobel (misal email terkirim 2x).
- Di Level 6 kita akan pakai `Event::fake()` untuk memastikan event ter-dispatch tanpa benar-benar menjalankan listener saat test.

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

- **Listener tidak terdaftar** — event di-dispatch tapi tidak ada reaksi, dan tidak ada error. Solusi: cek registrasi di `bootstrap/app.php` atau `EventServiceProvider`.
- **Lupa `implements ShouldQueue` pada listener berat** — email berjalan sinkron dan memblokir request lagi. Solusi: tambahkan `implements ShouldQueue` dan pastikan worker berjalan.
- **Menaruh semua reaksi di controller** — controller membengkak dan sulit diuji. Solusi: pindahkan reaksi ke listener.
- **Event memuat logic, bukan data** — listener jadi tidak fleksibel. Solusi: event hanya pembawa data + `Dispatchable`.
- **Mengirim object non-model di constructor** — masalah serialisasi saat listener di-queue. Solusi: bawa model atau scalar (ID, array), bukan closure.
- **Duplicate logic** — ada yang menulis reaksi langsung di controller *dan* lewat event, sehingga notifikasi terkirim dua kali. Solusi: pilih satu jalur (event) dan gunakan konsisten.
- **Tidak menjalankan worker** — listener `ShouldQueue` tidak pernah jalan, pengguna tidak menerima email, dan tidak ada error. Solusi: jalankan `php artisan queue:work` dan pantau `queue:failed`.

## 8. Soal Latihan & Kunci Jawaban

### Tantangan

1. **Latihan 1:** Buat event `BukuDikembalikan` dengan dua listener: `HitungDendaPeminjaman` (hitung dan simpan denda jika terlambat) dan `KirimBuktiPengembalian` (kirim email bukti, dibuat async dengan `ShouldQueue`). Registrasikan keduanya, lalu fire event di `PeminjamanController` pada method kembalikan buku.
2. **Latihan 2:** Jelaskan perbedaan mendasar antara event dan job, serta beri contoh kasus pada sistem perpustakaan kapan harus pakai masing-masing.

### Jawaban & Pembahasan

**Jawaban Latihan 1:**

```bash
php artisan make:event BukuDikembalikan
php artisan make:listener HitungDendaPeminjaman --event=BukuDikembalikan
php artisan make:listener KirimBuktiPengembalian --event=BukuDikembalikan
```

File: `app/Events/BukuDikembalikan.php`

```php
<?php

namespace App\Events;

use App\Models\Peminjaman;
use Illuminate\Foundation\Events\Dispatchable;

class BukuDikembalikan
{
    use Dispatchable;

    public function __construct(
        public readonly Peminjaman $peminjaman,
    ) {}
}
```

File: `app/Listeners/HitungDendaPeminjaman.php`

```php
<?php

namespace App\Listeners;

use App\Events\BukuDikembalikan;

class HitungDendaPeminjaman
{
    public function handle(BukuDikembalikan $event): void
    {
        $peminjaman = $event->peminjaman;

        // Kalau melewati batas_kembali, hitung denda (misal 5000/hari)
        if ($peminjaman->tanggal_kembali->gt($peminjaman->batas_kembali)) {
            $hariTerlambat = $peminjaman->batas_kembali
                ->diffInDays($peminjaman->tanggal_kembali);

            $peminjaman->update(['denda' => $hariTerlambat * 5000]);
        }
    }
}
```

File: `app/Listeners/KirimBuktiPengembalian.php`

```php
<?php

namespace App\Listeners;

use App\Events\BukuDikembalikan;
use App\Mail\BuktiPengembalianMail;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Support\Facades\Mail;

class KirimBuktiPengembalian implements ShouldQueue
{
    public function handle(BukuDikembalikan $event): void
    {
        Mail::to($event->peminjaman->anggota->email)
            ->send(new BuktiPengembalianMail($event->peminjaman));
    }
}
```

Registrasi (Laravel 11, di `bootstrap/app.php`):

```php
->withEvents(function () {
    //
})
```

Lalu di `EventServiceProvider` atau langsung daftarkan pasangan:

```php
protected $listen = [
    BukuDikembalikan::class => [
        HitungDendaPeminjaman::class,
        KirimBuktiPengembalian::class,
    ],
];
```

Fire di controller:

```php
public function kembalikan(Request $request, Peminjaman $peminjaman)
{
    $peminjaman->update(['tanggal_kembali' => now()]);

    BukuDikembalikan::dispatch($peminjaman);

    return response()->json($peminjaman);
}
```

**Alur:** `kembalikan()` hanya memperbarui tanggal lalu membunyikan lonceng `BukuDikembalikan`. Laravel memanggil `HitungDendaPeminjaman` (sinkron, menghitung denda) dan melempar `KirimBuktiPengembalian` ke queue karena `ShouldQueue` — jadi email tidak memblokir request.

**Jawaban Latihan 2 — perbedaan event vs job:**

| Aspek | Event | Job (Queue) |
|---|---|---|
| Arti | "Sesuatu telah terjadi" | "Ada tugas yang harus dikerjakan" |
| Reaksi | Banyak listener independen | Satu pekerjaan, satu `handle()` |
| Fokus | Decoupling pemicu dari aksi | Menunda eksekusi berat |
| Contoh | `BukuDipinjam` -> email + statistik + log | `KirimEmailKonfirmasiPeminjaman` kirim 1 email |

Kasus perpustakaan: pakai **event** untuk `BukuDipinjam` karena satu kejadian memicu banyak reaksi yang bisa bertambah. Pakai **job** untuk `KirimEmailKonfirmasiPeminjaman` karena itu satu tugas berat yang ditunda. Keduanya saling melengkapi — listener yang berat (kirim email) justru diimplementasikan sebagai `ShouldQueue`, memakai mekanisme queue dari materi 29.
