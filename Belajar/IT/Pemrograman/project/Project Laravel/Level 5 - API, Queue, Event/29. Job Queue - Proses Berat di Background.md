# 29. Job Queue — Proses Berat di Background

Setelah berhasil membangun REST API dengan Sanctum di Level 5, sekarang waktunya menyelesaikan masalah klasik: proses yang lambat memblokir request. Di materi ini kita akan belajar Job Queue — cara mengeksekusi pekerjaan berat secara asinkron di background agar API tetap responsif. Materi ini langsung berhubungan dengan Event System di materi 30, karena listener event juga bisa diubah menjadi job.

## 1. Penjelasan Singkat & Konsep Dasar

Queue adalah mekanisme antrean tugas. Saat sebuah proses berat (misalnya kirim email) dijalankan langsung di dalam controller, request akan "diblokir" selama proses itu berjalan. Bayangkan user menekan tombol "Pinjam Buku" lalu harus menunggu 2 detik hanya karena email konfirmasi dikirim secara sinkron.

Dengan queue, kita cukup mendaftarkan tugas ke antrean, lalu request langsung selesai. Tugasnya diproses nanti oleh *worker* yang berjalan di background. Ini melanjutkan konsep REST API dari materi sebelumnya — dan menjadi fondasi untuk Testing di Level 6 (karena queue mudah di-fake saat test).

## 2. Fungsi & Kegunaan Utama dalam Laravel

Queue menjawab dua masalah utama:

1. **Request yang lambat.** Operasi berat seperti kirim email, generate PDF, resize gambar, atau panggil API eksternal memakan waktu detik-an. Jika dijalankan sinkron, user menunggu dan halaman terasa lambat. Dengan queue, request balas dalam milidetik dan proses berat jalan di belakang.
2. **Kebutuhan decoupling dan retry.** Kalau proses berat gagal (misal server email down), dengan queue tugas bisa di-*retry* secara otomatis dengan backoff. Tanpa queue, user harus mencoba lagi manual atau kita kehilangan data proses tersebut.

Laravel menyediakan banyak driver queue: `sync` (langsung eksekusi, default di dev), `database` (mudah, tanpa dependency), dan `redis` (cepat, cocok untuk production).

## 3. Contoh Kode & Implementasi (Real-world Example)

**Kasus:** setiap peminjaman berhasil, kita kirim email konfirmasi ke anggota. Email butuh ~2 detik. Kita tidak mau user menunggu, jadi kita jadikan job.

### Langkah 1 — Setup tabel jobs

```bash
# Buat migration untuk tabel jobs (dan failed_jobs)
php artisan queue:table
php artisan migrate
```

### Langkah 2 — Set driver queue

```env
# .env
# Dev: pakai database (tanpa Redis, gampang diamati lewat tabel)
QUEUE_CONNECTION=database

# Production: pakai redis yang jauh lebih cepat
# QUEUE_CONNECTION=redis
```

### Langkah 3 — Buat job

```bash
php artisan make:job KirimEmailKonfirmasiPeminjaman
```

### Langkah 4 — Isi job

File: `app/Jobs/KirimEmailKonfirmasiPeminjaman.php`

```php
<?php

namespace App\Jobs;

use App\Models\Peminjaman;
use App\Mail\KonfirmasiPeminjamanMail;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;
use Illuminate\Support\Facades\Mail;

class KirimEmailKonfirmasiPeminjaman implements ShouldQueue
{
    use Queueable;

    // Dependency constructor: job ini bisa discan oleh worker karena model di-serialize
    public function __construct(
        private Peminjaman $peminjaman,
    ) {}

    // Ini fungsi yang dieksekusi worker di background
    public function handle(): void
    {
        Mail::to($this->peminjaman->anggota->email)
            ->send(new KonfirmasiPeminjamanMail($this->peminjaman));
    }

    // Dipanggil kalau job sudah gagal dan tidak mau di-retry lagi
    public function failed(\Throwable $e): void
    {
        logger()->error('Email konfirmasi gagal terkirim', [
            'peminjaman_id' => $this->peminjaman->id,
            'error' => $e->getMessage(),
        ]);
    }

    // Konfigurasi tambahan: jumlah percobaan, batas waktu, jeda antar retry
    public int $tries = 3;
    public int $timeout = 60;

    public function backoff(): array
    {
        return [5, 15, 60]; // retry pertama setelah 5 dtk, lalu 15, lalu 60
    }
}
```

### Langkah 5 — Dispatch dari controller

File: `app/Http/Controllers/PeminjamanController.php` (sebagian)

```php
<?php

namespace App\Http\Controllers;

use App\Jobs\KirimEmailKonfirmasiPeminjaman;
use App\Models\Peminjaman;
use Illuminate\Http\Request;

class PeminjamanController extends Controller
{
    public function store(Request $request)
    {
        // ... validasi & simpan peminjaman

        $peminjaman = Peminjaman::create($request->validated());

        // Dispatch ke queue "email", baru jalan 10 detik lagi
        // Kenapa onQueue? Supaya worker bisa fokus per jenis tugas
        KirimEmailKonfirmasiPeminjaman::dispatch($peminjaman)
            ->delay(now()->addSeconds(10))
            ->onQueue('email');

        return response()->json($peminjaman, 201);
    }
}
```

### Langkah 6 — Jalankan worker

```bash
# Proses antrean di queue "email", lalu fallback ke "default"
# tries=3: maksimal 3x percobaan; timeout=60: tiap job maksimal 60 detik
php artisan queue:work --queue=email,default --tries=3 --timeout=60

# Di production, worker diawasi oleh Supervisor agar restart otomatis
# Contoh konfigurasi supervisor di /etc/supervisor/conf.d/laravel-worker.conf:
# [program:laravel-worker]
# command=php /path/project/artisan queue:work --queue=email,default --sleep=3 --tries=3
# autostart=true
# autorestart=true
```

### Langkah 7 — Pantau dan retry job gagal

```bash
# Lihat semua job yang gagal
php artisan queue:failed

# Retry job gagal tertentu (isi dengan ID dari queue:failed) atau retry semua
php artisan queue:retry <id_job>

# Hapus semua job gagal
php artisan queue:flush

# Monitor statistik antrean (jumlah job, worker, memory)
php artisan queue:monitor email:default
```

## 4. Analogi Sederhana

**Queue = prep bahan di dapur belakang.** Saat kasir menerima banyak pesanan, memasak semua makanan di depan kasir akan membuat antrean pembayaran macet. Dapur belakang mengerjakan persiapan berat secara paralel di antrean tersendiri, sementara kasir tetap cepat melayani pelanggan. Customer diberi nomor antrean — begitu juga job punya ID dan bisa di-*retry* kalau gagal.

Pada sistem kita: kasir adalah `PeminjamanController`, pesanan adalah request, dan "memasak" adalah mengirim email. Request langsung selesai karena email "dimasak" di dapur belakang (worker queue).

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

**Gunakan queue untuk tugas yang berat, lambat, atau boleh ditunda:**

- Kirim email notifikasi/konfirmasi (contoh: `KirimEmailKonfirmasiPeminjaman`)
- Generate PDF/laporan laporan peminjaman
- Proses/resize gambar cover buku
- Panggil API eksternal (misal cek ISBN, push notifikasi)
- Proses batch (impor data buku dari file Excel)

**Jangan selalu queue:** operasi yang user wajib tunggu hasilnya (misal validasi login) tetap jalankan sinkron.

**Pemilihan driver:**

| Driver | Cocok untuk | Catatan |
|---|---|---|
| `sync` | Pengembangan lokal | Eksekusi langsung, gampang debug |
| `database` | Dev / produksi kecil | Tanpa dependency tambahan |
| `redis` | Production skala besar | Cepat, butuh Redis server |

**Hubungan dengan event (materi 30):** listener event yang berat (kirim email, update statistik) juga bisa `implements ShouldQueue`. Jadi queue dan event sering dipakai bersamaan.

## 6. Poin-poin Penting & Best Practices

- Jangan lupa `php artisan queue:table` lalu `migrate`, kalau tidak muncul error `SQLSTATE: table not found` (tabel jobs tidak ada).
- `QUEUE_CONNECTION=sync` bagus untuk dev tapi jangan dipakai di production karena semua job menjadi *blocking* lagi.
- Job harus `implements ShouldQueue` agar diproses asinkron; tanpa itu, `handle()` langsung dieksekusi sinkron di request.
- Constructor menerima dependency (biasanya model) — model di-serialize otomatis, jadi jangan pass object yang bukan model (akan error `SerializesModels`).
- Tulis logika utama di `handle()`, dan tambahkan `failed()` untuk logging error.
- Atur `$tries`, `$timeout`, dan `backoff()` sesuai karakter tugas. Timeout terlalu kecil bikin job gagal padahal sebenarnya lama.
- Nama job berbasis *action* (verb): `KirimEmailKonfirmasiPeminjaman`, bukan `EmailPeminjaman`.
- Gunakan `->onQueue('email')` untuk memisahkan antrean per jenis tugas dan jalankan worker khusus: `--queue=email,default`.
- Jangan dispatch job yang sangat berat langsung di web request; tetap cepat, tapi jangan overload worker.
- Di production, kelola worker dengan Supervisor (auto-restart) dan pantau via `queue:failed`.

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

- **Error `SQLSTATE[HY000] ... table not found`** — lupa menjalankan `queue:table` dan `migrate`. Solusi: buat tabel jobs.
- **`QUEUE_CONNECTION=sync` di production** — semua job jalan sinkron dan memblokir request. Solusi: pakai `database` atau `redis`.
- **Job gagal tanpa ada log** — tidak ada `failed()` method atau tidak menjalankan `queue:failed`. Solusi: definisikan `failed()` dan cek `queue:failed` berkala.
- **`SerializesModels` error** — constructor menerima object yang bukan instance model (misal collection). Solusi: pastikan hanya model (atau array ID) yang masuk.
- **`timeout` terlalu kecil** — job yang butuh 3 menit diberi timeout 60 detik, gagal terus. Solusi: ukur durasi sebenarnya dan sesuaikan timeout.
- **Menjalankan `dispatch()` di dalam `handle()`** — membuat job memicu job lain secara tak terbatas. Solusi: dispatch dari controller/service, bukan dari dalam job.
- **Tidak mengecek `queue:failed`** — job gagal mengendap dan pengguna tidak menerima email tanpa tahu. Solusi: integrasikan monitoring (queue:monitor, FailedJobProvider).

## 8. Soal Latihan & Kunci Jawaban

### Tantangan

1. **Latihan 1:** Buat job `KirimEmailDendaPeminjaman` yang mengirim email denda ke anggota ketika peminjaman melewati `batas_kembali`. Job harus punya `tries = 3`, `timeout = 30`, dan logging di `failed()`. Dispatch dari `PeminjamanController::update` (atau method kembalikan buku) ke queue `email`.
2. **Latihan 2:** Setelah menyelesaikan Latihan 1, amati di tabel `jobs` (database). Jelaskan alur: apa yang terjadi saat dispatch, siapa yang memproses, dan bagaimana cara melihat/retry job yang gagal.

### Jawaban & Pembahasan

**Jawaban Latihan 1:**

```bash
php artisan make:job KirimEmailDendaPeminjaman
```

File: `app/Jobs/KirimEmailDendaPeminjaman.php`

```php
<?php

namespace App\Jobs;

use App\Mail\DendaPeminjamanMail;
use App\Models\Peminjaman;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;
use Illuminate\Support\Facades\Mail;

class KirimEmailDendaPeminjaman implements ShouldQueue
{
    use Queueable;

    public int $tries = 3;
    public int $timeout = 30;

    public function __construct(
        private Peminjaman $peminjaman,
    ) {}

    public function handle(): void
    {
        // Pastikan denda benar-benar terhitung sebelum kirim email
        $denda = $this->peminjaman->hitungDenda();

        Mail::to($this->peminjaman->anggota->email)
            ->send(new DendaPeminjamanMail($this->peminjaman, $denda));
    }

    public function failed(\Throwable $e): void
    {
        logger()->error('Email denda gagal terkirim', [
            'peminjaman_id' => $this->peminjaman->id,
            'error' => $e->getMessage(),
        ]);
    }
}
```

Dispatch di controller:

```php
public function kembalikan(Request $request, Peminjaman $peminjaman)
{
    $peminjaman->update(['tanggal_kembali' => now()]);

    if ($peminjaman->hitungDenda() > 0) {
        KirimEmailDendaPeminjaman::dispatch($peminjaman)
            ->delay(now()->addSeconds(5))
            ->onQueue('email');
    }

    return response()->json($peminjaman);
}
```

**Pembahasan Latihan 2 (alur queue):**

1. Saat `dispatch()` dipanggil, Laravel memasukkan satu baris ke tabel `jobs` dengan payload berisi model `Peminjaman` yang di-serialize (sebenarnya yang disimpan adalah class name + ID, lalu di-*restore* saat diproses — inilah manfaat `SerializesModels`).
2. Worker (`php artisan queue:work --queue=email`) menarik job paling depan yang tersedia, mengeksekusi `handle()`, lalu menandai job sebagai selesai dan menghapusnya dari tabel.
3. Kalau `handle()` melempar exception, worker menganggap gagal. Karena `tries = 3`, job dicoba ulang setelah jeda `backoff` (default 5 detik antar percobaan). Setelah 3x gagal, job dipindah ke tabel `failed_jobs`.
4. Untuk memantau: `php artisan queue:failed` menampilkan daftar; `php artisan queue:retry <id>` memindahkan job gagal kembali ke antrean; `php artisan queue:flush` membersihkan semua job gagal. Pastikan `failed()` menulis log supaya error tidak berlalu tanpa jejak.
