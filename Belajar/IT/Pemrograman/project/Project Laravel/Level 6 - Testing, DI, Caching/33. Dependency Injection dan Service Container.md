# 33. Dependency Injection dan Service Container

Di Level 2 materi 14 kita sudah kenal konsep DI secara sederhana: "jangan buat objek di dalam, minta saja dari luar". Sekarang kita perdalam: Laravel punya **Service Container** — wadah yang mengurus pembuatan objek dan dependency-nya secara otomatis. Materi ini adalah fondasi sebelum masuk ke Action Pattern (35), karena action yang testable juga bergantung pada cara kita meng-inject dependency.

## 1. Penjelasan Singkat & Konsep Dasar

**Dependency Injection (DI)** adalah pola di mana sebuah class tidak membuat dependency-nya sendiri, melainkan menerimanya dari luar (lewat constructor, setter, atau parameter method). Ini membuat class lebih longgar terikat (loose coupling) dan mudah diuji.

**Service Container** adalah mesin Laravel yang bertugas:
- Menyimpan "resep" (binding) cara membuat sebuah class.
- Me-resolve (membuatkan) class beserta seluruh dependency-nya secara otomatis.
- Memungkinkan kita mengganti implementasi konkret dengan interface.

Kaitannya dengan materi lain:
- **Testing (Level 6)** — berkat DI, kita bisa inject *mock* ke controller tanpa menyentuh kode produksi.
- **Action Pattern (35)** — action class menerima dependency lewat constructor injection, persis seperti controller kita.
- **BukuRepositoryInterface + EloquentBukuRepository** — contoh nyata binding interface ke implementasi.

## 2. Fungsi & Kegunaan Utama dalam Laravel

Service Container menyelesaikan tiga masalah klasik:

1. **Manual `new` di mana-mana.** Bayangkan kalau setiap controller menulis `new EloquentBukuRepository()` — kalau nanti ganti ke repository berbasis API eksternal, semua file harus dirombak. Container memusatkan keputusan itu di satu tempat (AppServiceProvider).

2. **Kesulitan mocking saat testing.** Kalau controller membuat dependency sendiri, test tidak punya celah untuk menyuntikkan pengganti (fake/mock). Dengan DI, kita tinggal me-resolve object dari container lalu mengganti binding-nya.

3. **Arsitektur tidak testable.** Konstruksi objek yang tersebar membuat kode susah diuji dan susah diprediksi. Container menyeragamkan cara objek lahir.

Alasan Laravel memakai ini: memungkinkan *auto-resolution* — cukup type-hint di parameter constructor, Laravel menebak dan membuatkan objeknya. Tidak perlu konfigurasi apa-apa untuk class sederhana; konfigurasi hanya dibutuhkan saat ada *interface* yang harus dipetakan ke implementasi.

## 3. Contoh Kode & Implementasi (Real-world Example)

Kasus nyata: repository buku untuk sistem Perpustakaan Digital.

### a) Interface — kontrak perilaku

Lokasi: `app/Repositories/BukuRepositoryInterface.php`

```php
<?php

namespace App\Repositories;

use App\Models\Buku;
use Illuminate\Database\Eloquent\Collection;

interface BukuRepositoryInterface
{
    public function findAll(): Collection;

    public function findById(int $id): ?Buku;

    public function create(array $data): Buku;

    public function update(Buku $buku, array $data): Buku;

    public function delete(Buku $buku): bool;
}
```

### b) Implementasi konkret dengan Eloquent

Lokasi: `app/Repositories/EloquentBukuRepository.php`

```php
<?php

namespace App\Repositories;

use App\Models\Buku;
use Illuminate\Database\Eloquent\Collection;

class EloquentBukuRepository implements BukuRepositoryInterface
{
    public function findAll(): Collection
    {
        return Buku::query()
            ->with('penulis')   // eager load supaya tidak N+1
            ->get();
    }

    public function findById(int $id): ?Buku
    {
        return Buku::with('penulis')->find($id);
    }

    public function create(array $data): Buku
    {
        return Buku::create($data);
    }

    public function update(Buku $buku, array $data): Buku
    {
        $buku->update($data);

        return $buku->refresh();
    }

    public function delete(Buku $buku): bool
    {
        return $buku->delete();
    }
}
```

### c) Daftarkan binding di AppServiceProvider

Lokasi: `app/Providers/AppServiceProvider.php`

```php
<?php

namespace App\Providers;

use App\Repositories\BukuRepositoryInterface;
use App\Repositories\EloquentBukuRepository;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // Setiap kali ada yang butuh interface, berikan implementasi konkret.
        $this->app->bind(BukuRepositoryInterface::class, EloquentBukuRepository::class);

        // Singleton: hanya dibuat sekali, dipakai bersama sepanjang request/process.
        // Cocok untuk service yang menyimpan state (mis. service statistik aktif).
        // $this->app->singleton(StatistikService::class);
    }

    public function boot(): void
    {
        // Untuk hal yang harus jalan setelah semua provider terdaftar
        // (mis. register event listener, gate, middleware aliases).
    }
}
```

Catatan: `bind` membuat instance **baru setiap kali di-resolve**. `singleton` membuat satu instance yang dibagikan. Pilih `singleton` hanya untuk service yang memang stateful dan aman dibagi.

### d) Constructor injection di BukuController

Lokasi: `app/Http/Controllers/BukuController.php`

```php
<?php

namespace App\Http\Controllers;

use App\Repositories\BukuRepositoryInterface;
use Illuminate\Http\Request;
use Illuminate\View\View;
use Symfony\Component\HttpFoundation\RedirectResponse;

class BukuController extends Controller
{
    public function __construct(
        // Auto-resolution: cukup type-hint, Laravel membuatkannya.
        private BukuRepositoryInterface $bukuRepository,
    ) {
    }

    public function index(): View
    {
        $daftarBuku = $this->bukuRepository->findAll();

        return view('buku.index', ['daftarBuku' => $daftarBuku]);
    }

    public function store(Request $request): RedirectResponse
    {
        $data = $request->validate([
            'judul' => 'required|string|max:255',
            'penulis_id' => 'required|exists:penulis,id',
            'jumlah_stok' => 'required|integer|min:0',
        ]);

        $this->bukuRepository->create($data);

        return redirect()->route('buku.index')
            ->with('sukses', 'Buku berhasil ditambahkan.');
    }
}
```

### e) Resolve manual dari container (tidak selalu diperlukan)

```php
use Illuminate\Support\Facades\App;

// Membuat/mengambil instance dari container
$repo = App::make(BukuRepositoryInterface::class);

// Bind cepat untuk satu resolve (kadang dipakai saat testing)
App::bind(BukuRepositoryInterface::class, EloquentBukuRepository::class);
```

Utamakan constructor injection. Resolve manual via `app()->make()` hanya untuk kasus khusus (mis. factory, atau kondisi dinamis).

### f) Mock saat testing (mengapa DI ini berharga)

Lokasi: `tests/Feature/BukuControllerTest.php`

```php
<?php

namespace Tests\Feature;

use App\Repositories\BukuRepositoryInterface;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Tests\TestCase;

class BukuControllerTest extends TestCase
{
    use RefreshDatabase;

    public function test_index_menampilkan_daftar_buku(): void
    {
        // Ganti implementasi asli dengan fake — tanpa DB, test jadi cepat & deterministik.
        $this->app->bind(BukuRepositoryInterface::class, function () {
            $fake = $this->createMock(BukuRepositoryInterface::class);
            $fake->method('findAll')->willReturn(collect([
                ['judul' => 'Belajar Laravel 11'],
            ]));

            return $fake;
        });

        $response = $this->get(route('buku.index'));

        $response->assertOk();
        $response->assertSee('Belajar Laravel 11');
    }
}
```

## 4. Analogi Sederhana

Bayangkan restoran. Koki tidak menyimpan semua alat di sakunya — saat butuh pisau, **manajer restoran** memberikannya. Itu Service Container:

- **Service Container = Manajer** yang menyiapkan peralatan & staf sesuai kebutuhan tiap pekerjaan. Koki (controller) cukup *mengucapkan* apa yang dibutuhkan (type-hint), manajer langsung memberikannya (DI otomatis).
- **Interface = spesifikasi pekerjaan** ("saya butuh seseorang yang bisa memasak nasi goreng"). Manajer yang memilih staf konkret yang sesuai (mis. staf A hari ini, staf B besok) — controller tidak peduli siapa.
- **Saat QC (testing), manajer bisa mengganti staf asli dengan staf latihan** — inilah mocking. Koki tetap mendapat "seseorang yang memasak nasi goreng", tapi kali ini itu boneka latihan, bukan koki asli.

Intinya: siapa pun yang di-resolve, controller tetap bekerja terhadap kontrak (interface), bukan terhadap orang/implementasi tertentu.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

| Situasi | Keputusan |
|---|---|
| Type-hint class biasa (mis. `Request`, model, service stateless) | **Auto-resolution** — tidak perlu binding apa pun |
| Controller butuh interface (`BukuRepositoryInterface`) | **Bind interface ke concrete** di `register()` |
| Service stateful yang boleh dibagi (koneksi cache, service statistik) | **Singleton** |
| Data berbeda per request / harus baru tiap kali | **Bind** biasa |
| Tidak ada kebutuhan untuk swap/mock | **Jangan buat repository** — langsung pakai Eloquent |

Kapan **tidak** boleh over-engineer:
- Repository hanya menambah nilai kalau kamu punya alasan nyata: akan ganti storage, mau mocking lebih bersih, atau ada logika query yang dipakai banyak tempat.
- Untuk CRUD sederhana yang langsung pakai model, `Buku::all()` di controller sudah cukup. Menambah lapisan tanpa kebutuhan = kerumitan yang tidak perlu.

## 6. Poin-poin Penting & Best Practices

- **Auto-resolution via type-hint**: cukup tulis tipe di parameter constructor, Laravel membuatkannya. Tidak perlu daftar untuk class konkret.
- **`$this->app->bind(Interface, Concrete)`** di `AppServiceProvider::register()` untuk memetakan interface ke implementasi.
- **`singleton`** hanya untuk service stateful yang aman dibagi; jangan asal singleton.
- **Resolve** lebih baik lewat constructor injection. Hindari `app()->make()` bertebaran.
- **Jangan service locator berlebihan** — pola `app('repo')` di dalam method membuat dependency tersembunyi dan susah ditest.
- **Contract (interface) meningkatkan testability**: kamu bisa swap fake tanpa menyentuh kode pemanggil.
- **`register()` vs `boot()`**: daftarkan binding di `register()`; pakai `boot()` untuk hal yang butuh semua provider sudah termuat (listener, gate).
- **Jangan over-engineer**: buat repository hanya kalau benar-benar menambah nilai.

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

1. **"Target [X] is not instantiable"** — interface belum di-bind ke concrete. Solusi: tambahkan binding di `AppServiceProvider::register()`.

2. **Salah pakai `bind` vs `singleton`** — service yang menyimpan state (mis. penghitung, buffer) dipakai `bind`, akibatnya tiap resolve mendapat instance baru dan state hilang; atau kebalikannya, singleton untuk objek berstate yang ternyata dipakai tiap request sehingga data bocor antar request.

3. **Meng-inject class konkret padahal butuh interface** — mis. type-hint `EloquentBukuRepository` di controller. Ini mengunci controller ke implementasi tertentu; hilanglah manfaat swap & mock. Type-hint interface-nya.

4. **`app()->make()` berlebihan (service locator)** — dependency jadi tersembunyi, test lebih sulit, dan kode susah dibaca.

5. **Membuat repository padahal tidak perlu** — lapisan abstraksi tanpa alasan membuat kode lebih banyak untuk dirawat (over-engineering).

6. **Lupa meng-update mock saat contract berubah** — jika interface menambah method, semua implementasi & mock lama langsung error; ini sebenarnya "bug yang baik" karena dikomplain di waktu compile/test, bukan di production.

## 8. Soal Latihan & Kunci Jawaban

### Tantangan

1. Daftarkan `BukuRepositoryInterface` → `EloquentBukuRepository` sebagai singleton, lalu jelaskan kapan keputusan itu benar dan kapan salah.
2. Tulis test `buku_store_menyimpan_data_baru` di mana `BukuRepositoryInterface` di-mock sehingga `create()` mengembalikan Buku palsu tanpa menyentuh database, lalu verifikasi redirect berhasil.

### Jawaban & Pembahasan

**1. Binding sebagai singleton**

```php
// app/Providers/AppServiceProvider.php
public function register(): void
{
    $this->app->singleton(
        BukuRepositoryInterface::class,
        EloquentBukuRepository::class
    );
}
```

Pembahasan:
- **Benar** jika `EloquentBukuRepository` tidak menyimpan state yang berbeda-beda per request (repository kita stateless — hanya membungkus query). Dengan singleton, satu instance dipakai semua controller dalam satu process; hasil sama, konsumsi memori lebih hemat.
- **Salah** jika repository menyimpan state per request (mis. menyimpan nilai counter internal, atau memegang cache lokal yang bisa kadaluarsa). Jika begitu, pakai `bind` biasa agar tiap request mendapat instance segar.

**2. Test dengan mock repository**

```php
<?php

namespace Tests\Feature;

use App\Models\Buku;
use App\Repositories\BukuRepositoryInterface;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Tests\TestCase;

class BukuControllerTest extends TestCase
{
    use RefreshDatabase;

    public function test_store_menyimpan_data_baru(): void
    {
        // Siapkan Buku palsu yang akan "dikembalikan" oleh mock.
        $bukuPalsu = new Buku(['judul' => 'Laravel 11', 'jumlah_stok' => 5]);

        $mock = $this->createMock(BukuRepositoryInterface::class);
        $mock->expects($this->once())          // pastikan create() benar dipanggil sekali
            ->method('create')
            ->willReturn($bukuPalsu);

        // Ganti implementasi di container — ini yang membuat test terisolasi.
        $this->app->instance(BukuRepositoryInterface::class, $mock);

        $response = $this->post(route('buku.store'), [
            'judul' => 'Laravel 11',
            'penulis_id' => 1,
            'jumlah_stok' => 5,
        ]);

        $response->assertRedirect(route('buku.index'));
        $response->assertSessionHas('sukses', 'Buku berhasil ditambahkan.');
    }
}
```

Pembahasan alur:
1. Karena `BukuController` menerima `BukuRepositoryInterface` lewat constructor, kita bisa menukarnya.
2. `$this->app->instance()` mengganti implementasi di container dengan mock.
3. Saat request `POST /buku` masuk, container me-resolve controller dan menyuntikkan mock.
4. `create()` tidak menyentuh database — behavior-nya dikendalikan test.
5. `expects($this->once())` memverifikasi controller memang memanggil `create()` tepat satu kali.
6. Test ini membuktikan alasan utama kita pakai DI: **logika controller bisa diuji tanpa DB**, cepat dan deterministik.
