# 32. Unit Test dan Mocking

Jika feature test menguji seluruh alur HTTP, unit test justru mempersempit fokus: hanya satu class atau satu method, tanpa database dan framework penuh. Materi ini melanjutkan materi 31 (Feature Test) dan membuka jalan ke materi 33 (Service Container), karena dependency injection yang rapi itulah yang membuat sebuah method mudah diuji secara terisolasi.

## 1. Penjelasan Singkat & Konsep Dasar

Unit test menguji satu unit kecil kode — biasanya satu method pada satu class — secara terisolasi. Isolasi berarti kita tidak menyalakan server, tidak membutuhkan HTTP request, dan umumnya tidak menyentuh database. Inilah bedanya dengan feature test: di feature test kita menjalankan aplikasi seutuhnya; di unit test kita langsung memanggil method-nya dan mengecek hasil kembaliannya.

```bash
php artisan make:test BukuTest --unit
```

Perintah di atas membuat file `tests/Unit/BukuTest.php`. File unit test berada di folder `tests/Unit`, sedangkan feature test di `tests/Feature`.

Kenapa bisa diuji tanpa framework penuh? Karena method yang bagus itu punya dependency yang bisa "disuntikkan" (dikirim lewat parameter atau constructor). Konsep inilah yang nanti diperdalam di materi 33 (Service Container): Laravel meresolusi dependency otomatis, dan saat testing kita bisa menggantinya dengan fake/mock. Jadi hubungannya saling menguatkan — DI yang baik membuat kode mudah dites, testing yang baik menuntut DI yang baik.

## 2. Fungsi & Kegunaan Utama dalam Laravel

Laravel mendukung unit test secara native lewat PHPUnit (dengan Pest sebagai alternatif modern). Kegunaan utamanya:

- **Menguji logika murni dengan cepat**: method seperti `Buku::tersedia()` atau `Buku::harga_format()` tidak butuh HTTP — test-nya jalan dalam milidetik.
- **Menangkap regresi logika**: perubahan kecil pada format harga atau logika stok langsung terdeteksi tanpa harus membuka browser.
- **Fondasi TDD**: saat mengerjakan method kecil, tulis unit test dulu, lihat merah, implementasikan, lihat hijau.
- **Isolasi dependency eksternal**: mail, queue, event, storage, dan HTTP client tidak perlu benar-benar berjalan karena bisa di-fake.
- **Speed di CI**: unit test yang cepat membuat feedback loop cepat saat pipeline (materi 37) dijalankan.

Masalah yang diselesaikan: logika kecil yang tampak sederhana (misal format angka atau cek ketersediaan stok) justru paling sering rusak diam-diam. Unit test mengunci perilakunya selamanya.

## 3. Contoh Kode & Implementasi (Real-world Example)

Contoh-contoh berikut menguji model `Buku` pada Perpustakaan Digital, di `tests/Unit/BukuTest.php`.

**Model yang akan diuji:**

```php
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Factories\HasFactory;
use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\SoftDeletes;
use Illuminate\Support\Number;

class Buku extends Model
{
    use HasFactory, SoftDeletes;

    protected $guarded = [];

    public function tersedia(): bool
    {
        return $this->stok > 0;
    }

    public function harga_format(): string
    {
        return 'Rp ' . Number::format($this->harga, locale: 'id');
    }
}
```

**Unit test 1: `tersedia()` — tanpa database, cukup instansiasi langsung.**

Karena ini logika murni dari data yang kita isi sendiri, tidak perlu database sama sekali. Cukup buat objek model lalu isi atributnya.

```php
<?php

namespace Tests\Unit;

use App\Models\Buku;
use PHPUnit\Framework\TestCase;

class BukuTest extends TestCase
{
    public function test_buku_tersedia_saat_stok_masih_ada(): void
    {
        $buku = new Buku(['stok' => 5]); // isi atribut langsung, tanpa DB

        $this->assertTrue($buku->tersedia());
    }

    public function test_buku_tidak_tersedia_saat_stok_nol(): void
    {
        $buku = new Buku(['stok' => 0]);

        $this->assertFalse($buku->tersedia());
    }
}
```

Catatan: `tests/Unit` memakai `PHPUnit\Framework\TestCase` (bukan `Tests\TestCase`) karena kita tidak butuh aplikasi Laravel seutuhnya. Ini membuat test super cepat.

**Unit test 2: `harga_format()` dengan `dataProvider`.**

`dataProvider` memungkinkan satu method test dijalankan berkali-kali dengan data berbeda. Baris pertama parameter adalah nama kasus, sisanya adalah input yang diteruskan ke method test.

```php
<?php

namespace Tests\Unit;

use App\Models\Buku;
use PHPUnit\Framework\Attributes\DataProvider;
use PHPUnit\Framework\TestCase;

class BukuTest extends TestCase
{
    /**
     * @param array{harga: int, expected: string} $kasus
     */
    #[DataProvider('dataHarga')]
    public function test_format_harga(array $kasus): void
    {
        $buku = new Buku(['harga' => $kasus['harga']]);

        $this->assertSame($kasus['expected'], $buku->harga_format());
    }

    public static function dataHarga(): array
    {
        return [
            'nol rupiah' => [
                ['harga' => 0, 'expected' => 'Rp 0'],
            ],
            'ribuan' => [
                ['harga' => 1000, 'expected' => 'Rp 1.000'],
            ],
            'ratusan ribu' => [
                ['harga' => 150000, 'expected' => 'Rp 150.000'],
            ],
        ];
    }
}
```

Satu method test, tiga kasus. Kalau nanti format berubah menjadi "Rp1.000" tanpa spasi, test langsung merah dan kita tahu persis kasus mana yang gagal.

**Mocking & Fakes: kenapa dibutuhkan?**

Method yang bergantung pada dependency eksternal (mail, queue, event, storage, HTTP) tidak boleh benar-benar terkirim/dieksekusi saat test. Kita menggantinya dengan fake agar:

- Test berjalan cepat dan deterministik (tidak menunggu server mail atau antrian).
- Tidak ada efek samping nyata (email sungguhan terkirim, file tersimpan di disk asli).
- Bisa di-assert "apakah dependency dipanggil dan dengan apa".

**Contoh `Queue::fake()` di feature test:**

```php
use Illuminate\Support\Facades\Queue;

public function test_peminjaman_memicu_job_notifikasi(): void
{
    Queue::fake(); // job dibekukan, tidak dieksekusi

    // ... lakukan alur peminjaman buku ...

    Queue::assertPushed(KirimNotifikasiPeminjaman::class);
}
```

**Contoh `Mail::fake()`:**

```php
use Illuminate\Support\Facades\Mail;
use App\Mail\PeminjamanTerkonfirmasi;

public function test_email_konfirmasi_dikirim_ke_anggota(): void
{
    Mail::fake(); // email ditahan

    // ... lakukan alur yang memicu email ...

    Mail::assertSent(PeminjamanTerkonfirmasi::class, function ($mail) use ($anggota) {
        return $mail->hasTo($anggota->email); // pastikan penerima benar
    });
}
```

**Contoh `Event::fake()`:**

```php
use Illuminate\Support\Facades\Event;
use App\Events\BukuDipinjam;

public function test_event_buku_dipinjam_didispatch(): void
{
    Event::fake(); // event ditahan

    // ... alur peminjaman ...

    Event::assertDispatched(BukuDipinjam::class);
}
```

**Contoh `Http::fake()`:** menguji konsumen API luar tanpa koneksi internet.

```php
use Illuminate\Support\Facades\Http;

public function test_cek_isbn_ke_api_eksternal(): void
{
    Http::fake([
        'openlibrary.org/api/*' => Http::response([
            'judul' => 'Sapiens',
            'pengarang' => 'Yuval Noah Harari',
        ], 200),
    ]);

    $hasil = app(IsbnService::class)->cari('9786020382063');

    $this->assertSame('Sapiens', $hasil['judul']);
    Http::assertSent(function ($request) {
        return $request->url() === 'https://openlibrary.org/api/search?q=9786020382063';
    });
}
```

**Contoh `Storage::fake()`:** uji upload/export tanpa menulis file sungguhan.

```php
use Illuminate\Support\Facades\Storage;

public function test_export_laporan_tersimpan(): void
{
    Storage::fake('public'); // gudang file tiruan

    // ... alur export ...

    Storage::disk('public')->assertExists('laporan/buku.csv');
}
```

**Perbedaan kapan Mockery diperlukan:**

Laravel menyediakan fakes bawaan untuk facade dan service yang paling umum. Namun ada kasus di mana kamu perlu mock class sendiri (misal service custom yang dibangun sendiri) — di sinilah `Mockery` (bundling) berguna:

```php
public function test_service_menggunakan_repository_mock(): void
{
    $mock = Mockery::mock(StokRepository::class);
    $mock->shouldReceive('kurangi')
        ->once()
        ->with(5)
        ->andReturn(true);

    $service = new PeminjamanService($mock); // dependency injection manual

    $this->assertTrue($service->prosesPeminjaman(5));
}
```

**Menjalankan unit test:**

```bash
php artisan test                     # jalankan semua
php artisan test --filter=BukuTest   # hanya BukuTest (unit + feature)
php artisan test --filter=Unit       # hanya folder tests/Unit
```

## 4. Analogi Sederhana

Tetap di restoran yang sama: testing adalah **quality control menu sebelum dirilis**.

- **Unit test = QC resep per hidangan**: dapur uji hanya mengambil satu resep — "bahan sekian + teknik sekian harus menghasilkan rasa sekian". `Buku::tersedia()` dengan stok 5 harus mengembalikan `true`, stok 0 harus `false`. Tidak perlu pelanggan, tidak perlu pelayan, cukup dapur dan resepnya.
- **Feature test = QC end-to-end** (materi 31): pesan lewat pelayan sampai hidangan keluar, seluruh alur restoran ikut diuji.
- **Mocking/Faking = uji dengan bahan tiruan**: hasil uji rasa tidak boleh bergantung pada gudang atau supplier asli. Kalau resep meminta telur dari supplier A, dan supplier A sedang tidak ada, kita pakai telur tiruan yang sudah pasti kualitasnya — hasilnya tetap bisa kita nilai. `Queue::fake()`, `Mail::fake()`, dan `Http::fake()` adalah "bahan tiruan" itu: behavior dependency bisa kita kendalikan 100%.

Prinsipnya sama: yang diuji adalah logika resep kita, bukan keberuntungan supplier.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

**Gunakan unit test ketika:**

- **Method berisi logika murni**: `Buku::tersedia()`, `Buku::harga_format()`, perhitungan denda keterlambatan peminjaman, perhitungan total harga.
- **Tidak butuh database**: cukup instansiasi model/class, isi data, panggil method, bandingkan hasil.
- **Kamu ingin dataProvider**: satu method diuji banyak variasi input dengan mudah (seperti format harga untuk 0, ribuan, ratusan ribu).
- **Ingin feedback super cepat saat TDD**: unit test jalan dalam milidetik, cocok untuk loop merah-hijau-refactor.

**Gunakan feature test ketika:**

- Menguji alur HTTP, auth, policy, validasi form, redirect, dan isi database (materi 31). Misal "admin bisa menambah buku" melibatkan route, middleware, session, dan DB — itu domain feature test.

**Kapan fakes vs Mockery:**

- **Fakes bawaan Laravel** (Queue, Mail, Event, Storage, Http): untuk hampir semua kasus sehari-hari. Lebih sederhana, lebih aman, dan menyediakan assertion siap pakai (`assertPushed`, `assertSent`, `assertDispatched`).
- **Mockery**: hanya saat kamu perlu partial mock class sendiri atau mensimulasikan class yang tidak punya fake bawaan. Jangan digunakan untuk Eloquent model tanpa alasan kuat — factory + database test jauh lebih realistis.

**Kasus nyata perpustakaan:** test denda keterlambatan (logika murni, unit test), test format harga di halaman (dataProvider), test notifikasi email saat peminjaman (Mail::fake + feature test), test konsumen API ISBN eksternal (Http::fake).

## 6. Poin-poin Penting & Best Practices

- **Unit test di `tests/Unit`**, feature test di `tests/Feature`. Buat dengan `php artisan make:test NamaTest --unit` atau `--feature`.
- **Nama method deskriptif** dalam Bahasa Inggris: `test_buku_tersedia_saat_stok_lima` atau `testFormatHargaRatusanRibu` — bukan `test_buku`.
- **Gunakan `dataProvider`** untuk menguji banyak variasi input dengan satu method test; setiap baris data menjadi kasus test terpisah yang namanya tampil di output.
- **Isolasi mutlak**: satu test = satu kasus. Jangan bergantung pada urutan eksekusi atau data yang dibuat test lain.
- **`assertSame` untuk nilai eksak** (type-sensitive), `assertTrue`/`assertFalse` untuk boolean, `assertStringContainsString` untuk substring.
- **Fakes > Mockery**: default ke fakes bawaan Laravel. Mockery hanya untuk partial mock class sendiri.
- **Jangan mock Eloquent model tanpa perlu** — jika kamu menguji logika model seperti `tersedia()`, gunakan instansiasi langsung (`new Buku(['stok' => 5])`) tanpa DB. Jika butuh query/relasi, gunakan factory di feature test.
- **Fakes selalu dipasang di awal test** (`Queue::fake();` sebelum alur yang memicu job), lalu di-assert di akhir.
- **Jalankan rutin**: `php artisan test` setelah setiap perubahan; gabung dengan `--coverage --min=70` untuk menjaga cakupan kode (materi 31).
- **Partial mock class sendiri**: kalau perlu, mock hanya method tertentu (misal method yang memanggil API), biarkan method lain berjalan asli.

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

- **Unit test yang "berat"**: memanggil seluruh framework padahal hanya menguji format string. Solusi: test di `tests/Unit` cukup pakai `PHPUnit\Framework\TestCase` dan instansiasi langsung.
- **Test bergantung urutan**: test B butuh data dari test A. Solusi: setiap test menyiapkan datanya sendiri; di feature test, `RefreshDatabase` menormalkan kondisi.
- **Mock terlalu banyak (brittle)**: semua dependency di-mock sehingga test hanya mengulang apa yang di-hardcode di mock — test jadi "bohong" dan pecah saat refactor. Solusi: mock hanya boundary eksternal (mail, queue, http, storage), biarkan logika internal berjalan asli.
- **Lupa `Queue::fake()` / `Mail::fake()`**: email atau job benar-benar terkirim/dieksekusi saat test. Ini berbahaya di CI — bisa spam user asli. Solusi: selalu fake di awal test yang memicu efek samping.
- **Mock Eloquent model tanpa perlu**: mock `Buku::find(...)` padahal tinggal pakai factory — yang diuji jadi perilaku mock, bukan perilaku asli query. Solusi: gunakan factory + database (feature test) atau instansiasi langsung (unit test).
- **Assertion terlalu longgar atau terlalu ketat**: `assertSame` vs `assertEquals` penting; pastikan tipe data sesuai (misal harga integer vs string).
- **Tidak memakai `dataProvider`**: test yang sama disalin tiga kali untuk tiga input. Solusi: satu method + dataProvider = mudah dirawat dan output kasus jelas.
- **Troubleshooting**: jika unit test gagal, cek dulu apakah method benar-benar logika murni (bebas dependency tersembunyi seperti `auth()` global atau facade). Dependency tersembunyi inilah penyebab umum test unit yang "tiba-tiba gagal" — solusinya refactor agar dependency disuntikkan lewat parameter (ini jembatan ke materi 33).

## 8. Soal Latihan & Kunci Jawaban

### Tantangan

1. Di `tests/Unit/BukuTest.php`, tulis unit test untuk method `harga_format()` menggunakan dataProvider dengan kasus `0 -> 'Rp 0'`, `1000 -> 'Rp 1.000'`, dan `150000 -> 'Rp 150.000'`. Lalu jalankan hanya file tersebut dengan `php artisan test --filter=BukuTest`.
2. Tulis sebuah feature test sederhana di `tests/Feature/BukuTest.php` bernama `test_email_konfirmasi_dikirim_ketika_buku_dipinjam`: pakai `Mail::fake()`, buat user anggota dan buku lewat factory, panggil route peminjaman (bebas sesuai implementasi), lalu `Mail::assertSent(...)` dengan pengecekan penerima email anggota.

### Jawaban & Pembahasan

**Jawaban tantangan 1:**

```php
<?php

namespace Tests\Unit;

use App\Models\Buku;
use PHPUnit\Framework\Attributes\DataProvider;
use PHPUnit\Framework\TestCase;

class BukuTest extends TestCase
{
    /**
     * @param array{harga: int, expected: string} $kasus
     */
    #[DataProvider('dataHarga')]
    public function test_format_harga(array $kasus): void
    {
        $buku = new Buku(['harga' => $kasus['harga']]);

        $this->assertSame($kasus['expected'], $buku->harga_format());
    }

    public static function dataHarga(): array
    {
        return [
            'nol rupiah'   => [['harga' => 0,       'expected' => 'Rp 0']],
            'ribuan'       => [['harga' => 1000,    'expected' => 'Rp 1.000']],
            'ratusan ribu' => [['harga' => 150000,  'expected' => 'Rp 150.000']],
        ];
    }
}
```

Jalankan dengan `php artisan test --filter=BukuTest`. Penjelasan alur: method test dipanggil tiga kali dengan data berbeda; setiap kali, `Buku` diinstansiasi langsung tanpa database, lalu `harga_format()` dibandingkan eksak (`assertSame`) dengan nilai yang diharapkan. Jika salah satu format berubah, hanya kasus itu yang gagal dan namanya tampil jelas di output.

**Jawaban tantangan 2:**

```php
use Illuminate\Support\Facades\Mail;
use App\Mail\PeminjamanTerkonfirmasi;

public function test_email_konfirmasi_dikirim_ketika_buku_dipinjam(): void
{
    Mail::fake(); // email ditahan, tidak benar-benar terkirim

    $anggota = User::factory()->create(['role' => 'anggota']);
    $buku = Buku::factory()->create(['stok' => 3]);

    $this->actingAs($anggota)->post(route('peminjaman.store', [
        'buku_id' => $buku->id,
    ]));

    Mail::assertSent(PeminjamanTerkonfirmasi::class, function ($mail) use ($anggota) {
        return $mail->hasTo($anggota->email); // penerima harus email anggota
    });
}
```

Penjelasan alur: `Mail::fake()` dipasang paling awal agar tidak ada email sungguhan keluar; data dibuat lewat factory; request peminjaman dijalankan dengan `actingAs`; di akhir kita memastikan kelas mail di-"kirim" dan penerimanya benar. Ini adalah perpaduan feature test (alur HTTP) dengan faking (isolasi dependency email) — persis pola yang dipakai di aplikasi nyata.
