# 37. CI/CD dengan GitHub Actions

Materi ini membahas otomatisasi pipeline untuk repositori "Perpustakaan Digital" di GitHub menggunakan GitHub Actions. Setelah menguasai deployment manual (materi 36) dan testing (materi 31-32), sekarang saatnya kedua hal itu digabung: setiap push memicu test otomatis, dan bila lulus, kode otomatis diterbangkan ke server produksi. Hasilnya, deploy tidak lagi tergantung ingatan atau catatan manual.

## 1. Penjelasan Singkat & Konsep Dasar

CI (Continuous Integration) adalah praktik menjalankan test secara otomatis setiap kali kode di-push atau dibuat pull request. CD (Continuous Deployment) adalah kelanjutannya: bila semua test lulus, kode otomatis di-deploy ke server. Keduanya dijalankan oleh GitHub Actions, yaitu service GitHub yang mengeksekusi workflow (file YAML) di dalam container bernama runner.

Konsep intinya: **satu file YAML, dua job**. Job `test` memastikan kualitas (build, migrate, jalankan seluruh test suite). Job `deploy` hanya berjalan bila `test` lulus dan hanya di branch `main`. Ini otomatisasi penuh dari langkah-langkah manual di materi 36, sehingga aturan "test dulu, baru rilis" menjadi sistem yang tidak bisa dilupakan.

## 2. Fungsi & Kegunaan Utama dalam Laravel

Mengapa CI/CD penting?

- **Menghilangkan deploy manual yang error-prone.** Semua langkah manual (composer install, migrate, optimize) dijalankan mesin secara konsisten. Tidak ada lagi "lupa storage:link" atau "lupa migrate".
- **Environment konsisten.** Setiap pipeline dijalankan di container yang sama (`ubuntu-latest`), sehingga hasil test di CI bisa dipercaya sebagai indikator perilaku di produksi.
- **Feedback cepat.** Setiap pull request langsung tahu "kode ini gagal test" sebelum di-merge, mencegah bug masuk ke main.
- **Rollback yang lebih mudah.** Karena setiap deploy tercatat di history Actions, versi mana pun bisa di-deploy ulang dengan menjalankan workflow pada commit lama.
- **Kecepatan tim.** Developer cukup push; pipeline menangani sisanya. Waktu yang dulu dipakai deploy manual bisa untuk kerja produktif.

Masalah yang diselesaikan: deploy manual yang rapuh, environment yang tidak konsisten antar mesin, dan ketiadaan jejak audit ("siapa deploy kapan dan dengan kode mana").

## 3. Contoh Kode & Implementasi (Real-world Example)

File workflow diletakkan di `.github/workflows/ci.yml` dalam root repositori. Workflow berikut punya dua job: `test` (menjalankan suite di container dengan MySQL dan Redis) dan `deploy` (SSH ke server produksi saat push ke `main`).

```yaml
name: CI/CD Perpustakaan

# Jalankan pada push dan pull request ke branch utama pengembangan.
on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main, develop ]

jobs:
  # -------------------------------------------------------------
  # JOB 1: TEST — memastikan semua test lulus di lingkungan bersih.
  # -------------------------------------------------------------
  test:
    name: Test & Coverage
    runs-on: ubuntu-latest

    # Service container: MySQL dan Redis dipasang di dalam runner,
    # diberi nama agar bisa diakses lewat hostname 'mysql' dan 'redis'.
    services:
      mysql:
        image: mysql:8
        env:
          MYSQL_DATABASE: perpustakaan_test
          MYSQL_USER: test_user
          MYSQL_PASSWORD: secret
          MYSQL_ROOT_PASSWORD: root
        ports:
          - 3306:3306
        # Health check: pipeline menunggu MySQL benar-benar siap.
        options: >-
          --health-cmd="mysqladmin ping"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=10
      redis:
        image: redis:7
        ports:
          - 6379:6379
        options: >-
          --health-cmd="redis-cli ping"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=10

    steps:
      - name: Checkout kode
        uses: actions/checkout@v4

      - name: Setup PHP 8.3 + ekstensi + coverage
        uses: shivammathur/setup-php@v2
        with:
          php-version: '8.3'
          extensions: mbstring, xml, bcmath, intl, pdo_mysql, redis
          coverage: xdebug   # dibutuhkan php artisan test --coverage
          tools: composer:v2

      - name: Cache dependency Composer
        uses: actions/cache@v4
        with:
          path: ~/.cache/composer
          key: composer-${{ hashFiles('composer.lock') }}
          restore-keys: composer-

      - name: Install dependency
        run: composer install --no-interaction --prefer-dist

      # Siapkan konfigurasi test. key:generate --env=testing membuat
      # APP_KEY khusus untuk environment testing.
      - name: Setup environment testing
        run: |
          cp .env.example .env.testing
          php artisan key:generate --env=testing

      # Migrate skema ke database testing, bukan ke database produksi.
      - name: Migrate database testing
        env:
          DB_CONNECTION: mysql
          DB_HOST: 127.0.0.1
          DB_PORT: 3306
          DB_DATABASE: perpustakaan_test
          DB_USERNAME: test_user
          DB_PASSWORD: secret
        run: php artisan migrate --env=testing --force

      # Jalankan seluruh test secara paralel (split ke beberapa worker).
      # --min=70 memaksa pipeline gagal bila coverage di bawah 70%.
      - name: Jalankan test suite
        env:
          DB_CONNECTION: mysql
          DB_HOST: 127.0.0.1
          DB_PORT: 3306
          DB_DATABASE: perpustakaan_test
          DB_USERNAME: test_user
          DB_PASSWORD: secret
        run: php artisan test --env=testing --coverage --min=70 --parallel

  # -------------------------------------------------------------
  # JOB 2: DEPLOY — hanya jika test lulus, dan hanya dari branch main.
  # -------------------------------------------------------------
  deploy:
    name: Deploy ke Production
    runs-on: ubuntu-latest
    # Kunci: tidak berjalan kecuali job 'test' sukses.
    needs: test
    # Hanya deploy bila push (bukan PR) ke branch main.
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    environment: production   # terikat environment protection

    steps:
      - name: Deploy via SSH ke server
        uses: appleboy/ssh-action@v1.2.0
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SERVER_SSH_KEY }}
          # Script ini setara dengan deploy manual materi 36.
          script: |
            cd /var/www/perpustakaan
            sudo -u www-data git pull origin main
            sudo -u www-data composer install --optimize-autoloader --no-dev --no-interaction
            sudo -u www-data php artisan migrate --force
            sudo -u www-data php artisan optimize
            sudo -u www-data php artisan queue:restart
            sudo -u www-data npm install
            sudo -u www-data npm run build
            sudo systemctl reload nginx
```

### Mengisi GitHub Secrets

Semua nilai rahasia disimpan sebagai Secrets, bukan hardcoded di YAML. Di halaman repositori GitHub: `Settings > Secrets and variables > Actions`:

```
SERVER_HOST      = perpustakaan.kota.id
SERVER_USER      = deploy (user dengan akses sudo ke /var/www/perpustakaan)
SERVER_SSH_KEY   = private key SSH (tanpa passphrase) untuk user deploy
```

Buat user deploy di server dengan kunci SSH:

```bash
sudo useradd -m -s /bin/bash deploy
sudo mkdir -p /home/deploy/.ssh
sudo cp ~/.ssh/authorized_keys /home/deploy/.ssh/   # dari kunci publik
sudo chown -R deploy:deploy /home/deploy/.ssh
sudo chmod 700 /home/deploy/.ssh
sudo chmod 600 /home/deploy/.ssh/authorized_keys
sudo usermod -aG www-data deploy     # agar bisa manage file aplikasi
echo 'deploy ALL=(ALL) NOPASSWD: ALL' | sudo tee /etc/sudoers.d/deploy
```

### Branch Protection dan Environment

- **Branch protection** (`Settings > Branches > Add rule`): tandai `main` sebagai protected, wajibkan status check dari job `test` lulus sebelum merge, dan larang push langsung.
- **Environment protection** (`Settings > Environments`): buat environment `production`, dan pilih "Required reviewers" — deploy ke produksi harus disetujui reviewer yang ditunjuk, memberi titik kontrol manusia sebelum kode sampai ke pengguna.

## 4. Analogi Sederhana

**Deployment = Membuka cabang baru restoran.** Seluruh SOP dapur, resep, stok, izin bangunan, dan karyawan disiapkan mengikuti standar yang sama — persis seperti kode yang sama dikirim ke server baru. Persiapannya: `composer install` = membongkar kiriman bahan sesuai daftar; `php artisan migrate` = membangun dapur sesuai blueprint; `optimize` = menata ulang agar dapur efisien; `storage:link` = menghubungkan gudang umum dengan etalase.

**CI/CD = Proses QC otomatis & audit sebelum cabang dibuka.** Setiap menu baru wajib lolos QC (test) dulu sebelum dirilis; prosesnya otomatis terpantau (CI — kontinu). Kalau lolos, menu otomatis dikirim ke semua cabang (CD — deploy kontinu). Kalau gagal, tidak ada yang dirilis: chef tidak akan pernah menyajikan menu yang belum lolos uji rasa, berapa pun buru-burunya.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

- **Setiap push ke `develop`** — jalankan hanya job `test`. Ini menjaga cabang pengembangan selalu hijau tanpa mengganggu produksi.
- **Setiap merge/push ke `main`** — jalankan `test` lalu `deploy`. Ini alur standar: main selalu dalam keadaan "layak rilis".
- **Pull request** — jalankan `test` saja sebagai preflight. Developer melihat langsung apakah PR-nya memecahkan test lain.
- **Kapan pakai deploy manual vs CI/CD** — CI/CD untuk rilis rutin dan change berulang. Deploy manual hanya untuk pertama kali (setup server), migrasi berisiko tinggi di luar pipeline, atau rollback darurat.
- **Kapan pakai staging** — buat workflow tambahan (misal `deploy-staging`) yang jalan otomatis saat push ke `develop`, ke server `staging.perpustakaan.kota.id`. Production hanya menerima yang sudah terbukti di staging dan lulus review.

## 6. Poin-poin Penting & Best Practices

- `on.push` untuk `main` dan `develop`, plus `on.pull_request` — tapi hanya job `test` yang jalan untuk PR.
- Gunakan `services` untuk MySQL dan Redis di dalam runner; sertakan health check agar pipeline tidak "memulai test lebih cepat dari database siap".
- `shivammathur/setup-php` dengan versi PHP yang sama persis dengan server (8.3) agar hasil CI merepresentasikan produksi.
- Cache `composer.lock` agar install dependency di pipeline berikutnya jauh lebih cepat.
- Siapkan environment testing lewat `.env.testing` dan `key:generate --env=testing`; jangan pernah memakai `.env` produksi di CI.
- `php artisan test --coverage --min=70 --parallel` — coverage minimum memaksa tim menjaga kualitas, dan `--parallel` mempercepat suite.
- Job `deploy` memakai `needs: test` dan `if: github.ref == 'refs/heads/main'` — dua lapis pengaman agar deploy hanya terjadi setelah test lulus dan hanya dari branch yang benar.
- GitHub Secrets untuk semua nilai rahasia (`SERVER_HOST`, `SERVER_USER`, `SERVER_SSH_KEY`); jangan pernah menuliskannya di YAML.
- Aktifkan branch protection untuk `main` dan environment protection untuk `production` (required reviewers).
- Script deploy di SSH sebaiknya **idempotent** (bisa dijalankan ulang tanpa efek ganda). `migrate` memang aman, tapi hindari `db:seed` tanpa pengecekan — atau jangan seeder di production sama sekali.
- Pertimbangkan menambahkan `post-deploy` check: setelah deploy, jalankan `php artisan route:list` atau ping health endpoint untuk memastikan aplikasi benar-benar hidup.

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

- **Test lolos di lokal tapi gagal di CI** — biasanya karena environment berbeda (versi PHP, ekstensi, atau database). Solusi: samakan versi PHP dan ekstensi di `setup-php` dengan server, dan jangan andalkan state lokal.
- **Deploy branch `develop` ke produksi** — karena workflow terlalu longgar (`on.push` ke semua branch, atau `if` yang salah). Pastikan `if: github.ref == 'refs/heads/main'` dan `github.event_name == 'push'` terpasang.
- **`.env` ter-commit** — kredensial produksi bocor ke repo. Laravel sudah menaruh `.env` di `.gitignore`; jangan pernah `git add -f .env`. Pastikan `.env.example` selalu sinkron dengan struktur `.env` asli.
- **Tidak ada rollback plan** — kalau deploy baru rusak, tidak ada mekanisme cepat kembali. Praktik baik: simpan tag git per rilis dan dokumentasikan perintah rollback (deploy ulang commit sebelumnya).
- **Menjalankan `db:seed` di production** — seeder sering dibuat untuk data dev. Di pipeline produksi, pastikan tidak ada seeder yang menambah data test; atau hilangkan sama sekali dari script deploy.
- **`migrate:fresh` di produksi** — menghapus seluruh data pengguna. Jangan pernah masuk ke workflow produksi.
- **Secrets hardcoded di YAML** — contoh `password: "secret"` di file ini hanya untuk service container test yang disposable; di production, semua rahasia lewat Secrets.
- **Workflow yang terlalu besar / tidak parallel** — seluruh test dijalankan satu worker lebih lambat. Manfaatkan `--parallel` dan cache Composer.
- **Health check service tidak ada** — test mulai jalan saat MySQL belum siap, hasilnya error acak yang menyulitkan debugging. Selalu sertakan `--health-cmd`.

### Troubleshooting Cepat

- Workflow gagal di job `test` → cek bagian yang error, biasanya `composer install` (versi PHP tidak cocok) atau migrasi (env DB salah). Lihat log per step di halaman Actions.
- SSH timeout di job `deploy` → pastikan IP server terbuka untuk port 22 dari GitHub runner, dan user `deploy` punya akses ke repo dan `/var/www/perpustakaan`.
- Deploy tidak berjalan sama sekali → cek kondisi `if` dan apakah push memang ke `main`; deploy tidak jalan untuk PR.

## 8. Soal Latihan & Kunci Jawaban

### Tantangan

1. Kamu menambah workflow baru agar semua push ke `develop` ikut di-deploy ke server staging. Tuliskan potongan YAML untuk job `deploy-staging` beserta kondisinya.
2. Seorang developer mengeluh: test di komputernya selalu lulus, tapi job `test` di GitHub Actions gagal saat migrasi karena "connection refused" ke MySQL. Sebutkan dua kemungkinan penyebab dan perbaikannya.
3. Setelah menambahkan fitur baru, coverage project turun di bawah 70% dan pipeline otomatis merah. Apa artinya, dan apa pilihanmu sebagai arsitek: menurunkan ambang batas atau menulis test baru?

### Jawaban & Pembahasan

**Soal 1.** Deploy staging mirip job `deploy`, bedanya kondisi trigger dan environment. Contoh:

```yaml
deploy-staging:
  name: Deploy ke Staging
  runs-on: ubuntu-latest
  needs: test
  if: github.ref == 'refs/heads/develop' && github.event_name == 'push'
  environment: staging
  steps:
    - name: Deploy via SSH ke staging
      uses: appleboy/ssh-action@v1.2.0
      with:
        host: ${{ secrets.STAGING_HOST }}
        username: ${{ secrets.STAGING_USER }}
        key: ${{ secrets.STAGING_SSH_KEY }}
        script: |
          cd /var/www/perpustakaan
          sudo -u www-data git pull origin develop
          sudo -u www-data composer install --optimize-autoloader --no-dev --no-interaction
          sudo -u www-data php artisan migrate --force
          sudo -u www-data php artisan optimize
          sudo -u www-data php artisan queue:restart
          sudo -u www-data npm run build
          sudo systemctl reload nginx
```

Poin penting: kondisi `github.ref == 'refs/heads/develop'` memastikan staging hanya menerima dari `develop`, dan jangan lupa daftarkan secrets staging terpisah dari produksi.

**Soal 2.** Penyebab pertama: job `test` tidak mendefinisikan `DB_*` env, atau definisinya salah sehingga aplikasi mencoba konek ke database default yang tidak ada. Perbaikan: pastikan step migrasi dan test memakai env `DB_HOST: 127.0.0.1`, `DB_PORT: 3306`, `DB_DATABASE: perpustakaan_test` sesuai service yang didefinisikan. Penyebab kedua: MySQL belum siap menerima koneksi (health check hilang atau terlalu cepat). Perbaikan: pastikan `options: --health-cmd="mysqladmin ping"` dengan interval dan retries yang memadai agar pipeline menunggu sampai MySQL benar-benar hidup. Jangan lupa samakan kredensial pada `env` service dengan yang dipakai di step migrasi.

**Soal 3.** Artinya kualitas test tidak lagi memenuhi standar minimum yang sudah disepakati tim (70% baris kode tercakup test) — fitur baru tidak didampingi test yang memadai. Sebagai arsitek, pilihan yang benar adalah **menulis test baru** untuk fitur tersebut sampai coverage kembali naik, bukan menurunkan ambang batas. Menurunkan `--min` demi membuat pipeline hijau adalah anti-pattern: kamu menurunkan standar alih-alih memperbaiki kualitas. Ambang coverage adalah jaring pengaman tim; semakin jarang diutak-atik, semakin berarti.
