# 36. Deployment ke VPS dengan Nginx

Materi ini membahas langkah lengkap menerbangkan aplikasi Laravel 11 "Perpustakaan Digital" ke server Ubuntu 22.04 dengan Nginx, PHP-FPM, MySQL, Redis, dan Supervisor. Setelah materi testing (Level 6) yang memastikan kode sudah sehat, sekarang saatnya kode itu benar-benar hidup di server sungguhan. Materi ini adalah fondasi dari CI/CD di materi berikutnya (37), jadi pahami dulu langkah manualnya sebelum mengotomatiskan.

## 1. Penjelasan Singkat & Konsep Dasar

Deployment adalah proses memindahkan aplikasi dari mesin pengembangan ke server produksi dan membuatnya berjalan melayani pengguna asli. Yang membedakan produksi dari lokal bukan hanya tempatnya, tapi juga mindset-nya: tidak ada lagi `php artisan serve` untuk debugging, tidak ada error di layar, dan setiap keputusan harus bisa dipertanggungjawabkan.

Konsep dasarnya sederhana: server produksi harus meniru lingkungan pengembangan sedekat mungkin, lalu menjalankan perintah yang sama (install dependency, migrate, build asset) dengan mode produksi aktif. Di materi sebelumnya kamu belajar testing dan cache Redis; keduanya berperan besar di sini — testing memastikan kode siap terbang, dan cache Redis mempercepat aplikasi saat sudah mendarat. Hubungannya ke depan: CI/CD (materi 37) hanyalah otomatisasi dari semua langkah manual yang kamu pelajari di materi ini.

## 2. Fungsi & Kegunaan Utama dalam Laravel

Mengapa deployment perlu dibahas serius? Karena deploy manual yang asal-asalan adalah sumber masalah paling umum di produksi:

- **Deploy manual yang error-prone.** Menjalankan 20 perintah secara manual dengan copy-paste dari catatan mudah terlewat satu langkah, seperti lupa `storage:link` sehingga gambar sampul buku tidak muncul.
- **Environment tidak konsisten.** Versi PHP berbeda, ekstensi kurang, atau `APP_ENV` masih `local` di server bisa membuat aplikasi berperilaku aneh — atau malah bocorkan informasi sensitif.
- **Tidak ada rollback.** Kalau versi baru bermasalah, tanpa rencana rollback (misalnya menyimpan rilis sebelumnya) pengguna terjebak di aplikasi rusak sampai developer turun tangan.

Laravel menyediakan tooling untuk mengurangi semua itu: `php artisan config:cache` mempercepat dan mengunci konfigurasi, `migrate --force` memindahkan skema database tanpa prompt interaktif (yang justru akan gagal di produksi), dan `php artisan optimize` menggabungkan cache config, route, dan view dalam satu perintah.

## 3. Contoh Kode & Implementasi (Real-world Example)

Struktur file standar yang akan kita bangun di server:

```
/var/www/perpustakaan/          # root aplikasi (repo clone)
  public/                       # document root Nginx
/etc/nginx/sites-available/perpustakaan   # server block nginx
/etc/supervisor/conf.d/perpustakaan-worker.conf  # queue & schedule
```

### 3.1 Persiapan Server: Install Dependencies

```bash
# Install paket utama: Nginx, MySQL, PHP 8.3 beserta ekstensinya,
# Redis, dan Supervisor (pengelola proses background).
sudo apt update && sudo apt upgrade -y
sudo apt install -y nginx mysql-server \
  php8.3-fpm php8.3-cli php8.3-mysql php8.3-mbstring \
  php8.3-xml php8.3-curl php8.3-zip php8.3-gd php8.3-bcmath \
  php8.3-intl php8.3-redis php8.3-sqlite3 \
  redis-server supervisor unzip git

# Install Composer secara global.
curl -sS https://getcomposer.org/installer -o composer-setup.php
sudo php composer-setup.php --install-dir=/usr/local/bin --filename=composer
rm composer-setup.php

# Pastikan service utama aktif dan ikut start saat reboot.
sudo systemctl enable --now nginx mysql redis-server supervisor php8.3-fpm
```

### 3.2 Clone Repo dan Set Permission Awal

```bash
# Pastikan PHP-FPM berjalan sebagai www-data, lalu clone repo.
sudo mkdir -p /var/www
sudo chown -R www-data:www-data /var/www
cd /var/www
sudo -u www-data git clone https://github.com/username/perpustakaan.git
cd perpustakaan
```

### 3.3 Setup .env dan Kunci Aplikasi

```bash
cd /var/www/perpustakaan
sudo -u www-data cp .env.example .env

# Isi .env dengan mode produksi. APP_DEBUG=false wajib agar
# stack trace dan informasi sensitif tidak bocor ke pengguna.
sudo -u www-data nano .env
```

Isi minimal `.env` untuk produksi:

```ini
APP_NAME="Perpustakaan Digital"
APP_ENV=production
APP_KEY=            # diisi oleh php artisan key:generate
APP_DEBUG=false
APP_URL=https://perpustakaan.kota.id
LOG_CHANNEL=stack

DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=perpustakaan
DB_USERNAME=perpustakaan_user
DB_PASSWORD=rahasia_super_kuat

CACHE_STORE=redis
SESSION_DRIVER=redis
QUEUE_CONNECTION=redis

REDIS_CLIENT=phpredis
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
```

Buat database dan user-nya di MySQL, lalu generate key:

```bash
sudo mysql <<'SQL'
CREATE DATABASE perpustakaan CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'perpustakaan_user'@'localhost' IDENTIFIED BY 'rahasia_super_kuat';
GRANT ALL PRIVILEGES ON perpustakaan.* TO 'perpustakaan_user'@'localhost';
FLUSH PRIVILEGES;
SQL

# Generate APP_KEY (harus jalan setelah .env berisi APP_ENV=production).
sudo -u www-data php artisan key:generate
```

### 3.4 Install Dependency, Migrate, dan Optimize

```bash
cd /var/www/perpustakaan

# --optimize-autoloader: gabungkan class map agar lebih cepat.
# --no-dev: jangan install paket untuk development (phpunit, dll).
sudo -u www-data composer install --optimize-autoloader --no-dev

# --force: jalankan tanpa konfirmasi (wajib untuk mode produksi).
sudo -u www-data php artisan migrate --force
sudo -u www-data php artisan db:seed --force

# Cache config, route, dan view sekaligus.
sudo -u www-data php artisan optimize

# Hubungkan storage/app/public ke public/storage
# (tanpa ini, file cover buku tidak akan tampil).
sudo -u www-data php artisan storage:link

# Build aset frontend (Tailwind/Vite).
sudo -u www-data npm install
sudo -u www-data npm run build
```

### 3.5 Perbaiki Permission

```bash
# Pastikan storage dan bootstrap/cache writable oleh www-data,
# jika tidak, Nginx akan mengembalikan error 500.
cd /var/www/perpustakaan
sudo chown -R www-data:www-data storage bootstrap/cache
sudo chmod -R ug+rw storage bootstrap/cache
```

### 3.6 Konfigurasi Nginx: Server Block

Buat file `/etc/nginx/sites-available/perpustakaan`:

```nginx
server {
    listen 80;
    server_name perpustakaan.kota.id;
    root /var/www/perpustakaan/public;

    index index.php;

    # Security headers: cegah clickjacking, MIME sniffing, dan
    # memberikan arahan rujukan halaman agar tidak bocor.
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header X-XSS-Protection "1; mode=block" always;

    # Blokir akses langsung ke file sensitif.
    location ~ /\.(?!well-known).* {
        deny all;
    }
    location ~* \.(env|git|gitignore|log)$ {
        deny all;
    }

    # Semua request masuk diarahkan ke Laravel.
    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    # Cache aset statis agar tidak membebani PHP-FPM.
    location ~* \.(css|js|jpg|jpeg|png|gif|ico|svg|woff2?|ttf)$ {
        expires 30d;
        add_header Cache-Control "public, max-age=2592000";
        try_files $uri =404;
    }

    # Teruskan request PHP ke PHP-FPM via unix socket.
    location ~ \.php$ {
        try_files $uri =404;
        fastcgi_pass unix:/var/run/php/php8.3-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;
    }

    # File-file tersembunyi (misal .htaccess) jangan pernah dilayani.
    location ~ /\.ht {
        deny all;
    }
}
```

Aktifkan site dan reload:

```bash
sudo ln -s /etc/nginx/sites-available/perpustakaan /etc/nginx/sites-enabled/
sudo nginx -t          # uji konfigurasi dulu, baru reload
sudo systemctl reload nginx
```

### 3.7 SSL Let's Encrypt dengan Certbot

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d perpustakaan.kota.id

# Test auto-renewal (certbot otomatis menambahkan timer).
sudo certbot renew --dry-run
```

### 3.8 Supervisor untuk Queue dan Schedule

Laravel tidak menjalankan queue secara permanen dengan `queue:listen` di terminal saja — itu akan mati saat sesi SSH ditutup. Supervisor menjaga proses tetap hidup. Buat file `/etc/supervisor/conf.d/perpustakaan-worker.conf`:

```ini
; Jalankan 2 proses queue worker secara paralel.
[program:perpustakaan-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/perpustakaan/artisan queue:work redis --sleep=3 --tries=3 --max-time=3600
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
user=www-data
numprocs=2
redirect_stderr=true
stdout_logfile=/var/www/perpustakaan/storage/logs/worker.log
stopwaitsecs=3600

; Jalankan scheduler Laravel (schedule:run) tiap menit.
; schedule:run akan mengeksekusi task yang waktunya tiba.
[program:perpustakaan-scheduler]
command=php /var/www/perpustakaan/artisan schedule:work
autostart=true
autorestart=true
user=www-data
redirect_stderr=true
stdout_logfile=/var/www/perpustakaan/storage/logs/scheduler.log
```

Load dan mulai semua proses:

```bash
sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl status
```

## 4. Analogi Sederhana

**Deployment = Membuka cabang baru restoran.** Seluruh SOP dapur, resep, stok, izin bangunan, dan karyawan disiapkan mengikuti standar yang sama — persis seperti kode yang sama diletakkan di server baru. Setiap langkah punya padanan dunia nyata:

- `composer install` = membongkar kiriman bahan sesuai daftar belanja yang sudah ditentukan.
- `php artisan migrate` = membangun dapur sesuai blueprint (skema tabel = tata letak meja dan kompor).
- `php artisan optimize` = menata ulang dapur agar pergerakan karyawan efisien (cache = rak-rak yang mudah dijangkau).
- `storage:link` = menghubungkan gudang umum dengan etalase agar pelanggan bisa melihat stok yang sebenarnya.

**CI/CD = Proses QC otomatis & audit sebelum cabang dibuka.** Setiap menu baru wajib lolos QC (test) dulu sebelum dirilis. Prosesnya otomatis terpantau oleh tim (CI — kontinu, tidak menunggu hari Senin). Kalau lolos, menu otomatis dikirim ke semua cabang (CD — deploy kontinu). Kalau gagal, tidak ada yang dirilis — tidak ada drama "menu baru kok bikin pelanggan keracunan" di produksi.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

- **Deploy manual** — dipakai untuk deploy pertama kali (karena harus setup server dari nol), dan untuk situasi darurat yang butuh kontrol penuh. Setelah infrastruktur terbentuk, sebagian besar deploy harian sebaiknya lewat CI/CD.
- **Staging vs production** — buat lingkungan staging (subdomain seperti `staging.perpustakaan.kota.id`) dengan kode yang sama seperti production, lengkap dengan `APP_ENV=production`. Uji di staging dulu; production hanya menerima apa yang sudah lulus di staging.
- **Kapan menjalankan `php artisan optimize`** — setiap kali ada perubahan config, route, atau view (misalnya tiap deploy). Cache lama akan membuat perubahan tidak terlihat, jadi selalu optimize di akhir deploy.
- **Kapan deploy di waktu sibuk** — hindari. Migrasi atau `npm run build` di jam ramai berisiko menurunkan performa. Gunakan jendela sepi (maintenance window) dan pertimbangkan mode `php artisan down` untuk update yang sangat besar.

## 6. Poin-poin Penting & Best Practices

- `APP_ENV=production` dan `APP_DEBUG=false` — wajib, agar tidak ada stack trace atau informasi sensitif yang tampil ke publik.
- Jalankan `php artisan key:generate` sekali setelah `.env` final; jangan pernah menimpa key setelah aplikasi dipakai (akan memutus semua data terenkripsi, termasuk session).
- `composer install --optimize-autoloader --no-dev` — dependency produksi minimal dan otoload lebih cepat.
- Selalu `migrate --force` dan `db:seed --force` (jangan pakai versi tanpa `--force` yang butuh prompt interaktif).
- `php artisan optimize` untuk cache config/route/view; jangan lupa `php artisan queue:restart` setelah deploy jika ada perubahan logika queue.
- `storage:link` — tanpanya, gambar di `storage/app/public` tidak akan pernah muncul.
- Permission: seluruh `storage` dan `bootstrap/cache` harus writable oleh `www-data`.
- Nginx: sertakan security headers (`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`), blokir akses `.env`/`.git`, dan cache aset statis.
- Pasang SSL via Certbot; aktifkan auto-renewal.
- Supervisor: `queue:work` (numprocs disesuaikan beban) dan `schedule:work` — jangan pernah mengandalkan proses manual yang mati saat SSH ditutup.
- Gunakan Redis untuk cache dan session; jangan pakai file session di mesin dengan banyak worker.
- Jangan pernah menjalankan `migrate:fresh` di production — itu menghapus seluruh data pengguna.
- Selalu backup database dan folder `storage/app` sebelum deploy besar (misalnya `mysqldump` terjadwal).

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

- **Lupa set `APP_DEBUG=false`** — error 500 menampilkan stack trace lengkap termasuk path server dan isi `.env`. Ini pintu masuk serangan.
- **`.env` ter-commit ke repo** — kredensial database dan APP_KEY terbaca siapa saja yang punya akses repo. Pastikan `.env` masuk `.gitignore` (Laravel sudah otomatis) dan isi `.env.example` sinkron dengan struktur `.env` asli.
- **Migrasi berjalan dengan user salah / permission error** — Nginx membaca file sebagai `www-data`, tapi jika file dimiliki `root`, muncul 500. Selalu `chown -R www-data:www-data`.
- **Storage tidak writable** — Laravel tidak bisa menulis log/session, hasilnya error 500 misterius. Cek dengan `ls -la storage`.
- **Symlink storage tidak dibuat** — lupa `php artisan storage:link`, gambar cover buku tidak tampil padahal file ada.
- **Deploy di jam sibuk tanpa maintenance** — asset berubah-ubah saat pengguna membuka halaman, cache campur aduk, dan pengguna mengalami error acak.
- **Optimize tidak dijalankan ulang** — config lama masih ter-cache, perubahan `config/app.php` tidak berefek.
- **Tidak ada rollback plan** — kalau versi baru rusak, tidak ada cara cepat kembali. Buat kebiasaan: catat versi aktif, dan simpan cadangan rilis sebelumnya (tag git atau backup folder).

### Troubleshooting Cepat

- Error 502 Bad Gateway → cek status PHP-FPM (`sudo systemctl status php8.3-fpm`), pastikan socket di `fastcgi_pass` cocok.
- Error 500 → cek `storage/logs/laravel.log`, pastikan permission dan `APP_DEBUG` benar untuk debugging awal.
- Cache aneh → `php artisan optimize:clear` lalu `php artisan optimize` ulang.
- Queue tidak jalan → `sudo supervisorctl status`, cek log worker di `storage/logs/worker.log`.

## 8. Soal Latihan & Kunci Jawaban

### Tantangan

1. Setelah deploy pertama, halaman utama tampil tapi semua gambar cover buku tidak muncul (404). Padahal filenya sudah di-upload dan tersimpan. Sebutkan kemungkinan penyebab dan cara memperbaikinya.
2. Kamu baru saja mengubah `config/cache.php` lalu menjalankan `php artisan config:cache` sebelum deploy. Setelah deploy, aplikasi masih menggunakan konfigurasi lama. Jelaskan penyebabnya dan langkah perbaikannya.
3. Pengguna melaporkan halaman login sangat lambat dan session sering hilang saat aplikasi dijalankan di banyak worker. Sebutkan solusi arsitektur yang benar.

### Jawaban & Pembahasan

**Soal 1.** Penyebab paling umum adalah symlink `public/storage` tidak dibuat, karena Laravel menyimpan file upload di `storage/app/public` yang berada di luar document root. Solusi: jalankan `sudo -u www-data php artisan storage:link` di `/var/www/perpustakaan`, pastikan permission `storage` benar (`chown -R www-data:www-data storage`), lalu cek URL gambar apakah mengarah ke `/storage/...`. Kalau tetap 404, cek aturan `try_files` di blok Nginx untuk file statis (jangan sampai request gambar dianggap sebagai request PHP).

**Soal 2.** Perintah `config:cache` menyimpan hasil akhir config ke `bootstrap/cache/config.php`. Saat deploy berikutnya, jika `php artisan config:cache` dijalankan lagi, cache baru akan menimpa yang lama. Tapi jika kamu hanya menjalankan `optimize` tanpa memastikan cache di-refresh setelah perubahan file config, atau jika urutan deploy salah (misal file diganti setelah cache dibuat), cache lama tetap dipakai. Solusinya: selalu jalankan `php artisan optimize:clear` (atau `config:clear`) dulu, lalu `php artisan optimize` di akhir proses deploy, setelah semua file sudah terpasang. Jangan pernah meng-cache config sebelum file-file baru benar-benar ada di server.

**Soal 3.** Masalahnya adalah penggunaan session/cache berbasis file di mesin dengan banyak worker (setiap worker punya file session sendiri sehingga session "hilang" berpindah worker). Solusi yang benar adalah menggunakan Redis sebagai store session dan cache: set `SESSION_DRIVER=redis` dan `CACHE_STORE=redis` di `.env` produksi, pastikan ekstensi `php-redis` terpasang dan Redis berjalan. Dengan begitu session tersimpan di satu tempat terpusat dan aman dibaca worker mana pun, sekaligus meningkatkan kecepatan karena Redis berada di memori.
