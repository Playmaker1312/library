# 33. Pengalaman Pengguna yang Baik saat Loading dan Error

Materi ini mengajarkan tiga "wajah" yang wajib dimiliki setiap bagian aplikasi yang mengambil data: **loading** (sedang memuat), **error** (gagal memuat), dan **empty** (berhasil tapi kosong) — lengkap dengan wrapper `loadData` yang merangkum ketiganya, tombol retry, serta aksesibilitas `role="status"` dan `role="alert"`. Inilah yang membuat aplikasi terasa hidup dan tidak pernah "diam".

## 1. Penjelasan Singkat & Konsep Dasar

Sejak materi 31, setiap bagian aplikasi yang menampilkan data dari server punya "fase menunggu". Lima detik menunggu data tiba tanpa apa pun di layar adalah pengalaman yang terasa seperti sepuluh menit — user mulai klik-klik, menutup tab, atau mengira aplikasi rusak. Materi ini mengubah cara pandang: **tunggu bukan sesuatu yang disembunyikan, melainkan sesuatu yang dikelola dan dijelaskan ke user**. Prinsipnya sederhana: jangan pernah membiarkan layar diam, dan selalu beri tahu user apa yang sedang terjadi.

Ada tiga state yang menjadi dasar UX aplikasi data. **Loading state** muncul *sebelum* data tiba: spinner berputar, tulisan "Memuat...", atau yang lebih modern dan nyaman — **skeleton screen**, rangka persegi panjang abu-abu meniru bentuk kartu buku yang sedang "diiisi". Skeleton lebih baik daripada spinner karena menunjukkan *bentuk* apa yang akan muncul, sehingga layout tidak melompat-lompat saat data baru datang. **Error state** muncul saat request gagal: bukan berupa `TypeError: Failed to fetch` yang mentah, melainkan pesan ramah ("Koneksi internet bermasalah") plus tombol **"Coba Lagi"** yang menjalankan ulang pemuatan. **Empty state** muncul saat request *sukses* tetapi hasilnya tidak ada: "Tidak ada buku yang cocok dengan pencarianmu" — bukan grid kosong yang membingungkan.

Untuk merangkum ketiganya, pola yang paling sering dipakai adalah **wrapper `loadData(kontainer, fetchFn, renderFn)`**: sebuah fungsi yang menerima tempat menampilkan, fungsi pengambil data, dan fungsi perender. Wrapper ini berurutan: tampilkan loading, jalankan `fetchFn`, bila data kosong tampilkan empty, bila berhasil panggil `renderFn`, dan bila gagal tampilkan error + retry yang memanggil ulang dirinya sendiri. Memakai wrapper berarti setiap bagian baru dari aplikasi hanya perlu menyediakan `fetchFn` dan `renderFn` — pola state-nya tidak ditulis ulang berulang kali.

Kenapa state ini wajib? Karena **feedback** adalah kewajiban desain, bukan kemewahan. Otak manusia menafsirkan "layar diam beberapa detik" sebagai "aplikasi mati". Spinner menyampaikan "masih memuat, sebentar lagi"; error dengan pesan jelas menyampaikan "ada yang salah, ini solusinya"; tombol retry menyampaikan "kamu bisa mencobanya lagi". Tanpa feedback, user tidak pernah tahu apakah aplikasinya sedang bekerja, macet, atau gagal — dan itu sama saja dengan aplikasi rusak di mata mereka.

**Benang merah**: materi 31 menghubungkan kontainer ke server lewat async, materi 32 membuat sebagian data bertahan lokal. Materi 33 menyatukan semuanya ke dalam pengalaman: setiap alur `fetch` kini dibungkus pola state yang konsisten dan accessible. Cache dari materi 32 bahkan berinteraksi alami di sini — data dari cache belum basi sehingga loading-nya sebentar, sementara data baru dari jaringan membutuhkan spinner yang jujur. Ke Level 7, wrapper ini tumbuh menjadi modul `ui.js` dan fungsi `render` yang disatukan ke arsitektur aplikasi.

## 2. Fungsi & Kegunaan Utama dalam Web

Di **Perpustakaan Digital Kota**, empat bagian paling terasa manfaatnya. Pertama, **katalog yang dimuat dari Open Library**: saat halaman dibuka pertama kali, muncul skeleton katalog; bila jaringan putus, muncul "Tidak dapat terhubung ke internet" dengan tombol "Coba Lagi"; bila pencarian tidak menemukan apa pun, muncul "Tidak ada buku yang cocok untuk 'xyz'". Ini memastikan halaman depan tidak pernah menampilkan layar kosong yang membingungkan.

Kedua, **pencarian real-time**: user mengetik, hasil muncul dengan skeleton ringan; jika query baru lebih lambat, `AbortController` (materi 31) membatalkan yang lama dan state loading dimulai ulang dengan bersih — tidak ada kartu lama yang "berkedip" menimpa hasil baru. Ketiga, **detail buku**: klik kartu menampilkan skeleton detail, lalu mengisi judul, penulis, dan sinopsis; bila id tidak ditemukan, pesan friendly + tombol kembali. Keempat, **halaman favorit**: state empty penting di sini — "Kamu belum punya buku favorit. Tekan ♥ pada kartu buku." mengajak user bertindak, bukan sekadar dinding kosong.

Satu prinsip yang menyatukan semuanya: **data atau tidak, user selalu dijelaskan**. Skeleton saat memuat, pesan jelas + solusi saat gagal, ajakan saat kosong. Ini juga yang membuat aplikasi terlihat "dibuat dengan serius" — state yang direncanakan menunjukkan kematangan produk.

// js/ui-states.js

// ─── Library rendering state (materi ini) ──────────────────────────────────
const UIState = {
    loading(kontainer, pesan = "Memuat data...") {
        // role="status" + aria-live: pembaca layar mengumumkan tanpa mengganggu.
        kontainer.innerHTML = `
            <div class="loading-state" role="status" aria-label="${pesan}">
                <div class="spinner" aria-hidden="true"></div>
                <p>${pesan}</p>
            </div>
        `;
    },

    error(kontainer, pesan, onRetry = null) {
        // role="alert": pembaca layar segera mengabarkan perubahan penting.
        kontainer.innerHTML = `
            <div class="error-state" role="alert">
                <p class="error-state__pesan">${pesan}</p>
                ${onRetry ? `<button class="btn-retry">Coba Lagi</button>` : ""}
            </div>
        `;
        if (onRetry) kontainer.querySelector(".btn-retry")?.addEventListener("click", onRetry);
    },

    kosong(kontainer, pesan = "Tidak ada data yang ditemukan.") {
        kontainer.innerHTML = `
            <div class="empty-state">
                <p>${pesan}</p>
            </div>
        `;
    },
};

```javascript
// js/load-data.js

// ─── Wrapper: satu tempat yang mengatur loading → sukses/empty/gagal ───────
export async function loadData(kontainer, fetchFn, renderFn, pesanKosong = "Tidak ada data.") {
    // 1) Selalu tampilkan feedback segera — jangan biarkan layar diam.
    UIState.loading(kontainer);

    try {
        const data = await fetchFn();           // bisa dari cache (materi 32)

        // 2) Berhasil tapi tidak ada isi → empty state (jika array).
        if (!data || (Array.isArray(data) && data.length === 0)) {
            UIState.kosong(kontainer, pesanKosong);
            return;
        }

        // 3) Ada data → render. Kontainer diisi `renderFn`.
        renderFn(data);

    } catch (error) {
        // 4) Gagal → pesan RAMAH + tombol retry yang memanggil ulang dirinya.
        console.error(error); // log mentah untuk developer — bukan untuk user
        UIState.error(
            kontainer,
            pesanRamahError(error),
            () => loadData(kontainer, fetchFn, renderFn, pesanKosong),
        );
    }
}

// Petakan error teknis ke pesan manusia. Jangan pernah tampilkan yang mentah.
function pesanRamahError(error) {
    if (error instanceof TypeError) {
        return "Koneksi internet bermasalah. Periksa jaringanmu, lalu coba lagi.";
    }
    // HTTP error (dari request() di materi 31) sudah punya pesan.
    if (typeof error.message === "string" && error.message.includes("HTTP")) {
        return "Server kami sedang bermasalah. Silakan coba beberapa saat lagi.";
    }
    return "Terjadi kesalahan yang tidak terduga. Silakan coba lagi.";
}
```

    });
}

## 4. Analogi Sederhana — Membangun Rumah

Di rumah analogi kita, **HTML** adalah kerangka, **CSS** adalah cat, dan **JavaScript** adalah instalasi listrik. **Loading spinner** dalam rumah ini adalah **lampu "sedang mengantar" di pintu**: sebelum pesanan buku datang, ada indikator terang yang menyala — tamu yang menunggu di teras tahu barang sedang diantar, bukan terlupa. **Skeleton screen** adalah versi lebih cerdas dari lampu itu: dia bukan hanya "sedang memuat", tapi menampilkan cetakan lemari dan rak yang akan diisi — sehingga pemilik rumah sudah membayangkan posisi rak buku sebelum barang sampai.

**Error state** adalah **plang "paket gagal terkirim, coba lagi"** di pintu. Bukan teras kelam tanpa penjelasan. Plang itu memberitahu apa yang terjadi (gagal terkirim), mengapa (alamat salah / kurir macet), dan memberi jalan keluar (tombol coba lagi). Bayangkan kontrasnya: teras gelap gulita — pemilik rumah tidak tahu apakah kurir masih di jalan, tersesat, atau tidak pernah datang. Plang, walau sebenarnya kabar buruk, lebih berharga daripada diam.

**Empty state** adalah **rak yang kosong tapi diberi kartu tulisan**: "Belum ada buku yang disimpan — pilih favoritmu di toko buku." Rak kosong tanpa tutur kata membingungkan (apakah rusak? lupa diisi?); dengan tulisan itu, pemilik rumah tahu rak memang kosong dan diajak bertindak. **Tombol retry** adalah **menelepon ulang kurir** — satu aksi nyata yang diberikan kepada pemilik rumah, alih-alih memintanya menunggu dalam ketidakpastian selamanya. Dan `role="status"`/`role="alert"` adalah **pengumuman lewat speaker rumah**: mereka yang tidak bisa melihat lampu/plang (pembaca layar) tetap mendengar apa yang terjadi.

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

- **Saat halaman katalog pertama dimuat** — skeleton katalog; bila belum ada jaringan, error + retry; bila hasil kosong, empty state.
- **Real-time search** — setiap keystroke memicu loading state (dengan debounce), dan `AbortController` memastikan request lama dibatalkan agar state beralih dengan benar.
- **Halaman detail buku** — klik kartu → skeleton detail → isi data, atau error 404 dengan pesan "Buku tidak ditemukan" dan tombol kembali.
- **Halaman favorit** — empty state yang mengajak: "Kamu belum punya favorit, tekan ♥ pada kartu buku", bukan dinding kosong.
- **Aksi yang butuh konfirmasi server** (mis. checkout peminjaman) — button disable + spinner kecil di dalamnya, lalu sukses/error eksplisit.

## 6. Poin-poin Penting & Best Practices

- **Jangan pernah membiarkan layar diam**: setiap permintaan data wajib punya state loading, dan setiap kegagalan wajib punya umpan balik.
- **Skeleton > spinner bila bentuknya bisa ditebak** (grid kartu); spinner cukup untuk area yang bentuknya tidak jelas. Keduanya relatif murah dan dipakai bersamaan.
- **Selalu sediakan tombol retry** pada error state — jangan hanya menampilkan pesan dan berhenti; beri user jalan keluar yang jelas.
- **Jangan pernah menampilkan error mentah** (`TypeError: Failed to fetch`) langsung ke user; petakan ke pesan ramah, dan log `error` mentah hanya untuk developer di konsol.
- **Gunakan `role="status"` untuk loading dan `role="alert"` untuk error** + `aria-live` yang sesuai pada kontainer agar pembaca layar mengabarkan perubahan — aksesibilitas bukan afterthought.
- **Debounce tetap dipakai** untuk pencarian; padukan dengan `AbortController` agar state tidak bertabrakan antar request.
- **Rangkum dengan wrapper `loadData(kontainer, fetchFn, renderFn)`** — satu tempat mengelola giliran state, konsisten dipakai di seluruh aplikasi.
- **Terapkan textContent** untuk konten dari API (jangan masukkan data tak terkontrol ke innerHTML) — materi 33 menutup mata rantai keamanan yang mulai di materi 26.

## 7. Kesalahan Umum (Common Pitfalls & Bugs)

- **Lupa memeriksa hasil kosong** → grid menampilkan layout kosong yang membingungkan saat pencarian tidak menemukan buku. Perbaikan: state empty, bukan grid kosong (di dalam `loadData`).
- **Menampilkan pesan error mentah ke user** → "TypeError: Failed to fetch" tidak membantu user memutuskan tindakan. Perbaikan: petakan lewat `pesanRamahError()`; konsol hanya untuk developer.
- **Error tanpa tombol retry** → user mencapai jalan buntu: harus reload manual. Perbaikan: selalu `onRetry` yang memanggil ulang `loadData`.
- **Loading state tidak pernah dihapus** → jika `renderFn` error di luar try/catch, spinner bertahan selamanya (stuck). Perbaikan: pastikan `renderFn` ikut dalam `try/catch` atau tangani dengan `finally`.
- **Skeleton/spinner tidak accessible** → pembaca layar diam saat konten berubah. Perbaikan: `role="status"`/`aria-live` pada kontainer, `aria-hidden` pada dekorasi visual.

```javascript
// js/main.js (solusi lengkap 1 & 2)

// ─── UI States (soal 1) ────────────────────────────────────────────────────
const UIState = {
    loading(kontainer, pesan = "Memuat data...") {
        kontainer.innerHTML = `
            <div class="loading-state" role="status" aria-label="${pesan}">
                <div class="spinner" aria-hidden="true"></div>
                <p>${pesan}</p>
            </div>
        `;
    },
    error(kontainer, pesan, onRetry) {
        kontainer.innerHTML = `
            <div class="error-state" role="alert">
                <p class="error-state__pesan">${pesan}</p>
                <button class="btn-retry">Coba Lagi</button>
            </div>
        `;
        kontainer.querySelector(".btn-retry")?.addEventListener("click", onRetry);
    },
    kosong(kontainer, pesan = "Tidak ada data yang ditemukan.") {
        kontainer.innerHTML = `<div class="empty-state"><p>${pesan}</p></div>`;
    },
};

async function loadData(kontainer, fetchFn, renderFn, pesanKosong) {
    UIState.loading(kontainer);
    try {
        const data = await fetchFn();
        if (!data || (Array.isArray(data) && data.length === 0)) {
            UIState.kosong(kontainer, pesanKosong);
            return;
        }
        renderFn(data);
    } catch (error) {
        console.error(error);
        UIState.error(kontainer, pesanRamah(error),
            () => loadData(kontainer, fetchFn, renderFn, pesanKosong));
    }
}

function pesanRamah(error) {
    if (error instanceof TypeError) return "Koneksi internet bermasalah. Coba lagi.";
    if (String(error.message).includes("HTTP")) return "Server bermasalah, coba sebentar lagi.";
    return "Terjadi kesalahan. Silakan coba lagi.";
}

// ─── Cache 5 menit (materi 32) ──────────────────────────────────────────────
class Cache {
    constructor(prefix = "cache") { this.prefix = prefix; }
    simpan(key, data, ttlDetik = 300) {
        localStorage.setItem(`${this.prefix}_${key}`, JSON.stringify({
            data, expired: Date.now() + ttlDetik * 1000,
        }));
    }
    ambil(key) {
        const entry = JSON.parse(localStorage.getItem(`${this.prefix}_${key}`) || "null");
        if (!entry) return null;
        if (Date.now() > entry.expired) { localStorage.removeItem(`${this.prefix}_${key}`); return null; }
        return entry.data;
    }
}
const cache = new Cache("katalog");

// ─── Fetch + debounce (materi 31) ───────────────────────────────────────────
async function ambilBuku(query) {
    const key = `q=${query}`;
    const cached = cache.ambil(key);
    if (cached) return cached;

    const response = await fetch(
        `https://openlibrary.org/search.json?q=${encodeURIComponent(query)}&limit=10`
    );
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const data = await response.json();

    cache.simpan(key, data, 300);
    return data;
}

let timer = null;
document.querySelector("#input-cari").addEventListener("input", (event) => {
    clearTimeout(timer);
    const q = event.target.value.trim();
    if (!q) return;
    timer = setTimeout(() => muatKatalog(q), 300); // debounce
});

function renderKatalog(data) {
    const kontainer = document.querySelector("#konten-katalog");
    kontainer.textContent = "";
    data.docs.forEach((buku) => {
        const item = document.createElement("p");
        item.textContent = buku.title;             // textContent: aman
        kontainer.appendChild(item);
    });
}

function muatKatalog(q) {
    loadData(
        document.querySelector("#konten-katalog"),
        () => ambilBuku(q),
        renderKatalog,
        `Tidak ada buku yang cocok untuk "${q}".`,
    );
}

// Muat awal halaman dengan query default.
muatKatalog("pemrograman");
```

**Pembahasan.** Soal 1 menghasilkan satu titik pengatur state — `loadData` — yang dipakai semua pemanggilan, dengan pesan ramah dan tombol retry yang merekrusif memanggil dirinya sendiri sehingga tidak perlu reload halaman. Soal 2 menunjukkan sinergi ketiga materi Level 6: cache menegaskan bahwa data masih segar menghemat request dan membuat loading singkat; debounce mencegah spam request; dan jika jaringan putus, `loadData` memberi error + retry sementara hasil lama di cache tetap bisa digunakan bila masih berlaku. Perhatikan bahwa empty state dibedakan dengan jelas dari error state: "tidak ada hasil" bukan "gagal memuat" — keduanya ditangani di jalur yang berbeda.
