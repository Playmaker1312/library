# 38. Deploy ke Netlify dan Vercel

Materi ini membahas proses meluncurkan aplikasi ke internet: deploy ke **Netlify** (drag-drop, CLI, import GitHub), **Vercel** (CLI atau import repo), konfigurasi **netlify.toml** (build command, publish dir, redirect SPA `/* → index.html`), **CI/CD otomatis dengan GitHub Actions** (workflow build → deploy dengan secrets `NETLIFY_AUTH_TOKEN` & `NETLIFY_SITE_ID`), custom domain, dan alasan mengapa auto-deploy adalah praktik terbaik.

## 1. Penjelasan Singkat & Konsep Dasar

Setelah semua kode rapi (materi 34-37), tahap terakhir adalah **deploy** — menempatkan hasil build (`dist/`) ke server yang bisa diakses publik melalui URL. Sampai Level 6, aplikasi hanya jalan di komputer kamu (LocalStorage live server di `localhost`). Deploy memindahkan produk ke *internet nyata*: dikelola penyedia **hosting statis** seperti **Netlify** atau **Vercel**, yang menyimpan file HTML/CSS/JS dan menyajikannya ke pengunjung dengan CDN (jaringan server global), HTTPS otomatis (SSL), dan dashboard untuk konfigurasi.

Mengapa disebut *hosting statis*? Aplikasi vanilla ini menghasilkan file-file YANG SUDAH JADI: browser mengeksekusi JS di sisi klien, dan server hanya perlu mengirim file. Tidak ada server runtime yang menjalankan database atau bahasa pemrograman di belakangnya (back-end API tetap dipanggil dari klien, mis. Open Library). Ini membuat hosting murah, cepat, dan bisa di-deploy dengan sangat sederhana — bahkan **drag-and-drop** folder hasil build ke Netlify langsung membuat situs online. Tetapi untuk pengembangan nyata, kita tidak mau mengunggah manual setiap kali ada perubahan; di situlah **CI/CD** (Continuous Integration / Continuous Deployment) masuk.

**CI/CD** menghubungkan **GitHub Actions** dengan penyedia hosting. Setiap `git push` ke branch `main`, GitHub menjalankan *workflow* (file YAML di `.github/workflows/`): checkout kode, setup Node.js, `npm ci`, `npm run build`, lalu `netlify deploy --prod --dir=dist` dengan token otentikasi. Injeksi credential ke alur itu memakai **secrets** — variabel tersembunyi (`NETLIFY_AUTH_TOKEN`, `NETLIFY_SITE_ID`) yang disimpan di halaman *Settings → Secrets* repo, sehingga kredensial tak pernah tertulis di kode atau history commit.

Satu hal khusus untuk **SPA (Single Page Application)**: aplikasi yang "menjadi satu halaman" (routing oleh JS, misalnya saat memakai `pushState` atau template menyimpan `catalogs/...` di path) membutuhkan **fallback redirect**. Jika user membuka `https://site/detail-buku-123` langsung (bookmark atau refresh), server statis mencari file `dist/detail-buku-123` yang tidak ada → **404**. Solusinya: redirect `/*` → `/index.html` (status 200), sehingga HTML di-serve dan JS membaca URL untuk menampilkan halaman yang benar. Di Netlify ini ditulis di `netlify.toml`; di Vercel analog fungsinya lewat `vercel.json`.

**Custom domain** adalah tahap terakhir: pindahkan nama yang dibeli (misal `perpustakaan-kota.id`) menunjuk ke layanan hosting via DNS (A record atau CNAME), lalu HTTPS aktif otomatis. Deployment tidak selesai, ia menjadi loop: konten satu-satunya yang benar adalah repositori; perubahan apa pun di anggap *renovasi* yang disertifikasi dan dibuka lagi ke publik secara otomatis.

**Benang merah**: materi 34-37 menghasilkan artefak `dist/` (hasil build Vite yang diproduksi & diminify). Materi 38 menutup lingkaran: mengirim artefak itu ke publik, membangun pipeline yang menempa ulang setiap ada *push*, dan memastikan aplikasi terbuka lewat nama domain. Dengan deploy selesai, checklist akhir roadmap lengkap: skor Lighthouse tinggi, bundle kecil, aksesibilitas teruji, dan aplikasi yang hari ini dibuka jutaan orang ternyata berkembang dari "halaman statis" hingga "production-ready".

## 2. Fungsi & Kegunaan Utama dalam Web

Bagi **Perpustakaan Digital Kota**, deploy berarti layanan benar-benar tersedia: pengunjung bisa mencari buku, membuka detail, menandai favorit — semua lewat URL publik, dilindungi HTTPS ketika SSL otomatis aktif, dan disajikan cepat karena CDN Netlify/Vercel. Tim tidak perlu server sendiri, tidak perlu invoice besar, dan tidak perlu mengelola sekuritas server — cukup *push* kode dan pembaruan tiba di seluruh dunia dalam hitungan menit.

**Auto-deploy** mengubah cara kerja tim. Setiap penambahan fitur atau perbaikan bug cukup lewat satu pull request: workflow menjalankan build di commit yang berbeda, dan bila lolos, versi tersebut otomatis online. Tidak ada lagi "siapa yang mengunggah ke FTP?", "mana dist terbaru?", atau "buildnya di laptop siapa yang benar?". Repositori menjadi satu-satunya sumber kebenaran — **reproducible**: `npm ci` memastikan build CI persis seperti `npm run build` di lokal (materi 37).

Bagi organisasi/perusahaan, CI/CD menjembatani **review**: workflow bisa menambah *deploy preview* (Netlify Deploy Previews / Vercel Previews) yang membuat setiap PR punya URL uji tersendiri — tim dan stakeholder bisa mengklik tautan versi *staging* sebelum disetujui. Sementara **deploy preview + branch policy** memisahkan "versi utama" (`main` → production) dari "versi uji" (PR → preview). Ini adalah praktik yang membuat aplikasi publik tetap stabil saat fitur baru diuji. Dan dengan **custom domain + SSL** yang otomatis, pengguna melihat layanan resmi yang dipercaya, bukan URL acak `.netlify.app`.

## 3. Contoh Kode & Implementasi Real-World

Konfigurasi penuh: mem-build dengan Vite, `netlify.toml` dengan redirect SPA, `vercel.json`, dan GitHub Actions untuk deploy otomatis ke Netlify; plus langkah manual Netlify/Vercel.

```bash
# ─── Persiapan build produksi ─────────────────────────────────────────────
npm create vite@latest perpustakaan-web
cd perpustakaan-web
# (isi src/ sesuai materi 34-37)
npm install
npm run build          # → menghasilkan folder dist/
npm run preview        # cek hasil build lokal sebelum deploy
```

```text
# Deploy MANUAL ke Netlify
# 1) Buka app.netlify.com → Drag & Drop folder dist/ ke kolom "drag & drop"
#    → situs online instan di URL random.netlify.app
#    (cocok untuk demo cepat; 'Deploy Preview' otomatis untuk perubahan)

# 2) Via CLI (repeatable dari terminal):
npm install -g netlify-cli
netlify login
netlify deploy --prod --dir=dist

# 3) Import dari GitHub (untuk CI/CD):
#    app.netlify.com → Add new site → Import an existing project → pilih repo.
#    Setting build (atau baca dari netlify.toml):
#      Build command: npm run build
#      Publish directory: dist
```

```toml
# netlify.toml — konfigurasi deploy di Netlify (dibaca saat import/CLI)
[build]
  command = "npm run build"   # perintah untuk membangun kode
  publish = "dist"            # folder hasil build yang disajikan

# Redirect SPA: semua path (/*) fallback ke index.html dengan status 200
# sehingga refresh/bookmark di path dalam aplikasi tidak 404.
[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200
```

```json
// vercel.json — analog netlify.toml untuk Vercel (SPA fallback)
{
  "buildCommand": "npm run build",
  "outputDirectory": "dist",
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
```

```yaml
# .github/workflows/deploy.yml — CI/CD otomatis (GitHub Actions → Netlify)

name: Build dan Deploy

# Kapan workflow dijalankan:
on:
  push:
    branches: [main]          # setiap push ke main
  pull_request:
    branches: [main]          # setiap PR ke main (untuk uji build)

jobs:
  build-deploy:
    runs-on: ubuntu-latest

    steps:
      # 1. Ambil kode repo ke runner (mesin CI)
      - uses: actions/checkout@v4

      # 2. Siapkan Node.js 20 + cache npm (percepat install)
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: "npm"

      # 3. Install dependensi PERSIS dari package-lock.json
      - name: Install dependencies
        run: npm ci

      # 4. Bangun bundle produksi → dist/
      - name: Build
        run: npm run build

      # 5. Deploy ke Netlify HANYA saat push ke main (bukan PR)
      - name: Deploy ke Netlify (production)
        if: github.ref == 'refs/heads/main'
        uses: netlify/actions/cli@master
        with:
          args: deploy --prod --dir=dist
        env:
          # Secret dibaca dari Setting → Secrets and variables → Actions di repo
          NETLIFY_SITE_ID: ${{ secrets.NETLIFY_SITE_ID }}
          NETLIFY_AUTH_TOKEN: ${{ secrets.NETLIFY_AUTH_TOKEN }}
```

```yaml
# .github/workflows/deploy.yml — varian: deploy PR sebagai preview (non-prod)
# Tambahkan job/step ini bila ingin setiap PR punya URL uji di Netlify:
      - name: Deploy ke Netlify (preview)
        if: github.event_name == 'pull_request'
        uses: netlify/actions/cli@master
        with:
          args: deploy --dir=dist --alias=pr-${{ github.event.pull_request.number }}
        env:
          NETLIFY_SITE_ID: ${{ secrets.NETLIFY_SITE_ID }}
          NETLIFY_AUTH_TOKEN: ${{ secrets.NETLIFY_AUTH_TOKEN }}
```

```bash
# ─── Deploy Vercel (alternatif) ───────────────────────────────────────────
# Vercel CLI:
npm install -g vercel
vercel         # deploy (pilih Y untuk version saat diminta)
vercel --prod  # deploy ke production
# atau: import repo di vercel.com → otomatis CI/CD + preview per PR.
```

```text
# Custom domain (Netlify):
# 1) Beli domain (mis. perpustakaan-kota.id)
# 2) Netlify → Site settings → Domain management → Add custom domain
# 3) Ikuti instruksi DNS: tambahkan A record @ → IP Netlify, atau
#    CNAME www → site.netlify.app. Tunggu propagasi (bisa 30m-24jam)
# 4) Netlify mengeluarkan sertifikat SSL otomatis (HTTPS aktif)
```

## 4. Analogi Sederhana — Membangun Rumah

**HTML** adalah kerangka, **CSS** adalah cat, **JS** adalah listrik, dan **TS** adalah blueprint presisi. Deploy adalah **menyerahkan kunci rumah ke publik** — dan sebelumnya harus memastikan rumah sudah selesai dibangun (hasil build, materi 37) serta memakai **gerbang pengaman (SSL/HTTPS)**. Netlify/Vercel seperti **penjaga gerbang perumahan** yang menjaga pintu masuk; semua pengunjung (browser) masuk lewat satu gerbang yang sama, keamanannya diurus tanpa kita ikut campur (HTTPS otomatis, CDN menyebar "iklan papan arah" ke banyak kota agar pengunjung dari tangga mana pun cepat tiba).

**CI/CD** adalah **petugas pemeliharaan yang otomatis mengecak ulang rumah setiap ada renovasi lalu membukanya kembali**. Ketika kami mengganti dinding (push fitur ke `main`), petugas tidak menunggu seseorang menyalakan lampu secara manual di malam hari. Ia langsung: memeriksa material yang dipakai (`npm ci`), membangun ulang sesuai blueprint (`npm run build`), memastikan tidak ada yang patah, dan bila semuanya lolos — membuka kembali pintu ke publik (`deploy --prod`). Kalau renovasi gagal di tengah, pintu TETAP terkunci di versi sebelumnya: pengunjung tidak pernah melihat versi yang rusak, karena deployment hanya terjadi saat build sukses.

**Redirect SPA** seperti **catatan "kamar ini sekarang pindah lokasi" yang ditempel di lobi**. Aplikasi perpustakaan digital menampilkan semua serat di satu lobi raksasa (SPA) — URL `/detail/123` adalah *posisi kursi* di lobi itu. User yang me-refresh dari kursi tersebut langsung tiba di alamat lama yang kosong (server statis mencari file `detail/123` — tidak ada, 404). Portal lobi memberikan petunjuk: "semua siapa pun yang masuk di sini, dipersilakan masuk lewat pintu utama dulu" (`/* → index.html`, status 200), lalu JS menunjuk menunjukkan lokasi yang benar. **Custom domain** adalah **papan nama resmi di gerbang perumahan**: bukan nomor rumah acak dari penjaga (`.netlify.app`), melainkan alamat yang diingat orang — dengan jam tahan yang tersambung (SSL) yang membuat papan nama sulit dipalsukan (HTTPS).

## 5. Kapan Harus Digunakan & Kasus Penggunaan (Use Cases)

- **Rilis pertama aplikasi** — deploy statis cepat (Netlify drag-drop atau Vercel CLI) untuk membagikan application URL dengan stakeholders/hari peresmian perpustakaan; `npm run preview` (materi 37) memastikan build benar sebelum publikasi.
- **Feed live development** — hook GitHub + Netlify/Vercel: setiap push ke `main` ter-deploy otomatis; pelanggan internal tidak perlu menunggu rilis manual.
- **PR review dengan URL uji** — deploy preview per pull request: reviewer klik tautan staging, uji fitur baru di browser nyata, tanpa menyentuh versi production.
- **Aplikasi yang menangani berbagai path** — SPA dengan route (`/katalog`, `/detail/:id`) wajib redirect `/ *` → `index.html` agar refresh dan share link tidak 404; untuk site multi-halaman statis, redirect tidak wajib.
- **Melindungi workflow dari credential leak** — deploy ditangani CI (GitHub Actions) dengan secrets repo (`NETLIFY_AUTH_TOKEN`, `NETLIFY_SITE_ID`), tidak ada token tertulis di kode/`netlify.toml`; `vercel` CLI menyimpan token di login pribadi.
- **Mengganti brand/jangka panjang** — custom domain + SSL: alamat publik resmi, cache CDN tetap, dan siap saat traffic naik (pricing gratis/enterprise yang jelas per penyedia).

## 6. Poin-poin Penting & Best Practices

- **Build dulu, verify dulu**: jalankan `npm run build && npm run preview` (materi 37) sesaat sebelum deploy; pastikan `dist/` berisi `index.html`, `assets/`, dan folder `public/`.
- **Baca netlify.toml sebagai kontrak**: `[build] command` = `npm run build`; `publish` = `dist`. Jika path salah → deployment sukses tapi situs kosong/404. Redirect SPA `/* → /index.html, status 200` hanya jika aplikasi ber-route (SPA).
- **CI/CD adalah best practice**: `.github/workflows/deploy.yml` + secrets — deploy otomatis per push, reproducible (`npm ci`), dan versi production tidak pernah rusak karena build gagal (artefak lama tetap hidup).
- **Secrets jangan pernah di-commit**: token di repositori sama berbahaya dengan password; selalu lewat GitHub Settings → Secrets. Abaikan `.env`, `node_modules`, `dist` (materi 37 punya `.gitignore`).
- **Deploy previews**: aktifkan preview untuk setiap PR supaya uji sebelum merge; jaga production hanya dari `main`.
- **Custom domain + HTTPS**: aktifkan, periksa DNS (A/CNAME) dan tunggu propagasi; sertifikat SSL otomatis (Let's Encrypt) aktif biasanya dalam beberapa menit.
- **Kontrol setelah deploy**: verifikasi di URL production (navigate, refresh di route dalam, uji form), dan jalankan Lighthouse sekali lagi terhadap URL produksi — bukan hanya localhost.
- **Rollback yang mudah**: Netlify & Vercel menyimpan riwayat deploy; jangan panik — kembalikan ke versi sebelumnya lewat dashboard bila ada regresi.

## 7. Kesalahan Umum (Common Pitfalls & Bugs)

- **Deploy tanpa redirect SPA → 404 di route dalam** — user refresh/reopen `https://site/detail/123` mendapat 404 karena server mencari file `detail/123` (fisik). Perbaikan: tambahkan `[[redirects]] from="/*" to="/index.html" status=200` di `netlify.toml` (atau `rewrites` di `vercel.json`), sesuai materi.
- **Build path `publish` salah** — `publish = "dist"` dirujuk ke `publish = "."` atau `public` — site tampil kosong / error 404. Perbaikan: cocokkan dengan `outDir` Vite (`dist`); pastikan `command` menghasilkan folder yang dimaksud dengan `npm run build && ls dist`.
- **Kredensial hilang/ekspos di workflow** — secret bernama salah (mis. `NETLIFY_SITE_ID` vs `NETLIFY_SITE_ID`) atau token di-commit → deploy gagal / kebocoran. Perbaikan: definisikan secrets dengan nama yang sama persis di Settings → Secrets; jangan pernah tuliskan nilai token di file manapun; putar token bila bocor.
- **`netlify deploy --prod` di jalankan untuk semua event** — workflow menjalankan deploy produksi saat PR juga (tiap helikopter checkout), menumpuk versi atau menghapus preview. Perbaikan: kondisikan job (`if: github.ref == 'refs/heads/main'`); gunakan `--alias=pr-N` untuk preview.
- **Build di CI tidak cocok dengan local** — CI memakai `npm install` (memperbarui versi) atau tidak `npm ci` sehingga versi dependensi berubah → behavior berubah. Perbaikan: selalu `npm ci` (+ `cache: npm`) agar persis `package-lock.json`.
- **Domain tidak begitu aktif setelah add** — user tanya kenapa situs tidak muncul: propagasi DNS dan sertifikat butuh waktu. Perbaikan: ikuti instruksi DNS, tunggu (30m-24j), gunakan Netlify "Verify DNS configuration"; periksa via `nslookup`.

## 8. Mini Project / Soal Latihan & Kunci Jawaban

### Tantangan

1. Siapkan project Vite (dari materi 37) dan deploy ke **Netlify**: buat `netlify.toml` yang benar (build command, publish dir `dist`, redirect SPA `/* → index.html`), lalu deploy via **drag-drop** dulu, kemudian via **CLI** (`netlify deploy --prod --dir=dist`). Pastikan aplikasi berjalan online dan refresh dari route dalam (`/detail-buku`) tidak 404.
2. Latihan lanjutan: buat **CI/CD dengan GitHub Actions** — file `.github/workflows/deploy.yml` yang menjalankan checkout → setup node (20, cache npm) → `npm ci` → `npm run build` → `netlify deploy --prod --dir=dist` hanya saat push ke `main`. Tambahkan dua secrets di repo (`NETLIFY_AUTH_TOKEN` dari netlify.com, `NETLIFY_SITE_ID` dari pengaturan situs), dorong satu commit ke `main`, dan buktikan auto-deploy berjalan (terlihat di tab Actions; URL production diperbarui).

### Solusi & Pembahasan

```toml
# netlify.toml — pembahasan tantangan 1
[build]
  command = "npm run build"
  publish = "dist"

# SPA: semua path dapat di-serve (fallback ke index.html, status 200)
[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200
```

```yaml
# .github/workflows/deploy.yml — pembahasan tantangan 2
# Simpan di perpustakaan-web/.github/workflows/deploy.yml

name: Build dan Deploy

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: "npm"

      - name: Install dependencies
        run: npm ci

      - name: Build
        run: npm run build

      # Deploy production hanya dari push ke main
      - name: Deploy ke Netlify (production)
        if: github.ref == 'refs/heads/main'
        uses: netlify/actions/cli@master
        with:
          args: deploy --prod --dir=dist
        env:
          NETLIFY_SITE_ID: ${{ secrets.NETLIFY_SITE_ID }}
          NETLIFY_AUTH_TOKEN: ${{ secrets.NETLIFY_AUTH_TOKEN }}

      # Preview untuk setiap PR
      - name: Deploy ke Netlify (preview)
        if: github.event_name == 'pull_request'
        uses: netlify/actions/cli@master
        with:
          args: deploy --dir=dist --alias=pr-${{ github.event.pull_request.number }}
        env:
          NETLIFY_SITE_ID: ${{ secrets.NETLIFY_SITE_ID }}
          NETLIFY_AUTH_TOKEN: ${{ secrets.NETLIFY_AUTH_TOKEN }}
```

```bash
# Cara mendapatkan kedua secrets untuk repo kamu:
# 1) NETLIFY_AUTH_TOKEN:
#    app.netlify.com → User settings → Applications → New access token
#    (simpan sekali; Netlify tidak menampilkan lagi)
# 2) NETLIFY_SITE_ID:
#    di situs Netlify → Site settings → General → "API ID" (kode site id)
#    (atau jalankan `netlify status` setelah `netlify login`)

# Lalu di repo GitHub:
# Settings → Secrets and variables → Actions → New repository secret
#   NETLIFY_AUTH_TOKEN = ...
#   NETLIFY_SITE_ID    = ...
```

**Pembahasan**: Tantangan 1 selesai ketika aplikasi bisa dibuka di URL Netlify, dan saat kamu membuka url lalu me-refresh halaman `https://your-site.netlify.app/detail-buku/abc` halaman **tetap tampil** (bukan 404 standar) — bukti `[[redirects]]` bekerja: server mengirim `index.html` dengan status 200 dan JS aplikasi menampilkan tujuan yang benar. `publish = "dist"` harus cocok dengan output `npm run build` (materi 37); jika challenger melihat situs kosong atau 404 di root, periksa isi `dist/` dan path publish. Deploy CLI (`netlify deploy --prod --dir=dist`) memakai `netlify.toml` sebagai sumber autentikasi dan konfigurasi, sehingga hasilnya sama persis dengan deploy otomatis.

Untuk tantangan 2, mekanisme CI jelas: setiap `push` ke `main` memicu checkout kode sementara (di runner), `npm ci` menginstal dependensi dari `package-lock.json` (reproducible — tidak seperti `npm install`), `npm run build` membangun `dist/`, dan step deploy dipisah dengan kondisi `if`: step produksi hanya untuk main (`--prod` = deploy ke production URL), step preview hanya untuk pull request (`--alias=pr-N` menghasilkan URL test terpisah). Kedua step membaca credential dari `secrets.*` — tidak pernah tertulis di file. Bukti keberhasilan: tab Actions menampilkan workflow yang sukses berlabel yang kamu push, dan URL production Netlify otomatis menyajikan versi terbaru tanpa tindakan manual. Untuk verifikasi menyeluruh, jalankan Lighthouse terhadap URL production (target Performance > 90, Accessibility > 90 dari checkpoint Level 7), dan kamu telah menyelesaikan seluruh roadmap: dari halaman HTML pertama hingga aplikasi perpustakaan digital yang production-ready, versioned, dan terintegrasi CI/CD.
