# Test Utility Functions — TDD Approach

## Penjelasan
**TDD** (Test-Driven Development) adalah pendekatan di mana test ditulis **sebelum** kode implementasi. Siklusnya: **Red** (tulis test yang gagal) → **Green** (tulis kode minimal agar test lulus) → **Refactor** (perbaiki kode tanpa mengubah perilaku). Pendekatan ini memastikan setiap baris kode memiliki test yang valid, kode dirancang untuk mudah di-test, dan regression terdeteksi dini. Untuk utility functions — fungsi kecil murni yang melakukan satu hal — TDD sangat cocok karena input/output-nya jelas.

## Fungsi
- Memastikan kode yang ditulis benar-benar dibutuhkan (tidak over-engineering)
- Dokumentasi hidup — test menjelaskan bagaimana fungsi seharusnya berperilaku
- Jaring pengaman — perubahan kode tidak merusak fungsi yang sudah ada
- Mendorong desain kode yang modular dan terisolasi

## Cara Pengimplementasian

### Siklus TDD: Red → Green → Refactor

```js
// 🔴 RED — Tulis test yang gagal TERLEBIH DAHULU
// 📁 src/utils/rumahUtils.test.js

import { describe, it, expect } from "vitest";

describe("formatUkuranRumah", () => {
  it("mengembalikan string ukuran dalam meter persegi", () => {
    // Test ini akan FAIL karena fungsi belum ada
    expect(formatUkuranRumah(120)).toBe("120 m²");
  });

  it("menangani angka desimal", () => {
    expect(formatUkuranRumah(45.5)).toBe("45.5 m²");
  });

  it("melempar error untuk input negatif", () => {
    expect(() => formatUkuranRumah(-10)).toThrow("Ukuran tidak valid");
  });
});
```

```js
// 🟢 GREEN — Tulis kode minimal AGAR test lulus
// 📁 src/utils/rumahUtils.js

export function formatUkuranRumah(ukuran) {
  if (ukuran < 0) throw new Error("Ukuran tidak valid");
  return `${ukuran} m²`;
}
```

```js
// 🔵 REFACTOR — Perbaiki kode, test tetap hijau
// Misal: tambah validasi tipe data
export function formatUkuranRumah(ukuran) {
  if (typeof ukuran !== "number") throw new Error("Ukuran harus angka");
  if (ukuran < 0) throw new Error("Ukuran tidak valid");
  return `${ukuran} m²`;
}
```

### TDD Lengkap — Utility Functions untuk Rumah

```js
// 🔴 RED: tulis test untuk semua fungsi utility rumah
// 📁 src/utils/rumahUtils.test.js

import { describe, it, expect } from "vitest";
import {
  hitungLuas,
  formatAlamat,
  cekKetersediaanAir,
  hitungBiayaCat,
} from "./rumahUtils";

describe("hitungLuas", () => {
  it("menghitung luas dengan benar", () => {
    expect(hitungLuas(10, 8)).toBe(80);
  });
  it("melempar error jika lebar <= 0", () => {
    expect(() => hitungLuas(10, 0)).toThrow();
  });
});

describe("formatAlamat", () => {
  it("menggabungkan jalan dan kota", () => {
    expect(formatAlamat("Anggrek", "Bandung")).toBe("Jl. Anggrek, Bandung");
  });
  it("trim spasi berlebih", () => {
    expect(formatAlamat("  Anggrek  ", "  Bandung  ")).toBe("Jl. Anggrek, Bandung");
  });
});

describe("cekKetersediaanAir", () => {
  it("mengembalikan true jika debit > 0", () => {
    expect(cekKetersediaanAir(10)).toBe(true);
  });
  it("mengembalikan false jika debit 0", () => {
    expect(cekKetersediaanAir(0)).toBe(false);
  });
});

describe("hitungBiayaCat", () => {
  it("menghitung biaya total dengan benar", () => {
    expect(hitungBiayaCat(50, 15000)).toBe(750000);
  });
  it("melempar error jika luas <= 0", () => {
    expect(() => hitungBiayaCat(0, 15000)).toThrow();
  });
});
```

```js
// 🟢 GREEN: implementasi minimal

export function hitungLuas(p, l) {
  if (p <= 0 || l <= 0) throw new Error("Dimensi tidak valid");
  return p * l;
}

export function formatAlamat(jalan, kota) {
  return `Jl. ${jalan.trim()}, ${kota.trim()}`;
}

export function cekKetersediaanAir(debit) {
  return debit > 0;
}

export function hitungBiayaCat(luasDinding, hargaPerMeter) {
  if (luasDinding <= 0) throw new Error("Luas tidak valid");
  return luasDinding * hargaPerMeter;
}
```

### Testing Edge Cases dalam TDD
```js
describe("Edge cases utility rumah", () => {
  it("hitungLuas dengan angka desimal", () => {
    expect(hitungLuas(10.5, 2.5)).toBeCloseTo(26.25);
  });

  it("formatAlamat dengan null — harus error", () => {
    expect(() => formatAlamat(null, "Jakarta")).toThrow();
  });

  it("cekKetersediaanAir dengan angka negatif — tetap true (air mengalir balik)", () => {
    // Ini menunjukkan kasus yang perlu didiskusikan dengan tim
    expect(cekKetersediaanAir(-5)).toBe(true);
  });

  it("hitungBiayaCat dengan luas dinding 0 — error", () => {
    expect(() => hitungBiayaCat(0, 10000)).toThrow();
  });
});
```

## Analogi
**TDD** ibarat **membuat daftar inspeksi rumah sebelum membangun rumah**. 🔴 **Red**: Kontraktor membuat daftar periksa terlebih dahulu — "Pintu depan harus terbuka", "Jendela harus kedap air" — lalu mencoba menggunakan daftar itu, dan **semua gagal** karena rumah belum dibangun. 🟢 **Green**: Tukang membangun rumah secara minimal — memasang pintu yang bisa terbuka, jendela yang kedap air — lalu inspektur (test) memeriksa ulang, dan **semua lulus**. 🔵 **Refactor**: Tukang merapikan kabel, mengecat rapi, menambal celah — rumah tetap berfungsi sama, test tetap hijau. Tanpa TDD, inspeksi dilakukan setelah rumah selesai — bisa saja ada ruang yang tidak sesuai dan harus dibongkar ulang (mahal). Dengan TDD, setiap langkah diverifikasi sejak awal.

| Konsep | Analogi Rumah |
|---|---|
| **Red** | Membuat daftar inspeksi SEBELUM bangun — semua gagal |
| **Green** | Membangun minimal agar lolos inspeksi |
| **Refactor** | Merapikan rumah tanpa mengubah fungsi |
| Utility function | Satu alat rumah (meteran, water stop) |
| Edge case | Kondisi ekstrem (hujan badai, gempa kecil) |
| Test suite | Buku besar inspeksi seluruh rumah |
| `describe` | Bab buku per ruangan |
| Regression test | Inspeksi ulang setelah renovasi |

## Dipakai Untuk Apa
- Mengembangkan library atau utility functions yang membutuhkan keandalan tinggi
- Proyek tim — TDD memastikan semua anggota paham spesifikasi sebelum coding
- Codebase yang terus berkembang — test mencegah fitur baru merusak yang lama
- Refactoring besar-besaran — test memberi kepercayaan untuk mengubah struktur kode
- Open source — maintainer butuh jaminan bahwa kontribusi tidak merusak

## Kesalahan Umum
- Menulis test yang **terlalu kompleks di awal** — TDD dimulai dari test paling sederhana (baby steps)
- **Lupa Refactor** — kode hijau sering dibiarkan berantakan karena "sudah lulus test"
- **Test yang sama dengan implementasi** — test menulis ulang logika yang sama, bukan memverifikasi output
- **TDD hanya untuk pure function** — memang benar, TDD paling cocok untuk fungsi tanpa efek samping
- **Terlalu banyak mock** — utility functions seharusnya murni, tidak perlu mock sama sekali
- **Skip Red phase** — langsung menulis kode lalu test, ini bukan TDD

## Keterkaitan dengan Materi Sebelumnya
- **LEVEL 1-6**: TDD bisa diterapkan pada materi level mana pun — buat test dulu, baru implementasi
- **LEVEL 2 (Function)**: Utility functions selalu berupa function — pure function adalah kandidat utama TDD
- **LEVEL 3 (Object & Array)**: Test sering melibatkan array/object sebagai input/output
- **LEVEL 5 (Async)**: TDD untuk async function — tulis test dengan `await`, lalu implementasi
- **LEVEL 7 (File 62)**: NPM & Vite menyediakan environment untuk menjalankan test
- **LEVEL 7 (File 64)**: Vitest adalah framework yang digunakan untuk TDD — `vitest --watch` sangat mendukung siklus Red-Green-Refactor
