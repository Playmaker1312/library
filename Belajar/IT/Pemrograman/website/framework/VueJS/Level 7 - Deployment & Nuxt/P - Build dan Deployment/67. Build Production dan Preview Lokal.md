# 67. Build Production dan Preview Lokal

## Penjelasan

Build production adalah proses di mana Vite mengoptimasi kode Vue.js kamu untuk lingkungan production. Vite melakukan:

- **Minify** — menghapus spasi, komentar, dan mempersingkat nama variabel
- **Code splitting** — memecah kode menjadi chunk-chunk kecil berdasarkan dynamic import
- **Tree shaking** — membuang kode yang tidak terpakai (dead code)
- **Asset hashing** — menambahkan content hash pada nama file (misal: `index.abc123.js`) untuk cache busting

Perintah `npm run build` menghasilkan folder `dist/` yang siap di-deploy ke server. `npm run preview` memungkinkan kamu melihat hasil build tersebut di lokal sebelum benar-benar di-deploy.

Selain itu, validasi environment variables perlu dilakukan saat build agar aplikasi tidak error di production karena env variable yang hilang.

## Fungsi

- Memastikan aplikasi siap untuk production — tidak ada error build
- Mengecilkan ukuran file agar loading lebih cepat
- Cache busting melalui content hash — pengguna selalu dapat versi terbaru
- Memvalidasi environment variables sudah lengkap sebelum build
- Preview lokal untuk memeriksa apakah semuanya berfungsi

## Cara Implementasi / Kode

### 1. Build production dasar

```bash
npm run build
```

Output:

```
dist/
├── assets/
│   ├── index.abc123.js
│   ├── About.def456.js
│   ├── index.ghi789.css
│   └── logo.jkl012.png
├── index.html
└── favicon.ico
```

### 2. Preview lokal

```bash
npm run preview
```

Vite akan menjalankan server lokal di `http://localhost:4173` yang melayani file dari folder `dist/` persis seperti server production.

### 3. Validasi environment variables saat build

Buat file `src/utils/env.ts`:

```ts
const requiredEnvVars = [
  'VITE_API_BASE_URL',
  'VITE_AUTH_DOMAIN',
  'VITE_SENTRY_DSN',
] as const

type EnvVars = Record<typeof requiredEnvVars[number], string>

export function validateEnv(): EnvVars {
  const missing: string[] = []

  const env = {} as EnvVars

  for (const key of requiredEnvVars) {
    const value = import.meta.env[key]
    if (!value) {
      missing.push(key)
    } else {
      env[key] = value
    }
  }

  if (missing.length > 0) {
    throw new Error(
      `[Build Error] Environment variables berikut tidak terisi:\n` +
        missing.map((k) => `  - ${k}`).join('\n') +
        '\n\nPeriksa file .env atau dashboard deployment.'
    )
  }

  return env
}
```

Panggil di `src/main.ts`:

```ts
import { validateEnv } from './utils/env'

if (import.meta.env.PROD) {
  validateEnv()
}
```

### 4. Analisis output dist/

Lihat ukuran masing-masing chunk:

```bash
npx vite-bundle-analyzer
```

Atau via `rollup-plugin-visualizer` di `vite.config.ts`:

```ts
import { visualizer } from 'rollup-plugin-visualizer'

export default defineConfig({
  plugins: [
    vue(),
    visualizer({
      filename: 'dist/stats.html',
      open: true,
    }),
  ],
})
```

## Analogi — Toko Buku

Build production seperti **persiapan grand opening toko**. Semua barang dirapikan, label harga diperbarui, dekorasi dipasang (minify + code splitting). Hasilnya adalah toko yang siap beroperasi — yaitu folder `dist/`.

Preview seperti **soft opening**: lihat apakah semua berfungsi seperti diharapkan sebelum benar-benar buka untuk publik. Kasir berfungsi? Rak tidak roboh? Lampu menyala?

Validasi env ibarat **memastikan semua stok barang sudah ada label harganya** sebelum toko dibuka. Kalau ada buku tanpa harga, kasir bingung saat transaksi — lebih baik ketahuan dari awal.

## Dipakai untuk Apa

- **Deploy ke Vercel / Netlify / server** — hasil build `dist/` yang diupload
- **CI/CD pipeline** — `npm run build` dijalankan di pipeline, hasilnya di-upload ke server
- **Bundle analysis** — mengetahui bundle size, mencari chunk yang terlalu besar
- **Cache strategy** — content hash di nama file memudahkan CDN cache

## Kesalahan Umum

| Kesalahan | Akibat | Solusi |
|-----------|--------|--------|
| Build sukses tapi error di production | Env variable tidak ada di server | Validasi env saat build |
| Routing SPA 404 di refresh | Server tidak di-setup fallback ke index.html | Setup SPA fallback (lihat file 68) |
| Ukuran bundle membengkak | Lupa lazy loading, library besar tidak di-tree-shake | Analisis dengan visualizer |
| Preview berbeda dengan production | Konfigurasi server production berbeda | Uji coba di staging environment |

## Hubungan dengan Materi Sebelumnya

Di Level 6 (Poin 65) kita melakukan **bundle analysis** — sekarang kita benar-benar menjalankan build. Optimasi yang sudah dipelajari sebelumnya (lazy loading di Poin 49, tree shaking, code splitting) semuanya terlihat hasilnya di folder `dist/`.

Aplikasi yang sudah jadi dari Level 1—6 kini siap di-build. Semua fitur — routing, state management, komposisi — dioptimasi menjadi file statis yang siap di-deploy.

## Soal Latihan

### Soal 1

Apa yang dimaksud dengan content hash pada nama file output build? Mengapa penting untuk production?

<details>
<summary>Jawaban</summary>
Content hash adalah string unik (biasanya hash dari isi file) yang ditambahkan ke nama file, misal `index.abc123.js`. Nilainya berubah setiap kali isi file berubah. Ini penting untuk **cache busting**: browser akan menyimpan file di cache berdasarkan nama file. Jika nama berubah (karena ada perubahan kode), browser tahu harus mengambil versi baru. Tanpa content hash, pengguna bisa melihat versi lama meskipun sudah di-deploy versi baru.
</details>

### Soal 2

Saat menjalankan `npm run preview` di lokal, aplikasi berjalan normal. Tapi setelah di-deploy, semua halaman selain `/` mengembalikan 404. Jelaskan penyebab dan solusinya.

<details>
<summary>Jawaban</summary>
Penyebab: Server production tidak dikonfigurasi untuk SPA fallback. Saat pengguna mengakses `/books/clean-code`, server mencari file `dist/books/clean-code` yang tidak ada. Solusi: konfigurasi server agar semua route diarahkan ke `index.html`. Di Vercel, buat `vercel.json` dengan rewrite rules. Di Netlify, buat `_redirects` dengan `/* /index.html 200`.
</details>
