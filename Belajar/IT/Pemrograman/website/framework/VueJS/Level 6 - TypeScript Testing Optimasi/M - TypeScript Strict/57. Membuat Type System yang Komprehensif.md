# 57. Membuat Type System yang Komprehensif

## Penjelasan

Setelah strict mode aktif, langkah selanjutnya adalah **audit dan lengkapi semua tipe** di seluruh codebase. Setiap data yang berinteraksi dengan API, komponen, store, dan router harus punya definisi TypeScript yang eksplisit dan tidak boleh ada `any` yang lolos.

Tujuan utama:
- Semua **API response** punya bentuk baku — `ApiResponse<T>`, `PaginatedResponse<T>`
- Semua **entitas bisnis** punya tipe lengkap — `Book`, `Author`, `Category`
- Semua **properti opsional** ditandai dengan `?` — tidak ada properti misterius
- Semua **union type** untuk field diskrit — `BookCategory` sebagai union literal

## Fungsi

- **Data yang masuk dari API punya bentuk jelas** — tidak ada field misterius
- **Type safety end-to-end** — dari API response sampai render komponen
- **Refactoring lebih aman** — ganti satu field di tipe, error muncul di semua tempat
- **Dokumentasi otomatis** — tipe adalah dokumentasi yang tidak bisa kadaluarsa
- **IDE autocompletion maksimal** — developer tidak perlu buka dokumentasi API terus-menerus

## Cara Implementasi

### 1. Buat base type untuk API response

`src/types/api.types.ts`:

```typescript
export interface ApiResponse<T> {
  statusCode: number
  message: string
  data: T
}

export interface PaginationMeta {
  page: number
  perPage: number
  totalItems: number
  totalPages: number
}

export interface PaginatedResponse<T> {
  statusCode: number
  message: string
  data: T[]
  pagination: PaginationMeta
}

export interface ApiError {
  statusCode: number
  message: string
  errors?: Record<string, string[]>
}
```

### 2. Update entitas Book dengan semua field dari API

### 4. Gunakan di composable

```typescript
import type { ApiResponse, PaginatedResponse } from '@/types'

export async function getBooks(page = 1): Promise<PaginatedResponse<Book>> {
  const response = await api.get('/books', { params: { page } })
  return response.data
}

export async function getBookById(id: string): Promise<ApiResponse<Book>> {
  const response = await api.get(`/books/${id}`)
  return response.data
}
```

### 5. Ganti semua `any` dengan tipe yang proper

```vue
<script setup lang="ts">
// ❌ Sebelum: any
const books = ref<any[]>([])
const selectedCategory = ref<string>('')

async function loadBooks() {
  const res: any = await getBooks()
  books.value = res.data
}

// ✅ Sesudah: tipe eksplisit
const books = ref<Book[]>([])
const selectedCategory = ref<BookCategory | ''>('')

async function loadBooks() {
  const res = await getBooks()
  books.value = res.data
}
</script>
```

### 6. Type guard untuk runtime validation

```typescript
export function isBookCategory(value: string): value is BookCategory {
  return ['fiction', 'non-fiction', 'science', 'technology', 'history'].includes(value)
}

export function parseBookCategory(value: string): BookCategory | null {
  return isBookCategory(value) ? value : null
}
```

## Analogi — Toko Buku

Dulu **catatan pengiriman barang** dari gudang sering ditulis asal:

- Terkadang harga dalam **string** ("Rp50.000"), terkadang **number** (50000), terkadang **tidak ada** sama sekali.
- Kategori buku ditulis bebas: "Fiksi", "fiksi", "FICTION", "Sci-Fi", "science-fiction" — **tidak konsisten**.
- Ada field **misterius** seperti `extraInfo`, `notes`, `data` — isinya apa? Tidak ada yang tahu.
- Stok barang kadang dikirim sebagai number (10), kadang sebagai string ("10"), kadang tidak dikirim.

**Sekarang setiap catatan punya FORMAT BAKU:**

- `ApiResponse<T>` — amplop resmi toko yang selalu berisi:
  - `statusCode` (number) — kode transaksi
  - `message` (string) — keterangan
  - `data` (T) — isi pesanan, bentuknya tergantung jenis barang

- `Book` — formulir standar untuk setiap buku:
  - `title` (string) — judul wajib
  - `price` (number) — harga dalam angka, tidak boleh string
  - `stock` (number) — stok angka
  - `category` — salah satu dari 5 pilihan: fiction, non-fiction, science, technology, history

- `BookCategory` — stempel kategori: **tidak bisa ditulis sembarangan**, hanya 5 pilihan yang valid

- `CreateBookPayload` — formulir **isi** untuk buku baru (tanpa id, createdAt, updatedAt yang di-generate server)

- `UpdateBookPayload` — formulir **edit** (semua field opsional kecuali id)

**Tidak ada lagi kebingungan** "Ini harga bentuk apa?" — TypeScript akan teriak kalau ada yang tidak sesuai. Pegawai toko (developer) tinggal ikuti format yang sudah ditentukan.

## Dipakai untuk Apa

- **Aplikasi e-commerce** — produk, kategori, keranjang, order — semua entitas punya tipe eksplisit
- **Dashboard analytics** — data charts, filter, aggregasi — tipe menjamin konsistensi data
- **Sistem manajemen konten** — artikel, tag, author, metadata — tipe mencegah error struktural
- **Micro-frontend / monorepo** — shared types dipakai di banyak package, konsistensi terjaga
- **Third-party API integration** — tipe response dari API eksternal didokumentasikan lewat type definition

## Kesalahan Umum

| Kesalahan | Dampak | Solusi |
|---|---|---|
| Over-engineering — tipe terlalu kompleks untuk data sederhana | Maintenance burden, onboarding susah | Mulai dari tipe minimum yang dibutuhkan, tambah saat diperlukan |
| Tipe terlalu longgar (`any` atau `Record<string, any>`) | TypeScript tidak berguna | Audit dan ganti dengan tipe konkret |
| Lupa update tipe saat API spec berubah | Type mismatch error di runtime | Integrasikan type generation dari OpenAPI/Swagger |
| Union type terlalu besar (>10 anggota) | Sulit di-maintain | Group dengan tipe pembantu atau enum |
| Field opsional tidak ditandai `?` | Dipaksa mengisi field yang tidak selalu ada | Tandai dengan `?` untuk field yang bisa `undefined` |
| Duplikasi tipe di banyak file | Update satu lupa update yang lain | Gunakan barrel export dari `src/types/index.ts` |

## Hubungan dengan Level 1–5

- **Level 1–3** — Tipe dasar seperti `string`, `number`, `boolean`, interface sederhana untuk props komponen. Masih banyak `any` di fungsi utility.
- **Level 4** — `ApiResponse` mulai dikenal saat belajar fetching data, tapi definisinya masih inline di file composable — tidak ada type sharing.
- **Level 5** — Store Pinia mulai pakai interface untuk state, tapi action store masih sering `as any` saat mutasi data kompleks di array.
- **Level 6 poin 56** — Strict mode memaksa kita mendefinisikan tipe dengan benar. Sekarang kita lengkapi **semua tipe** yang diperlukan — ini adalah eksekusi dari komitmen strict mode.

### Soal 2

Kode berikut menggunakan `any` di beberapa tempat. Ganti dengan tipe yang proper menggunakan tipe yang sudah dibuat (`ApiResponse<T>`, `Book`, `PaginatedResponse<T>`):

```vue
<script setup lang="ts">
import { ref, onMounted } from 'vue'
import { api } from '@/lib/api'

const books = ref<any[]>([])
const loading = ref(false)
const error = ref<any>(null)

async function fetchBooks() {
  loading.value = true
  try {
    const response: any = await api.get('/books?page=1')
    books.value = response.data.data
  } catch (err: any) {
    error.value = err.message
  } finally {
    loading.value = false
  }
}

onMounted(fetchBooks)
</script>
```

```vue
<script setup lang="ts">
import { ref, onMounted } from 'vue'
import { api } from '@/lib/api'
import type { PaginatedResponse, Book, ApiError } from '@/types'

const books = ref<Book[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

async function fetchBooks(): Promise<void> {
  loading.value = true
  error.value = null
  try {
    const response = await api.get<PaginatedResponse<Book>>('/books?page=1')
    books.value = response.data.data
  } catch (err: unknown) {
    if (err instanceof Error) {
      error.value = err.message
    } else {
      error.value = 'Terjadi kesalahan yang tidak diketahui'
    }
  } finally {
    loading.value = false
  }
}

onMounted(fetchBooks)
</script>
```
