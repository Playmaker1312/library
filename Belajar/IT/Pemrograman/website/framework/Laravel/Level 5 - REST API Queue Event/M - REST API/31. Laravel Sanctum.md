# 31. Laravel Sanctum — Token-Based Auth untuk API

## Penjelasan

**Sanctum** adalah paket autentikasi ringan untuk API. Tidak seperti session-based auth (web), API menggunakan **token** — string acak yang dikirim di header setiap request. API bersifat stateless: tidak ada session, setiap request berdiri sendiri.

**Cara Kerja:**
1. User login dengan email + password → dapat token
2. Token disimpan di client (localStorage, secure storage)
3. Setiap request API menyertakan token di header `Authorization: Bearer {token}`
4. Server verifikasi token → jika valid, proses request

```bash
composer require laravel/sanctum
php artisan vendor:publish --provider="Laravel\Sanctum\SanctumServiceProvider"
php artisan migrate
```

## Fungsi

- Autentikasi API tanpa session — cocok untuk mobile app, SPA, frontend JS
- Token-based: setiap user bisa punya banyak token (beda device)
- Abilities (kemampuan) per token: batasi akses per token
- Token expiry: token bisa kadaluarsa

## Cara Pengimplementasian

```php
<?php
// app/Models/Anggota.php — tambahkan trait

use Laravel\Sanctum\HasApiTokens;

class Anggota extends Authenticatable
{
    use HasApiTokens, HasFactory, Notifiable;
    // ...
}
```

```php
<?php
// app/Http/Controllers/Api/V1/AuthController.php

namespace App\Http\Controllers\Api\V1;

use App\Http\Controllers\Controller;
use App\Http\Resources\AnggotaResource;
use App\Models\Anggota;
use Illuminate\Http\JsonResponse;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Hash;

class AuthController extends Controller
{
    public function login(Request $request): JsonResponse
    {
        $request->validate([
            'email'    => ['required', 'email'],
            'password' => ['required'],
        ]);

        $anggota = Anggota::where('email', $request->email)->first();

        if (!$anggota || !Hash::check($request->password, $anggota->password)) {
            return response()->json([
                'message' => 'Email atau password salah.',
            ], 401);
        }

        // Hapus token lama (opsional: 1 device = 1 token)
        // $anggota->tokens()->delete();

        // Buat token baru
        $token = $anggota->createToken(
            name: $request->device_name ?? 'api-client',
            abilities: $anggota->isAdmin() ? ['*'] : ['buku:read', 'pinjam:create'],
            expiresAt: now()->addDays(30),
        );

        return response()->json([
            'token' => $token->plainTextToken,
            'user'  => new AnggotaResource($anggota),
        ]);
    }

    public function logout(Request $request): JsonResponse
    {
        // Hapus token yang sedang dipakai
        $request->user()->currentAccessToken()->delete();

        return response()->json(['message' => 'Berhasil logout.']);
    }

    public function me(Request $request): AnggotaResource
    {
        return new AnggotaResource($request->user());
    }
}
```

```php
<?php
// routes/api.php

Route::prefix('v1')->name('api.v1.')->group(function () {
    // Public
    Route::post('auth/login', [AuthController::class, 'login']);

    // Protected (butuh token)
    Route::middleware('auth:sanctum')->group(function () {
        Route::post('auth/logout', [AuthController::class, 'logout']);
        Route::get('auth/me', [AuthController::class, 'me']);
        Route::apiResource('buku', BukuController::class)
             ->except(['index', 'show']);  // index/show publik
    });
});
```

```php
<?php
// Di controller — cek abilities token
class BukuController extends Controller
{
    public function store(Request $request): JsonResponse
    {
        // Cek apakah token punya ability 'buku:create'
        if (!$request->user()->tokenCan('buku:create')) {
            return response()->json(['message' => 'Forbidden'], 403);
        }
        // ...
    }
}
```

**Test dengan cURL:**
```bash
# Login
curl -X POST http://localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@test.com","password":"password"}'

# Response:
# {"token":"1|abc123...", "user": {...}}

# Akses API dengan token
curl http://localhost:8000/api/v1/buku \
  -H "Authorization: Bearer 1|abc123..."
```

## Analogi

Sanctum seperti **sistem kunci loker di perpustakaan**:

- **Login (email + password)** = Daftar ke meja sirkulasi, perlihatkan KTP
- **Mendapat token** = Dapat kunci loker — setiap kunci unik untuk setiap kunjungan
- **Token di Header** = Tunjukkan kunci loker setiap kali buka loker
- **Abilities** = Kunci dengan akses terbatas: "Kunci ini hanya buka loker kecil (baca buku), bukan loker besar (pinjam buku)"
- **Expiry** = Kunci otomatis kadaluarsa setelah 30 hari
- **Logout** = Kembalikan kunci, tidak bisa dipakai lagi

**Perbedaan Web Auth vs API Auth:**
```
Web (Session):             API (Sanctum):
- Login sekali             - Login → dapat token
- Session di server        - Token di client
- Cookie otomatis          - Header manual
- Logout → session hapus   - Logout → token hapus
- Stateful                 - Stateless
```

## Dipakai untuk Apa

- **REST API** — mobile app, SPA (React/Vue), frontend JS
- **Third-party API** — aplikasi lain yang perlu akses data
- **Multi-device** — user bisa login di banyak device, masing-masing punya token sendiri
- **Fine-grained access** — batasi token hanya untuk operasi tertentu

## Kesalahan Umum

1. **Token bocor di response** — jangan log `plainTextToken` — hanya kirim saat pertama login
2. **Lupa `auth:sanctum` guard** — `auth:sanctum` bukan `auth` — sanctum punya guard sendiri
3. **Token di localStorage (XSS risk)** — untuk web SPA, simpan di httpOnly cookie, bukan localStorage
4. **Tidak ada expiry** — token bisa dipakai selamanya. Set expiry untuk keamanan
5. **Abilities tidak didefinisikan** — semua token punya akses penuh. Definisikan abilities untuk kontrol
6. **Lupa migrate** — tabel `personal_access_tokens` harus ada

## Koneksi dengan Materi Sebelumnya

Poin 25-27 membahas auth untuk web (session-based). Sanctum adalah auth untuk API (token-based). Keduanya menggunakan model User/Anggota yang sama. Poin 30 (API Resource) dan Sanctum bekerja bersama untuk API yang aman dan konsisten.

**Benang merah ke depan:**
- Poin 32 (Error Handling API): Error response API perlu format konsisten
- Poin 33 (Queue): Job bisa di-trigger dari API endpoint
