# 23. Unit Test — Test Service dan Repository

> ⚫ **Level 6 — Bagian J** | 🧩 **Melanjutkan [[22. Setup dan Feature Test]]**

---

## 1. Penjelasan Singkat & Konsep Dasar

Integration test (materi 22) menguji *keseluruhan pipeline*. **Unit test** mengisolasi **satu unit** — biasanya sebuah service atau repository — dan **mock semua dependency-nya** (misal repository di-mock saat menguji service). Dengan begitu:

```text
yang diuji   : BukuService.getById
dependency   : BukuRepository (di-mock dengan vi.fn())
hasil test   : apakah service benar-benar berperilaku benar,
               TERLEPAS dari repository (yang diuji terpisah)
```

**Kunci fitur Vitest untuk mocking:**
- `vi.fn()` — membuat function mock yang bisa ditetapkan return-nya.
- `vi.mocked(x).mockResolvedValue(...)` — menetapkan return async.
- `toHaveBeenCalledWith`, `toHaveBeenCalledOnce` — memeriksa pemanggilan.
- `rejects.toThrow(...)` — memeriksa promise yang melempar error.

**Benang merah**: service di materi 21 memakai dependency injection (constructor). Itulah yang membuat unit test begitu mudah — kita bisa *menyuntikkan mock* tanpa menyentuh kementahan asli. Pola ini juga jadi dasar testing React (materi 25-27) dengan mock hooks.

---

## 2. Fungsi & Kegunaan Utama

- **Presisi**: tahu persis unit mana yang rusak saat test gagal.
- **Kecepatan**: tanpa I/O (DB, jaringan) — test berjalan dalam milidetik.
- **Kontrol penuh**: kita memilih data yang dikembalikan dependency → menentukan semua branch.
- **TDD-friendly**: tulis unit test dulu, implementasikan setelah.
- **Dokumentasi perilaku unit**, independent dari infrastruktur.

## 3. Contoh Kode & Implementasi (Real-world Example)

```typescript
// tests/unit/buku.service.test.ts
import { describe, it, expect, vi, beforeEach } from "vitest";
import { BukuService } from "../../src/services/buku.service";
import { BukuNotFoundError } from "../../src/errors/AppError";
import type { BukuRepository } from "../../src/repositories/buku.repository";

describe("BukuService", () => {
    let service: BukuService;
    let repo: BukuRepository;              // mock object

    const bukuContoh = {
        id: 1,
        judul: "Clean Code",
        pengarang: "Robert Martin",
        isbn: "9780132350884",
        tahun: 2008,
        harga: 150000,
        stok: 5,
        kategori: "Teknologi" as const,
        createdAt: new Date(),
        updatedAt: new Date(),
        deletedAt: null,
    };

    beforeEach(() => {
        // Bangun mock repository dari nol tiap test — state bersih
        repo = {
            findAll: vi.fn(),
            findById: vi.fn(),
            create: vi.fn(),
            update: vi.fn(),
            delete: vi.fn(),
        } as unknown as BukuRepository;

        service = new BukuService(repo);   // injeksi mock
    });

    describe("getById", () => {
        it("mengembalikan buku bila ditemukan", async () => {
            vi.mocked(repo.findById).mockResolvedValue(bukuContoh);

            const hasil = await service.getById(1);

            expect(hasil).toEqual(bukuContoh);
            expect(repo.findById).toHaveBeenCalledWith(1);
            expect(repo.findById).toHaveBeenCalledOnce();
        });

        it("melempar BukuNotFoundError bila buku tidak ada", async () => {
            vi.mocked(repo.findById).mockResolvedValue(null);

            await expect(service.getById(999))
                .rejects.toBeInstanceOf(BukuNotFoundError);
            await expect(service.getById(999))
                .rejects.toThrow("Buku dengan ID 999 tidak ditemukan");
        });
    });

    describe("create", () => {
        it("berhasil membuat buku baru", async () => {
            const dataBaru = {
                judul: "New Book", pengarang: "Author",
                tahun: 2024, harga: 100000, stok: 5,
                kategori: "Umum" as const,
            };

            vi.mocked(repo.create).mockResolvedValue({ ...bukuContoh, ...dataBaru });

            const hasil = await service.create(dataBaru);

            expect(hasil.judul).toBe(dataBaru.judul);
            expect(repo.create).toHaveBeenCalledWith(dataBaru);
        });
    });
});
```

**Mengapa `as unknown as BukuRepository`?** Kita membuat objek yang hanya berisi method-method mock — tapi tipe membutuhkan semua method; casting via `unknown` menyatakan "ini memang mock yang disengaja".

## 4. Analogi Sederhana

**Sistem Perpustakaan.**

- **Unit test service** = **menguji keputusan seorang asisten perpustakaan di ruangan tertutup**: kamu bertanya kepadanya (memanggil `service.getById(1)`), tapi *kamu* yang menyediakan jawaban yang akan ia terima dari "koleksi" (mock repository). Kamu mengatur skenario:
  - "Koleksi punya buku id 1" → asisten harus menyerahkan buku itu.
  - "Koleksi bilang tidak ada" → asisten harus menolak dengan `BukuNotFoundError`.
- **Mock repository** = **rekan kerja bayangan**: tidak benar-benar pergi ke gudang; kamu yang menentukan apa yang "dibacanya" (`mockResolvedValue`). Ini membuat test konsisten, cepat, dan tanpa bergantung kondisi DB nyata.
- **`toHaveBeenCalledWith`** = **memeriksa pesan yang dikirim asisten ke gudang**: "apakah ia benar-benar menanyakan id 1, bukan id lain?"
- **`beforeEach`** = **membersihkan meja asisten di tiap tes**: setiap skenario mulai dari keadaan bersih, tidak ada data sisa antar test.

---

## 5. Kapan Harus Digunakan (Use Cases)

- **Business logic dalam service**: validasi, perhitungan denda, batas pinjam, transformasi data.
- **Repository yang bergantung sumber eksternal** — saat diuji isolasi, mock datanya.
- **Setiap kali dependency (DB, API) tidak stabil / mahal / lambat** untuk dijalankan di test.
- **TDD** — menulis unit test yang menggambarkan kontrak service sebelum implementasi.
- **Branch coverage** — paksa semua jalur `if`/error diuji dengan mock yang berbeda.

---

## 6. Poin-poin Penting & Best Practices

1. **Satu `describe` per unit; `describe` ber-nested per method**. Bersih & runnable.
2. **`beforeEach` membangun ulang mock** — hindari "state” antar test.
3. **Mock di-inject via constructor (DI)** — method service tak boleh membuat instance repo sendiri.
4. **Assert pemanggilan dependency** — `toHaveBeenCalledWith` memverifikasi *interaksi*, bukan cuma output.
5. **Assert error dengan `rejects.toThrow`** — kedua assertion (error type & message) untuk kontrak lengkap.
6. **Mock return data yang realistis & typed** — halau `as any` di data test.
7. **Fokus pada kontrak** — jangan menguji implementasi internal service.

---

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

| Kesalahan | Contoh | Akibat | Perbaikan |
|---|---|---|---|
| Mock tidak di-inject (memakai repo asli) | service `new BukuRepository()` di dalamnya | test kena DB | injeksi via constructor |
| Mock di-set di luar beforeEach | shared state antar test | saling ganggu | bangun ulang di `beforeEach` |
| `mockResolvedValue` vs `mockReturnValue` tertukar | untuk async pakai return | test gagal hambar | sesuaikan dengan async |
| Assert output saja tanpa interaksi | ignore `toHaveBeenCalledWith` | interaksi salah tak terdeteksi | tambahkan assertion pemanggilan |
| Data test pakai `as any` | `data as any` | tipe tidak teruji | definisikan data typed |
| Menguji method private secara tidak sengaja | memanggil `(service as any).priv()` | fragili | hanya uji API publik |

## 8. Soal Latihan & Kunci Jawaban

### Soal 1
Mock ini: `service.prosesPeminjaman(bukuId, anggotaId)` yang:
- bila buku dengan id tidak ada → `throws BukuNotFoundError(bukuId)`,
- bila ada → memanggil `repo.update(stokBaru)` (mengurangi stok) lalu return buku.

Buat unit test dua skenario dengan `vi.mocked`.

### Soal 2
Jelaskan mengapa **dependency injection** (materi 15/21) sangat membantu unit testing — sebutkan alasan teknis dalam 2-3 kalimat.

---

### Jawaban & Pembahasan

```typescript
// Soal 1 — menguji service dengan mock repo
import { describe, it, expect, vi, beforeEach } from "vitest";
import { ServicePinjam } from "../../src/services/service-pinjam";
import { BukuNotFoundError } from "../../src/errors/AppError";
import type { BukuRepository } from "../../src/repositories/buku.repository";

describe("ServicePinjam.prosesPeminjaman", () => {
    let svc: ServicePinjam;
    let repo: BukuRepository;

    const buku = {
        id: 1, judul: "X", pengarang: "Y", isbn: "0", tahun: 2024,
        harga: 1000, stok: 5, kategori: "Umum" as const,
        createdAt: new Date(), updatedAt: new Date(), deletedAt: null,
    };

    beforeEach(() => {
        repo = {
            findAll: vi.fn(), findById: vi.fn(),
            create: vi.fn(), update: vi.fn(), delete: vi.fn(),
        } as unknown as BukuRepository;
        svc = new ServicePinjam(repo);
    });

    it("melempar BukuNotFoundError bila buku tidak ada", async () => {
        vi.mocked(repo.findById).mockResolvedValue(undefined);

        await expect(svc.prosesPeminjaman(1, 2))
            .rejects.toBeInstanceOf(BukuNotFoundError);
    });

    it("mengurangi stok dan return buku bila tersedia", async () => {
        vi.mocked(repo.findById).mockResolvedValue(buku);

        const hasil = await svc.prosesPeminjaman(1, 2);

        expect(hasil.stok).toBe(buku.stok - 1);
        expect(repo.update).toHaveBeenCalledWith(1, { stok: 4 });
    });
});
```

**Pembahasan**: dengan mock, dua skenario (ada/tidak) deterministik. Perhatikan: kita memeriksa *pemanggilan* `update` dengan argumen yang tepat — kontrak interaksi service-repository terverifikasi.

**Soal 2** — Karena service menerima dependency **melalui constructor**, pada test kita bisa mengganti repositori asli dengan *mock object* (objek berisi `vi.fn()`). Tanpa DI, service akan membuat sendiri koneksi DB/API nyata — langkah lambat, tidak stabil, dan sulit dikendalikan; dengan DI, testnya cepat, isolasi, dan kita bisa memaksa setiap jalur kode. Ini alasan teknis kenapa DI bukan sekadar gaya, tapi *fondasi testability*.
