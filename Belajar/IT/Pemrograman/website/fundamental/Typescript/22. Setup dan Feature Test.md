## 1. Penjelasan Singkat & Konsep Dasar

API kita sudah berjalan (Level 5). Tapi "berjalan" dan "bisa dipercaya" adalah dua hal yang berbeda. **Testing** menjawab pertanyaan: *bagaimana kita yakin perubahan berikutnya tidak merusak yang sudah ada?*

**Vitest** adalah test runner modern untuk TypeScript:
- mendukung TS secara **native** (tanpa transpile setup tambahan),
- sangat cepat (berbasis Vite),
- API kompatibel dengan Jest (`describe`/`it`/`expect`) sehingga mudah dipelajari.

Dua tingkatan test yang kita pelajari:

```text
Unit test          → menguji SATU unit (fungsi/service/repository) terisolasi
                     dengan mock dependency — cepat, presisi.
Integration test   → menguji API end-to-end (request HTTP nyata via supertest)
                     terhadap app yang kita buat (createApp dari materi 19).
```

Kunci: berkat pemisahan `app.ts`/`index.ts` (materi 18-19), kita bisa **mengimpor app** tanpa listen — dan memintanya langsung lewat **supertest**.

**Benang merah**: seluruh arsitektur Level 5 (controller-service-repository, error handler, Zod) kini *dibuktikan* dengan test. Kualitas kode ditentukan bukan oleh "running", tapi oleh *regression safety*.

---

## 2. Fungsi & Kegunaan Utama

- **Regression safety** — perubahan di satu tempat tidak memecahkan yang lain.
- **Dokumentasi yang dapat dieksekusi** — test menggambarkan *behavior yang diharapkan*.
- **Feedback cepat saat development** — `vitest` watch mode.
- **Confidence untuk refactor** — pindahkan kode, yakinkan behavior tetap.
- **Coverage** — mengukur seberapa banyak kode yang diuji (threshold di CI).
- **Supertest** — menguji HTTP layer tanpa server benar-benar listen.

## 3. Contoh Kode & Implementasi (Real-world Example)

### Setup

```bash
npm install --save-dev vitest @vitest/coverage-v8 supertest @types/supertest
```

```typescript
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
    test: {
        globals: true,                 // describe/it/expect tanpa import
        environment: "node",
        coverage: {
            provider: "v8",
            reporter: ["text", "html"],
            thresholds: { lines: 70, functions: 70 },
        },
    },
});
```

Tambahkan script di package.json:

```json
{ "scripts": { "test": "vitest run", "test:watch": "vitest", "coverage": "vitest run --coverage" } }
```

### Integration test (feature test) — end-to-end HTTP

```typescript
// tests/integration/buku.test.ts
import { describe, it, expect, beforeAll } from "vitest";
import request from "supertest";
import { createApp } from "../../src/app";
import type { Application } from "express";

describe("Buku API", () => {
    let app: Application;

    beforeAll(() => {
        app = createApp();          // import app TANPA listen
    });

    it("GET /api/v1/buku → 200 dengan daftar", async () => {
        const res = await request(app).get("/api/v1/buku");

        expect(res.status).toBe(200);
        expect(res.body.success).toBe(true);
        expect(Array.isArray(res.body.data)).toBe(true);
    });

    it("GET /api/v1/buku?kategori=Teknologi → filter bekerja", async () => {
        const res = await request(app)
            .get("/api/v1/buku")
            .query({ kategori: "Teknologi" });

        expect(res.status).toBe(200);
        for (const buku of res.body.data) {
            expect(buku.kategori).toBe("Teknologi");
        }
    });

    it("POST /api/v1/buku tanpa auth → 401", async () => {
        const res = await request(app).post("/api/v1/buku").send({
            judul: "X", pengarang: "Y", tahun: 2024,
            harga: 1000, stok: 1, kategori: "Umum",
        });
        expect(res.status).toBe(401);
    });

    it("POST /api/v1/buku data tidak valid → 422", async () => {
        const token = await dapatkanToken(app, "admin");
        const res = await request(app)
            .post("/api/v1/buku")
            .set("Authorization", `Bearer ${token}`)
            .send({ judul: "" });

        expect(res.status).toBe(422);
        expect(res.body.errors).toHaveProperty("judul");
    });

    it("POST /api/v1/buku data valid → 201 & buku tercipta", async () => {
        const token = await dapatkanToken(app, "admin");
        const data = {
            judul: "TS Deep Dive", pengarang: "Basarat",
            isbn: "9781234567890", tahun: 2023,
            harga: 200000, stok: 10, kategori: "Teknologi",
        };

        const res = await request(app)
            .post("/api/v1/buku")
            .set("Authorization", `Bearer ${token}`)
            .send(data);

        expect(res.status).toBe(201);
        expect(res.body.success).toBe(true);
        expect(res.body.data).toMatchObject({
            judul: data.judul,
            kategori: data.kategori,
        });
        expect(res.body.data.id).toBeDefined();
    });
});

// Helper: login untuk mendapat token
async function dapatkanToken(app: Application, role: string): Promise<string> {
    const res = await request(app)
        .post("/api/v1/auth/login")
        .send({ email: `${role}@test.com`, password: "password123" });
    return res.body.data.token;
}
```

## 4. Analogi Sederhana

**Sistem Perpustakaan.**

- **Integration test (feature test)** = **simulasi kunjungan tamu penuh**: seseorang (supertest) datang ke gedung, mengikuti alur dari pintu (request) sampai rak (gudang), lalu melaporkan apa yang terjadi. Tanpa harus benar-benar membuka gedung di alamat tertentu (tanpa `listen`) — cukup lewat jalur khusus.
- **Unit test** (materi 23) = **menguji satu petugas di meja kerjanya**: isolasi — kita beri data palsu (mock) lalu periksa apakah ia memproses dengan benar, tanpa seluruh bangunan.
- **Coverage** = **peta kunjungan**: bagian mana gedung sudah "dikunjungi" oleh test (diuji) dan mana yang belum — agar perbaikan tidak buta.
- **vitest watch** = **petugas pengawas yang menyalakan alarm otomatis** setiap kali ada perubahan di gedung — langsung diuji ulang.

---

## 5. Kapan Harus Digunakan (Use Cases)

- **Setiap endpoint publik** — setidaknya satu integration test: happy path + error path (401/422/404).
- **Saat behavior bersifat "regression-prone"** — CRUD, auth, validasi.
- **Di CI (GitHub Actions)** — jalankan `vitest run` saat setiap push (materi 27).
- **Sebelum refactor besar** — tulis test untuk behavior saat ini, lalu refactor dengan aman.
- **Saat menambah fitur** — TDD ringan: tulis test yang gagal, implementasikan, pastikan hijau.

---

## 6. Poin-poin Penting & Best Practices

1. **Fokus test pada behavior, bukan implementasi** — apa yang dipanggil kurang penting daripada hasilnya.
2. **Pakai `beforeAll`/`beforeEach` untuk setup** — app dibangun sekali, data di-reset tiap test bila perlu.
3. **`createApp()` reusable** — tidak listen; supertest langsung memanggil internal.
4. **Tetapkan threshold coverage** (misal 70%) di config agar CI gagal bila turun.
5. **Grouping test**: `describe` per resource (`Buku API`), `it` per scenario.
6. **Helper login/token** dipisah agar tidak duplikasi.
7. **Jangan test hal sepele** (implemen private); fokus pada kontrak publik.

---

## 7. Kesalahan Umum (Common Pitfalls & Anti-patterns)

| Kesalahan | Contoh | Akibat | Perbaikan |
|---|---|---|---|
| Test bergantung pada server `listen` | menghidupkan server di test | lambat & fragile | import `createApp()` + supertest |
| Menguji implementasi (private method) | memanggil method `private` | test patah saat refactor internal | fokus API publik |
| Test yang bergantung order | test kedua butuh data test pertama | flaky | setup sendiri di `beforeEach` |
| Lupa reset state DB | data menumpuk antar test | hasil tidak deterministik | bersihkan di beforeEach/afterAll |
| Memakai `any` di assertion | `res.body as any` | kehilangan bantuan tipe | gunakan tipe dari `ApiResponse` |
| Cover semua tapi assert sedikit | status 200 saja tanpa cek isi | "hijau palsu" | assert konten (data, errors) |

## 8. Soal Latihan & Kunci Jawaban

### Soal 1
Tulis integration test untuk endpoint `GET /api/v1/anggota` yang mengharapkan 200 + `success: true` + `data` array, dan untuk `GET /api/v1/anggota/:id` yang tak ada (mengembalikan 404 via `BukuNotFoundError`-style resource). Gunakan `createApp()`.

### Soal 2
Mengapa kita **tidak** memanggil `app.listen()` di test? Jelaskan & beri satu alternatif praktik yang lebih baik.

---

### Jawaban & Pembahasan

```typescript
// Soal 1 — tests/integration/anggota.test.ts
import { describe, it, expect, beforeAll } from "vitest";
import request from "supertest";
import { createApp } from "../../src/app";
import type { Application } from "express";

describe("Anggota API", () => {
    let app: Application;

    beforeAll(() => {
        app = createApp();
    });

    it("GET /api/v1/anggota → 200 dengan daftar", async () => {
        const res = await request(app).get("/api/v1/anggota");

        expect(res.status).toBe(200);
        expect(res.body.success).toBe(true);
        expect(Array.isArray(res.body.data)).toBe(true);
    });

    it("GET /api/v1/anggota/9999 → 404 bila tidak ada", async () => {
        const res = await request(app).get("/api/v1/anggota/9999");

        expect(res.status).toBe(404);
        expect(res.body.success).toBe(false);
    });
});
```

**Pembahasan**: endpoint diuji lewat HTTP path & status — bukan melalui pemanggilan langsung controller. Ini membuktikan *seluruh pipeline* (route → auth → controller → service → error handler) bekerja.

**Soal 2** — Menjalankan `app.listen()` akan membuka port sungguhan, membuat test lambat dan sulit dijalankan paralel/CI, serta membutuhkan lifecycle server. Lebih baik: `createApp()` (yang murni menyusun middleware/route tanpa listen) diimpor, lalu supertest memakai instance tersebut. Inilah kenapa pemisahan `app.ts`/`index.ts` di materi 18-19 merupakan keputusan arsitektur penting.
